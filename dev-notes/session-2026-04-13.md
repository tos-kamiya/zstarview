- Topic: Overture release check cadence
  - Decision: Limit release checks to startup or initial enablement, but skip the check when the last successful lookup is within 24 hours.
  - Rationale: This keeps the cache refresh path responsive to upstream publication changes without adding unnecessary catalog traffic on every launch.
- Topic: Overture release metadata layout
  - Decision: Store `overture_release` alongside each urban-outline cache entry, and keep `last_release_check_utc` / `last_seen_overture_release` in a root-level release-check metadata file.
  - Rationale: Per-cache release IDs make stale detection local to each dataset or tile, while the shared timestamp avoids duplicating one network-check result across every cache directory.
- Topic: Overture release metadata schema
  - Decision: Use `cache_meta.json` sidecars for dataset-level metadata and `overture_buildings_release_check_meta.json` at the cache root for release lookup state.
  - Rationale: The split keeps the cache-key metadata colocated with each derived dataset while preserving a single 24-hour suppression clock for release catalog checks.
- Topic: Overture release metadata failure mode
  - Decision: If release metadata is missing or unreadable, keep the cache and fall back to TTL-based stale handling instead of deleting data.
  - Rationale: Release metadata is advisory. Treating it as required would turn a small metadata problem into an unnecessary full cache invalidation.
- Topic: Overture release check implementation flow
  - Decision: Read the root-level release-check metadata first, skip the release catalog query when the last check is within 24 hours, and update `overture_release` in dataset sidecars only after successful refresh.
  - Rationale: This minimizes catalog traffic, keeps refresh decisions local to each dataset or tile, and preserves the existing TTL-based fallback path when release metadata is missing or stale.
- Topic: Legacy cache timestamp fallback
  - Decision: For caches missing `fetched_at_utc`, use `cache_meta.json` mtime first and `bldg` directory mtime second as the initial freshness timestamp.
  - Rationale: This is closer to the actual cache update time than migrating everything to `now`, while still avoiding a destructive invalidation of old caches.
