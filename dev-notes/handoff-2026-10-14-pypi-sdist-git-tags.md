# Handoff: sdist2tag

日付: 2026-10-14
対象: PyPI sdistとGitコミットを照合し、対応するタグを作成する独立した開発者用ツール
状態: 仕様のみ。ツール実装、タグ作成、push、PyPIファイル削除は未実施。

## ツール名と位置付け

- ツール名・CLIコマンド名: `sdist2tag`
- 名前の意味: source distributionから対応するGitタグへ。
- zstarviewアプリ本体とは独立した開発者用ツールとして開発する。
- パッケージ名、リポジトリ、対象refを入力として受け取り、zstarview専用の
  パスやバージョン取得方法を処理に固定しない。
- zstarviewを最初の適用対象・検証対象とする。
- 名前は本handoffでの採用名。PyPI等での名前の空き状況は未確認。

## 背景と目的

PyPIの累積容量が標準の10 GiB上限に近づき、1.62.12のpublishに失敗した。
調査時の公開済みファイルは79リリース・158ファイル、合計
10,728,591,680 bytesで、10 GiBまでの残りは8,826,560 bytesだった。
1.62.12のsdistは97,171,587 bytes、wheelは97,138,282 bytesである。
エラーログはHTTP 400までしか示しておらず、容量上限が原因と推定している。

容量確保の候補として、古いsdist (`.tar.gz`) を削除し、wheelを残す方針を
相談した。ただし、ビルドは手動のため、バージョン更新コミットが実際の
ビルド元とは限らない。削除の検討に先立ち、公開済みsdistと内容が一致する
Gitコミットを探し、対応関係をタグとレポートに残す。

## 合意した基本仕様

- 公開済みsdistの内容と一致する、mainの履歴上で最初のコミットを選ぶ。
- 実際にビルドに使ったコミットの断定ではなく、公開されたソース内容を
  再現できるコミットの特定として扱う。
- コミット日時やバージョン更新コミットだけでは判定しない。
- 一致しないリリースにはタグを作らず、調査対象として報告する。
- タグの注釈にsdistのファイル名、SHA-256、選択ルールを記録する。

## 入力と処理範囲

- ローカルGitリポジトリ、対象ref（既定: main）、対象バージョンを入力する。
- PyPIのJSON APIからsdistのURLとSHA-256を取得し、ダウンロードして照合する。
- 全公開バージョンを対象にするモードと、特定バージョンを指定するモードを設ける。
- ローカルsdistを使う場合もPyPIのSHA-256との一致を検証し、公開物と同一で
  あることを確認する。未公開のローカル成果物は別モードとして明記する。
- PyPIから削除する前に、取得したsdistと照合結果を保管する。
- このツールによるPyPIファイル削除、自動publish、タグの自動pushは範囲外。

## 「最初のコミット」の定義

mainのfirst-parent履歴を古い順に探索する。開始時に対象refをコミットSHAへ
解決して固定し、実行中のref更新で結果が変わらないようにする。
想定する列挙方法は `git rev-list --first-parent --reverse <resolved-sha>`。

first-parentを採用するのは、分岐した履歴全体では「最初」が一意に決まらない
ため。マージされたブランチ内で先に一致していても、mainに取り込まれた
時点のコミットを選ぶ。この詳細は合意したmain履歴の方針を具体化した
実装上の提案であり、実装時に文書・CLIヘルプへ明記する。

探索の絞り込みやキャッシュは許容するが、最初の一致を取りこぼしてはならない。

## 比較規則

1. sdistの単一トップディレクトリを除去し、リポジトリ相対パスに対応させる。
2. sdist内のソース、データ、テスト、README、LICENSE、設定、lockファイル等を
   すべてバイト単位で比較する。改行、空白、文字コードを正規化しない。
3. ビルドで生成されたメタデータ（例: トップレベルの `PKG-INFO`）は明示した
   除外リストで除く。除外パスと理由をレポートに残す。
4. 除外は広いパターンで行わない。未知の生成物やGitにないファイルを勝手に
   無視せず、不一致または要調査として報告する。
5. 比較対象の各ファイルがコミット内に存在し、全内容が一致した場合に一致とする。
   バージョンファイルも必ず比較対象に含める。
6. sdistに含まれないリポジトリ内のファイルは比較しない。その違いは
   この照合では区別できないことをレポートに明記する。
7. tar/gzipの時刻、所有者、圧縮結果は比較しない。sdistそのものの再ビルドや
   バイト単位でのアーカイブ再現は要求しない。

Gitのblobを直接読むなど、作業ツリーのcheckoutや変更を伴わない実装を優先する。
大きいデータの比較はハッシュ等で効率化し、パス・blobごとに結果をキャッシュする。

## 不一致・例外

- 一致なし: 未コミット変更、生成物、履歴不足などを候補理由として示すが、
  推測でコミットを選ばない。欠落パス・内容差分の代表例を報告する。
- 複数一致: 定義した探索順で最初の一致を選び、他にも一致がある旨を報告する。
- shallow clone: 完全な履歴がなく最初を保証できない場合は確定しない。
  自動fetchはせず、必要な対応を案内する。
- sdistなし、取得失敗、SHA-256不一致: バージョンごとのエラーとして記録する。
- アーカイブの絶対パス、親ディレクトリ参照、重複パス、不正な構造は拒否する。
  シンボリックリンク等の特殊メンバーは、初期実装では要調査として扱い、
  一致扱いにしない。アーカイブ内のコードやビルドフックを実行しない。

## 出力とタグ作成

既定は照合のみとし、人が読める一覧と機械可読のJSONレポートを出力する。
レポートには次を含める。

- バージョン、sdist名、取得URL、SHA-256、ファイルサイズ
- 固定した対象refのSHA、探索範囲・順序、比較規則の識別子
- 比較したファイル数、除外パスと理由
- 一致／不一致／要調査／取得エラーの状態
- 選択したコミットSHA、一致候補、既存タグとの競合

タグ作成は明示的なオプションでのみ実行する。タグ名は既存の命名規則を
確認して決める（例: `v1.62.9`）。注釈付きタグとし、以下を記録する。

- リリースバージョン、sdist名、SHA-256
- mainのfirst-parent履歴で内容が一致する最初のコミットを選んだこと
- 実際のビルド元コミットを証明するものではないこと
- 除外した生成メタデータと照合レポートの参照

既存タグを上書き・削除しない。同じコミットなら既存タグとして報告し、
異なるコミットなら競合として停止する。タグ作成前に全対象の競合を確認する。
リモートへのpushは別の明示的な作業として扱う。

## 実装の進め方と検証

1. まず1バージョンの読み取り専用照合とJSON出力を実装する。
2. 全バージョン処理、ダウンロード検証、キャッシュを追加する。
3. レポートを確認してから、明示オプションによるローカルタグ作成を追加する。

一時Gitリポジトリと小さいsdistを使い、少なくとも以下を検証する。

- 同一内容が続く場合に最初の一致を選ぶこと
- 日時が逆転していても履歴順で選ぶこと
- マージ履歴でfirst-parentの定義に従うこと
- 含まれるファイルの欠落・変更、未コミット内容で不一致になること
- sdistにないファイルの変更では一致が維持されること
- 生成メタデータだけを除外し、未知のファイルを無視しないこと
- SHA-256不一致、危険なtarパス、履歴不足、既存タグ競合を扱えること
- 既定実行で作業ツリー、タグ、リモートを変更しないこと

CLI出力・ログ・例外メッセージはリポジトリ規約に従いASCII-onlyにする。
独立した開発者用ツールとして実装し、zstarviewの実行時依存やGUIへ影響を広げない。

## 制約と将来の改善

この照合はsdistに含まれたファイルについての一致であり、リポジトリ全体の
同一性、ビルド環境、wheelとの一致、実際のビルド元コミットを保証しない。
Git LFSや外部生成データが過去リリースにある場合は別途対応が必要となる。

今後はクリーンなリリースコミットからビルドし、コミットハッシュを成果物に
記録する方式を検討する。ビルド自動化やhatch-vcs導入は今回の実装範囲に含めない。
