- Topic: Make place-query resolution deterministic
  - Finding: The app log records two different Nominatim result sets for the same Matsue Station query. At 2026-10-16 00:29 and 00:57 JST, four candidates were returned and the first was `amenity=bus_station`, resolving to 35.4641778, 133.0628539. At 04:00 and 04:06 JST, two candidates were returned and the first was `highway=bus_stop`, resolving to 35.4641008, 133.0626625. Candidate importance values were tied at 0.000062. The current stable sort preserves provider order for ties, so the selected result changes with provider order and candidate membership.
  - Decision proposal: Rank candidates using query/name match and feature semantics before a stable OSM identity tie-breaker. For queries indicating a railway station, prefer railway stations, then public-transport stations, bus stations, bus stops, and generic nearby objects. Ask Nominatim for namedetails and extratags so classification uses OSM tags rather than display-name text. Use `(osm_type, osm_id)` as the final stable tie-breaker; use normalized name, category/type, and rounded coordinates only when OSM identity is absent. Keep importance as diagnostic metadata, not the selection key.
  - Stability: Persist the chosen OSM identity for the normalized query. Reuse it when it remains among refreshed candidates, refreshing its coordinates if that same object moved. If it disappears, select the next candidate with the deterministic ranking and report the old/new identities and coordinates. If equally ranked candidates are semantically distinct and identity cannot resolve intent, report ambiguity rather than imply certainty.
  - Caveat: Deterministic ranking makes a fixed candidate set/order reproducible; it cannot guarantee the same choice when Nominatim changes the candidate set. Persisting selected identity addresses ordinary response churn. A live `--list-cache-ranges -p` query is online-first and can refresh the Nominatim cache; numeric coordinates avoid that lookup.
  - Status: Design only; no resolver behavior changed in this entry.
  - Refinement: Keep Nominatim importance as the primary rank, then, only among candidates with the same top importance, prefer the candidate matching the most recent GUI resolution for the same normalized query, country code, and language. Match by `(osm_type, osm_id)` when stored; use exact resolved coordinates for older launch records that lack OSM identity. Apply a canonical OSM identity sort as the final tie-breaker. If the prior candidate is absent from the current response, use the deterministic fallback and report the location change. Do not promote a prior candidate with lower importance.
  - Rationale: This retains the provider's relevance ranking while preventing response order from moving an already resolved query to a different equal-rank feature. Current launch metadata stores coordinates but not OSM identity; new records should store both identity fields when Nominatim provides them.
  - User refinement: Treat a prior candidate as an OSM-identity match only when both `osm_type` and `osm_id` match and its coordinates match after canonicalization to seven decimal places. If that fails, search for an equal-rank candidate whose canonical latitude and longitude match the previous resolution. This guards against trusting an ID whose associated location changed and also supports old launch records without IDs. If neither match exists, use the deterministic fallback and report the change.
