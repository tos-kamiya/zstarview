# Session: 2026-07-26

Scope: Prototype 5m water raster tiles around Taipei using the refined global grid.

- Topic: Taipei-area 5m raster tile prototype
  - Decision: Extend the existing global-grid prototype with west, north, and northwest neighbors of `x134/y28`: `x133/y28`, `x134/y27`, and `x133/y27`.
  - Rationale: The handoff identifies `x134/y28` as the Taipei 101 tile and recommends checking the immediately adjacent tiles before considering a wider archive or runtime integration.
  - Result: Four `.tif` tiles now exist under `raw-data/water_tiles_5m_global_grid_taipei/`. All use the 5m EPSG:4326 grid and tiled 1-bit DEFLATE GeoTIFF encoding. The three adjacent tiles contained both 0 and 1 in sampled windows; the Taipei tile's sampled windows were all 1, which is consistent with sampling only a few locations in a water-dense tile.
  - Validation: The generated dimensions and bounds were inspected with GDAL; sampled values were limited to the expected binary mask values.

- Topic: Global north-south size-estimation strip
  - Decision: Keep longitude columns `x=133,134` unchanged and generate every latitude row `y=0..79`, covering 119.25–123.75E and 90N–90S.
  - Result: 160 tiles were generated: 102 GeoTIFFs and 58 zero-byte `.0` empty markers. The GeoTIFF total is 131,796,232 bytes (125.69 MiB); the total directory payload is the same because empty markers have zero bytes.
  - Estimate: Scaling this 4.5-degree-wide strip by 80 longitude strips gives approximately 10.54 GB of compressed GeoTIFF payload for a full 360-degree global grid, assuming similar coastline complexity and compression. This is a rough density estimate, not a global forecast.
  - Validation: The strip bounds, tile dimensions, and aggregate file counts/sizes were checked after generation. The largest sampled tile near the equator is 50,085 x 49,759 pixels.

- Topic: All-water marker support and Honolulu estimate
  - Decision: Extend `dev-samples/build_grid_water_tile.py` to inspect the rasterized band with GDAL statistics and emit a zero-byte `.1` marker when every pixel is water. Keep mixed tiles as GeoTIFFs and empty tiles as `.0` markers.
  - Result: The Honolulu longitude column `x=9` (−159.75 to −157.5E) was regenerated for `y=0..79`. It contains 59 `.1` tiles, 9 `.0` tiles, and 12 mixed GeoTIFFs totaling 19,519,356 bytes (18.62 MiB).
  - Estimate: Scaling this one 2.25-degree longitude column by 160 columns gives approximately 2.91 GiB of compressed GeoTIFF payload for the full global grid, assuming comparable water-mask complexity and compression.
  - Validation: The Honolulu coordinate sample (−157.8583, 21.3069) in `tile_y30_x9.tif` returned mask value 0. The helper now has explicit `.1` output logic.

- Topic: Taipei one-column estimate with all-water markers
  - Decision: Generate the Taipei 101 column `x=134` (121.5–123.75E) for every latitude row `y=0..79`, using the new `.1` classification.
  - Result: 80 tiles were generated: 22 `.1` all-water markers, 29 `.0` empty markers, and 29 mixed GeoTIFFs. The GeoTIFF total is 60,273,771 bytes (57.48 MiB); marker files are zero bytes.
  - Estimate: Scaling this 2.25-degree column by 160 longitude columns gives approximately 9,643,803,360 bytes (8.98 GiB, about 9.64 GB decimal) for a full global grid, assuming similar regional complexity and compression.
  - Validation: `tile_y28_x134.tif` covers 121.5–123.75E and 24.75–27.0N with dimensions 45,072 x 49,759 pixels. Aggregate counts and sizes were checked after generation.

- Topic: 25m one-column size comparison
  - Decision: Generate one full latitude column at 25m for Honolulu `x=9` and Taipei `x=134`, preserving the same 2.25-degree longitude width and `.0`/`.1` marker classification.
  - Result: Honolulu has 12 mixed GeoTIFFs, 9 `.0` markers, and 59 `.1` markers totaling 912,730 bytes (0.87 MiB). Taipei has 29 mixed GeoTIFFs, 29 `.0` markers, and 22 `.1` markers totaling 3,351,626 bytes (3.20 MiB).
  - Estimate: Scaling one column by 160 longitude columns gives approximately 0.15 GB for Honolulu and 0.54 GB for Taipei (decimal units). The Taipei value is the more conservative estimate for this source and region.
  - Validation: Both output directories contain 80 tiles, and aggregate counts/sizes were checked after generation.

- Topic: Full-global 25m tiles in the existing 125m format
  - Decision: Add 25m to `osm_water_polygons_to_tiff.py` using the existing 32 x 16 global tile grid, `tile_y{row}_x{col}` naming, CCITTFAX4 1-bit GeoTIFFs, and `.0`/`.1` markers. Use direct GeoTIFF writing and GDAL statistics for 25m tiles so a roughly 54,000 x 54,000 raster is not loaded into a Python array.
  - Result: Generated all 512 global tiles under `raw-data/water_tiles_25m_global_format/`: 312 GeoTIFFs, 73 `.0` markers, and 127 `.1` markers. GeoTIFF payload is 1,137,688,581 bytes (1.060 GiB, 1.14 GB decimal); marker files are zero bytes.
  - Validation: Representative 25m tiles are 54,000 x 54,000 pixels with 0.0002083333333333-degree pixel spacing and CCITTFAX4 compression, matching the existing 125m format apart from resolution. Ruff and `git diff --check` passed.

- Topic: 32x16 coastline vector tile size experiment
  - Decision: Generate one GeoJSON tile per existing 32 x 16 global tile. Each tile stores source polygon boundary geometries clipped to the tile bounds; empty tiles use a `.0` marker. This is a size experiment, not yet a runtime format decision.
  - Result: All 512 vector tiles were generated under `raw-data/coastline_vector_tiles_32x16/`. There are 479 GeoJSON tiles and 33 empty markers, totaling approximately 2.50 GiB uncompressed.
  - Result: The largest observed tile is `tile_y12_x9.geojson` at 252,291,387 bytes (about 252.3 MB). A gzip level-9 stream of that tile is 51,129,037 bytes (about 48.8 MiB). The next-largest sampled tiles were also above 100 MB uncompressed.
  - Caveat: This prototype keeps full GeoJSON coordinate text and clipped boundary feature overhead. Topology-aware vector tiles, coordinate quantization, simplification, and binary encoding could reduce the size substantially, but were not applied here.

- Topic: Selective 4x4 subdivision of the eight largest vector tiles
  - Decision: Replace the eight largest parent GeoJSON tiles with 4 x 4 geographic child tiles for a size experiment; keep the other 504 parent tiles unchanged. The child tiles are clipped from the parent boundary geometries and use names such as `tile_y12_x9_q11.geojson`.
  - Result: 128 child outputs were generated: 111 GeoJSON files and 17 empty `.0` markers. The child GeoJSON total is 1,008,239,114 bytes (0.939 GiB). The largest child is `tile_y12_x9_q11.geojson` at 72,884,341 bytes (69.51 MiB); the largest sampled gzip result is 15,809,127 bytes (15.07 MiB) for `tile_y2_x17_q13.geojson`.
  - Conclusion: Fixed 4x4 subdivision materially reduces the worst-case tile from 252.3MB to 72.9MB uncompressed, but does not meet a 50MB uncompressed target. A second subdivision level or coordinate quantization/simplification would be needed for that target.

- Topic: Minimal coastline vector preview integration
  - Decision: Add a read-only preview loader for the experimental GeoJSON tiles and feed its projected line fragments into the existing water polyline renderer. Keep downloading, manifest validation, persistent vector-tile caching, and automated tests out of this trial.
  - Result: The loader reads the planned cache location when present, then falls back to the uncommitted experiment directories. It supports the flat 32 x 16 files and the selective 4 x 4 child files, clips linework to 10 km around the observer, and reuses the existing Alt/Az polyline drawing path for both the GUI and export-image CLI.
  - Validation: The loader returned projected line fragments for Honolulu (13), a Taipei port-area point (10), Patagonia (38), and coastal Scandinavia (93). Compile, Ruff, and `git diff --check` passed.
  - Limitation: This is intentionally a visual trial. The repository data is not added to the commit, and missing or malformed preview tiles simply produce no vector coastline layer.

- Topic: Water overlay distance limit
  - Decision: Keep the existing altitude-dependent search radius for water dots, while using a fixed 10 km maximum for inland-water and coastline boundary polylines.
  - Rationale: A 1 km observation tower places a 10 km distant sea surface at approximately -5.76 degrees altitude. Boundary geometry benefits from the wider fixed range, but dot rendering should retain its existing behavior and cost.

- Topic: Coastline preview tests
  - Decision: Add small fixture-based tests for normal and split vector tiles, `.0` markers, malformed GeoJSON, 10 km clipping, and the separation between dot and boundary distance settings.
  - Result: The new coastline test module passed 7 tests. The complete non-GUI suite passed 1,299 tests, and the GUI suite passed 15 tests with `QT_QPA_PLATFORM=offscreen`.
  - Fix: An explicitly configured `ZSTARVIEW_COASTLINE_TILE_DIR` now suppresses repository preview fallbacks, preventing unrelated local data from contaminating cache tests or preview runs.
