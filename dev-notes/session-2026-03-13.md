# Session 2026-03-13

- Scope: Verify whether the star rendering surface resizes with the window.
- Topic: Window resize and star rendering surface behavior
  - Decision: The app does resize the internal star-render surface in response to window size changes.
  - Rationale: `SkyWindow.resizeEvent()` enters viewport-interaction mode and invalidates the composition cache. The subsequent `paintEvent()` path recalculates screen geometry from `self.width()` and `self.height()`, and `_draw_star_layer()` recomputes the star render surface size from that current window size before allocating a `QImage`.
  - Alternatives Considered: None. The existing code path is direct enough that runtime probing was not necessary for this verification.
- Topic: Document square-root star-surface downsampling
  - Decision: Added the internal star-render surface scaling rule to `docs/design.md`.
  - Rationale: The behavior is an implementation detail of `window_render.py`, not just a CLI option description. Recording it in the design doc makes the resize/render tradeoff explicit for future maintenance.
- Topic: Scale asterism and terrain line widths with star-surface enlargement
  - Decision: Reused the star-layer downsampling rule to derive an on-screen upscale factor, and applied that factor only to asterism strokes and terrain-horizon strokes.
  - Rationale: When the star layer is rendered to a reduced internal surface and then enlarged, stars appear thicker on large windows. Matching only the related visual overlays keeps those elements visually consistent without changing the thickness of reference lines, zenith marker, crosshair, or urban outlines.
