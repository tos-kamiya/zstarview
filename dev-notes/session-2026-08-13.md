- Scope: Review licensing and request frequency before enabling GMN meteor trails by default.

- Topic: Enable meteor trails by default
  - Decision: Change the `--meteor-trails-opacity` default to `0.4` for the interactive viewer and add the required GMN attribution and modification notice to the bundled license summary and README. Keep `0` as the explicit session-level disable. Do not advertise the option for image export until that path implements meteor loading and rendering.
  - Rationale: GMN publishes its high-level products under CC BY 4.0 and states that they update every six hours. No explicit request-rate limit is published. The existing shared cache limits directory-index and recent-file network refreshes to once per six hours, matching the source update cadence; historical files are reused indefinitely.

- Scope: Restrict Open-Meteo forecast precipitation to real-time views.

- Topic: Forecast precipitation time gating
  - Decision: Add precipitation to the shared real-time overlay availability
    policy and enforce it for interactive startup, background refreshes, menu
    state, and image export.
  - Rationale: Open-Meteo values represent the current forecast snapshot, so
    showing them against a past or future sky time is misleading. Reusing the
    existing five-minute real-time tolerance keeps precipitation consistent
    with clouds and tropical cyclones.

- Topic: GMN publication-delay display policy
  - Decision: Specify a 24-hour meteor window ending at the latest GMN
    observation available at or before the display time. Show its age as
    `M {count}, {oldest}-{newest}h ago`, using hours only.
  - Rationale: GMN trajectory publication commonly trails observation by one
    or more days, so a window ending at real time is often empty. A relative
    range communicates the actual age compactly without implying live data.

- Topic: Implement delayed GMN observation windows
  - Decision: Search indexed daily files newest-first for up to seven days,
    then load only the additional files needed to cover the 24 hours ending at
    the newest observation at or before the display time. Store both the
    requested display time and selected window in `MeteorWindowResult`.
  - Rationale: Progressive discovery avoids routinely downloading a full week
    of large trajectory summaries, while the bounded lookback prevents an
    unbounded historical scan. Keeping both times in the result makes status
    ages deterministic for past views and lets rendering fade relative to the
    selected data window rather than publication delay.
  - Alternatives Considered: Loading the entire seven-day search range before
    choosing a window was simpler, but would add unnecessary network and parse
    cost on every cold-cache update.
