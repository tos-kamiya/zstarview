# 建物IDの重複排除の引き継ぎ

作成日: 2026-11-24。状態: 実装済み（`85d7c0bd`、`fix: deduplicate building outlines`）。
近景建物の壁表示の検討は `dev-notes/handoff-2026-11-24-nearby-building-walls.md` に戻る。
以下の現状と注意点は実装前の調査記録である。

実装では、合成ID以外の建物レコードが全フィールド一致する場合に重複を除去し、同じIDでも
内容が異なるレコードは保持する。合成IDは識別し、重複排除の対象にしない。既存の親子処理も維持する。

## 目的

複数の派生建物キャッシュやタイルから同じ建物が読み込まれた場合、都市アウトラインの
候補や処理が重複しないようにする。既存の建物本体と建物部分の親子関係も維持する。
重複排除の対象と採用規則は以下の注意点を確認して決める。

## 現状と再現例

- `src/zstarview/data/building_source.py` は観測地点周辺の有効なPLATEAUキャッシュを
  複数選択する。`src/zstarview/urban_outline_layer.py` の
  `_build_observer_centric_urban_outline_result` は各ディレクトリ・タイルの建物を
  `collected_buildings` に追加し、`_merge_building_footprints` に渡す。
- `_merge_building_footprints` は `parent_building_id` を使って、部分がある場合に
  親建物を抑制するが、同一 `building_id` のレコードは重複排除しない。
  `tests/test_urban_outline_layer.py` に親子関係の既存テストがある。
- 例: `uv run zstarview "Tokyo" -A5 -Zse` の地点（35.6895, 139.69171）では、
  新宿区 `13104_2025` と渋谷区 `13113_2025` の両キャッシュの
  `53394525_bldg_6697_op.json` に、以下の同じIDが現れる。
  - `bldg_94caaf2f-dec2-41a7-8b0f-06ecd0fac6c7`（高さ226.0 m、地点を含む）
  - `bldg_b3c5d347-d7e8-422a-95c4-4538e4957c51`（高さ27.1 m）
  - `bldg_f507090f-502d-45eb-b8ac-0fad64b8c311`（高さ10.3 m）
  2キャッシュの該当レコードはID・高さ・近傍距離が一致した。形状・全属性の同一性は未検証。
- 重複は候補上限、計算量、輪郭や半透明の描画に影響し得る。影響の大きさは未測定。

## 設計上の注意

- `src/zstarview/data/derived_tile_cache.py` の `parse_derived_tile_buildings` は
  IDがない場合にタイル内インデックスから `bldg-{index}` を補完する。別タイルの異なる
  建物が同じ補完IDになる可能性があるため、**単純なIDだけの全体重複排除は危険**。
  IDの出所・有効範囲、データソース、タイル情報を確認し、欠損IDは誤って除外しない。
- 同一IDでも形状や高さが異なるケースの扱い（先着優先、内容検証・ログ、適切な
  データを選択する等）は未決定。ソース間・年度間のIDの意味や、同一建物の部分を
  どう識別するかを確認し、安易に別レコードを消さない。決定的な順序を維持する。
- Overtureの親建物と `building_part` はIDと親IDの関係を持つ。重複排除が部分形状を
  消したり、現在の親抑制の動作を変えたりしないようにする。
- PLATEAUとOvertureは通常同時に重ねないが、共通の読み込み経路が使われるため両方への
  影響を確認する。建物上端の地点解決は別経路なので、対象に含める必要性を別途判断する。
- 候補上限やDEMサンプリングの前に重複を除くと無駄な処理を避けられる。どの層で
  識別情報を保持し判定するかは、欠損IDやタイル由来の衝突を考慮して決める。

## 検証と完了後

1. 別キャッシュの同一建物を1件にするケース、別タイルのID欠損レコード、同一IDで
   内容が異なるケース、異なるIDの建物、親と部分の関係をテストする。
2. Tokyoの上記キャッシュで重複が減ること、近傍の別建物が残ることを確認する。
3. 都市アウトライン関連テストを実行し、実装に応じて必要な追加検証を行う。
4. 完了したら設計判断と検証結果をセッション記録に残し、近景の壁表示の検討へ戻る。

この資料作成時点でアプリケーションの実装は変更していない。
