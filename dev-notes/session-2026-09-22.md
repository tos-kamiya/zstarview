# Session 2026-09-22

Scope: Review long-running GUI heap retention and garbage-collection behavior.

- Topic: NumPy/CuPy applicability review
  - Decision: Audit all NumPy-heavy paths, data movement to Qt/Astropy/Skyfield,
    and available benchmark evidence before recommending GPU changes.
  - Rationale: CuPy can accelerate large homogeneous array kernels, but transfer
    overhead and library/API boundaries may outweigh gains in an interactive GUI.

- Topic: Initial memory-lifetime audit
  - Decision: Inspect GUI state holders, background controllers, image caches,
    timers, futures, and shutdown paths before proposing changes.
  - Rationale: The request is diagnostic; changes should not be made until
    retained references and bounded caches are identified with file evidence.

- Topic: Findings
  - Decision: Report the normal render/update path as mostly bounded, but flag
    the Moon/Sun hover image dictionaries and water-overlay scope dictionary as
    unbounded in-memory retention points.
  - Rationale: `_images` and `_scope_cache` are keyed by changing time/location
    values and have no eviction or clear operation. Other inspected render
    caches are single-entry or explicitly bounded LRU caches, and worker
    futures are removed by done callbacks.

- Topic: Terrain horizon lifetime
  - Decision: Treat terrain memory as latest-result retention rather than a
    history leak. DEM file handles are explicitly closed, the controller keeps
    only a completed-location marker, and GUI state replaces the previous
    profile and sample arrays.
  - Rationale: The terrain result intentionally retains profile, ridge, and
    sample arrays for rendering and water-overlay reuse, but no per-refresh
    cache was found. With a fixed observation location, the terrain update is
    normally performed once per window lifetime.

- Topic: NumPy/CuPy applicability findings
  - Decision: Do not introduce CuPy as a general NumPy replacement. The only
    worthwhile follow-up candidate is an optional GPU benchmark for the large
    cloud/geosatellite projection or night-light accumulation paths, behind a
    CPU fallback.
  - Rationale: The default observer cloud grid is only 90x720 (64,800 cells),
    geosatellite projection defaults to a 510x510 image (260,100 samples), and
    projection coordinates are cached. These workloads are one-shot or cached,
    while input decoding, Satpy/xarray/Polars, Astropy/Skyfield, Numba CPU
    kernels, disk I/O, and QImage/QPainter/Pillow boundaries remain on CPU.
    GPU transfer and initialization overhead would likely erase any kernel
    speedup in normal interactive use.
  - Alternatives Considered: GPU-rendering the star canvas and replacing all
    NumPy imports with CuPy. Both were rejected because the result is copied
    into CPU QImage/QPainter and the code uses irregular scatter operations,
    object/string arrays, external CPU libraries, and APIs not compatible with
    CuPy device arrays.

- Topic: Prioritized optimization targets
  - Decision: If performance data justifies GPU work, benchmark in this order:
    (1) repeated/high-resolution geosatellite bilinear projection, (2) cloud
    alt/az ingestion with substantially larger source grids, and (3) night
    light glow accumulation. Keep NumPy/Numba as the default path.
  - Rationale: These contain the most contiguous trigonometric, interpolation,
    and accumulation work. Star rendering, small coordinate helpers, cache
    serialization, and scalar astronomy calculations have poor GPU economics.

- Session summary
  - Completed a read-only NumPy/CuPy applicability audit; no source code or
    dependency changes were made.
  - Local environment has NumPy and Numba but no CuPy, and no usable NVIDIA
    driver was detected, so GPU speedup was not empirically benchmarked.
  - Follow-up: benchmark only the prioritized projection/ingestion/glow paths
    on a representative CUDA machine if those paths are measured bottlenecks.

- Topic: Star rasterizer Numba experiment
  - Decision: Keep the production star renderer unchanged for now; add a
    dev-samples benchmark for the regular-star rectangle stage and a matching
    Numba prototype.
  - Rationale: The prototype showed 11.1x-16.0x faster rasterization alone,
    but only 1.15x-2.34x faster when RGBA conversion, QImage construction, and
    QPainter composition were included. The benchmark excludes bright-star
    diamond/outline paths and twinkle, so integrating it without a pixel-level
    comparison for all modes would be premature.
  - Validation: `ruff check dev-samples/benchmark_star_rasterizers.py` passed.
    At 1920x1080, 5,000 / 20,000 / 50,000 / 100,000 synthetic stars produced
    full-pipeline speedups of 1.15x / 1.45x / 1.91x / 2.34x respectively.

- Topic: 4K star rasterizer benchmark
  - Decision: Treat 4K as buffer-bandwidth dominated for the current pipeline;
    Numba remains useful only for the star-pixel stage and does not yet justify
    production integration by itself.
  - Rationale: At 3840x2160, full-pipeline speedups for 5,000 / 20,000 /
    50,000 / 100,000 stars were 1.09x / 1.17x / 1.35x / 1.55x. The isolated
    raster stage measured 2.12x / 2.96x / 4.29x / 5.78x, while RGBA creation,
    QImage copying, and QPainter composition dominated the total time.

- Topic: Premultiplied QImage experiment
  - Decision: Switch star-buffer images to `Format_ARGB32_Premultiplied` while
    retaining `.copy()` for ownership safety. Convert straight-alpha helper
    images with integer premultiplication; encode the additive star canvas
    directly because its RGB values already equal premultiplied values.
  - Rationale: This removes the regular-star path's float unpremultiplication
    and uses a QPainter-preferred format. Thin colors are not multiplied twice:
    the canvas path writes RGB <= alpha directly, while the light-background
    path premultiplies exactly once.
  - Validation: Added `tests/test_star_premultiplied_image.py`; focused star,
    twinkle, and asterism tests passed (38 tests). At 3840x2160 and 20,000
    stars, old/new full-pipeline timings were 0.530s/0.362s for NumPy and
    0.464s/0.296s for Numba, respectively.

- Topic: Production adoption of conservative star-image path
  - Decision: Adopt NumPy + `Format_ARGB32_Premultiplied` in the production
    star renderer; leave the Numba star rasterizer as benchmark-only code.
  - Rationale: This keeps the existing NumPy rasterizer and Qt composition
    behavior while removing unnecessary straight-alpha RGB reconstruction and
    avoiding the additional Numba compilation and kernel-correctness risks.
  - Validation: Focused star, twinkle, asterism, deep-sky, and premultiplied
    image tests passed (42 tests); Ruff passed for the changed implementation
    and tests.
