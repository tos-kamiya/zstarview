- Topic: アステリズム表示機能の実装確認
  - Decision: プラネタリウム描画にはアステリズム機能が実装済みと判断した。
  - Rationale: `src/zstarview/asterisms.py` に定義群があり、`src/zstarview/render/draw.py` で常時の淡色描画とホバー時の強調描画・ラベル表示を行い、`src/zstarview/ui/window.py` と `src/zstarview/ui/famous_star_shortcuts.py` で表示トグルと検索導線も接続されているため。
- Topic: アステリズム線の FOV クリップ境界
  - Decision: アステリズム用に `ASTERISM_CLIP_FIELD_OF_VIEW_DEG` を新設し、広い側の背景 FOV (`BACKGROUND_FIELD_OF_VIEW_DEG2`) を既定値として使うことにした。
  - Rationale: 明るい恒星は通常の空円盤より外側まで見えるため、アステリズム線だけ狭い境界で切ると「星は見えるのに線が途切れる」不整合が起きるため。アステリズム専用定数にしておけば、将来の描画調整も星とは独立に行える。
- Topic: アステリズム線の部分表示ロジック
  - Decision: 線分端点の単純な FOV AND 判定をやめ、正規化座標上で円形クリップして境界内の折れ線片だけ描くようにした。
  - Rationale: 片端だけが視野内にある線分を表示しつつ、画面外へ長く伸びる線や不自然なはみ出しを防ぐため。サンプル済みの大円弧を円でクリップする実装なら既存描画に小さく載せられる。
- Topic: 方向キー視線変更時の簡易表示モード
  - Decision: 方向キーによる向き変更では、後にリサイズとも共有できるよう `viewport_interaction_mode` へ整理した簡易表示モードを導入し、最後の入力から一定時間は `vmag <= 4.0` の明るい星とガイドライン、方位ラベル、天頂マーカーのみを描く構成にした。
  - Rationale: 方向キー連打中に sky worker や雲・地形地平線更新まで追随させると、見た目も負荷も不安定になるため。`render_view_center` を即時更新して再投影だけで追随させ、停止後に一度だけ通常更新を流す方が操作感が安定する。
  - Alternatives Considered: 既存 `interaction_mode` のみを流用する案も考えたが、リサイズやジャンプ操作でも使っている状態のため意味が広すぎ、副作用が出やすいので専用状態に分離した。
- Topic: タワー dataset 参照専用 CLI
  - Decision: GUI を起動しない軽量経路として `--list-towers`、`--list-tower-names`、`--show-tower-json NAME` を追加した。
  - Rationale: タワー名候補や 1 件の詳細を確認したい用途は、起動位置解決と同じ dataset をそのまま参照できれば十分であり、GeoNames 読込や GUI 初期化を伴わせる必要がないため。人間向けの英語主表示名一覧と、多言語入力候補一覧、単一タワーの JSON 取得を分けることで責務も明確になる。
  - Alternatives Considered: 検索・フィルタをさらに増やす案もあるが、それ以上が必要な場合は JSON ファイルを直接参照してもらう方針にした。
- Topic: タワー名の ASCII フォールバック
  - Decision: dataset の `name` は保持したまま、一覧表示と名前解決用に `ascii_name` を動的に算出することにした。
  - Rationale: `Žižkov` や `Tsūtenkaku` のようなダイアクリティカルマーク付き名称は、正式表示としては維持したい一方、CLI 入力や一覧表示では ASCII 表記の方が扱いやすいため。別フィールドとして扱えば、表示と解決の利便性を上げつつ元データも失わない。
  - Alternatives Considered: dataset 側の `name` を ASCII に置き換える案もあるが、正本データの表記を崩すので採用しなかった。
- Topic: 山頂ビュー候補の抽出スクリプト
  - Decision: `dev-samples/` には、Wikipedia 由来の curated 候補 JSON を入力にして Wikidata で正規化する `build_curated_mountain_viewpoints.py` を追加した。
  - Rationale: 山の候補選定は地域代表性ベースの手 curated が必要であり、いきなり自動抽出するよりも、候補選定と正規化を分離した方がデータ品質を管理しやすいため。実装では seed 側の座標・標高を override として扱い、足りない情報だけ Wikidata API から補う形にした。
  - Alternatives Considered: Wikipedia 直接スクレイピングを行うスクリプトも考えられるが、構造変化に弱く、選定ポリシーと抽出ロジックが混ざるため見送った。
- Topic: 山の raw query 結果の中間整形
  - Decision: `highest point of each country` の raw result を直接 curated seed にせず、まず `build_wikidata_mountain_candidates.py` で `(country_qid, item_qid)` 単位のレビュー用候補へ畳むことにした。
  - Rationale: raw result には同一山の重複行、複数座標、複数標高、共有峰が混在しており、そのまま最終 seed にすると判断根拠が見えにくくなるため。中間 JSON に `needs_coord_review`、`needs_elevation_review`、`is_shared_peak` を持たせることで、人手レビューを先に行えるようにした。
  - Alternatives Considered: raw result をそのまま `build_curated_mountain_viewpoints.py` に食わせる案もあるが、レビュー対象の揺れが埋もれるため採用しなかった。
