- Topic: PyPI release list extraction
  - Decision: Use the PyPI `Release history` section as the source of truth and store only version identifiers, one per line, in descending release order.
  - Rationale: The user requested a list of released versions from the linked page. Keeping only the version strings makes the output directly reusable for diffing, scripting, or comparisons without additional cleanup.
  - Alternatives Considered: Including release dates alongside versions. Rejected because the request asked for a version list, not a dated changelog.

- Topic: Release-note material generator
  - Decision: Add a local script that maps released versions to the first git commit that introduced each `__version__`, then collects commit subjects and `pyproject.toml` diffs between released versions.
  - Rationale: The release-note task depends on more than commit subjects alone. Using release-window commit lists plus `pyproject.toml` changes makes dependency and packaging shifts visible without manually walking git history for each version.
  - Alternatives Considered: Deriving release notes only from tag names or only from commit subjects. Rejected because this repository's releases are better identified by version-file transitions, and dependency changes often live in `pyproject.toml`.
