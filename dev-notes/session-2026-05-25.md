- Topic: Cloud refresh scheduler regression
  - Decision: Stop resetting `cloud_next_refresh_utc` from the sky-data completion path, and let cloud fetch scheduling remain owned by cloud startup / source-ready / failure handlers.
  - Rationale: Reusing the sky completion hook to push the cloud deadline forward broke the intended fixed-interval cloud fetch behavior. Frequent sky refreshes, including interactive follow-up updates, could indefinitely postpone the next cloud download even while the cloud layer stayed enabled.
  - Alternatives Considered: Recomputing the cloud deadline conditionally from the sky path. Rejected because cloud refresh cadence is already defined by cloud-specific events, and a second scheduling owner would keep the coupling fragile.

- Topic: Version bump release-note rule
  - Decision: Add a repository rule that any package version bump should include a matching update to `release-notes.md` in the same change unless the version bump is intentionally undocumented.
  - Rationale: Version changes are user-visible release events, so the release notes should stay in lockstep with the shipped version history. Requiring the note update in the same change reduces drift and avoids forgotten release entries.
  - Alternatives Considered: Allowing release-note updates to land later as follow-up work. Rejected because it increases the chance of version/release-note mismatch.

- Topic: Release-note scope rule
  - Decision: When drafting release notes, review changes back to the previous version-bump commit so the entry reflects the whole release window rather than only the immediate parent commit.
  - Rationale: The last commit before a release bump is often only part of the story. Scoping by version boundary produces complete release notes and avoids dropping earlier fixes or features from the same release.
  - Alternatives Considered: Limiting the review to the latest commit or a small recent range. Rejected because it can omit significant changes that were already shipped in the same version.
