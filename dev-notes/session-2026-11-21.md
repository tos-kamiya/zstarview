- Topic: 矢印キーのリピートを描画1回につき1ステップに制限
  - Decision: 押下中の自動リピートは受け取るが、前回の回転ステップがまだ描画されていなければ捨てる。描画開始時（`paintEvent`）に描画待ちを解除する。最初の押下とキー解放の処理は従来どおり。
  - Rationale: キーリピートは約30ms間隔（xset: delay 500ms, rate 33/s）で届き、操作中の描画は1フレーム90-150msかかる。Qtは描画要求をまとめるため、描画の合間に3-6回分（15-30度）が処理され、画面上で角度が飛んで見えていた。利用者の要望で、回転速度が描画速度に依存する（約8fpsで毎秒40度前後）ことを受け入れて、1コマ5度の滑らかさを優先した。
  - 安全策: 実ウィンドウの自動テストで、描画待ちが解除されないまま約4秒間リピートがすべて捨てられ回転が止まる事象が1回出た（原因は未確定。描画中に入力が処理される経路などが考えられる）。対策として、捨てるときにも再描画を要求し、最後の回転から250ms（`VIEWPORT_ROTATION_PAINT_WAIT_S`）以上経ったリピートは描画を待たずに回す。利用者が実機で5度ずつ滑らかに回ることを確認した。
  - Alternatives Considered: 前回描画からの経過時間に応じて回転量を決める方式は、回転速度が環境に依存しない利点があるが、1コマの飛びが描画時間に比例するため今回は採用しなかった。
  - 補足: 先に報告された「fast-modeで更新されず、離すと大きく回った画面になる」現象は再現しなかった。GNOME Wayland でリモート操作の許可前に xdotool の入力が数秒遅れてまとめて届いた自動テストを見ていた可能性が高い。許可はプロセスごとに求められる模様で、自動操作時に警告音が出ることがあったため、以降の確認は利用者が実機で行った。

## PySide6 の stub と実行時の食い違いの調査

- 調査: PySide6 6.10.0 / 6.10.3 / 6.11.0 / 6.11.3 / 6.12.0（PyPI の最新）を `uv run --no-project --with "PySide6==X"` で切り替え、offscreen で確認した。
  - `QImage.save(path, fmt)`: どのバージョンも str の `"PNG"` は受け付け、bytes の `b"PNG"` は `ValueError`（wrong argument values）で拒否する。format を省くと、拡張子 `.tmp` では保存に失敗する。stub はどのバージョンも `format: bytes | bytearray | memoryview | None`。`QPixmap.save` の stub は `format: str | None` なので、`QImage` の stub の誤りと見られる。
  - `QImageWriter(path, b"PNG").write(image)`: 6.10.0 と 6.12.0 で成功し、読み戻しも確認した。stub と実行時が一致しており、`mypy --strict` でもエラーは出ない（str を渡すと実行時に `TypeError`）。
  - `QListWidget.setCurrentItem(None)`: どのバージョンも選択解除として動き、stub はどのバージョンも `None` を受け付けない。`setCurrentRow(-1)` でも結果と発行されるシグナル（`itemSelectionChanged`、`currentItemChanged(None, prev)`、`currentRowChanged(-1)`）とその順序が同じだった。
  - 上流: 該当する issue は見つからなかった。類似の報告は PYSIDE-1968（`QPixmap.save` の bytes の format、6.3.0 で修正済み）と PYSIDE-2235（`setParent(None)` の stub）。

- Topic: PNG ファイルの保存方法
  - Decision: `QImage.save(path, "PNG")` をやめ、`render/qt_image.py` に新設した `save_qimage_png(image, path)`（`QImageWriter(os.fspath(path), b"PNG")`）に統一した。対象は `replay/sequence.py`、`gui/window.py`（定期デバッグスナップショット）、`data/test_draw_sky_disc.py`、`scripts/prototype_cloud_cell_shading.py`、`scripts/render_star_gray_background_experiment.py`。これで `type: ignore[call-overload]` が2件なくなった。

## 地球ガイドを日照付きの陸・海の塗りに変更

- Topic: 地平線下の地球ガイド（地球裏面の大陸輪郭）の見せ方
  - Decision: 輪郭線（太いアンダーレイ付き）と緯度方向の点線による陸の塗りをやめ、地平線下の各画素を地球の向こう側の地表点へ逆投影して、陸と海を色分けした面として塗る。明るさは各地表点での太陽高度で決め、昼側だけが光り、薄明（0〜-18度）で滑らかに消え、夜側は描かない。
  - Rationale: 利用者から「視覚的に邪魔になる割にあまり楽しくない」との指摘。透視投影では近い陸地が地平線直下に圧縮され形が読みにくく、線の量に比べて得られる情報が少なかった。日照を加えると「今、足元のどの大陸に日が当たっているか」が読め、時間を進めると昼の領域が動く。線をなくしたことで星空の邪魔も減る。
  - 色: 陸は従来の `PALETTE_EARTH_GUIDE_RGB (112, 99, 89)`。海は利用者の案で近景の水域線の色 `(122, 218, 240)` を基にしつつ、そのままでは明るく彩度が高く地球の7割を占めて主張しすぎるため、同じ色相で彩度を半分にし陸と同程度の明るさにした `(89, 117, 123)` とした。うるさければ `EARTH_GUIDE_OCEAN_ALPHA_SCALE`（既定1.0）で海だけ不透明度を下げる。アステリズムの色 `(122, 226, 240)` と重なって見えにくくならないかは、利用者が実画面で確認・調整する。
  - 日照計算: 太陽は平行光とみなし、地表点の単位ベクトル `p` と太陽方向 `s`（既存の太陽 alt/az を観測者の east/north/up 基底で地球固定座標へ変換）の内積を太陽高度の正弦とする。新たな天文計算は不要で、観測地点では自分の空の太陽高度と一致する。
  - 実装: 陸地判定は LOD 3 のリングを Pillow で0.25度格子の陸地率マスクへ一度だけ塗り、双線形補間で引く。描画は表示の1/2（fast-mode は1/4）で計算して平滑拡大する。表示半径による LOD 切り替えは不要になったので削除した。
  - Alternatives Considered:
    - 陸だけを塗る案: 明暗境界が海上にある時間帯に昼夜の区切りが読めないため、海も塗る案（利用者の提案）を採用。
    - 都市・対蹠点のラベルと現地時刻を出す案、ホバー時だけ情報を出す案: 将来の拡張候補として保留。
    - 「その地点の天頂が自分の空のどこにあたるか」で投影する案（地平線下の星が「どこの真上か」を示せる）: 意味が変わる大きな方針転換なので見送り。
    - 輪郭線を細い点線にするなど見た目だけ軽くする案: 「楽しくない」点が解決しないため不採用。
  - 検証: 夜の東京から南の地平線下を見た export 画像で、太陽方向を中心にアフリカと南アメリカの昼側が淡く浮かぶことを確認。2400×1400・半径1100px での描画時間は約0.3秒で旧実装と同程度。`tests/test_earth_guide_render.py` を新方式に合わせて書き直した（マスク、日照の段階、対蹠点・半角の関係、地平線上に描かないこと、陸と海の色、合成への太陽位置の受け渡しなど）。`test_sky_compositor.py` の never-rises の色のテストは、地球ガイドの海色が混ざるため地球ガイドを無効にして対象を分離した。全テスト成功、mypy 問題なし。

- Topic: 地球ガイドの昼側が小さく見える件と、夜側の輪郭線
  - 経緯: 利用者が実機で「昼の部分がかなり小さく見える。太陽の方向に90度くらいまで明るいのか」と確認。透視投影では中心角θの地点が伏角θ/2に見える（円周角の定理）ため、地表で半球を占める昼側は空では半径約45度にしかならない。昼側の中心も太陽の方向ではなく、同じ方位の伏角 45+a/2 度（太陽高度 -a 度のとき）にある。加えて、明るさを太陽高度の正弦に比例させ、明暗境界付近を45%まで落としていたので、見える範囲はさらに狭かった。
  - Decision: (1) 明るさの曲線を平らにした。`EARTH_GUIDE_DAY_MIN_LEVEL` を 0.45 から 0.8 にし、薄明の消える高度を -18 度から -12 度にした。(2) 利用者の提案で、塗りが消えた夜側に陸の輪郭線を白い細線（幅1px）で描く。輪郭線は -12 度から現れ、-18 度で最大になる。最大不透明度は塗りの最大値の80%。(3) 利用者の指摘で、観測地点から地表距離500km以内は塗りも輪郭線も描かず、800kmまでにフェードインさせる。地平線からの角度によるフェードは3度から1度に縮めた。
  - Rationale: 曲線を平らにすると、幾何的な45度の範囲がそのまま昼側として読める。夜側を輪郭線にしたことで、地球全体の配置が分かり、昼と夜の差も明確になる。近い陸地の扱いは、最初は輪郭線だけ地平線から8度かけてフェードさせたが、利用者の「500kmくらいは描かないほうがよい」という意見の方が意味が明確（距離で決まり、観測高度や視線に依存しない）なので置き換えた。
  - Alternatives Considered: 投影を「各地点の天頂が自分の空のどこに当たるか」に変える案。この投影では太陽から90度以内がちょうど昼側になるが、「地面を透かして見た地球」という意味が失われ、近い側の大陸も写らなくなるため見送った。
  - 実装メモ: 同梱リングは日付変更線で分割され、南極は南極点の辺で閉じている。その辺を輪郭線として描くと偽の線になるので除外した（`_is_seam_segment`）。
  - 検証: 夜の東京から南の地平線下を見た export 画像で、夜側のオーストラリアや東南アジアが白い輪郭線で、昼側のアフリカと南アメリカが塗りで表示され、地平線際の筋が消えたことを確認。テストを6件追加（輪郭線の強さの範囲、継ぎ目の除外、線分の長さ、500kmの距離フェード、夜側だけに輪郭線が出ること、輪郭線が白いこと）。

- Topic: fast-mode では地球ガイドを線だけにする
  - Decision: 利用者の要望で、`fast_mode`（視線操作・リサイズ中）は塗りを省略し、LOD 0 の陸の輪郭線を昼夜にかかわらず白い細線で描く。距離500km・地平線・視野の条件は通常と同じ。太陽位置がなくても描く。
  - Rationale: 操作中は軽さと向きの手がかりが優先で、低解像度の塗りはぼやけて重い。夜側だけの線にすると、昼側の大陸が操作中に何も見えなくなるので、全周の輪郭線にした。2400×1400 で fast-mode の1回の描画は約20〜30ms（塗りを1/4解像度で計算していたときは約30〜150ms）。
  - 補足: 同じ計測で通常描画は約0.4〜0.5秒だった。夜側の LOD 3 輪郭線を足した分、輪郭線追加前（約0.3〜0.4秒）より遅い。必要なら後で最適化する。
  - 検証: fast-mode で塗りが出ず白線だけになるテストと、`night_only=False` で日照に関係なく線が出るテストを追加。
