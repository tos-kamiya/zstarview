- Topic: 矢印キーのリピートを描画1回につき1ステップに制限
  - Decision: 押下中の自動リピートは受け取るが、前回の回転ステップがまだ描画されていなければ捨てる。描画開始時（`paintEvent`）に描画待ちを解除する。最初の押下とキー解放の処理は従来どおり。
  - Rationale: キーリピートは約30ms間隔（xset: delay 500ms, rate 33/s）で届き、操作中の描画は1フレーム90-150msかかる。Qtは描画要求をまとめるため、描画の合間に3-6回分（15-30度）が処理され、画面上で角度が飛んで見えていた。利用者の要望で、回転速度が描画速度に依存する（約8fpsで毎秒40度前後）ことを受け入れて、1コマ5度の滑らかさを優先した。
  - 安全策: 実ウィンドウの自動テストで、描画待ちが解除されないまま約4秒間リピートがすべて捨てられ回転が止まる事象が1回出た（原因は未確定。描画中に入力が処理される経路などが考えられる）。対策として、捨てるときにも再描画を要求し、最後の回転から250ms（`VIEWPORT_ROTATION_PAINT_WAIT_S`）以上経ったリピートは描画を待たずに回す。利用者が実機で5度ずつ滑らかに回ることを確認した。
  - Alternatives Considered: 前回描画からの経過時間に応じて回転量を決める方式は、回転速度が環境に依存しない利点があるが、1コマの飛びが描画時間に比例するため今回は採用しなかった。
  - 補足: 先に報告された「fast-modeで更新されず、離すと大きく回った画面になる」現象は再現しなかった。GNOME Wayland でリモート操作の許可前に xdotool の入力が数秒遅れてまとめて届いた自動テストを見ていた可能性が高い。許可はプロセスごとに求められる模様で、自動操作時に警告音が出ることがあったため、以降の確認は利用者が実機で行った。

## PySide6 の stub と実行時の食い違いの調査

- 調査: PySide6 6.10.0 / 6.10.3 / 6.11.0 / 6.11.3 / 6.12.0（PyPI の最新）を `uv run --no-project --with "PySide6==X"` で切り替え、offscreen で確認した。
  - `QImage.save(path, fmt)`: どのバージョンも str の `"PNG"` は受け付け、bytes の `b"PNG"` は `ValueError`（wrong argument values）で拒否する。format を省くと、拡張子 `.tmp` では保存に失敗する。stub はどのバージョンも `format: bytes | bytearray | memoryview | None`。`QPixmap.save` の stub は `format: str | None` なので、`QImage` の stub の誤りと見られる。
  - `QImageWriter(path, b"PNG").write(image)`: 6.10.0 と 6.12.0 で成功し、読み戻しも確認した。stub と実行時が一致しており、`mypy --strict` でもエラーは出ない（str を渡すと実行時に `TypeError`）。
  - `QListWidget.setCurrentItem(None)`: どのバージョンも選択解除として動き、stub はどのバージョンも `None` を受け付けない。`setCurrentRow(-1)` でも結果と発行されるシグナル（`itemSelectionChanged`、`currentItemChanged(None, prev)`、`currentRowChanged(-1)`）とその順序が同じだった。
  - 上流: 該当する issue は見つからなかった。類似の報告は PYSIDE-1968（`QPixmap.save` の bytes の format、6.3.0 で修正済み）と PYSIDE-2235（`setParent(None)` の stub）。

- Topic: PNG ファイルの保存方法
  - Decision: `QImage.save(path, "PNG")` をやめ、`render/qt_image.py` に新設した `save_qimage_png(image, path)`（`QImageWriter(os.fspath(path), b"PNG")`）に統一した。対象は `replay/sequence.py`、`gui/window.py`（定期デバッグスナップショット）、`data/test_draw_sky_disc.py`、`scripts/prototype_cloud_cell_shading.py`、`scripts/render_star_gray_background_experiment.py`。これで `type: ignore[call-overload]` が2件なくなった。

## 雲レイヤー生成時間の調査

- Topic: 雲（voxel）レイヤー生成時間の内訳と緩和策の調査（読み取りのみ、実装変更なし）
  - Results: 松江、2026-11-20 14:30 UTC の Himawari を使用した。source worker は、タイル未キャッシュ時に 89 s、キャッシュ済みで 9.8 s かかった。キャッシュ済みの内訳は、S3 一覧 2.8 s、B13 結合 1.2 s、B16 の一覧・取得・結合 3.9 s、alt/az グリッド 0.9 s。タイル取得（`hima.py` の B13 と B16）は逐次実行。voxel subprocess は半径 430 px（58万レイ）で 6.9 s、215 px で 4.0 s。in-process の内訳は、import 0.66 s、unpickle 0.12 s、prepare 0.2〜0.9 s、`_render` 5.1〜5.5 s（単一スレッド）。
  - Finding: `_render` の光線ループを `prange`（`parallel=True`、12スレッド）にした試作で 5.49 s → 0.99 s、半径 215 px では 1.92 s → 0.40 s となり、出力の最大差は 0.0 だった。試作は太陽光・月光キャッシュ（`light_fractions` 等）への書き込み競合を残している。製品化するには、可視ボクセルの照明を先に並列で計算する2段構成にする必要がある。
  - Finding: GUI では source 取得の直後に、太陽位置の更新で render key が変わり、2回目の render が走ることがある（app.log の request_id 14→15）。
  - Candidates: (1) `_render` の並列化。(2) 描画解像度を下げてアップサンプリングする。(3) 常駐 worker で `PreparedNativeVoxelCloud` を再利用する。(4) Himawari タイル取得の並列化。(5) voxel モードで B16 取得を省くか遅延させる。(6) 太陽の微小移動では再描画しない。
  - Finding: voxel モード（既定）では、B16 は描画結果に影響しない。B16 を読むのは `altaz_grid.py` のシェル再配分だけで、`prepare_native_voxel_cloud` は B13 のみを使い、info に `"b16_redistribution": False` を記録する。voxel モードの描画経路（`zstarview_pipeline.py`）は shell 雲を描かず、`cloud_altaz_grid` を None にする。`cloud_controller.py` が alt/az グリッドから使うのは観測地点の緯度経度、coverage、meta だけで、どれも B16 に依存しない。仕様書（「B16による再配分は適用しない」）と design.md にも明記されており、意図された仕様である。B16 が効くのは `--cloud-mode shell` の場合だけ。

## B16・shell 雲方式・Atlas の削除

- Topic: 雲描画を voxel のみに一本化する
  - Decision: (1) B13/B16 補助バンドの取得と、シェル再配分を削除する。(2) `--cloud-mode` を廃止して voxel のみとする。shell 描画を削除し、`--cloud-stripe` は `cutout[,COUNT]` のみとする。`--cloud-missing-tint-opacity` も廃止する。廃止したオプションを CLI で指定したら入力エラーとし、保存済み起動プロファイルに残る古いキーは無視する。(3) Atlas（配布対象外）を削除する。
  - Rationale: 既定の voxel 方式は B13 のみを使い、B16 の取得は描画に寄与しないまま、キャッシュ済みでも約 3.9 s と、描画ごとに約 121 MB の受け渡しを生んでいた。shell 方式は voxel 以前の描画方式で、B16 補正と欠損域の色付けはこの方式でしか使われていない。
  - Alternatives Considered: voxel モードのときだけ B16 の取得を省く案。shell 方式が残る限り、B16 経路と描画の分岐が残り続けるため採らなかった。
  - Implementation (1): `cloud_source.py` から B16/C16 の取得を、`hima.py` / `goes.py` から companion 取得 API を、`altaz_grid.py` と `_numba_kernels.py` から B16 再配分と差分集計を削除した。あわせて `clouddisc/sampling/b13_b16.py` と dev-samples の B13/B16 診断スクリプトも削除した。`CloudSourceData.auxiliary_bands` は削除し、`__setstate__` で旧 pickle の余分な slot を読み捨てる。`CloudBandData` は旧履歴キャッシュの unpickle 用にだけ残した。
  - Implementation (2): CLI から `--cloud-mode` と `--cloud-missing-tint-opacity` を削除し、未知オプションとして argparse がエラーにする（`--cloud-voxel-threshold` 廃止時と同じ扱い）。`--cloud-stripe` は `cutout[,COUNT]` のみとした。`SkyWindowRuntimeOptions` から `cloud_voxel` / `cloud_stripe_style` / `cloud_stripe_mode` / `cloud_missing_tint_opacity` を削除した。`gui/cloud_render.py`、`clouddisc/altaz_render.py`、`SkyCompositorCache` の shell 描画・欠損ティント・Atlas 雲レイヤーも削除し、cloud / geo state の `missing_mask` / `cloud_amount_field` を外した。export-image の `_fetch_cloud_layer` は `(coverage, altaz_grid, voxel_source)` を返す形にした。起動プロファイルでは、cutout 以外の `cloud_stripe` と `cloud_missing_tint_opacity` を読み込み時に捨てる。
  - Finding: 以前の文書には「夜間は雲の実効 opacity を最大30%上げる」とあったが、この `CLOUD_NIGHT_BOOST` は shell 合成でしか適用されておらず、voxel 雲には効いていなかった。CLI 文書からこの記述を削除した。
  - Validation: キャッシュ済みタイルで source worker を計測し、9.8 s から 5.5 s に、pickle は 243 MB から 122 MB に減った。B16 入りの旧 pickle が読めることも確認した。pytest は 1849 passed。mypy（src+tests）は成功した。ruff の残りは既存の E402 9件だけ。export-image で実データの voxel 雲を出力し、HEAD の worktree と見た目が同等であることを確認した。
