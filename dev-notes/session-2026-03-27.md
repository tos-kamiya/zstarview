- Topic: DEM and Overture cache retention defaults
  - Decision: Document default retention as `90 days` for DEM and `30 days` for Overture-derived building caches, and define them as TTLs for stale/re-fetch rather than immediate deletion thresholds.
  - Rationale: DEM updates are rare enough that a monthly refresh is unnecessarily aggressive, while building data can reasonably drift within a month. Treating expiry as "re-fetch on next use" preserves responsiveness and provides a stale-cache fallback when network refresh fails.
  - Alternatives Considered: A uniform `30-day` TTL for both DEM and buildings was rejected because DEM churn is much lower and would cause avoidable downloads.

- Topic: Unify DEM and building cache age origin
  - Decision: Use `fetched_at_utc` as the single freshness timestamp for DEM and Overture cache management, attached to each re-fetch unit rather than mixing manifest-generated times.
  - Rationale: Aligning the timestamp with the actual re-fetch unit keeps fresh/stale judgment consistent with replacement behavior and makes the model closer to the existing aircraft cache flow without forcing a directory-layout rewrite.
  - Alternatives Considered: Using manifest or generated timestamps as an alternate freshness origin was rejected because it adds ambiguity without helping the refresh decision.

- Topic: Backward compatibility for legacy cache entries
  - Decision: When a legacy DEM or Overture cache entry is missing `fetched_at_utc`, assign the current read time as a provisional `fetched_at_utc` and write it back.
  - Rationale: This avoids a migration spike that would otherwise mark all existing cache entries stale at once, while still moving the cache into the new age-based management model.
  - Alternatives Considered: Treating missing timestamps as immediately stale was rejected because it would trigger unnecessary bulk re-downloads after upgrade.

- Topic: Manual cache clear CLI
  - Decision: Add `--clear-long-lived-cache` to both the GUI CLI and `zstarview-export-image` so users can force-delete DEM and urban-outline cache roots before startup.
  - Rationale: DEM and building caches have intentionally long TTLs and offline fallback behavior, so users still need an explicit, predictable escape hatch when they want a cold refresh.
  - Alternatives Considered: Separate flags per cache type were deferred because a single long-lived-cache reset is simpler for the current use case.

- Topic: Cache-clear cooldown
  - Decision: Gate `--clear-long-lived-cache` with a `3-day` cooldown recorded in cache-root metadata, and show the rejection reason on the splash screen as well as in normal logs.
  - Rationale: This keeps the troubleshooting escape hatch while discouraging habitual cold starts that would negate long-lived cache benefits.
  - Alternatives Considered: A `--force-clear-long-lived-cache` override was rejected in favor of documenting manual directory deletion for exceptional cases.

- Topic: OS-independent manual cache-clear guidance

- Topic: Skyscraper seed tile growth when extending outer radius from 10km to 60km
  - Decision: Measured the increase using the current `select_skyscraper_seed_tiles_for_viewer(...)` logic against bundled tower and mountain viewpoint datasets, then raised the default far-range limit to `60km`.
  - Rationale: The current `10km` cutoff hides tall landmarks that are still visibly above the horizon from farther away. The bundled-data experiment showed the tile-count increase stays modest for most locations.
  - Result: Across 227 viewpoints, the maximum increase was 32 tiles, the mean increase was 0.83, and the median was 0. Only four viewpoints increased by 20 tiles or more. The largest increases were Macau Tower (+32), Chiba Port Tower (+26), Yokohama Landmark Tower (+26), and Yokohama Marine Tower (+26).
