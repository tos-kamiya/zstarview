- Topic: Investigate glow vs cloud draw order
  - Decision: Keep this as a design-only investigation for now and do not change rendering code yet.
  - Rationale: The current base scene compositor builds a single sky/cloud image first, then adds night-light and ridge-glow onto that composited image in `SkyCompositorCache.draw()`. To make glow appear in front of clouds in a controlled way, the glow pass would need to be split out of the shared sky/cloud composite so it can be layered explicitly relative to clouds instead of being baked into the same cached image.
  - Result: Identified the relevant boundaries in `src/zstarview/gui/composite.py` and `src/zstarview/render/pipeline.py`; no implementation or tests were changed.
- Topic: Repaint trigger for glow visibility
  - Decision: The useful design split is not "cloud missing => skip cloud composite", because that branch already exists. The meaningful change would be to separate sky/glow repaint triggers from cloud projection/render triggers so a completed sky snapshot can become visible immediately, even if cloud fetching or cloud projection is still pending.
  - Rationale: `request_client_update()` only schedules a Qt repaint; the actual frame is still governed by the shared frame cache and by whichever background callback last invalidated it. Because the base frame cache currently keys sky, glow, and cloud state together, cloud progress can effectively coalesce the visible update even when glow is already computed.
  - Update: Reflected this separation in `docs/design/rendering-pipeline.md` and added a short note to `docs/design.md` that glow visibility should not wait on cloud download completion.
