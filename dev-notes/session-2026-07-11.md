# Session 2026-07-11

Scope: Increase Atlas cloud contrast without changing zstarview.

- Topic: Atlas cloud color contrast
  - Decision: Change only `ATLAS_OVERLAY_STYLES.cloud.rgb` from `(112, 139, 160)`
    to the darker blue-gray `(55, 78, 96)`.
  - Rationale: Atlas clouds were too close to the white background. The normal
    viewer keeps `DEFAULT_OVERLAY_STYLES.cloud.rgb` at white, so its appearance is
    unaffected.
  - Verification: Update the Atlas palette regression assertion and run targeted
    palette/cloud tests plus Ruff.

- Topic: Atlas cloud opacity
  - Decision: Set the Atlas-only default `cloud_opacity` to `0.15`, while keeping
    the normal viewer default at `0.05`.
  - Rationale: The previous effective opacity was approximately `0.05 * 0.88`,
    so darkening the RGB value alone could not make the overlay sufficiently
    visible on the white background.

- Topic: Tune Atlas cloud opacity
  - Decision: Reduce the Atlas-only default from `0.35` to `0.15` after visual
    comparison, leaving the darker Atlas RGB and the normal viewer unchanged.

- Topic: Atlas observation HUD
  - Decision: Change the Atlas profile's observation info mode from `off` to
    `bottom` so location, local time, and center alt/az are rendered by the
    shared HUD path.
  - Rationale: The shared HUD already resolves text through `ThemeStyle`, so the
    Atlas label color is inherited without adding a separate HUD renderer.

- Topic: Atlas startup log splash opacity
  - Decision: Keep the existing translucent startup overlay for the regular viewer and use an opaque background when the window presentation is `instrument`, which is the Atlas profile's presentation mode.
  - Rationale: The Atlas entry point already identifies itself through the shared presentation setting, so this avoids coupling the window implementation to the executable name while covering the requested launch path.
  - Verification: Added a regression test and ran the startup-log tests plus Ruff.

- Topic: Version 1.34.0 release
  - Decision: Bump the package version from `1.33.0` to `1.34.0` and promote the accumulated Unreleased notes to the dated `1.34.0` release section.
  - Rationale: The release includes the Atlas entry and its related rendering/startup improvements accumulated since the previous version bump.

- Topic: Night-light data source and distribution for version 1.35.0
  - Decision: Adopt the Earth Observation Group's 2025 annual VIIRS Nighttime Lights VNL v2.2 product, distribute converted GeoTIFF assets through GitHub Releases, and keep the large raster data out of the PyPI package.
  - Rationale: The product is directly available as GeoTIFF, avoiding user-side HDF conversion, while GitHub Releases provides versioned binary assets without requiring a separate website or GitHub Pages site.
  - Licensing: Redistributed VNL data follows CC BY 4.0. The release and application credits must identify EOG, indicate the GeoTIFF conversion, and include the relevant source citation.
  - Version: Bump `zstarview` from `1.34.0` to `1.35.0`.

- Topic: VNL conversion script
  - Decision: Add `dev-samples/build_vnl_night_lights.py` to accept a local or authenticated EOG VNL GeoTIFF, split it into eight 90-degree tiles, and emit a checksum-bearing manifest.
  - Rationale: Keep raw data and credentials outside the repository while making the release-data transformation reproducible.
  - Result: Ruff and Python syntax checks passed. Actual tile generation is pending a downloaded EOG source file because the current EOG download page requires authentication.

- Topic: VNL 2025 tile generation
  - Decision: Use `VNL_npp_2025_global_vcmslcfg_v2_c202604011200.average_masked.dat.tif.gz` and update the documented dataset year from 2020 to 2025.
  - Result: Generated eight 90-degree EPSG:4326 GeoTIFF tiles under `build/night-lights/2025`, plus `manifest.json` and `NOTICE-night-lights.txt`.
  - Validation: All tiles are 21600 x 21600 at 15 arc-seconds. Sampled values are non-negative after converting masked and negative source values to zero.
  - Fix: Replaced the invalid `Window.from_slices()` call with an explicit rasterio `Window` construction after the first run failed on integer row/column arguments.
