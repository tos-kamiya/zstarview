  - Decision: Use the bundled `water_tiles_100m` GeoTIFFs as the sea source and extract shoreline-adjacent boundary points instead of fetching Overture river/lake footprints for the water overlay.
  - Rationale: The local raster already encodes the sea mask, so it can act as a ground-attached texture-like source without per-feature water classification. Boundary points are a simple first step that reuses the existing point renderer.

- Topic: Water tile generation resolution
  - Decision: Update the water polygon rasterization script to generate 100m-class tiles instead of 500m-class tiles.
  - Rationale: The 500m tiles were too coarse for the horizon sampling path, which could leave far-off water points visible in places where finer sea-mask detail should suppress them.

- Topic: Water tile footprint size
  - Decision: Split the rasterized water mask into 9-degree tiles so each image is about one-fifth the former geographic width/height.
  - Rationale: The 100m-resolution global tiles would be too large to handle comfortably at the original 45-degree tile footprint, so shrinking each tile keeps per-file size manageable while preserving the higher sampling resolution.

- Topic: Water tile generation speed
  - Decision: Reuse the opened OGR layer across tiles and apply a per-tile spatial filter before rasterization, skipping tiles with zero intersecting features early.
  - Rationale: Reopening the datasource for every tile and rasterizing the full global layer each time was the dominant cost. Spatial filtering reduces the feature set per tile and avoids unnecessary raster work for empty tiles.

- Topic: Water tile generator resolution switch
  - Decision: Add `--resolution-m {100,500}` to the rasterizer so it can generate either `water_tiles_100m` or `water_tiles_500m` tile groups from the same source data.
  - Rationale: A single script keeps the two datasets consistent while making it cheap to regenerate whichever resolution is needed for a given rendering path.

- Topic: Mixed-resolution water tile loading
  - Decision: Load `water_tiles_100m` for points within 2 km of the observer and `water_tiles_500m` beyond that distance.
  - Rationale: Near-field water edges are sensitive to coarse rasterization, but far-field water is visually forgiving. The split preserves local detail while reducing the amount of fine-grained raster I/O at long range.

- Topic: Water points should follow distance bands, not only the main horizon
  - Decision: Sample water mask points from both the main terrain horizon profile and the secondary horizon bands, then draw the combined result.
  - Rationale: Using only the main horizon concentrates water dots on the skyline. Secondary horizon bands let water appear on nearer ridges too, which better matches the intended distance-band rendering model.

- Topic: Prefer direct sea-mask points over horizon-derived water points
  - Decision: When terrain rendering is active, prefer `scene.water_overlay_points` from the sea-mask pipeline and use horizon-derived water points only as a fallback.
  - Rationale: The horizon-derived path still anchored water dots to skyline samples. Prioritizing the direct sea-mask points restores the actual water-surface placement while keeping the terrain horizon gate that hides water when the horizon is hidden.

- Topic: Water dot size reset
  - Decision: Reduce the water overlay dot radius from 10 px back to 5 px.
  - Rationale: 10 px was useful for debugging visibility, but it was too large for normal use and obscured the scene more than intended.

- Topic: Water tile multistage loading
  - Decision: Use 100m tiles within 2 km, 250m tiles from 2 km to 6 km, and 500m tiles beyond 6 km.
  - Rationale: The visible resolution step was coming from the coarse 100m/500m handoff. A single intermediate band gives smoother transitions without pushing the whole dataset to the smallest tile size.

- Topic: One dot per 500m tile
  - Decision: Collapse each sampled 500m water tile to a single representative point near the tile center.
  - Rationale: The old 5x5 style sampling made far-field water too dense. A single dot per tile keeps the distant water readable while preserving the coarse tile layout.

- Topic: One dot per 250m tile
  - Decision: Collapse each sampled 250m water tile to a single representative point as well.
  - Rationale: The intermediate band was still dense enough to show a visible seam. Matching the 500m treatment keeps the 2km-6km region coherent and leaves only the 100m band dense.

- Topic: Fetch water only after DEM and color bands by tile type
  - Decision: Stop the initial pre-DEM water fetch; start water loading only after terrain DEM readiness, and color water dots by 100m / 250m / 500m source band.
  - Rationale: The prefetch path was producing a transient far-only view before the DEM-backed update landed. Band colors make it easy to confirm which tile resolution generated each dot while debugging the transition between distance bands.

- Topic: Remove horizon-water fallback from rendering
  - Decision: Do not synthesize water dots from terrain horizon bands when direct water overlay points are absent.
  - Rationale: The fallback was still producing the startup "far-only" water dots before the DEM-backed water fetch completed, which caused the visual mode switch the user wanted removed. Rendering should now wait for the real water data to arrive instead of inventing a horizon-derived substitute.

- Topic: Water band count logging
