# 2026-05-16 Session Notes

- Topic: Sea-mask boundary rendering from local water tiles
  - Decision: Use the bundled `water_tiles_100m` GeoTIFFs as the sea source and extract shoreline-adjacent boundary points instead of fetching Overture river/lake footprints for the water overlay.
  - Rationale: The local raster already encodes the sea mask, so it can act as a ground-attached texture-like source without per-feature water classification. Boundary points are a simple first step that reuses the existing point renderer.

- Topic: GUI and export-image wiring for sea-mask interface points
  - Decision: Route both the GUI water overlay controller and `export_image` through the same sea-mask sampler, and keep the data on the ground by projecting boundary points at `target_height_m = 0.0`.
  - Rationale: This keeps inland water out of the path for now, avoids coastline ring reconstruction, and preserves the existing point-based renderer as a texture-like overlay.
  - Validation: `ruff check src/zstarview/water_mask_interface.py src/zstarview/cli/export_image.py src/zstarview/gui/water_overlay_controller.py tests/test_water_mask_interface.py tests/test_export_image_layer_gating.py tests/test_water_overlay_controller.py tests/test_controller_shutdown_waits.py`
  - Validation: `pytest tests/test_water_mask_interface.py tests/test_export_image_layer_gating.py tests/test_water_overlay_controller.py tests/test_controller_shutdown_waits.py -q`

- Topic: Sea should render as a surface, not only a shoreline
  - Decision: Sample all water pixels from the sea mask instead of only boundary pixels so the ocean appears as a filled, ground-attached texture in front of the observer.
  - Rationale: The boundary-only approach only highlighted coasts, which made high viewpoints like Cape Point show a distant strip of water instead of the expected broad sea surface.
  - Validation: `ruff check src/zstarview/water_mask_interface.py tests/test_water_mask_interface.py`
  - Validation: `pytest tests/test_water_mask_interface.py -q`

- Topic: Debug nearest sea distance
  - Decision: Log the nearest sea-point distance whenever sea-mask points are produced in the GUI controller and export-image path.
  - Rationale: This makes it possible to verify the actual closest water point in the current scene instead of inferring it from the terrain rings.
  - Validation: `ruff check src/zstarview/cli/export_image.py src/zstarview/gui/water_overlay_controller.py tests/test_export_image_layer_gating.py tests/test_water_overlay_controller.py`
  - Validation: `pytest tests/test_export_image_layer_gating.py tests/test_water_overlay_controller.py -q`

- Topic: Water overlay visibility follows terrain horizon visibility
  - Decision: Draw water dots only when the terrain horizon overlay is enabled, and keep them layered on top of the terrain horizon draw pass.
  - Rationale: The sea dots should behave like a surface texture attached to the ground; if the terrain horizon is hidden, the water overlay should also be hidden instead of floating independently.
  - Validation: `ruff check src/zstarview/render/pipeline.py tests/test_window_render_sync.py`
  - Validation: `pytest tests/test_window_render_sync.py -q`

- Topic: Horizon-sampled sea dots
  - Decision: Derive water dots from the terrain horizon profile by converting each horizon sample's observer-centered distance and azimuth back to a geographic point, then keep only the samples that land on the sea mask.
  - Rationale: This keeps the dots anchored to the terrain horizon circle, which matches the requested rendering model better than projecting all sea pixels directly.
  - Validation: `ruff check src/zstarview/water_mask_interface.py src/zstarview/render/pipeline.py tests/test_water_mask_interface.py tests/test_window_render_sync.py`
  - Validation: `pytest tests/test_water_mask_interface.py tests/test_window_render_sync.py -q`

- Topic: Flat-ground fallback when DEM is unavailable
  - Decision: Replace the empty terrain-horizon fallback with the normal horizon scan over a synthetic flat 0m surface, then reuse that ring for water sampling and terrain drawing.
  - Rationale: A missing DEM should behave like flat ground at elevation 0 instead of suppressing the horizon entirely. Reusing the standard horizon scan keeps the fallback aligned with the usual ridge rendering path and preserves the expected near-edge water placement.
  - Validation: `ruff check src/zstarview/terrain/horizon.py src/zstarview/terrain/__init__.py src/zstarview/gui/terrain_controller.py src/zstarview/cli/export_image.py tests/terrain/test_terrain_horizon_math.py tests/terrain/test_terrain_horizon_ui.py tests/test_export_image_layer_gating.py`
  - Validation: `pytest tests/terrain/test_terrain_horizon_math.py tests/terrain/test_terrain_horizon_ui.py tests/test_export_image_layer_gating.py -q`
  - Validation: `pytest tests/test_window_render_sync.py -q`
  - Validation: `pytest tests/test_water_mask_interface.py -q`

- Topic: Water dots were too easy to miss
  - Decision: Increase the water overlay dot radius from 2.7 px to 4.0 px.
  - Rationale: The dots were likely being visually lost against the terrain horizon and sky layers, so a modest size increase improves visibility without changing the underlying placement logic.

- Topic: Water tile generation resolution
  - Decision: Update the water polygon rasterization script to generate 100m-class tiles instead of 500m-class tiles.
  - Rationale: The 500m tiles were too coarse for the horizon sampling path, which could leave far-off water points visible in places where finer sea-mask detail should suppress them.

- Topic: Water tile footprint size
  - Decision: Split the rasterized water mask into 9-degree tiles so each image is about one-fifth the former geographic width/height.
  - Rationale: The 100m-resolution global tiles would be too large to handle comfortably at the original 45-degree tile footprint, so shrinking each tile keeps per-file size manageable while preserving the higher sampling resolution.

- Topic: Water tile generation speed
  - Decision: Reuse the opened OGR layer across tiles and apply a per-tile spatial filter before rasterization, skipping tiles with zero intersecting features early.
  - Rationale: Reopening the datasource for every tile and rasterizing the full global layer each time was the dominant cost. Spatial filtering reduces the feature set per tile and avoids unnecessary raster work for empty tiles.

- Topic: Water tile generator resolution switch
  - Decision: Add `--resolution-m {100,500}` to the rasterizer so it can generate either `water_tiles_100m` or `water_tiles_500m` tile groups from the same source data.
  - Rationale: A single script keeps the two datasets consistent while making it cheap to regenerate whichever resolution is needed for a given rendering path.

- Topic: Mixed-resolution water tile loading
  - Decision: Load `water_tiles_100m` for points within 2 km of the observer and `water_tiles_500m` beyond that distance.
  - Rationale: Near-field water edges are sensitive to coarse rasterization, but far-field water is visually forgiving. The split preserves local detail while reducing the amount of fine-grained raster I/O at long range.

- Topic: Water points should follow distance bands, not only the main horizon
  - Decision: Sample water mask points from both the main terrain horizon profile and the secondary horizon bands, then draw the combined result.
  - Rationale: Using only the main horizon concentrates water dots on the skyline. Secondary horizon bands let water appear on nearer ridges too, which better matches the intended distance-band rendering model.
