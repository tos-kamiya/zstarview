# Session 2026-04-10

- Scope: Investigate reports that the ISS disappears once it moves outside the 90-degree radius even though the rendered sky uses a wider content FOV.

- Topic: Content-FOV projection mismatch for overlays
  - Decision: Keep the existing overscan projection model and remove the ISS-specific remapping that compressed `content_fov_deg` back into a 90-degree-radius screen disc.
  - Rationale: The sky disc and star renderer already treat wider content FOVs as a larger visible radius, not as a remap to the base circle. Compressing only the satellite layer made ISS drift away from the surrounding sky geometry once it moved outside 90 degrees, which reads as the marker disappearing from the place where the sky still shows content.
  - Alternatives Considered: Expanding the remap to other overlays was rejected after checking the star overscan tests, which confirmed that the renderer's intended behavior is geometric overscan, not edge compression.

- Topic: Validation
  - Decision: Replace the satellite regression test so it asserts overscan positioning beyond 90 degrees instead of expecting compression to the base circle.
  - Rationale: The updated expectation now matches the renderer's actual contract: wider content FOV extends the visible radius, and the ISS marker must stay aligned with that geometry.

- Topic: Satellite marker opacity
  - Decision: Raise `SATELLITE_OVERLAY_MARKER_MAX_ALPHA` from 230 to 255.
  - Rationale: The ISS marker should use the full available alpha range instead of an intentionally reduced cap, while still respecting the existing layer opacity multiplier.

- Topic: Versioning
  - Decision: Bump the app version from `1.8.14` to `1.8.15`.
  - Rationale: The satellite visibility and opacity fixes have already been committed, so the package version should advance by one patch release.

- Topic: Subsurface Earth guide design
  - Decision: Specify the future below-horizon world-map feature as an observer-dependent guide layer that uses coarse continent polygons, observer-local filtering, and approximate projection rather than precise coastline rendering.
  - Rationale: The user goal is orientation aid, not cartographic fidelity. A coarse continent guide is enough if it changes with observer `lat/lon`, follows view rotation, and respects observer height well enough for tower viewpoints. Using observer-local filtering via `dot(v, up)` keeps the design consistent for both ground-level and elevated viewpoints without requiring a full GIS-grade visibility solver.
  - Alternatives Considered: Treating the lower hemisphere as a fixed antipode-centered decorative map was rejected because it would not respond correctly to observer height and would be too disconnected from the actual location-dependent geometry.

- Topic: Coarse SVG guide prototype
  - Decision: Add a self-contained `dev-samples` script that reads GeoJSON land polygons, simplifies them in pure Python, and renders an equirectangular SVG preview.
  - Rationale: The hand-authored polygon sketch was too coarse. The project still needs a low-dependency way to evaluate visually simplified continent shapes derived from real map data, so the prototype now targets `GeoJSON -> simplify -> SVG` without requiring `shapely` or `geopandas`.

- Topic: Runtime Earth-guide JSON export
  - Decision: Extend the GeoJSON simplification script so it can also emit a runtime-oriented JSON payload containing simplified lon/lat rings, per-ring point counts, approximate area, and bbox metadata.
  - Rationale: The SVG preview is useful for visual tuning, but the runtime path needs a stable serialized artifact that can be loaded without re-running simplification. Keeping the JSON in lon/lat form preserves editability while remaining easy to project into 3D at runtime.

- Topic: Current simplification baseline
  - Decision: Record `ne_110m_land.json` with `--simplify-deg 0.6 --min-ring-area-deg2 2.0` as the current acceptable coarse-guide baseline.
  - Rationale: This setting kept enough structure for Italy, Hokkaido, and New Zealand to look acceptable for guide purposes while still reducing the source to a lightweight artifact.

- Topic: Preview seam longitude
  - Decision: Add a configurable preview seam longitude so the equirectangular SVG cut can be moved away from visually awkward positions, including a Bering Strait placement between Siberia and Alaska.
  - Rationale: The default `-180/180` seam left a sliver of Siberia on the left edge, which made the preview harder to read. A seam control is enough for the prototype and does not change the underlying runtime lon/lat ring data.

- Topic: Runtime integration of the Earth guide
  - Decision: Integrate the simplified land-ring JSON into zstarview as a below-horizon overlay drawn after the ground tint inside the sky compositor path.
  - Rationale: The compositor already owns the geometric/terrain horizon mask and has the final sky image in hand, so it is the narrowest integration point for adding an observer-dependent ground-side guide without restructuring the main render pipeline. The runtime data remains lon/lat rings and is converted to unit-sphere vectors on load.
  - Alternatives Considered: A separate top-level render layer was deferred because it would have required duplicating some below-horizon clipping logic already present around the ground-tint stage.

- Topic: Earth guide segment refinement
  - Decision: Remove the artificial `-5°` altitude buffer and instead subdivide each land ring edge along the sphere before projection, so segments near the observer follow a great-circle-like path.
  - Rationale: The buffer could still leave ground-adjacent lines visibly above the surface. Geometry refinement is the more faithful fix because it reduces the projection error that caused the protrusion in the first place, while the actual horizon/terrain clip still determines the visible cutoff.

- Topic: Near-observer great-circle densification
  - Decision: Keep the below-horizon guide clipped to the geometric horizon, but sample segments much more densely when their midpoint is near the observer so local coastlines curve instead of cutting straight through the surface.
  - Rationale: The screenshot showed that a coarse path approximation near the viewer still allowed lines to read as above the horizon. A denser great-circle sample on nearby edges reduces that error without changing the map data model or the runtime clip rule.

- Topic: Screen-space recursive subdivision
  - Decision: Stop the great-circle refinement path and instead subdivide land-guide segments recursively based on their projected screen-space span, with a bounded recursion depth.
  - Rationale: The remaining protrusions were more directly caused by straight-line approximation after projection than by the data model itself. Recursing in screen space keeps the implementation local to the renderer, avoids forcing extra geodesic complexity into the data path, and gives a simpler control knob for "split when the projected segment is too large".

- Topic: Fragment stitching for line continuity
  - Decision: Stitch adjacent screen-space fragments back into longer polylines before painting them.
  - Rationale: Rendering each tiny fragment as its own polyline made some guide sections read as dotted strokes, especially near the horizon where recursive subdivision creates many short segments. Joining contiguous fragments preserves the subdivision benefit while keeping the final stroke visually continuous.

- Topic: Recursive midpoint merge
  - Decision: When a recursive split produces exactly one visible polyline on each side, merge the left and right halves into a single polyline before returning it.
  - Rationale: The intended interpretation of a split is "draw A-M and M-B as one continuous stroke when both halves remain visible." Returning the halves separately made some regions look dotted even after stitching, so merging at the recursion boundary is the more direct representation of the segment topology.

- Topic: Distance-based thinning
  - Decision: Scale the recursive subdivision threshold by the observer-distance of the midpoint so far-away segments are allowed to remain coarser.
  - Rationale: The user wants the close-in contour detail to stay readable, but distant guide shapes do not need the same density. Raising the subdivision threshold with distance keeps nearby coastlines clean while reducing point count in the far field.

- Topic: Earth guide line color sync
  - Decision: Reuse the terrain horizon line RGB for the earth-guide foreground stroke and share the terrain alpha curve.
  - Rationale: Matching the guide stroke to the terrain horizon line makes the below-horizon overlay read as part of the same visual language instead of a separate annotation layer.

- Topic: Terrain horizon alpha normalization
  - Decision: Remove the terrain-horizon `0.7` scale factor from the renderer, share the same alpha curve with the earth-guide overlay, and lower the CLI default opacity to `0.035`.
  - Rationale: The renderer-specific scale factor was a hidden adjustment that made the CLI opacity hard to reason about. Moving the compensation into the default preserves the perceived appearance for the default case, while the shared alpha helper keeps the terrain horizon line and the earth-guide line visually consistent.
  - Notes: The `max(..., min(...))` structure is retained because the inner `min` clamps the computed alpha to a valid upper bound, and the outer `max` ensures the requested opacity still acts as a lower floor for the foreground stroke.
  - Notes: The earth-guide overlay now uses the same alpha helper and is disabled when the terrain-horizon opacity is zero, so the two overlays remain coupled in both visibility and styling.

- Topic: Earth guide stroke width
  - Decision: Make the earth-guide foreground stroke thinner than the terrain horizon line.
  - Rationale: The guide layer should read as secondary guidance, not compete with the terrain horizon line. Reducing the stroke width preserves the same color and alpha behavior while lowering visual weight.

- Topic: Earth guide outline reduction
  - Decision: Reduce the earth-guide outline and foreground widths further so the whole guide remains visibly lighter than the terrain horizon stroke.
  - Rationale: The previous width was still reading too heavy in practice because the outline contributed most of the apparent thickness. Lowering both widths keeps the guide subordinate to the terrain horizon line.

- Topic: Earth guide outline removal
  - Decision: Remove the earth-guide outline entirely and keep only the foreground stroke.
  - Rationale: The outline was dominating the apparent thickness and made the guide read heavier than intended. Dropping it simplifies the stroke model and makes the comparison against the terrain horizon line easier to tune.

- Topic: Earth guide stroke re-thicken
  - Decision: Increase the earth-guide foreground stroke width after removing the outline.
  - Rationale: Without the outline, the guide became too faint and visually disappeared. A modestly thicker foreground stroke brings it back toward the terrain-horizon line's apparent weight while preserving the simpler single-stroke rendering.
