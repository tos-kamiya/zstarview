## 方針

PLATEAU の**zstarview 側の派生キャッシュ**に、LOD2 `WallSurface` 用の壁タイルを
追加する。壁タイルは自治体ディレクトリ内の `walls/` に、屋根・輪郭用の `bldg/` とは
別ファイルとして置く。両者は同じ準備処理で同じ ZIP から同時に生成し、同じ staging
から一括で切り替える。

キャッシュは**自治体ごとに1世代だけ**持つ。ディレクトリ名に年度を入れず、元 ZIP の
チェックサムで元データを識別する。新しいデータを準備したら、年度の比較はせずに
旧キャッシュを破棄する。

準備CLIのコマンド・オプション体系は後方互換性を維持せず作り直す。一方、旧形式の
キャッシュ（`<code>_<year>/`、スキーマ3）は、新たに準備するまで屋根・輪郭のデータとして
現行描画で使い続けられるようにする。新しいデータを準備したら、旧形式は差し替えて
削除する。元の CityGML ZIP は標準では変換後に削除されるため、旧形式から壁ポリゴンは
復元できない。壁面モードを使うには、再取得または保存済み ZIP からの再変換が必要である。
通常起動時に大容量データを自動ダウンロードしない。

`bldg/` の内容（輪郭・高さ・屋根）は現行スキーマ3を維持し、旧形式と同じ読込処理で読む。

## ディレクトリとデータ

```text
<CACHE_PATH>/plateau_buildings/
  13103/
    cache_meta.json                         # 元ZIPのチェックサム、bldg/walls のスキーマ
    bldg/                                   # 輪郭・高さ・屋根
      tile_index.json
      53393599_bldg_6697_op.json            # 輪郭・高さ・LOD2屋根
    walls/                                  # 新規
      tile_index.json                       # 壁を含むタイルと壁の bbox
      53393599_bldg_6697_op.json            # 建物ID -> 壁ポリゴン・状態
    source-citygml.zip                      # 元ZIP保持を指定した時のみ
  .13103-<unique-id>/                       # 作成中・破棄中。読込対象外
  13103_2025/                               # 旧形式。13103/ がなければ屋根用に読む
```

- `cache_meta.json` に `source_zip_sha256` と `source_zip_size_bytes` を記録する。
  チェックサムはダウンロード中のストリーム、または ZIP 指定時の読込時に計算する。
  カタログ由来の年度・登録年度・仕様・URL 等は従来どおり情報として記録するが、
  ディレクトリ名や更新の判定には使わない。ZIP 指定時はカタログ情報を記録しない。
- `walls/` のスキーマ版、生成件数、診断件数も `cache_meta.json` に記録する。
- 壁タイルは `bldg/` と同じタイル名を使い、`(タイル名, 建物ID)` で建物レコードと
  対応付ける。建物IDは CityGML の `gml:id`。港区・千代田区・大阪市・松江市の既存
  キャッシュ約76万棟で、`gml:id` 欠落による合成ID（`bldg-{index}`）は0件、タイル内の
  重複IDも0件だった。合成IDの建物は、詳細壁を使わず近似壁にする。
- `walls/` は `bldg/` と同じ変換時の建物条件（高さフィルタ等）を適用する。読込時に
  対応する建物レコードがない壁は捨てる。
- 壁ポリゴンは外周と頂点標高を保存し、穴は描画時に無視する。壁なし、未対応、不正を
  状態値で区別する。詳細は調査・描画仕様を参照。
- `walls/tile_index.json` は壁の張り出しを含む bbox を持つ。読み込み側は都市・タイル
  ・建物の各段で `bldg/` 側の bbox との和集合を使い、壁だけが検索範囲に入る建物を
  漏らさない。
- 壁は壁半径（既定0.2 km）以内でのみ使うため、都市アウトラインの検索半径とは別に、
  壁半径と交差するタイルの壁ファイルだけを読み込む。屋根と輪郭の読込時に壁を
  解析しない。港区の `bldg/` は現状で約176 MB、1タイルに LOD2 壁が2万面を超えるため、
  同じファイルに格納すると広域の屋根線の読込が重くなる。

## 読込対象の選択（必須）

現行の `find_plateau_building_dirs` は、root 直下の全ディレクトリを名前で絞らずに
`is_valid_plateau_cache` に掛けている。既存の `.outdated-*` が現在読み込まれないのは、
派生スキーマが1・2で現行の3と一致しないためにすぎない。2026-11-25時点の手元環境では、
多数の自治体で `<code>_<year>.outdated-*` が残っている。また、同じ自治体の別年度
（例: `13103_2024` と `13103_2025`）や、`--input-zip` を `--year` なしで使って作られる
`<code>_latest` は、現行実装では重複して読み込まれる。

新形式では自治体ごとに1ディレクトリなので、新形式どうしの重複は構造的に起きない。
読み込み側は次の規則に従う。

1. 新形式 `<5桁の自治体コード>/` を読む。
2. 新形式がない自治体に限り、旧形式 `<5桁の自治体コード>_<4桁の年度>/` を読む。
   同じ自治体に複数ある場合は、年度の数値が最大のもの1つだけを使い、他をログに出す。
   旧形式は `walls/` を持たないため、屋根・輪郭と近似壁による現行描画でのみ使える。
3. 上記以外（`.` で始まるもの、`.outdated-*`、`.replaced-*`、`.incomplete-*`、
   `_latest` 等）は読まない。

## 準備CLIでの更新手順

現行の `zstarview-download-plateau-buildings` のオプション体系（`--year`、`--api-url`、
`--overwrite` 等）は引き継がない。コマンド名・サブコマンド・オプション名は実装時に
決めるが、次の操作と意味を満たす。

- **準備（カタログ経由）**: 自治体コードを指定し、カタログの最新版を取得・変換して
  `<code>/` に出力する。カタログが既存キャッシュの記録と一致し、`walls/` が現行スキーマ
  であれば、ダウンロードせずに終了する。それ以外は推定ダウンロード量を表示し、確認の
  うえ再取得して旧キャッシュを置き換える。年度の比較はしない。
- **準備（ZIP 指定）**: ローカルの ZIP を変換して `<code>/` に出力する。チェックサムが
  既存キャッシュと一致すれば、同じ元データの再変換（変換器や壁形式の更新を反映）として
  そのまま実行する。一致しない場合や既存がない場合は、置き換える旨を表示して確認を
  求める。カタログとの照合はしない。
- 確認はどちらも同じ方法（対話の y/N と、非対話用の確認省略オプション）で行う。
  置換の意思を表す専用オプション（現行の `--overwrite`）は設けない。
- 準備は常に `bldg/` と `walls/` を同時に生成する。壁を生成しないオプションは設けない。
- 元 ZIP を残すオプション（現行の `--keep-zip` 相当）を指定したときは、ダウンロード・
  ZIP 指定のどちらでも、使用した ZIP を staging に `source-citygml.zip` としてコピーする。
  旧キャッシュ内の `source-citygml.zip` を指定する場合も、展開とコピーは旧キャッシュの
  破棄より前に終わるため問題ない。
- **一覧**: ローカルのキャッシュを一覧する。カタログ由来の年度などの記録は情報として
  表示する。旧形式は「屋根のみ・壁面モード不可」、選ばれなかった旧形式や `.` 始まりの
  残骸は「読込対象外・削除可能」として示す。
- **削除**: 指定した自治体のキャッシュ（旧形式を含む）、または読込対象外の残骸を削除する。
- 作業用ディレクトリ、カタログ URL、ダウンロード上限、変換時の最小建物高さなど、現行に
  ある補助的な設定のうち必要なものは、実装時に整理して引き継ぐ。
- 置換手順:
  1. `.<code>-<unique-id>/` の staging にタイル・索引・メタデータを生成し、読み戻して
     検証する。取得・変換・容量不足・中断時は staging を削除し、旧キャッシュを
     そのまま残す。
  2. 既存の `<code>/` を `.<code>-<unique-id>/` へ移し、staging を `<code>/` へ移す。
  3. 退避した旧 `<code>/` と、同じ自治体の旧形式（`<code>_<year>/` とその
     `.outdated-*`／`.replaced-*`／`.incomplete-*`）を削除し、削除したパスを表示する。
     他の自治体のディレクトリには触れない。
  4. 2と3の間で中断した場合、残った `.` 始まりのディレクトリは読込対象外で、次回の
     準備時に削除する。
- 現行のカタログ経路にある、staging 完成前に旧ディレクトリを `.outdated-*` へ移す処理
  （`_prepare_city_code`）と、`.replaced-*` へのバックアップは引き継がない。
- 実行中のプロセスが読み込んでいるディレクトリの移動・削除、Windows でのディレクトリ
  移動を検証する。
- 元 ZIP を標準で保持する方式への変更は今回の前提にしない。Overture Maps のキャッシュ
  形式と更新方法は変更しない。

### 年度指定を設けない理由

現行の `--year`（既定 `latest`）は年度を選択する機能を持たない。カタログ URL
（`.../citygml/{city_code}?types=bldg`）は年度を含まず最新版のみを返し、`--year` は
カタログに年度がない場合の代替値と、`--input-zip` 時のディレクトリ名にのみ使われていた。
ディレクトリ名から年度をなくすため、新しい体系には年度指定を設けない。年度入りの
URL 雛形 `DEFAULT_API_URL`・`build_download_url`・`--api-url` はテスト以外から呼ばれて
いないので削除する。

## 描画の切替と移行時の動作

- コマンドラインで現行の LOD2 `RoofSurface` を使う描画と、LOD2 `WallSurface` を使う
  描画を切り替える。当面の既定は現行描画とする。GUI 起動と静止画像出力で同じ意味を
  持たせる。オプション名は実装時に決める。Overture Maps と replay は対象外とする。
- 壁面モードでは、利用可能な LOD2 壁面で従来の近似壁を置き換える。屋根輪郭は両モードで
  `RoofSurface` から描画する。壁半径0は壁にのみ適用する。
- 詳細屋根の40 m閾値（`DETAILED_ROOF_MIN_BUILDING_HEIGHT_M`）の撤廃は決定済みで、
  壁面モードに限らず現行描画にも適用する。既定の描画結果が変わるため、公開時に
  `release-notes.md` に記載する。
- 新形式のキャッシュは常に `walls/` を持つため、両モードとも同じキャッシュで描画できる。
  旧形式は現行描画でのみ使える。
- 正常に準備されたキャッシュで個々の建物の詳細壁がない場合は、その建物に限り従来の
  近似壁を使う。対象地点に PLATEAU がない場合は従来どおり Overture を使う。
  壁面モードで、対象範囲の自治体のうち1つでも旧形式しかない場合は、不足分を
  特定してエラーにする。GUI 起動時は既存の起動ログ画面にエラーと再準備方法を表示して
  起動を止める。都市アウトラインの読込は非同期のため、ワーカー内で例外をログに出す
  だけでは起動が止まらない可能性がある。起動時に検出し、既存の起動失敗経路へ伝える。
  起動後の地点変更時はエラーを通知し、起動前の検査とは別に検証する。静止画の終了
  コードは実装時に決める。
- offline 時や再取得を見送った場合も、現行描画では旧形式を使える。壁面モードで
  旧形式しかない場合は、offline でも不足を報告する。
- 2.2.0 として公開する。`release-notes.md` の 2.2.0 に準備CLIの非互換変更と、壁面モード
  には再準備が必要なことを、
  `docs/specification.md` に新しい準備CLIを記載する。

## 検証事項

1. 旧形式のみの地域での現行描画（GUI・静止画・offline）と、壁面モードでの起動エラーと
   案内、カタログ経由での新規準備と旧形式の削除、カタログ不変時のスキップを検証する。
2. ZIP 指定で、チェックサム一致時の再変換、不一致時・既存なし時の確認、元 ZIP 保持の
   有無、キャッシュ内の `source-citygml.zip` からの再変換を検証する。
3. 新形式と旧形式の併存、旧形式の複数年度、`.outdated-*`、`.replaced-*`、
   `.incomplete-*`、`_latest`、`.` 始まりの残骸がある状態で、自治体ごとに1つだけ
   読み込まれ重複描画しないこと、一覧と削除が残骸を正しく扱うことを試験する。
4. 準備失敗や中断（置換手順の各段階）、ディスク不足、置換中の読込を試験する。
5. 港区データでダウンロード容量、チェックサム計算と変換の時間、`walls/` の容量、
   壁半径内の読込時間を計測し、利用者へ示す見積りの妥当性を確認する。部分タイルだけの
   再取得は今回の前提にしない。

## 取り下げた案

- `bldg/` の派生タイルに壁を同居させる案。屋根線の広域読込で壁も解析することになり、
  読込が重くなる。
- 元のキャッシュとは独立に、後から壁だけを補う補助キャッシュ。元データの一致を
  保証しにくく、旧キャッシュには元 ZIP がないため結局再取得が必要になる。
- ハッシュを持たず PLATEAU 提供元と利用者指定の ZIP を信頼し、`<code>_<year>/` を
  維持する案。`--input-zip` で年度を決める手段が必要になる。ZIP 内の
  `metadata/udx_<code>_[city_|pref_]<YYYY>_op.xml` から読み取る規則を検討し、8自治体
  （2020〜2025年度、仕様3.3/4.1/5.0）で年度を確認できたが、命名に変種があり、
  つくば市2023年 ZIP には `udx_08220_2022_fld_op.xml` のように別年度の副メタデータが
  同居する。初回公開時の旧仕様 ZIP も未確認で、規則が複雑になるため採用しない。
- 置換後に旧キャッシュを `.outdated-*`／`.replaced-*` としてバックアップする現行方式。
  読込対象の判定を複雑にし、容量も消費する。元データはカタログから再取得できるため、
  破棄する。
