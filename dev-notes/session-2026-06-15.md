# Session 2026-06-15

Scope: Remove unused glow-mask blur support and keep the glow path as a straight low-resolution composite.

- Topic: GlowMask blur cleanup
  - Decision: Remove the blur helper, its configuration constant, and the related test/documentation references.
  - Rationale: The blur path is no longer part of the rendering strategy, so keeping it adds dead code and mismatched docs/tests.

Summary:
- Removed `GLOW_MASK_BLUR_PASSES` and `_blur_glow_mask_alpha` from `src/zstarview/gui/composite.py`.
- Deleted the blur-specific unit test and updated `docs/design/glow-mask.md` to describe the no-blur path.
- Validation: `uv run -p .venv/bin/python pytest tests/test_glow_mask.py` passed.

- Topic: Stable noise for glow masks
  - Decision: Add a small deterministic noise modulation to `GlowMask.alpha` right before RGBA conversion, using screen-fixed low-resolution coordinates.
  - Rationale: This keeps the glow texture from reading as perfectly smooth while avoiding frame-to-frame shimmer. A deterministic field also keeps the pattern stable relative to the screen.
  - Notes: The noise is intentionally mild so the effect stays in the "slightly rough" range rather than turning into visible grain.

- Topic: GlowMask design doc sync
  - Decision: Update `docs/design/glow-mask.md` to remove stale blur language and document the new screen-fixed noise step.
  - Rationale: The design doc should match the current compositor path, including the alpha modulation that now happens before tinting and RGBA conversion.

- Topic: Version bump
  - Decision: Bump `__version__` to `1.31.5` and add a release note entry for the screen-fixed glow noise change.
  - Rationale: The glow texture behavior changed in a user-visible way, so it should be reflected in the public release history.

- Topic: Sky disc twilight tuning
  - Decision: Relax the `sun_up` threshold in `src/zstarview/render/sky_disc.py` from `-8.0` to `-10.0` degrees.
  - Rationale: This is the smallest change that lets the warm sunset branch stay active a little longer, which better matches the user's requested "Japan-like" evening redness without widening the rest of the sky model.

- Topic: Sky disc haze and twilight tuning
  - Decision: Increase `TURBIDITY` from `5` to `6` and move `twilight` from `-10.0` to `-11.0` degrees.
  - Rationale: This keeps the previous tweak narrow while slightly extending the residual warm/bright phase and adding a bit more haze, which nudges the model toward a more humid, Japan-like evening without changing the overall color design.

- Topic: Background press simplified view on framed windows
  - Decision: Treat left-button press/release on the client area as the same temporary simplified-view trigger even when the window uses the standard frame.
  - Rationale: The simplified render path is driven by `client_press_pending`, and the framed host was previously bypassing that state change. Reusing the existing toggle keeps the behavior consistent without altering drag logic for the frameless host.
  - Validation: Added a unit test that exercises `_handle_client_mouse_press` and `_handle_client_mouse_release` and confirms `client_press_pending` flips `True` then `False`.

- Topic: Simplified star-name labels
  - Decision: In simplified view, draw every visible named star with a fixed label position offset of upper-right from the star marker, and do not apply overlap avoidance or position search.
  - Rationale: Simplified view should surface names deterministically. Fixed placement keeps the mode predictable and avoids the extra layout work that the hover-label path uses.
  - Validation: Added coverage for visible-name collection and for fixed upper-right label placement in the HUD render path.

- Topic: Simplified star-name label styling
  - Decision: Render simplified-view star names using the star's own rendered color and disable the label outline entirely.
  - Rationale: This makes the labels read as part of the star glyph itself and simplifies the visual treatment in the dense simplified mode.
  - Validation: Confirmed the label path now passes a star-derived `QColor` with transparent outline and zero outline width, with tests covering both the collected RGB and the draw call style.

- Topic: Planet label readability
  - Decision: Keep planet labels keyed to each body's marker color, but lift the HSV value component for dark colors before drawing the text.
  - Rationale: This preserves the color association while keeping low-value planets readable on the sky background. Bright planet colors stay unchanged, so the change only affects dim labels.
  - Validation: Added coverage for the helper that raises the HSV value floor and for day/white themes using lifted colors for Mercury and Moon labels.

- Topic: Star label color source
  - Decision: Use `B-V`-derived star colors directly for simplified star labels, and do not apply an HSV value lift to either star or planet labels.
  - Rationale: `B-V` already gives a more meaningful stellar color than the post-magnitude-dimmed render color. Removing the extra value lift keeps the label pipeline simpler and avoids surprising color shifts.
  - Validation: Updated the named-star label collection test to expect a bright B-V color for a faint named star, and kept the simplified-label draw test focused on placement and outline removal.

- Topic: Simplified star label placement
  - Decision: Draw simplified-view star labels with alpha 0.7 and anchor the label's lower-left corner at the star position.
  - Rationale: Lower opacity keeps the labels from overwhelming the scene, and the lower-left anchor makes the association between marker and label immediate without introducing a larger offset.
  - Validation: Updated the simplified-label draw test to assert the alpha level and to verify the baseline is positioned so the text bounds' lower-left corner matches the star coordinates.

- Topic: Sun label
  - Decision: Draw a Sun text label in the same muted tone used for the Moon label and keep the existing Sun marker as-is.
  - Rationale: The Sun previously lacked a text label, while other solar-system bodies already had one. Matching the Moon label tone keeps the Sun label readable without making it visually louder than the other body labels.
  - Validation: Added a unit test that checks the Sun label reuses the Moon label RGB tone, and confirmed the existing marker rendering path remains unchanged.
