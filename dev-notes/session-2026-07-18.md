- Topic: Bright-star diamond rendering path
  - Finding: `zstarview-atlas` sets `light_background_star_outline=True` in `src/zstarview/gui/atlas.py`. The shared star renderer branches on this flag in `src/zstarview/render/stars.py` and returns after drawing square dark outlines plus square colored bodies.
  - Finding: The normal renderer's diamond overlay is below that branch and is therefore skipped for Atlas. The normal path overlays a diamond for stars with `vmag < 2.0`; with `bright_bodies=outline`, it uses a diamond outline.
  - Conclusion: Atlas's missing bright-star diamonds are caused by the light-background rendering branch, not by the Atlas catalog limit or the instrument pipeline's layer ordering.

- Topic: Design direction for Atlas bright-star diamonds
  - Decision: Keep the Atlas light-background renderer as a separate raster path, but split it conceptually into a dark underlay layer and a colored star-body/bright-marker layer. For bright stars, replace the current square underlay with diamond geometry so the black contrast does not leave square corners around a diamond.
  - Rationale: This preserves the Atlas white-background contrast requirement and avoids changing the scenic renderer's additive star behavior. The bright-marker mode should remain explicit: filled diamond for `fill`, outlined diamond for `outline`, with the dark underlay rendered before the colored layer.
  - Required follow-up: Pass magnitude and bright-body mode into the light-background path, and extend its cache key with every new visual input, especially `vmag`, mode, and geometry constants. Add focused raster tests for faint stars, bright fill/outline, the `vmag == 2.0` boundary, clipping, and cache separation.
