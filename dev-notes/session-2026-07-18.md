- Topic: Bright-star diamond rendering path
  - Finding: `zstarview-atlas` sets `light_background_star_outline=True` in `src/zstarview/gui/atlas.py`. The shared star renderer branches on this flag in `src/zstarview/render/stars.py` and returns after drawing square dark outlines plus square colored bodies.
  - Finding: The normal renderer's diamond overlay is below that branch and is therefore skipped for Atlas. The normal path overlays a diamond for stars with `vmag < 2.0`; with `bright_bodies=outline`, it uses a diamond outline.
  - Conclusion: Atlas's missing bright-star diamonds are caused by the light-background rendering branch, not by the Atlas catalog limit or the instrument pipeline's layer ordering.

- Topic: Design direction for Atlas bright-star diamonds
  - Decision: Keep the Atlas light-background renderer as a separate raster path, but split it conceptually into a dark underlay layer and a colored star-body/bright-marker layer. For bright stars, replace the current square underlay with diamond geometry so the black contrast does not leave square corners around a diamond.
  - Rationale: This preserves the Atlas white-background contrast requirement and avoids changing the scenic renderer's additive star behavior. The bright-marker mode should remain explicit: filled diamond for `fill`, outlined diamond for `outline`, with the dark underlay rendered before the colored layer.
  - Required follow-up: Pass magnitude and bright-body mode into the light-background path, and extend its cache key with every new visual input, especially `vmag`, mode, and geometry constants. Add focused raster tests for faint stars, bright fill/outline, the `vmag == 2.0` boundary, clipping, and cache separation.

- Topic: Strengthen Atlas bright-star contrast
  - Decision: Draw the dark diamond outline at three pixels and the colored diamond line at one pixel, using the same geometric path so integer rounding cannot hide the dark edge behind the colored line.

  - Validation: The same 16 targeted tests and Ruff checks passed after the change.

- Topic: Design review for raising the regular sky opacity
  - Decision: Consider changing the regular `zstarview` default `--sky-opacity` from `0.1` to `0.2`, and add a regular-view-only dark contrast underlay for bright stars and ordinary planet discs. Define "4th magnitude or brighter" as `vmag <= 4.0`, including the boundary.
  - Rationale: A higher sky-disc alpha improves recognition of sky color but reduces local contrast for point-like objects. A small, object-shaped dark underlay restores local contrast without reverting the sky disc or darkening the whole scene. The existing Atlas light-background path is a useful rendering precedent, but its white-background policy and bright-star marker shapes should not be enabled globally.
  - Proposed scope: Apply the underlay only when the sky disc is enabled (`sky_opacity > 0`), before the colored star/planet marker. Keep faint stars unchanged; keep the Sun cross gauge and Moon phase renderer unchanged initially. For ordinary planets, use the same finite-vmag threshold where available and define an explicit fallback for missing vmag before implementation.
  - Design constraints: Preserve the current additive rendering of the faint-star layer, avoid square black corners around diamond bright-star markers, include threshold/mode/geometry/opacity in raster cache keys, and validate the `vmag == 4.0` boundary, viewport clipping, overlap, sky-disc toggle, and export-image parity.
  - Open questions: Decide whether the underlay is a thin outline or a filled local backing shape, whether its alpha is fixed or scales with sky opacity, and whether a new CLI option is warranted. The initial recommendation is a subtle fixed dark alpha with no new option, derived from the sky-disc-enabled state.

- Topic: Document per-star bright-body rendering

  - Rationale: Per-object rendering lets the contrast underlay follow each star's projected size and shape, avoids duplicate additive rendering, and prevents nearby stars' underlays from covering already-drawn star colors by using an underlay-first/body-second order.
