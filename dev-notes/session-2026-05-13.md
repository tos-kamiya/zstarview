- Topic: Water overlay extent for the scan demo
  - Decision: Add `--water-extent-km` with a default half-width of 1.0 km, project water polygons into observer-centered local XY space, and clip them to a square window before hit-testing and SVG rendering.
  - Rationale: This keeps the plotted water data bounded to about 2 km across without changing the DEM scan radius or introducing a second coordinate system for rendering.
  - Validation: `python3 -m py_compile dev-samples/water_run_scan_demo.py`
- Topic: Water sampling density for narrow rivers
  - Decision: Reduce the default ray sample spacing from 200 m to 50 m in `dev-samples/water_run_scan_demo.py`.
  - Rationale: Narrow rivers are easy to skip at 200 m spacing, so a tighter default is a better tradeoff for this exploratory demo.
  - Validation: `python3 -m py_compile dev-samples/water_run_scan_demo.py`
- Topic: Distance-aware water sampling
  - Decision: Switch from one fixed ray spacing to two stages: a dense near field and a coarser far field, with `--sample-step-m` kept as a compatibility alias for the far spacing.
  - Rationale: This improves detection of nearby narrow rivers without making the full 32 km scan uniformly expensive.
  - Validation: `python3 -m py_compile dev-samples/water_run_scan_demo.py`
- Topic: argparse alias collision
  - Decision: Keep `--sample-step-m` as a separate legacy alias field and copy it into `sample_step_far_m` after parsing.
  - Rationale: The previous hidden-arg approach overwrote the visible default with `None`, which caused the runtime crash.
  - Validation: `python3 -m py_compile dev-samples/water_run_scan_demo.py`
- Topic: Water points in zstarview
  - Decision: Add a background water overlay controller that fetches Overpass data around the current observer location, samples water polygons into projected point markers, and renders them as always-on blue dots in the terrain layer.
  - Rationale: This keeps the feature experimental and non-interactive, reuses the existing background-update pattern, and avoids introducing a new menu or toggle path.
  - Validation: `python3 -m py_compile src/zstarview/water_overlay.py src/zstarview/render/terrain.py src/zstarview/render/pipeline.py src/zstarview/gui/window_state.py src/zstarview/gui/window_render.py src/zstarview/gui/window_updates.py src/zstarview/gui/window.py src/zstarview/gui/water_overlay_state.py src/zstarview/gui/water_overlay_controller.py`
- Topic: Water overlay near-field refinement
  - Decision: Change the water-point distance schedule to start at 2 m, continue in 2 m increments through 512 m, then continue with a coarser tail out to the 2 km overlay radius; fade point alpha with distance.
  - Rationale: The near field needs to stay dense enough to catch small waterways, while the far field still benefits from coverage but should visually recede instead of competing with closer water marks.
  - Validation: `python3 -m py_compile src/zstarview/water_overlay.py src/zstarview/render/terrain.py src/zstarview/gui/water_overlay_controller.py`
- Topic: Water overlay fetch throttling
  - Decision: Add a small persistent cache under the app cache root for water overlay results, reuse recent successful results briefly, and preserve a failure backoff window across restarts for each observer-location scope key.
  - Rationale: This follows the OpeySky pattern of persisting failure metadata so repeated launches do not immediately hammer the upstream API after a 504 or similar transient error.
  - Validation: `python3 -m py_compile src/zstarview/water_overlay.py src/zstarview/gui/water_overlay_controller.py src/zstarview/gui/water_overlay_cache.py`
- Topic: Water overlay cache retention and retry policy
  - Decision: Keep fetched water-overlay results for 90 days in the app cache, and do not retry Overpass within the same execution when a fetch fails with HTTP/network errors, including 429.
  - Rationale: Long-lived cache reuse reduces repeated upstream pressure across restarts, while single-attempt failures keep the current run from hammering Overpass when it is already unhealthy.
  - Validation: `python3 -m py_compile src/zstarview/water_overlay.py src/zstarview/gui/water_overlay_controller.py src/zstarview/gui/water_overlay_cache.py`
- Topic: Water overlay cache freshness policy
  - Decision: Use a cached water overlay result directly when it is still within the 90-day retention window; otherwise attempt a fresh fetch and fall back to the stale cache if that fetch fails.
  - Rationale: This matches the DEM pattern more closely and avoids unnecessary network calls when a usable cached result already exists.
  - Validation: `python3 -m py_compile src/zstarview/water_overlay.py src/zstarview/gui/water_overlay_controller.py src/zstarview/gui/water_overlay_cache.py`
