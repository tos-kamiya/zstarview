# Session 2026-04-02

- Scope: Investigate current handling of building heights in the codebase.

- Topic: Urban outline building height baseline
  - Decision: Treat Overture building `height` as above-ground building height, then add DEM-derived ground elevation for both building and observer before computing apparent altitude.
  - Rationale: The current method ignores terrain elevation differences and biases apparent altitude, especially for distant buildings on higher or lower ground.
  - Alternatives Considered: Continue using raw `height_m` only. Rejected because it systematically underestimates elevated buildings and overestimates buildings on lower ground.

- Topic: Tower viewpoint dataset curation
  - Decision: Keep tower viewpoint discovery semi-manual. Use broader Wikidata candidate queries, then review candidates individually before updating the bundled dataset.
  - Rationale: Tower and high-observation facilities are inconsistently classified in Wikidata. Restrictive auto-selection misses valid spots such as television towers, while broader queries inevitably include false positives.
  - Alternatives Considered: Fully automatic adoption from a strict `Q1440300`-centered query. Rejected because it trades away recall and still does not handle mixed cases like observation-deck buildings well.

- Topic: Tower review candidate extraction script
  - Decision: Add a separate dev-sample script that merges multiple WDQS raw JSON files into a review-candidate JSON with `matched_rules` provenance, instead of writing directly into the bundled tower dataset.
  - Rationale: Candidate discovery needs to stay broad, while the packaged dataset should remain curated. Separating the review artifact from the final bundled JSON keeps that boundary explicit.
  - Alternatives Considered: Extending the old tower normalization script to produce final dataset entries directly. Rejected because that path still encourages premature auto-adoption of broad candidates.

- Summary:
