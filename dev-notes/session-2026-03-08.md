# Session 2026-03-08

- Scope: Terrain horizon polyline integration planning for `zstarview` based on `dev-samples/horizon_polyline_demo.py`.

- Topic: Current horizon rendering path
  - Decision: Treat the existing horizon as a geometric baseline and add terrain horizon as a separate data source rather than mutating the current behavior immediately.
  - Rationale: `src/zstarview/astro.py` currently generates `alt=0` horizon points in view space only, and `src/zstarview/ui/sky_worker.py` computes them together with other sky overlays. Keeping the current path intact reduces regression risk while a terrain-backed path is introduced and validated.
  - Alternatives Considered: Directly replacing the geometric horizon was rejected for the first integration step because it would couple DEM/network/runtime risks to an always-on rendering path.

- Topic: Production decomposition of the demo script
  - Decision: Split the demo logic into three layers: DEM access/cache, terrain horizon computation, and UI-facing orchestration.
  - Rationale: `dev-samples/horizon_polyline_demo.py` currently mixes DEM download, raster loading, scan computation, and validation outputs. The app needs only the first three concerns, and they should be reusable from worker threads without CLI-only side effects.
  - Alternatives Considered: Importing the demo script directly was rejected because it keeps validation-only output paths and argument parsing coupled to runtime logic.

- Topic: Worker and responsiveness model
  - Decision: Run terrain horizon computation off the UI thread and isolate it from the fast sky update loop.
  - Rationale: The current `SkyDataWorker` already handles astronomy calculations in a background thread, but the DEM ray scan can be materially heavier and may involve cache misses or tile downloads. A dedicated worker or separately throttled task avoids stalling normal sky refresh.
  - Alternatives Considered: Folding DEM work into every ordinary sky update was rejected because view-center changes and timer-driven updates would trigger unnecessary recomputation.

- Topic: Initial product scope
  - Decision: Design for a terrain horizon overlay whose effective feature switch is opacity. A non-zero opacity enables DEM acquisition and rendering; opacity `0` disables both. The default is enabled. The GUI toggle will switch between `0` and a remembered non-zero default opacity. If the CLI sets opacity to `0` at startup, the GUI must not be allowed to raise it during that run.
  - Rationale: This collapses feature enablement and rendering strength into one user-facing control, matching the requested behavior while preserving the cloud-like “CLI can hard-disable GUI re-enable” rule. The overlay remains observer-location dependent and time independent, so it can be reused across view changes without recomputing unless the observer location changes.
  - Alternatives Considered: Terrain-clipped sky-disc shading was deferred because it requires a broader rendering contract than the current polyline overlay.

- Topic: Cache policy
  - Decision: Persist only DEM data and recompute the terrain horizon polyline on demand.
  - Rationale: The user estimates that the actual scan can complete in roughly five seconds when DEM data is already present. That makes precomputing and serializing observer-specific horizon profiles unnecessary complexity for the first production version.
  - Alternatives Considered: Caching finished horizon polylines per observer/parameter set was rejected because DEM-only caching is simpler and still performant enough.

- Topic: Rendering semantics
  - Decision: Keep the existing geometric horizon unchanged and draw the terrain horizon as an additional green polyline overlay.
  - Rationale: This preserves existing orientation aids and avoids redefining compass-marker behavior, label placement, or ground/sky shading. It also makes the terrain data visually comparable against the current geometric horizon.
  - Alternatives Considered: Replacing the geometric horizon or clipping the sky/ground boundary to the terrain horizon was rejected for v1 because both options have broader rendering consequences.

- Topic: Failure and retry behavior
  - Decision: Report DEM acquisition/render preparation status in the bottom status line alongside cloud status. If DEM acquisition fails, keep a persistent terrain-horizon failure message visible for the rest of the current app session and do not retry automatically. Retry happens only on the next app launch.
  - Rationale: This matches the requested UX and avoids repeated download attempts or noisy retry loops after a failure. It also keeps terrain failure semantics parallel to cloud status presentation while remaining simpler operationally.
  - Alternatives Considered: Silent fallback and background retries were rejected because they obscure failure state and may repeatedly hit the same network or data issue.

- Topic: Fetch timing
  - Decision: Trigger terrain horizon acquisition on the same lifecycle timing as cloud acquisition.
  - Rationale: The app already has infrastructure for kicking off non-blocking background fetch/render work around startup and view idle transitions. Using the same timing model minimizes new orchestration concepts and keeps user expectations aligned.
  - Alternatives Considered: Immediate eager fetch during window construction and fully lazy first-paint fetch were both rejected in favor of matching the existing cloud timing model.

- Topic: Open design questions
  - Decision: Keep the following unresolved until implementation planning: exact CLI option names for terrain-horizon opacity and whether the bottom status line should show cloud and terrain state as a combined single sentence or fixed left-to-right segments.
  - Rationale: The higher-level runtime behavior is fixed, but naming and final presentation wording still need a concrete API/UI choice.

- Topic: Hamburger menu grouping and view controls
  - Decision: Split the menu into three action groups separated by horizontal rules: view-direction changes, named-star jump/search, and display toggles. Add altitude raise/lower actions alongside azimuth rotation, and expose sky-disc visibility as another display toggle.
  - Rationale: The window already supports altitude changes on arrow keys, but the menu only exposed azimuth rotation. Mirroring both axes in the menu makes the controls consistent, while explicit separators match the requested information architecture and keep navigation, target jump, and layer toggles visually distinct.
  - Alternatives Considered: Leaving altitude control keyboard-only was rejected because it keeps menu behavior asymmetric. A separate submenu was rejected because the current menu is small enough that flat grouping is clearer.
