- Topic: Refactor assessment hotspots
  - Decision: Treat `src/zstarview/ui/window.py`, `src/zstarview/render/draw.py`, and `src/zstarview/zstarview.py` as the primary cleanup targets.
  - Rationale: They are the largest runtime modules, they mix multiple responsibilities, and `pyproject.toml` currently disables mypy checking for key files (`zstarview.render.draw`, `zstarview.ui.window`, `zstarview.ui.sky_worker`), which is a strong signal that maintainability has already degraded.

- Topic: Low-risk first refactor slice
  - Decision: Start by extracting pure logic from UI-heavy modules before touching behavior.
  - Rationale: `SkyWindow` currently combines setup, state orchestration, rendering coordination, cloud lifecycle, and input handling. Pulling pure helpers and config/state objects out first reduces regression risk and makes later UI refactors testable without Qt.

- Topic: Import boundary cleanup

  - Rationale: `src/zstarview/__init__.py` imports `zstarview.py` at module import time, which pulls in PySide6 immediately. That makes lightweight imports and some tests harder than necessary.

- Topic: Move window catalog preparation to startup-side construction
  - Decision: Stop passing raw star/DSO data frames into `SkyWindow`; instead build a `PreparedWindowCatalogs` value object in startup code and inject that into the window.
  - Rationale: `SkyWindow` should own widget assembly and runtime coordination, not catalog reshaping. Precomputing render arrays and named-star jump data before window construction removes data-preparation debt from the UI layer and makes the constructor easier to reason about.

- Topic: Move viewer-data assembly to startup-side construction
  - Decision: Build `ViewerData` before constructing `SkyWindow`, alongside the prepared catalogs.
  - Rationale: This keeps the window constructor focused on wiring an already-defined observer/view state into the UI, instead of translating primitive `city_name` / `city_data` / `view_center` inputs itself.

- Topic: Split SkyWindow options by responsibility
  - Decision: Replace the long `SkyWindow(...)` option list with separate user-facing and runtime option dataclasses.
  - Rationale: CLI/config choices such as theme, opacity, and initial toggles change for different reasons than runtime/window-hosting values such as geometry restore, timers, and render-surface sizing. Splitting them keeps constructor semantics readable and avoids a single catch-all config object.
