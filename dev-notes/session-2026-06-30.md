# 2026-06-30 session

Scope: Investigate GOES G19 cloud data fetch failures reported by the GUI status line.

- Topic: GOES G19 cloud fetch failure
  - Decision: The observed GUI failure was caused by the cloud-source worker process exiting with code `-11` before writing a result manifest.
  - Rationale: The app log for `2026-06-30 21:10:37 JST` reports `Network/S3 download error: cloud source worker exited with code -11 without writing a result`. The worker log stops immediately after `Searching GOES (order=G19,G18, window=120min)`, so the Python exception handler did not run. A direct GOES G19 C13 fetch in the repository venv succeeded at `2026-06-30T12:10:00Z`, showing that current NOAA S3 data was available and readable in that environment.
  - Follow-up: If this recurs, add lower-level crash diagnostics around worker subprocess execution or align the installed pipxu worker environment with the repository venv used for the successful direct check.

- Topic: GOES CMI open crash isolation
  - Decision: Open GOES CMI NetCDF files with `decode_times=False`.
  - Rationale: Replaying the downloaded `.nc.tmp` file under the same pipxu Python 3.14 worker environment crashed inside `xarray.open_dataset()` before the CMI compute step. `faulthandler` showed the stack in `xarray.coding.times.decode_cf_datetime`, `pandas._libs.tslibs.timedeltas`, and NumPy. The cloud renderer uses the `CMI` data, projection metadata, and `x/y` coordinates, not decoded CF datetime variables. Re-running the same file with `decode_times=False` completed open, CMI compute, CRS construction, and coordinate loading.

- Topic: Cloud source diagnostic CLI
  - Decision: Add `zstarview-diagnose-cloud-source` as a thin diagnostic wrapper around the existing cloud-source worker, with `--output-dir` required.
  - Rationale: Keeping the diagnostic path on the same worker/provider routines as the GUI avoids a second implementation that could drift from production behavior. The CLI maps `--output-dir` to an isolated worker directory and default diagnostic cache, while preserving the worker-compatible arguments users can copy from `Launching cloud source worker:` logs.
  - Alternatives Considered: A standalone downloader/parser was rejected because it would be easier to debug but less representative of the GUI failure path.

- Topic: Relative output-dir bug
  - Decision: Normalize diagnostic output paths to absolute paths before launching the worker.
  - Rationale: A relative `--output-dir tmp` caused the parent process and worker subprocess to resolve `tmp/worker`, `tmp/cache`, and the diagnostic log paths against different working directories. That made the worker succeed while the wrapper reported `failed` because it looked for the result JSON in the wrong place. Resolving the output directory in the wrapper keeps the parent and worker aligned without changing the visible CLI contract.
