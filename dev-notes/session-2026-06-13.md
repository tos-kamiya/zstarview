# Session 2026-06-13

- Scope: Design review for a click-to-minimize overlay mode that favors stars and preserves hover labels.
- Status: Investigating existing viewport-interaction and hover/HUD separation before proposing spec changes.

- Topic: Click-to-enter "stars-first" mode
  - Decision: Reuse the existing viewport-interaction rendering path as the base, but define a new explicit mouse-driven mode that can stay active for 30 seconds or until a second click.
  - Rationale: The current fast path already hides clouds and the menu button, keeps hover resolution available, and renders the simplified sky layers needed for a clean star-focused view. Extending it is lower risk than introducing a parallel rendering mode.
  - Alternatives Considered: A separate "minimal UI" flag, a pure CSS/widget hide pass, and a permanent toggle were considered but would duplicate rendering logic or diverge from the current responsive interaction model.

- Topic: Mouse click semantics
  - Decision: Treat background clicks as a mode toggle only when they do not become a drag gesture.
  - Rationale: The frameless window already uses the client area as a drag target, so the click path must respect existing window movement behavior. A click-vs-drag distinction avoids accidental mode flips during normal repositioning.

- Topic: Spec and design update
  - Decision: Document `star-focus` as a GUI-only, click-driven mode with a 30-second expiry, drag-cancel behavior, and hover-preserving rendering.
  - Rationale: The behavior is now sufficiently stable to describe in user-facing and design docs without committing to implementation details.
  - Notes: Updated `docs/specification.md` and `docs/design/rendering-pipeline.md`; implementation work remains pending.

- Topic: Press-state experiment
  - Decision: Track a pending press state separately from drag/resize, and use it to drive a centered `PRESSED` overlay.
  - Rationale: The press-pending window is the stable point between mouse press and drag/resize escalation, so it is a good signal for experimenting with composition changes without touching menu or resize interactions.
  - Notes: Background press now sets and clears a `client_press_pending` flag; the overlay is redrawn immediately on both transitions.

- Topic: Press-state composition follow-up
  - Decision: Remove the centered `PRESSED` overlay and instead use `client_press_pending` to suppress selected scene layers during a press.
  - Rationale: The overlay was only a probe. The useful signal is the pending-press state itself, which can be used to hide clouds, the earth guide, secondary terrain ridges, water overlays, and urban outlines while keeping hover behavior intact.
  - Notes: Added tests that verify the press-pending branch changes the rendered layer set rather than drawing text.

- Topic: Press-state refinement
  - Decision: Also suppress night-light and ridge-glow rendering during press-pending, but keep the main terrain profile visible by redrawing it explicitly.
  - Rationale: The night-light layers were still visually busy during the reduced mode, while the main horizon ridge was getting too weak when only the sky/cloud compositor path carried it. A direct terrain-profile redraw keeps the main ridge legible without bringing back the heavier overlays.
  - Notes: Replaced `mapFrom()`-based drag exclusion checks with global-coordinate checks to avoid Qt parent-hierarchy warnings during press detection.

- Topic: Press-state main ridge alignment
  - Decision: Redraw the main terrain profile in the same fast-mode path used for viewport interaction, and shrink the horizon line width globally to about one third.
  - Rationale: The press-pending mode should behave like the existing fast path for the main ridge, with only the width reduced for readability. Reusing the fast path keeps behavior consistent and reduces divergence between the two temporary display states.
  - Notes: Updated the terrain-horizon width constants and the press-pending redraw path accordingly.

- Topic: Specification simplification
  - Decision: Remove the old 30-second `star-focus` wording and treat the press-pending simplified rendering as the formal GUI behavior.
  - Rationale: The implementation has settled on a press-state-driven simplification rather than a timed click mode. Aligning the docs with the code avoids describing a behavior that no longer exists.
  - Notes: Updated the specification and rendering-pipeline design sections to describe `client_press_pending` and the reduced layer set instead of the timed mode.

- Topic: README GUI summary
  - Decision: Expand the README GUI summary to mention hover-driven labels and highlights for named stars, DSO, asterisms, and direction labels.
  - Rationale: The GUI section already described keyboard and menu operations, but the hover behavior is a major part of how the application is used and should be discoverable without reading the detailed specification.
  - Notes: Updated both English and Japanese README files to include a brief hover summary near the GUI operations section.

- Topic: README GUI reorganization

  - Notes: Updated both README variants and kept the simplified viewport-interaction note next to the resize behavior.

- Topic: README mouse interaction refinement

  - Notes: Updated both README variants to describe the simplified press state alongside hover and drag behavior.

- Topic: Ridge-glow keyboard binding

- Topic: Simplified-view mode design
  - Decision: Redefine the temporary press-state behavior as a `Space`-toggled simplified view, with background mouse press acting as a temporary inverse override.
  - Rationale: This keeps the global mode explicit while preserving the useful "peek through" behavior during mouse interaction. It also gives the HUD a stable, short label (`Simplified view [Space]`) when the normal status blocks are hidden.
  - Notes: Updated the specification and rendering-pipeline design to describe the effective `simplified_view_enabled XOR client_press_override_active` behavior and to exclude menus, the resize grip, and window dragging from the override.

- Topic: Simplified-view implementation
  - Decision: Implement the `Space` toggle as a persistent simplified-view flag and keep background mouse presses as a temporary inverse override.
  - Rationale: The toggle needs to survive drag/resize interactions, while the mouse press should only provide a momentary peek in the opposite direction. Keeping the two states separate makes the interaction model predictable and easy to explain.
  - Notes: Wired the new state through `SkyWindowState`, the HUD status text, and the render cache keys; added tests for `Space`, the simplified HUD label, and the XOR-based simplified rendering branch.

- Topic: Urban outline polygon fill trial
  - Decision: Add a lightweight fill pass to `draw_urban_outlines()` so closed-looking outline fragments are painted with a faint interior fill before the existing stroke layers.
  - Rationale: This is a low-risk visual experiment that reuses the current outline fragments and keeps the original line rendering intact.
  - Notes: The fill uses the same outline color with a low alpha derived from the configured urban outline opacity; no tests were added per request.

- Topic: Urban outline fill closure guard
  - Decision: Only fill fragments whose projected endpoints are close enough to behave like closed rings.
  - Rationale: Nearby buildings can produce clipped open fragments, and filling those creates obvious artifacts. A simple endpoint-distance gate keeps the fill effect on loop-like fragments while avoiding the broken shapes.

- Topic: Urban outline fill size filter
  - Decision: Skip filled urban outline fragments whose projected screen-space bounding box is too small on either axis.
  - Rationale: Using the projected `x/y` span is simpler than computing polygon area and matches the user's requested heuristic for suppressing tiny fills.

- Topic: Urban outline fill formalization
  - Decision: Keep the urban outline fill behavior as part of the shipped rendering spec, with no CLI toggle for it.
  - Rationale: The user confirmed the fill behavior as the desired default. Making it a fixed renderer rule keeps startup behavior simple and avoids extra mode switches for a purely visual detail.

- Topic: README urban outline wording
  - Decision: Update the README feature summary to mention the faint fill inside closed urban outline loops in both English and Japanese.
  - Rationale: The README previously described only the line overlay, which no longer matched the shipped rendering behavior after the fill became part of the fixed spec.
