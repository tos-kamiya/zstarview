# Session 2026-07-08

Scope: White-background object viewer specification and design discussion.

- Topic: White-background object viewer documentation split
  - Decision: Keep the new viewer's user-facing specification and internal design in separate documents: `docs/object-viewer-specification.md` and `docs/design/object-viewer.md`.
  - Rationale: The viewer is intended as a separate application entry, not a transient `zstarview` display mode. Separate docs keep the existing `zstarview` specification focused on the starry-sky viewer while still documenting the shared architecture and intended defaults.
  - Alternatives Considered: Adding a large section to `docs/specification.md` and `docs/design.md`; rejected because it would mix two user-facing product concepts in the same primary spec.

- Topic: White-background rendering defaults
  - Decision: The object viewer should use a fully white background, black labels, visible geographic helper layers, and a dedicated bright-star rendering path with outline and body separated into two passes.
  - Rationale: Geographic helper layers help users identify place and direction, while the white background requires different contrast rules from the dark sky viewer. Separating star outlines from star bodies prevents outlines from overpainting nearby star colors.

- Topic: Small star cutoff
  - Decision: Stars whose projected apparent diameter is below 1.0 px should not be drawn in the white-background viewer.
  - Rationale: Subpixel star rendering works for dark backgrounds but becomes either invisible or noisy on white backgrounds.

- Topic: White-background object viewer implementation
  - Decision: Add `zstarview-object-viewer` as a separate GUI script backed by `zstarview.gui.object_viewer`.
  - Rationale: A separate entry lets the viewer use white-background defaults without adding a cross-cutting mode flag to the main `zstarview` CLI.
  - Implementation Notes: The object profile applies only to options not explicitly set on the CLI. It uses the `object-white` theme, disables sky color, night-light, ridge glow, ground tint, DSO, and asterisms by default, keeps geographic helper layers available, limits stars to Vmag 6.0, and enables the light-background star outline path.

- Topic: Light-background star renderer
  - Decision: Add a separate star render path selected by render style instead of changing the existing additive star renderer.
  - Rationale: The dark-background renderer relies on additive subpixel light, while the white-background viewer needs SourceOver drawing, black outlines, and a hard 1 px apparent-size cutoff.

- Topic: Object-viewer overlay styling responsibility
  - Decision: Keep whole-window concerns in `ThemeStyle`, and add grouped overlay-layer styling for aircraft, satellites, terrain, urban outlines, water, and Earth guide instead of passing object-viewer constants through individual render arguments.
  - Rationale: White-background visibility needs layer-specific color, alpha, width, and figure-outline rules, but spreading those values through the pipeline would make callers know too much about render details. Label text defaults should continue to come from `ThemeStyle`; overlay styles may override label color only when an object-specific label should match its marker.
  - Alternatives Considered: Expanding `ThemeStyle` with many direct fields such as aircraft and satellite colors; rejected because it would turn the theme into a flat constant bag and make future layer-specific settings harder to group.

- Topic: Object-viewer white-background palette candidate
  - Decision: Use a white-background palette with dark neutral text, blue-gray clouds, magenta aircraft, blue satellites, muted gray/brown geographic helper layers, and teal water.
  - Rationale: The palette should remain visible on pure white without becoming fluorescent. Hue separation helps users distinguish moving objects from geographic context: aircraft are red-magenta, satellites are blue, clouds are blue-gray, water is teal, and terrain/Earth guide use muted brown-gray.
  - Candidate Values:
    - Text/HUD: near black `#101010`, muted text `#242424`, secondary text `#5A5A5A`.
    - Cloud: hatch `#6F8496`, light `#9AACBC`.
    - Aircraft: body/trail `#B21F6B`, figure outline `rgba(42, 24, 34, 80)`, label `#8F1858`.
    - Satellite: marker `#255DBA`, figure outline `rgba(20, 35, 63, 85)`, label `#1F4F9D`.
    - Terrain horizon: line `#8A7765`, outline `rgba(76, 64, 56, 55)`.
    - Urban outline: line `#6E6E6E`, low-alpha fill `#9A9A9A`, outline `rgba(52, 52, 52, 45)`.
    - Water: sea/large `#238B9F`, lake/river `#177DAE`, outline `rgba(14, 63, 82, 60)`.
    - Earth guide: line `#7A6B5C`, underlay `rgba(60, 52, 45, 40)`.
    - Planet annotations: sun `#B66A00`, moon `#5E6066`, default planet `#4A4A4A`.
    - Search/selection: active marker `#C74700`, hover marker `#007A5A`.

- Topic: Instrument sky presentation migration approval
  - Decision: Rework `zstarview-object-viewer` as an instrument-style presentation that reuses shared scene data but owns its layer ordering and rendering policy.
  - Rationale: The main `zstarview` presentation intentionally uses atmospheric effects such as glow, night lights, Earth guide hatching, and fast/simplified interaction modes. The object viewer should instead behave like a positional instrument: stable during interaction, low decoration, and focused on the locations of real objects.
  - Alternatives Considered: Reverting to an older commit and reimplementing from scratch; rejected because the existing object-white theme, overlay styles, entry point, and shared `RenderSceneData` are useful migration assets.
  - Command/Decision Point: A HARD STOP was raised for the cross-cutting rendering change. User replied `APPROVE`, with scope limited to adding an instrument presentation beside the existing scenic path and routing only `zstarview-object-viewer` to it first.

- Topic: Object-viewer star data policy
  - Decision: Add `star_data_policy` as an internal setting separate from `vmag_limit`. The normal viewer uses `scenic_view_scoped`; `zstarview-object-viewer` uses `positional_static`.
  - Rationale: The object viewer should not temporarily lose stars in newly exposed regions during arrow-key view changes. Naming the policy by purpose keeps the data-retention behavior separate from the magnitude limit, which remains a star selection/display limit.
  - Alternatives Considered: Keying unmasked behavior directly from `vmag_limit`; rejected because it would couple a display threshold to sky-worker data lifetime and make the behavior hard to reason about.
