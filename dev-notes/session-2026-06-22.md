# Session 2026-06-22 — Cloud Rendering Redesign (Night-Light Style)

- Date: 2026-06-22
- Scope: Design a new cloud rendering pipeline that caches satellite data as an observer-centric alt/az grid, then renders from that grid at draw time.
- Status: Design only; implementation deferred until approved.

---

- Topic: Replace per-frame lat/lon → screen projection with a cached alt/az cloud-coverage grid
  - Decision:
    - Introduce a new intermediate representation: `CloudAltAzGrid`.
    - During source-data fetch, transform satellite brightness-temperature samples from (lat, lon, cloud-shell height) into (altitude, azimuth) as seen by the observer, and store this sparse or dense alt/az grid on disk/memory.
    - At render time, convert the cached `CloudAltAzGrid` into a screen-space cloud image using a separate, much cheaper renderer.
    - The MVP renderer will draw soft circles at the alt/az locations; the amount of cloud controls circle size/opacity.
    - A later iteration can add stripe/hatch rendering from the same grid.
  - Rationale:
    - The current pipeline re-projects the entire satellite image every time the camera moves (az/alt/radius/FOV changes). This is CPU-heavy and hard to cache per camera view.
    - An alt/az grid is observer-centric and camera-independent: once built for a given observer location + satellite time + cloud shells, it can be reused for any view direction, zoom, or screen size.
    - Render-time work becomes simple image generation from a small 2D field (alt/az), which is fast and can run on the UI thread if needed.
    - The "night light" metaphor fits well: each satellite pixel becomes a point light on the celestial sphere, and we accumulate their contribution as seen by the observer.
  - Alternatives Considered:
    - Keep current per-frame re-projection and only cache source data: rejected because it does not reduce per-frame CPU cost for camera motion.
    - Pre-render a full RGBA disc at a fixed FOV and just rotate it: rejected because FOV/zoom changes would require re-projection anyway, and the current stripe style depends on screen-space density.
    - Build a 3D point cloud and project at render time: equivalent to alt/az grid but more complex; alt/az grid is the projection of that point cloud and is exactly what we need for a 2D sky view.

## Proposed Architecture

### Two-phase pipeline

```
┌─────────────────────────────────────────────────────────────────────────────┐
│ Phase A: INGESTION (background, runs when satellite data updates)           │
│                                                                             │
│  GOES/Himawari BT data                                                       │
│       │                                                                      │
│       ▼                                                                      │
│  For each cloud shell (3/5/7 km) and each relevant satellite pixel:            │
│    - lat/lon/height → ECEF point on the shell                                │
│    - observer lat/lon/sea-level → vector to that point                        │
│    - convert vector to local alt/az                                            │
│    - record (alt, az, cloud_amount)                                            │
│       │                                                                      │
│       ▼                                                                      │
│  CloudAltAzGrid (sparse or dense) + metadata                                 │
│       │                                                                      │
│       ▼                                                                      │
│  Cache to disk keyed by (observer_lat/lon, satellite, timeslot, shells)       │
└─────────────────────────────────────────────────────────────────────────────┘
                                      │
                                      ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│ Phase B: RENDER (cheap, runs every frame or on view change)                  │
│                                                                             │
│  CloudAltAzGrid                                                              │
│       │                                                                      │
│       ▼                                                                      │
│  For current camera (center alt/az, FOV, radius_px):                         │
│    - map grid cells to screen pixels (azimuthal equidistant or similar)       │
│    - generate cloud image:                                                    │
│      MVP: draw circles whose radius/opacity ∝ cloud_amount                    │
│      Later: variable-width stripes, hatch, gaussian splats, etc.             │
│       │                                                                      │
│       ▼                                                                      │
│  RGBA cloud layer → composite over sky                                       │
└─────────────────────────────────────────────────────────────────────────────┘
```

### CloudAltAzGrid representation

Two possible forms; the design leaves the choice open but recommends starting with the dense grid for simplicity and later moving to sparse if memory becomes an issue.

**Option 1: Dense alt/az grid (recommended for MVP)**

- Fixed angular resolution, e.g. `0.5°` per bin.
- Dimensions: `az_bins = 720` (0..360°), `alt_bins = 90` (0..90°).
- Stores `float32` cloud amount (0..1) per cell.
- Pro: trivial to render, easy to smooth, cache-friendly.
- Con: fixed resolution; polar regions waste bins.

```python
@dataclass(frozen=True)
class CloudAltAzGrid:
    amount: np.ndarray         # shape (alt_bins, az_bins), float32, 0..1
    alt_min_deg: float       # e.g. 0.0
    alt_max_deg: float       # e.g. 90.0
    az_min_deg: float        # e.g. 0.0
    az_max_deg: float        # e.g. 360.0
    observer_lat: float
    observer_lon: float
    satellite: str
    product: str
    time_utc: datetime
    shells_km: tuple[float, ...]
    source_key: SourceKey
    coverage_ratio: float
    source_completeness_ratio: float | None
```

**Option 2: Sparse point list (future optimization)**

- Store only cells with cloud_amount > threshold.
- Each entry: `(alt_deg, az_deg, amount)`.
- Pro: much smaller for clear skies; fine angular resolution possible.
- Con: rendering needs spatial indexing or splatting; harder to cache efficiently.

### Ingestion details

1. **Input**: `CloudSourceData` (data_array + metadata), observer `(lat, lon)`, cloud shells.
2. **Sampling strategy**:
   - For MVP, sample the satellite BT field on a coarse geographic grid (e.g. every 0.2° within the visible shells) and convert each sample to alt/az.
   - Alternatively, iterate over satellite pixels directly; may be too many.
3. **BT → cloud amount**: reuse existing `_bt_to_weight` + `_suppress_low_cloud_weight` from `clouddisc/render/grayscale.py`.
4. **Shell blending**: apply the same adaptive 3-shell weights as `CloudDisc._render_from_source_impl`.
   - Compute `cloud_amount` from a representative sample.
   - Blend shell contributions into a single cloud amount per alt/az cell.
5. **Cell accumulation**:
   - If multiple samples fall into the same alt/az bin, use `max` or `mean` depending on whether we want to preserve thin high clouds or average them out. Recommended: `max` for visual prominence, with a small gaussian pre-blur to reduce blockiness.
6. **Missing data**: keep a separate `missing_mask` grid of same shape indicating no satellite coverage for that cell; this feeds the existing yellow tint overlay.

### Render details (MVP: circle drawing)

```python
def render_altaz_grid_to_rgba(
    grid: CloudAltAzGrid,
    width: int,
    height: int,
    center_alt_deg: float,
    center_az_deg: float,
    edge_fov_deg: float,
    *,
    base_circle_radius_px: float = 2.0,
    max_circle_radius_px: float = 12.0,
    opacity_scale: float = 1.0,
) -> np.ndarray:
    """Draw white circles at alt/az positions; radius and alpha depend on cloud amount."""
```

Steps:
1. Create empty `(H, W, 4)` uint8 array.
2. For each grid cell with `amount > threshold`:
   - Convert `(alt, az)` to screen `(x, y)` using the current azimuthal-equidistant projection centered on `(center_alt, center_az)`.
   - Compute `radius = base_radius + amount * (max_radius - base_radius)`.
   - Compute `alpha = amount * 255 * opacity_scale`.
   - Draw a filled circle (or gaussian splat) at `(x, y)` with accumulated alpha.
3. Clip to the visible disc using existing `disc_mask` logic.
4. Return RGBA.

**Circle drawing implementation options**:
- Pure NumPy with precomputed circle stencil: fastest, no Qt dependency.
- Use `skimage.draw.disk` or OpenCV if available; but keep dependency-light.
- For soft edges, use a radial alpha falloff `exp(-r^2 / sigma^2)` (gaussian splat), which naturally blends overlapping circles.

### Cache design

Cache key should be independent of camera parameters so the same grid serves all views.

```python
@dataclass(frozen=True)
class CloudAltAzCacheKey:
    observer_lat_deg: float  # rounded to e.g. 0.01°
    observer_lon_deg: float  # rounded to e.g. 0.01°
    satellite: str
    timeslot_utc: datetime
    shells_km: tuple[float, ...]
    grid_resolution_deg: float
    source_hash: str  # hash of source data paths / checksum
```

Cache location: under `cache_root() / "altaz_grids" / <key_hash>.npz`.

Storage:
- `amount`: float32 array
- `missing`: uint8 mask
- `meta`: JSON string with satellite, product, time_utc, coverage_ratio

### Rendering pipeline options after MVP

1. **Gaussian splats**: replace circles with soft gaussian blobs; naturally handles overlap and gives a "night light" glow.
2. **Stripe field**: sample the alt/az grid into screen-space stripes whose width/alpha follows the amount; similar to existing stripe renderer but using the grid as input.
3. **MIP level-of-detail**: build a small pyramid of grids so zoomed-out views can render cheaply.

### Risks and open questions

- **Resolution vs. memory**: 720×90 float32 = ~250 KB per grid; negligible. Even 1440×180 = ~1 MB.
- **Angular wrapping at az=0/360**: must handle cells near 0° carefully when converting to screen coordinates and when smoothing.
- **Zenith singularity**: high-altitude cells project to small areas; may need variable bin size or higher resolution near zenith.
- **BT threshold stability**: the current `bt_warm`/`bt_cold` estimation depends on the view region. With alt/az grid, the same thresholds apply to the whole grid, which is acceptable but should be documented.
- **Backward compatibility**: CLI export and existing tests use `render_from_source_with_coverage`. Keep it; the new path can be opt-in via flag or GUI toggle initially.
- **Missing-data tint**: the grid `missing` mask must be re-projected to screen using the same alt/az → screen transform, not the old lat/lon mask.
