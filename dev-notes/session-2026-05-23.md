- Topic: GUI launcher profile separation

  - Notes: Added a Reset button requirement for the startup dialog so the GUI profile can be returned to defaults without touching the shared legacy config.

- Topic: Startup dialog tab layout
  - Decision: Organize the pre-launch settings dialog into tabs that follow the README CLI option groups, with the same group order.
  - Rationale: Matching the existing documentation structure reduces cognitive load and keeps the dialog aligned with the option taxonomy users already see in the README.

- Topic: GUI launcher implementation
  - Decision: Add `gui-launch-profile.json`, a tabbed startup dialog, and a `zstarview-gui` launch path that keeps its profile separate from `config.json`.
  - Rationale: This lets the new launcher remember nearly all startup values without changing the legacy persistence used by `zstarview` and `zstarview-export-image`.
  - Notes: Wired the GUI launcher through `viewer.py`, injected separate city/geometry persistence callbacks, and added targeted tests for profile round-tripping and launch-argument conversion.

- Topic: Startup dialog city auto-fill
  - Decision: Add an `Auto` button beside the `City` field and resolve it through the same auto-location path used by GUI `auto`, then write the resolved display name back into the field.
  - Rationale: This gives the startup dialog the same convenience as the main GUI while keeping the resolution logic in one place and avoiding a separate persistence path.
  - Notes: Ran the location resolution asynchronously through the GUI worker helper and added a regression test for button-driven city fill.

- Topic: Startup dialog time-mode split
  - Decision: Move launch-time controls into a dedicated `Time` tab and treat relative shift (`Hours` / `Days`) and absolute time (`Date/time` / `Timezone`) as mutually exclusive.
  - Rationale: Splitting the time controls makes the precedence rules easier to see, and validating the combination early avoids a later CLI-style launch error.
  - Notes: Added dialog validation and regression coverage for the conflict cases. The location tab was renamed to `Location`, and the `Time` tab now shows `Time shift` / `Absolute time` headings to make the two modes visually distinct.
  - Update: Replaced the headings with explicit checkboxes for each mode and made the inactive group's widgets disable when the other mode is selected.
  - Update: Allowed both mode checkboxes to remain off by default so the dialog can represent "no time override" directly.

- Topic: Startup location and view split
  - Decision: Split `View center` and `FOV` into their own `View` tab and make `City` mutually exclusive with the `Place query` fields.
  - Rationale: The location source and the view framing are separate concepts, and separating them makes the prelaunch dialog easier to understand while keeping the location lookup rules explicit.
  - Notes: `Place` mode now requires `Place query`; `City` keeps the existing auto-location behavior.
  - Update: `Location` now defaults to the `City` mode, while `View` carries the center/FOV controls separately from location source selection.

- Topic: Startup search tab guidance
  - Decision: Rename `Search Objects at Startup` to `Search Objects` and add a note explaining that fixed `Location` Alt/Az can leave startup search targets outside the visible area.
  - Rationale: The shorter tab name reads more naturally, and the warning matches the existing search-jump behavior where fixed view-center coordinates can prevent the target from being centered automatically.
  - Notes: Recommended leaving Alt/Az at their defaults when the user wants the startup search target centered on screen.

- Topic: Remove startup search tab
  - Decision: Remove search input from the startup dialog entirely.
  - Rationale: Search is interactive by nature, so prelaunch static input creates a misleading affordance and cannot capture the full search workflow.
  - Notes: Restored the dialog to the five-tab layout and kept search behavior in the in-app interactive flow only.

- Topic: GUI launcher blank-field normalization
  - Decision: Normalize empty optional text fields such as `place` to `None` before mapping the startup dialog profile back onto CLI-style arguments.
  - Rationale: Leaving blank optional fields as empty strings caused the launch resolver to treat them as explicit queries, which broke the normal city launch path when `City` was filled but `Place` remained blank.
  - Notes: Added a regression test that confirms `place=""` becomes `None` while `city` remains intact.
