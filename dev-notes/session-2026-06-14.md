# Session 2026-06-14

- Scope: Investigate a Windows-friendly GUI launcher that keeps a terminal attached and emits startup logs for `zstarview`.
- Topic: Windows diagnostic launcher for GUI startup
  - Decision: Prefer a separate console-subsystem launcher, likely `zstarview-debug`, rather than changing the existing GUI launchers' subsystem behavior.
  - Rationale: `setup_root_logger()` already writes to `stderr` and a file; the missing piece on Windows is console attachment, not log formatting. A separate launcher preserves the current silent GUI behavior for normal users while giving Windows troubleshooting a terminal-visible path.
  - Follow-up: Document the new launcher in `docs/specification.md` and `docs/design/*.md` if we decide to implement it; keep the existing startup overlay and file log paths unchanged.
- Summary:
  - Added `zstarview-debug` as a console-script alias of `zstarview.gui.viewer:main` in `pyproject.toml`.
  - Updated README, specification, and design docs to describe the diagnostic launcher and its Windows terminal-visible behavior.
  - Moved the specification entry from section 7 to section 10 so it sits with startup-error and status-display behavior.
  - No runtime tests were needed for this packaging/docs-only change.
- Topic: Investigate Windows `overturemaps` download failure
  - Decision: Treat the failure as an external `overturemaps` CLI encoding bug on Windows, not a `zstarview` runtime bug.
  - Rationale: The traceback shows `UnicodeEncodeError: 'cp932' codec can't encode character ...` inside `overturemaps` while writing GeoJSON output. `zstarview` only sees the child process exit code and reports `overturemaps download failed with return code 1`.
  - Follow-up: If we want to harden this path, the likely fix is to force UTF-8 for the child process or wrap the download command in a Windows-safe launcher, but that is a separate implementation decision.
- Topic: Force UTF-8 for `overturemaps` child processes
  - Decision: Inject `PYTHONUTF8=1` into the environment used for `overturemaps` subprocess launches.
  - Rationale: This is the smallest targeted change that makes Python-based `overturemaps` more likely to write GeoJSON using UTF-8 on Windows without changing the surrounding cache/merge logic.
  - Risk: This does not eliminate all Windows failures; it only addresses the specific default-encoding failure mode observed in the traceback.
