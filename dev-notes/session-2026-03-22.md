  - Decision: Keep the session note at the requirements-discussion level for now: direct coordinate input may expand beyond `lat;lon` to include Google Maps-derived forms, but the accepted prefixes, suffix handling, timezone behavior, and interaction with `--observer-height-m` still need to be fixed in the written spec before code changes are finalized.

- Topic: Document the planned direct-coordinate URL grammar on `dev`
  - Decision: Wrote the target behavior into `docs/specification.md` and the matching README section: `lat;lon` remains supported, new direct forms are `@lat,lon` and selected Google Maps `/maps/@lat,lon...` URLs under `maps.google.com/`, `www.google.com/maps/`, or `google.com/maps/` with optional `https://`.
  - Rationale: Restricting the accepted URL family keeps parsing predictable, avoids the ambiguity of bare `lat,lon`, and makes it explicit that Google Maps trailing zoom or camera metadata is ignored.

- Topic: Align timezone and observer-height rules across direct coordinate forms
  - Decision: Specified that `lat;lon`, `@lat,lon`, and accepted Google Maps URLs should all resolve timezone the same way as `--place`, with a planned `--timezone` override taking precedence; observer height remains controlled only by `--observer-height-m`.
  - Rationale: Input syntax should not silently change how local time is chosen, and Google Maps camera metadata should not be mistaken for physical observer height.

- Topic: Implement direct coordinate parsing for `@lat,lon` and Google Maps URLs
  - Decision: Added a shared direct-coordinate parser in `startup.py` that accepts existing `lat;lon`, new `@lat,lon`, and restricted Google Maps `/maps/@lat,lon...` URLs from `maps.google.com`, `www.google.com/maps/`, and `google.com/maps/`, with optional `https://`.
  - Rationale: Keeping all direct-coordinate forms in one parser preserves consistent validation and avoids scattering URL-specific parsing across CLI or viewer setup code.

- Topic: Use resolved location timezones by default for direct coordinates
  - Decision: Changed direct coordinate input to resolve timezone from the nearest GeoNames city, matching `--place`, and added a new `--timezone` override that feeds both on-screen timezone display and `--datetime` parsing when the datetime string omits an explicit timezone.
  - Rationale: Users expect pasted coordinates and pasted map URLs to behave like place lookups for local time, while still needing an explicit override for edge cases and alternate viewing contexts.

- Topic: Narrow Google Maps host matching and prefer place-pin coordinates
  - Decision: Refined the Google Maps parser to accept only `maps.google.com/` and `www.google.com/maps/` shared URLs, prefer `!3dLAT!4dLON` when present, and fall back to `@LAT,LON` only when the explicit pin coordinates are absent.
  - Rationale: Real shared `place/...` URLs often contain both a viewport center and a place pin, and the pin coordinates better match user intent. Dropping the broader `google.com/maps/` host also keeps the accepted URL family closer to the currently observed shared-link patterns.
