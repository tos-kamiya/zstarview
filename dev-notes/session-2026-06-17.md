# Session 2026-06-17

Scope: night-light street-light rendering design update.

- Topic: Street-light overlay should move from band polygons to discrete ray-sampled columns.
  - Decision: Treat each sampled night-light tile pixel as a vertical column with fixed height, no horizontal expansion, and height-only attenuation. Use 1 km ray-sample spacing for the initial trial, and apply log compression before accumulation.
  - Rationale: The current band approach looks like a flat board from tall viewpoints. A ray-sampled column model reuses the existing NASA tile data directly, keeps the trial implementation simple, and makes it easier to judge whether the new shape reads better before adding more sophistication.
  - Alternatives Considered: Keep the existing band polygons; add lateral blur or interpolation; use a more physically motivated volume model. These were deferred because they add complexity without helping the initial visual comparison.

- Topic: Documentation updates for the glow pipeline.
  - Decision: Record the new street-light approach in `docs/design.md` and `docs/design/glow-mask.md`, while keeping ridge glow conceptually separate.
  - Rationale: The design docs should reflect the intended direction before implementation so that the later code change can be aligned with the agreed rendering model.

- Topic: Return to band polygons for street-light glow.
  - Decision: Abandon the thin-column rendering for the street-light overlay and draw a 2-degree azimuth band polygon again, keeping the 1 km ray sampling for brightness estimation.
  - Rationale: The column look remained too pronounced. A filled band preserves the brightness sampling model while restoring a continuous silhouette.

## Summary

- Confirmed the street-light overlay will be changed only, not ridge glow.
- Fixed the trial parameters to 1 km spacing, fixed column height, height attenuation, and log compression.
- Switched the street-light silhouette back to a filled band polygon with 2-degree azimuth spacing and no interpolation.
- Next step is implementation planning and then code changes.
- Validation: `pytest tests/test_night_lights.py tests/test_glow_mask.py` and `ruff check src/zstarview/render/night_lights.py src/zstarview/night_lights.py tests/test_night_lights.py` passed after the revert.

- Topic: Implement ray-sampled GlowMask night lights
  - Decision: Replace the GlowMask night-light path with a direct inverse-projection rasterizer that interpolates the night-light profile on azimuth, uses the terrain horizon or profile horizon as the floor, and applies a fixed-height vertical decay in low-resolution alpha space.
  - Rationale: This matches the GlowMask design better than reusing the legacy band renderer, removes the experimental drawing path from the compositor, and produces a continuous alpha field instead of layered vector bands.
  - Alternatives Considered: Keep the legacy glow drawing in the GlowMask path and smooth it afterward. That would be less invasive, but it would preserve the old banded shape and would not reflect the intended ray-sampled model.
  - Validation: `uv run -p .venv/bin/python pytest tests/test_glow_mask.py tests/test_night_lights.py -q`

- Topic: Add azimuth-wise floor to the ray-sampled glow
  - Decision: Lift each azimuth sample with a small per-az floor before height decay so the glow can approximate ridge glow without a separate ridge pass.
  - Rationale: A local floor keeps the street-light profile shape, but prevents deep valleys in the sampled profile from collapsing to zero. This is the smallest change that can emulate the requested glow lift while preserving the ray-sampled model.

- Topic: Remove the hard horizon gate from the ray-sampled glow
  - Decision: Replace the binary `above_horizon > 0` cutoff with a soft falloff around the horizon so the glow no longer reads like it is clipped by the main ridge.
  - Rationale: The screenshot feedback indicated the glow still looked masked by the main ridge. A soft falloff keeps the ray-sampled model while allowing a ridge-like lift to bleed below the horizon instead of stopping abruptly.

- Topic: Simulate ridge glow as a post-scan offset
  - Decision: Add a small constant to the 128 km scan result in `night_lights.py` instead of using an azimuth-wise floor in the compositor.
  - Rationale: This keeps the ridge-glow approximation in the profile-generation step, which matches the idea of "scan first, then lift" and avoids baking a second floor model into the display path.

- Topic: Split ridge masking between street lights and ridge glow
  - Decision: Use cumulative secondary-ridge altitude for the street-light ray mask, and keep ridge glow on the main ridge only.
  - Rationale: The street-light simulation should be occluded by nearer secondary ridges encountered along the ray, while ridge glow should remain anchored to the main horizon silhouette.
