- Topic: Offline mode (`--offline`)
  - Decision: Add `--offline` to `zstarview` and `zstarview-export-image`,
    and an `Offline` checkbox to the startup dialog. Centralize it in
    `zstarview/offline.py`: the state is `ZSTARVIEW_OFFLINE=1` so worker
    subprocesses inherit it, and `zstarview/__init__.py` installs the guard
    at import time.
  - Decision: Install a socket-level guard (getaddrinfo / connect /
    connect_ex, loopback allowed) that raises `OfflineError(OSError)`, and
    add explicit skips at the main entry points to avoid warning/retry
    spam. Long-lived data keeps using the existing stale-cache fallbacks.
  - Decision (user): short-lived layers are off in offline mode: aircraft,
    satellites (incl. JPL/satellite search), forecast precipitation,
    satellite clouds, tropical cyclones, GMN meteor trails, Moon/Sun hover
    images. Long-lived (cache if present): terrain, urban outline, night
    lights, road lights, water, ground elevation. Entry points: viewer,
    export-image, startup dialog.
  - Rationale: A guard at the socket layer also stops library-internal
    downloads (Skyfield, astropy IERS) and fetch sites that might be
    missed; `OSError` makes the existing cache fallbacks apply unchanged.
    The explicit skips keep logs quiet and avoid side effects such as the
    Overture release check recording a failed check.
  - Alternatives Considered: Extending replay's `LocationDataPolicy` to
    all layers. It only covers location resolution and would need a new
    hook in every controller and subprocess payload; kept separate.
  - Finding: with IERS auto-download off, astropy raised because the
    bundled IERS-A predictions were older than `auto_max_age` (30 days).
    Offline mode sets `auto_max_age = None` and
    `iers_degraded_accuracy = "warn"`.
  - Validation: `zstarview-export-image --offline Tokyo` saved an image with
    cached terrain/urban/water; a location with partial cache skipped
    urban/road/water and still saved (exit 0). `zstarview --offline` ran
    60 s offscreen without errors; the Open-Meteo dialog did not appear
    with `-P 0.4`.
  - Follow-up decision: In offline mode, `fetch_copernicus_dem` no longer
    attempts tile downloads. Cached tiles are used even past TTL, missing
    tiles are skipped silently, and one INFO summary line replaces the
    per-tile "DEM refresh failed" / "DEM tile unavailable" warnings. With
    no cached tile at all it raises a RuntimeError that mentions offline.
