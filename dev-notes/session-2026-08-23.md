  - Decision: Remove unsupported `score` and `gaia_astrometric_params` fields from `hipparcos2_best_neighbour`; obtain astrometric solution information from `gaia_source.astrometric_params_solved` instead.
  - Rationale: In Gaia DR3, `score` belongs to neighbourhood data rather than the best-neighbour table, and the Gaia astrometric solution field is represented by the DR3 bitmask values (3 for two-parameter, 31/95 for five/six-parameter solutions). The original query was rejected with HTTP 400.
  - Validation: Query and script compile successfully. HTTP error handling now preserves the TAP response detail for future query failures.

- Topic: Interpretation of unmatched bright stars
  - Decision: Interpret an unmatched HIP ID as “no row in the Gaia DR3 Hipparcos-2 best-neighbour table,” not as proof that the source is absent from `gaia_source`.
  - Rationale: Gaia DR3 documents a bright limit near G=3 and saturation-related limitations; the official cross-match and main source catalogue have different completeness and processing behavior. Sirius-like cases therefore require a direct Gaia position query before claiming that Gaia has no source.
  - Follow-up: Keep Hipparcos as the authoritative fallback for feature-critical bright stars, and separately test direct Gaia `gaia_source` positional candidates where useful.

- Topic: Gaia faint-star sky bitmap prototype
  - Decision: Add `raw-data/gaia-dr3-sky-bitmap/generate_gaia_sky_bitmap.py` for small-area Gaia TAP sampling and PNG inspection output.
  - Rationale: Validate the visual treatment before designing 4K tiled assets. The renderer accumulates sub-pixel stars and overlapping stars in float32 linear RGB, maps `BP-RP` directly to an approximate RGB colour, and applies tone mapping only when writing the PNG.
  - Validation: CLI help and compilation passed; a synthetic five-star CSV produced a 640x640 PNG. Live Gaia sampling was not completed in this environment because the network resolver was unavailable to the Python process.

- Topic: Bitmap prototype visual tuning
  - Decision: Reduce default point-spread sigma from `0.45` to `0.25` pixels, reduce gain from `0.45` to `0.18`, and strengthen the BP-RP colour palette.
  - Rationale: The first real 10-degree sample appeared as oversized, mostly grey one-pixel points. A smaller kernel and lower gain better preserve sub-pixel faint-star character, while a stronger palette keeps colour visible after 8-bit PNG conversion.
  - Validation: Re-rendered the real 10-degree sample containing 36,715 Gaia rows.

- Topic: ESA-style integrated sky map
  - Decision: Change PNG tone mapping from per-channel exponential compression to per-pixel integrated luminance compression with `asinh`, chromaticity preservation, and configurable saturation.
  - Rationale: The ESA reference image is a total brightness-and-colour map, not a collection of individually visible star dots. The faint-star prototype must accumulate flux first and use a much fainter upper magnitude limit before it can show dense Galactic structure.
  - Validation: Script compilation passed and the existing sample was re-rendered. The README now uses a 1-degree, `G=10.5..20.7` example for the integrated-map prototype.

- Topic: Gaia faint-region TAP failures
  - Decision: Automatically subdivide a region into four child queries after a TAP HTTP 500 or a result reaching `MAXREC`, then merge the CSV rows.
  - Rationale: A 1-degree region through `G=20.7` can exceed the archive service's query execution or result limits even though the region is visually small. Subdivision keeps the prototype usable without requiring manual query planning.
  - Validation: Existing-CSV rendering and Python compilation passed; live retry against the service remains user-side because the execution environment cannot reliably resolve the Gaia TAP host from Python.

- Topic: Bitmap generation progress reporting
  - Decision: Add a dependency-free terminal progress bar for the star rasterization loop.
  - Rationale: High-density Gaia regions can contain many rows and take noticeable time to splat into the bitmap. Progress is written to stderr so the existing result messages remain clean.
  - Validation: Compilation passed and a 36,715-row sample rendered with 0-100% progress output.
