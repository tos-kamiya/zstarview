# Session 2026-07-10

Scope: Rebuild object-viewer background separation from `df74f0f8`.

- Topic: Split scenic and object-viewer CLI arguments
  - Decision: Keep location, time, search, star, and overlay arguments in shared parser helpers, while registering sky-disc and night-light arguments only for the scenic viewer.
  - Rationale: The object viewer has a deliberately different presentation and should not expose controls for layers it disables. Its `-V` default and maximum are passed as parser configuration rather than hidden post-parse mutations.

- Topic: Object-viewer background isolation
  - Decision: Give the instrument presentation its own solid-background renderer instead of reusing the scenic radial background / window-border helper.
  - Rationale: The object viewer is intentionally flat and opaque, while scenic `zstarview` keeps theme-dependent chrome and gradients. Separate background code prevents object-viewer changes from leaking into scenic themes.

- Topic: Window border responsibility
  - Decision: Remove the theme-level outer-border flag and always draw the scenic window frame in `draw_window_border()`.
  - Rationale: Whether the frame is present is a presentation decision, not a theme decision. The theme should carry border color and chrome colors, while object-viewer uses its own rendering path to omit the frame entirely.

- Verification: `tests/test_object_viewer_profile.py` and `tests/test_viewer_startup_errors.py` passed (`10 passed`); Ruff and `git diff --check` passed. The full suite has two pre-existing failures in launch-profile JSON serialization and the theme error-message expectation.

- Topic: Object-viewer satellite color
  - Decision: Use the object-viewer aircraft red-purple style for artificial satellites, including outline and label colors, while leaving the default/night theme unchanged.
  - Rationale: The object viewer uses marker shape to distinguish aircraft from satellites, so a shared high-contrast hue improves visual grouping without affecting `zstarview`.

- Topic: Object-viewer reference guides
  - Decision: Add a theme-scoped guide style for the object viewer: black, thin, simple lines for the horizon, direction labels, celestial equator, ecliptic, and zenith/pole markers.
  - Rationale: Guide projection and clipping remain shared, while the presentation-specific stroke policy is isolated from the scenic viewer's colored layered guides.

- Topic: Object-viewer guide visibility
  - Decision: Enable guideline overlays by default in the object-viewer profile.
  - Rationale: The requested reference lines must remain visible independently of the scenic viewer's saved guideline preference; explicit CLI or GUI profile overrides remain respected.

- Topic: Object-viewer guide rendering path
  - Decision: Add a dedicated instrument guide-layer routine that draws reference lines before the shared guide annotations.
  - Rationale: The instrument presentation previously drew direction annotations but never called the celestial reference-line renderer, so horizontal/equator/ecliptic lines could not appear regardless of opacity.

- Topic: Object-viewer permanent alt/az grid
  - Decision: Draw the direction grid unconditionally within the instrument guide layer when guidelines are enabled, using the object-viewer guide color.
  - Rationale: The scenic viewer's hover-triggered grid behavior is not useful for the object viewer's instrument-reading purpose; keeping the call in the instrument-specific path avoids changing scenic behavior.

- Topic: Object-viewer ecliptic line
  - Decision: Render only the object-viewer ecliptic as a thin black dotted line; keep the horizon and celestial equator solid.
  - Rationale: The dotted ecliptic remains distinguishable from the other reference guides without changing the scenic viewer's established dash pattern.

- Topic: Object-viewer below-horizon tint
  - Decision: Apply a default 0.15 gray tint below the terrain horizon in the instrument presentation.
  - Rationale: The initial 0.08 alpha produced an almost indistinguishable result over white; 0.15 remains subtle while making the below-horizon region visibly distinct. The existing compositor tint is not used by the instrument path, so the terrain profile is projected and filled directly before guides and scene objects; scenic rendering remains unchanged.
