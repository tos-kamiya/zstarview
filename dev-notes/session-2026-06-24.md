# Session 2026-06-24

## Scope

Add a top-left resize grip to frameless windows, mirroring the existing
bottom-right grip.

## Design Decisions

- Topic: Top-left resize grip for frameless windows
  - Decision: Reuse `ResizeGripWidget` with a new `top_left` keyword
    argument. When `top_left=True`, the widget uses
    `Qt.Edge.TopEdge | Qt.Edge.LeftEdge` for system resize and adjusts
    both position and size in the manual fallback. The grip marker is
    mirrored to the top-left corner of the widget.
  - Rationale: Both top-left and bottom-right corners use the same
    `SizeFDiagCursor` (the diagonal runs from top-left to bottom-right),
    so the cursor shape is shared. Keeping a single class avoids code
    duplication; only the edge selection, resize math, and marker
    orientation differ.
  - Alternatives Considered: A separate `TopLeftResizeGripWidget` class
    was considered but rejected because the shared logic (drag state,
    system resize initiation, paint event) is identical — only the edge
    flags and resize arithmetic differ, which are cleanly parameterized.

- Topic: Manual resize math for top-left corner
  - Decision: `new_width = start_width - delta.x`,
    `new_height = start_height - delta.y`, clamped to minimum size.
    Position is set via `setGeometry` with
    `new_x = start_x + (start_width - new_width)`,
    `new_y = start_y + (start_height - new_height)`.
  - Rationale: This keeps the bottom-right corner fixed while the
    top-left corner follows the mouse. The position adjustment uses
    the clamped size delta (not the raw mouse delta) so the window
    stays put once it hits minimum size.

## Update: Top-left grip move-then-resize behavior

- Topic: Interaction behavior for the top-left resize grip
  - Decision: The top-left grip now behaves like a normal window drag
    handle while the mouse button is held: the whole window follows the
    mouse exactly like dragging any other point. The actual resize
    (anchored at the bottom-right corner) is applied only when the
    button is released.
  - Rationale: The user wanted the top-left grip to provide the same
    visual feedback as dragging the window, then resize in one shot on
    release. This avoids the jarring "content stays put while the window
    frame shrinks" effect during the drag.
  - Implementation: `ResizeGripWidget` gained `_begin_top_left_move_resize`
    and `_finish_top_left_move_resize`. On press it calls the owner's
    drag path via new `DraggableWindow.begin_drag_from_child` and stores
    the initial geometry. On move it forwards events to
    `DraggableWindow._update_drag` so the window moves. On release it
    computes the delta from the initial press and calls `setGeometry` to
    keep the bottom-right corner fixed, then clears the owner's drag
    state via `DraggableWindow.clear_drag_state`.
  - Alternatives Considered: Removing the grip from drag exclusions and
    letting the main window's event filter handle it. Rejected because
    mouse events are delivered to the widget under the cursor and do not
    bubble automatically, so explicit delegation from the grip is more
    reliable.

- Topic: Test coverage for the new grip behavior
  - Decision: Added `tests/test_resize_grip.py` with tests for the
    top-left move-then-resize behavior, minimum-size clamping, and a
    regression test for the bottom-right grip.
  - Rationale: There were no existing tests for `ResizeGripWidget` drag
    behavior. The new tests use a `DraggableWindow` with
    `FramelessWindowHint` under the offscreen platform to avoid display
    dependencies.


- Cleanup: Removed now-unused top-left resize logic from
  `_start_system_resize`, `_begin_manual_resize`, and `_update_manual_resize`
  since the top-left grip no longer follows the resize-during-drag path.


- Fix: Top-left grip now starts moving immediately on press
  - Problem: The initial implementation forwarded top-left grip move events
    to `DraggableWindow._update_drag`, which waits for the generic drag
    threshold (`QApplication.startDragDistance()`, typically 10 px). While
    waiting, the grip fell back to `_update_manual_resize` and incorrectly
    resized the window from the bottom-right corner, making the drag feel
    interrupted or jumpy.
  - Fix: `_begin_top_left_move_resize` now calls `_owner._start_drag(event)`
    right after `begin_drag_from_child`, so the window starts moving on the
    first move event. A guard in `_update_manual_resize` prevents top-left
    from resizing during drag.
  - Added regression test `test_top_left_grip_starts_moving_immediately` that
    moves only 5 pixels and verifies the window follows without waiting for
    the threshold.

## Cloud Jellybean Rendering Mode (Design)

- Topic: New cloud stripe rendering mode "jellybean"
  - Decision: Add a third `cloud_stripe_mode` value `"jellybean"` that
    renders cloud amount as discrete rounded line segments (jellybeans)
    on a screen-fixed 2D grid. Cloud amount is linearly quantized into
    4 levels (0/1/3/5), and each grid cell with level > 0 is drawn as
    a QPainter RoundCap line segment along the 45-degree diagonal
    (u = x - y direction). Width expresses cloud amount; alpha is fixed.
  - Rationale: The existing `width` and `alpha` modes produce continuous
    stripe patterns. The jellybean mode provides a bolder, quantized
    look where cloud amount is read from segment thickness rather than
    stripe width or opacity. The grid-based approach (Δu = 6 px,
    Δv = 6 px) naturally handles segmentation, filters noise (isolated
    single-cell segments are inherently minimal), and ensures the
    thickest level (5 px) never overlaps adjacent lines (6 px spacing).
  - Key parameters:
    - Grid: screen-fixed, origin at viewport top-left, Δu = Δv = 6 px.
    - Quantization: linear in [0,1] → {0: 0–0.25, 1: 0.25–0.50,
      3: 0.50–0.75, 5: 0.75–1.00}.
    - Line widths: 0, 1, 3, 5 px (scalable via `width_factor`).
    - Sampling: cell center point → inverse project to alt/az →
      `CloudAltAzGrid.amount`.
    - Rendering: QPainter + RoundCap pen, circular clip path,
      white RGB, alpha from `hatch_cfg.strength`.
    - `CloudAltAzGrid` data is unchanged; quantization happens at
      render time in screen space.
  - Alternatives Considered:
    - Per-diagonal run extraction (like existing modes): rejected in
      favor of the grid approach, which naturally defines segment
      endpoints and spacing.
    - Numpy raster rendering: rejected; QPainter with RoundCap is
      simpler and leverages existing Qt anti-aliasing.
    - BT-temperature-based quantization: rejected; linear quantization
      in [0,1] is simpler and works for both CloudDisc and
      GeoSatellite data sources.
  - Implementation plan (not yet started):
    - Add `_render_jellybean_cloud_rgba_from_altaz_grid()` to
      `src/zstarview/gui/composite.py`.
    - Add `elif self._cloud_stripe_mode == "jellybean":` branch in
      `SkyCloudCompositor.draw()`.
    - Allow `"jellybean"` in `window_inputs.py` and CLI
      `--cloud-stripe` parsing.
  - Documented in: `docs/design/rendering-pipeline.md` §4.2a.


## Cloud Jellybean Mode Implementation

- Topic: Implement jellybean cloud stripe rendering mode
  - Decision: Implemented as designed. Added `_inverse_project_points` helper
    for batched point-to-alt/az projection and `_render_jellybean_cloud_rgba_from_altaz_grid`
    for the full rendering pipeline.
  - Files modified:
    - `src/zstarview/gui/composite.py`: Added `QPainterPath` import,
      `_inverse_project_points` (batched inverse projection for arbitrary
      screen points), `_render_jellybean_cloud_rgba_from_altaz_grid`
      (grid-based quantized rendering with QPainter RoundCap), and
      `elif` branch in `SkyCloudCompositor.draw()`.
    - `src/zstarview/cli/args.py`: Added `"jellybean"` to valid modes
      in `_parse_cloud_stripe`, with defaults `target_stripes=100`,
      `width_factor=1.0`.
    - `src/zstarview/gui/window_inputs.py`: Added
      `_normalize_cloud_stripe_mode` helper accepting `"jellybean"`.
  - Key implementation details:
    - Grid: Δu = Δv = ref_diameter / target_stripes (default 6 px at 600 px ref).
    - Cell centers are collected, batch inverse-projected to alt/az,
      batch-sampled from `CloudAltAzGrid.amount`, then quantized.
    - Quantization: linear thresholds at 0.25, 0.50, 0.75 → levels 0/1/3/5.
    - Line widths: (0, 1*wf, 3*wf, 5*wf).
    - Rendering: QPainter with `RoundCap` pen, circular clip path,
      white color with alpha from `hatch_cfg.strength`.
    - Empty result (no cells inside disc) returns zeroed RGBA array.
  - Tests: 1134 passed (no regressions).
  - Ruff: All checks passed.


- Topic: Jellybean segment length (Δu)
  - Decision: Changed Δu from 1×Δv (6 px) to 4×Δv (~24 px at default
    target_stripes=100). This makes each jellybean segment span 4 grid
    cells in the u direction, creating longer, more visible segments.
  - Rationale: At Δu = 6 px, segments were very short and the quantized
    levels were hard to distinguish visually. Longer segments make the
    level differences (1/3/5 px width) more apparent.

- Topic: Jellybean line widths scaled to 24 px max
  - Decision: Changed `level_widths` from `(0, 1*wf, 3*wf, 5*wf)` to
    `(0, 4.8*wf, 14.4*wf, 24*wf)`, scaling proportionally from the
    quantization levels (0/1/3/5) so the thickest level reaches 24 px.
  - Rationale: User requested "幅も24に太くしてください" — make line
    widths also ~24 px to match the segment length (Δu ≈ 24 px).
    Proportional scaling preserves the relative weight between levels.
  - Trade-off: At Δv = 6 px line spacing, 24 px wide lines will overlap
    adjacent rows. User accepted this for visual impact.

- Topic: Jellybean line spacing (Δv) increased to ~30 px
  - Decision: Changed default `target_stripes` for jellybean from 100 to 20,
    giving Δv ≈ 30 px (at 600 px ref) and Δu = 4×Δv ≈ 120 px.
  - Rationale: At Δv = 6 px with 24 px line widths, adjacent rows merged into
    a solid fill. With Δv = 30 > 24, lines are distinct stripes again.

- Topic: Jellybean line widths halved (max 12 px)
  - Decision: Changed `level_widths` from `(0, 4.8*wf, 14.4*wf, 24*wf)` to
    `(0, 2.4*wf, 7.2*wf, 12*wf)`. Halved all non-zero widths.
  - Rationale: User reported that with 24 px max width, the rendering looked
    like a solid fill rather than distinct stripes. Halving gives 18 px gap
    at Δv=30 for the thickest level, restoring the striped appearance.

- Topic: Jellybean redesign — circles + bottom-right chain connection
  - Decision: Replaced the u-direction line-segment rendering with a
    circle + chain-connection approach on a square grid (Δu = Δv).
    Each cell is drawn as a circle (diameter = quantized level: 0/2/4/6 px,
    scaled by `width_factor`). Consecutive cells with the same level
    along the bottom-right diagonal (v direction, grid index `(i, j+1)`)
    are connected into a single thick RoundCap line segment (jellybean).
  - Rationale: User requested a visual style where cloud amount is
    expressed as discrete circles that merge into jellybean shapes when
    adjacent cells share the same level. The square grid (Δu = Δv)
    provides uniform cell spacing in both diagonal directions.
  - Key changes in `_render_jellybean_cloud_rgba_from_altaz_grid()`:
    - Grid: `delta_u = delta_v = delta` (square cells, was `delta_v = 2.5*delta_u`).
    - Quantization: `level_diameters = (0, 2*wf, 4*wf, 6*wf)` (circle diameters,
      was `(0, unit*4, unit*6, unit*9)` line widths).
    - Chain extraction: `cell_level` dict → iterate j then i, follow
      `(i, j+1)` while same level → chain. Chain length ≥ 2 → line segment;
      length = 1 → isolated circle (`drawPoint` + RoundCap pen).
    - Removed: `min_gap_v`, u-direction segment gap logic.
  - Cell spacing and line thickness are adjustable via `target_stripes`
    and `width_factor` for later tuning.
  - Tests: 1134 passed (no regressions).
  - Docs: Updated `docs/design/rendering-pipeline.md` §4.2a.

- Topic: Jellybean circle diameters proportional to grid step
  - Decision: Changed `level_diameters` from fixed pixel values
    `(0, 2*wf, 4*wf, 6*wf)` to grid-step-proportional values
    `(0, 2*s, 4*s, 6*s)` where `s = delta/30 * wf`.
  - Rationale: User noted that changing `target_stripes` (grid division
    count) did not affect line thickness. Now diameters scale with the
    grid step `delta`, so denser grids (higher `target_stripes`, smaller
    `delta`) produce thinner circles/lines, and sparser grids produce
    thicker ones. Reference point: at `delta=30` px (target_stripes=20,
    ref=600 px), diameters are 2/4/6 px as before.

- Topic: Jellybean base diameters changed to 8/16/24 px
  - Decision: Changed `level_diameters` base multipliers from (2, 4, 6)
    to (8, 16, 24), giving diameters 8/16/24 px at reference delta=30 px.
  - Rationale: User requested bolder circles. At delta=30 px cell spacing,
    the 24 px max diameter will overlap adjacent cells; user accepted this
    trade-off for visual impact (consistent with earlier decisions).

- Topic: Jellybean quantization refined to 8 levels (0-7)
  - Decision: Changed from 4-level (0-3) to 8-level (0-7) quantization
    with 7 equal-interval thresholds at 1/8 steps. Diameters: 0, 4, 8,
    12, 16, 20, 24, 28 px at reference delta=30 px.
  - Rationale: User requested finer gradation ("量子化を細かくしてください").
    8 levels provide smoother visual transitions between cloud amounts.

- Topic: Jellybean level-0 threshold changed to 0.03
  - Decision: Changed the no-draw threshold from `amount < 0.125` (1/8)
    to `amount < 0.03`, matching the width-style "present" floor.
    Quantization now applies to [0.03, 1.0] divided into 7 equal
    intervals for levels 1-7.
  - Rationale: User noted visual discrepancy between width and jellybean
    styles at low cloud amounts. Aligning the floor threshold makes the
    two styles consistent in what they consider "no cloud."

- Topic: Jellybean nonlinear quantization (1.4⁻ⁱ thresholds)
  - Decision: Replaced linear equal-interval thresholds with nonlinear
    `1.4 ** -i` thresholds (i=7..1). Level 0: [0, 0.095), level 1:
    [0.095, 0.133), ..., level 7: [0.714, 1.0].
  - Rationale: User noted cloud lines were too prominent. The nonlinear
    scale suppresses low-amount noise (wider level-0 band) and spreads
    high amounts across more levels for finer gradation where it matters.

- Topic: Jellybean percentile normalization
  - Decision: Added percentile normalization (12%ile / 92%ile of non-zero
    cell amounts) before quantization, matching the width-style approach.
  - Rationale: User observed that jellybean amplified low cloud amounts
    compared to width style. The root cause was that width style adapts
    to the data range via normalization while jellybean used absolute
    thresholds. With normalization, both styles now scale their visual
    output to the actual cloud amount distribution in the scene.

- Topic: Jellybean diameter scaled by 1/√2 for perpendicular gap
  - Decision: Added `math.sqrt(2.0)` divisor to `diam_scale`, so
    diameters are proportional to the perpendicular distance between
    parallel chains (`delta / √2`) rather than the axis-aligned grid
    step `delta`.
  - Rationale: User observed that the thickest chains (level 7, 28 px)
    touched adjacent parallel chains with no gap. The perpendicular
    distance between chains is `delta / √2 ≈ 21.2 px` (at delta=30),
    so 28 px lines overlap. With the √2 factor, max diameter becomes
    ~19.8 px, leaving a ~1.4 px gap at the thickest level.
