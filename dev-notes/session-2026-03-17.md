- Topic: Overture urban outline detail for towers
  - Decision: Inspect the importer and outline-generation pipeline before proposing a data-source change.
  - Rationale: The Skytree appearing circular could come from either the upstream Overture geometry or an app-side simplification step; the code path needed to be checked first.

- Topic: Combine building and building_part for urban outlines
  - Decision: Change the app runtime default to `both`, meaning cached `building` and `building_part` datasets are loaded together, while `--urban-outline-feature-type building` remains available as an override.
  - Rationale: `building` and `building_part` are complementary in Overture. Treating them as separate caches and preferring `building_part` over its parent `building` preserves broad coverage without losing finer tower/building sub-footprints where parts exist.

- Topic: Verify urban outline spec/design against implementation
  - Decision: Confirm that the current docs and runtime are aligned around Overture Maps derived building caches, `both` mode by default, and parent-building suppression when `building_part` data exists.
  - Rationale: The app-side pipeline now consistently downloads `building` and `building_part` separately when needed, merges them at runtime, and converts them to height-aware outline polylines without reapplying a runtime height filter.

- Topic: Compare Overture download volume across radii
