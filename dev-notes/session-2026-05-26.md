# 2026-05-26
Scope: evaluate temporal suppression for Geo-satellite color-image cloud proxies using 3 local PNG frames.

- Topic: Temporal overlay suppression for Geo-satellite proxy
  - Decision: Add a separate `dev-samples` script that combines 3 frames, estimates static overlays from RGB consistency, and dampens those regions before producing the grayscale proxy.
  - Rationale: Persistent map overlays such as coastlines and borders are much easier to identify by temporal stability than by color alone. Keeping this outside `zstarview` preserves the exploratory workflow and avoids coupling the heuristic to the main app.
  - Alternatives Considered: Editing the earlier single-frame proxy script in place. Rejected because the single-frame workflow is still useful for quick experiments and should remain simple.

- Topic: Static RGB mask extraction
  - Decision: Replace the 3-frame exact-RGB/background-residual mask with a general multi-image mask that keeps only pixels that are gray-ish and not too white in every frame.
  - Rationale: The user wants to remove blue sea, green land, and over-bright clouds up front, then intersect the remaining gray-like pixels across multiple images to isolate boundary-like structure.
  - Alternatives Considered: Keeping the local-background residual detector. Rejected because the new requirement is to filter by color class first, then intersect across many frames.

- Topic: Current Geo-satellite processing split
  - Decision: Keep `geo_satellite_cloud_proxy.py` as the single-frame cloud-likelihood path and `geo_satellite_gray_common_mask.py` as the multi-frame boundary-mask path.
  - Rationale: The first script is the exploratory cloud proxy for a single color frame, while the second script now represents the shared gray-like structure across multiple frames and is the better fit for line-art extraction.
  - Alternatives Considered: Folding both behaviors into one script. Rejected because the two workflows now serve different purposes and should stay independently runnable.

- Topic: Geo-satellite sample index
  - Decision: Add a dedicated `dev-samples/geo-satellite-index.md` page and link it from `dev-samples/README.md`.
  - Rationale: The Geo-satellite helpers now cover both cloud proxy and projection/mapping experiments, so a compact index makes the inputs and outputs easier to scan than a single long README section.
  - Alternatives Considered: Keeping the list only in `dev-samples/README.md`. Rejected because the collection has grown enough to justify a dedicated index page.

- Topic: Cloud mask fill experiment
  - Decision: Add a standalone `geo_satellite_cloud_inpaint.py` helper that fills white mask regions in a grayscale cloud image by propagating nearby values inward.
  - Rationale: The current workflow now has a natural second stage after proxy and boundary-mask extraction: keep the cloud image, apply the gray-common mask as holes, and reconstruct the masked line-art regions from neighboring cloud pixels.
  - Alternatives Considered: Baking the fill step into the proxy or mask scripts. Rejected because the steps are easier to reason about and reuse when kept separate.

- Topic: Cloudimage projection from the Europe workflow
  - Decision: Add `geo_satellite_cloudimage.py` as a view-dependent projection step that takes the inpainted grayscale cloud image plus an observer `@lat,lon`, `alt`, `az`, `fov`, and the fitted Europe grid `.npz`.
  - Rationale: This mirrors the `zstarview.cloudimage` command shape while using the Europe image geometry that was inferred earlier in the session. Keeping the source image, the fitted grid, and the observer parameters explicit makes the transformation easier to reason about.
  - Alternatives Considered: Reusing the core `CloudDisc` pipeline directly. Rejected because this workflow needs to project a user-supplied Europe cloud image, not refetch satellite data.

- Topic: Cloud height CLI naming
  - Decision: Rename the cloud-shell argument to `--cloud-height-km` and interpret it as height above the Earth's surface, converting it to a shell radius internally.
  - Rationale: The new name matches user expectations better and avoids exposing the radius arithmetic at the CLI boundary. The internal projection math still needs a shell radius, so the script now adds the Earth radius before calling the geometry helper.
  - Alternatives Considered: Keeping `--cloud-shell-km`. Rejected because it hides the user-facing meaning and makes the option harder to reason about.

- Topic: Europe-band input validation for cloudimage
  - Decision: Reject observer locations outside the Europe workflow band (`32N` to `73N`, `15W` to `35E`) before rendering.
  - Rationale: The current Europe cloud image is only meant to be used within the geographic span that the fitted grid and the downstream proxy pipeline can plausibly represent. Failing fast avoids misleading all-black outputs and makes the CLI contract explicit.
  - Alternatives Considered: Letting the renderer run and returning a black image for out-of-band observers. Rejected because it hides invalid input behind a visually ambiguous result.

- Topic: Keep cloudimage validation in dev-samples only
  - Decision: Remove the pytest file for `geo_satellite_cloudimage.py` and keep the validation as a `dev-samples`-level check rather than a core test.
  - Rationale: The whole Geo-satellite pipeline here is exploratory. Keeping the validation close to `dev-samples` better matches the role of these scripts and avoids making them look like application-test surface.
  - Alternatives Considered: Retaining a `tests/` regression test. Rejected because it suggests the script is part of the main test surface when it is still a workflow helper.

- Topic: Europe/GOES split rule
  - Decision: Document the Europe-side responsibility band as roughly latitudes `32N` to `73N` and longitudes `15W` to `35E`, with cloud candidates clipped at `alt >= 3.0°`.
  - Rationale: The visual overlap between the Europe image and GOES is easiest to manage in geographic coordinates rather than image-space splits, and the 3-degree cutoff keeps the cloud-side footprint closer to the region we want to trust.
  - Alternatives Considered: Extending the lower latitude boundary to `25N`. Rejected because it collides with the embedded text and starts to pull in too much southern territory.
