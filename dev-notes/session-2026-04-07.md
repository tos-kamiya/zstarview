# Session 2026-04-07

- Scope: Refactor sky window rendering so the current frameless presentation becomes a reusable client-area component, and add an option to launch in a standard decorated window.

- Topic: Share the same sky-view client area between frameless and decorated windows
  - Decision: Keep `SkyWindow` as the `QMainWindow` host and move paint/input/resize responsibilities for the visible sky area into a dedicated central `SkyWindowClientWidget`.
  - Rationale: This preserves the existing controllers, timers, menu actions, and geometry persistence while making the rendered sky view explicitly client-area based. It also keeps the frameless drag behavior host-specific instead of mixing it into the render widget.
  - Alternatives Considered: Replacing `SkyWindow` with a pure `QWidget` and introducing a new host wrapper was possible, but it would have required wider changes to fullscreen handling, action ownership, and existing tests.

- Topic: Window decoration mode
  - Decision: Add CLI option `--window-frame {frameless,window}` with default `frameless`, and carry it through `SkyWindowRuntimeOptions`.
  - Rationale: This keeps the current default behavior unchanged while allowing a standard titled/bordered OS window when requested.

- Topic: Frameless dragging after central-widget refactor
  - Decision: Extend `DraggableWindow` so dragging can be initiated from registered drag-target widgets via an event filter.
  - Rationale: Once the sky view became a central widget, mouse events no longer naturally reached the host window. The event-filter approach keeps dragging working without coupling the client widget to host movement internals.

- Topic: Client-area geometry API cleanup
  - Decision: Stop overriding `SkyWindow.width()`, `height()`, `size()`, `rect()`, and `update()` to masquerade as client-area APIs, and replace that behavior with explicit `client_*` accessors plus `request_client_update()`.
  - Rationale: The overrides were only a temporary bridge. They would become ambiguous once a dedicated custom frame widget is introduced, because host, frame, and client sizes would diverge. Explicit client-area methods make the next refactor safer.
  - Follow-up: Convert mixin tests away from `SimpleNamespace`-only assumptions and into a small stub that explicitly implements the client-area API, then remove production fallback shims.

- Topic: Frameless chrome extraction
  - Decision: Introduce a dedicated `FramelessWindowFrame` wrapper widget that owns the frameless-only hamburger button and resize grip while hosting the reusable client-area widget.
  - Rationale: This moves frameless-specific chrome out of `SkyWindow`, so the main window can focus on actions, state, and client-area orchestration. It also creates a clean place to evolve custom frame behavior without mixing it into the sky rendering widget.

- Topic: Host-window split for frameless vs standard window modes
  - Decision: Move shared app/window logic into `SkyWindowCoreMixin`, then provide `FramelessSkyWindow` and `StandardSkyWindow` host classes that install different chrome around the same client-area widget and shared action menu.
  - Rationale: This separates sky-view behavior from the choice of window host. Frameless mode can keep custom chrome, while standard mode can use a normal decorated `QMainWindow` with a menu bar, without duplicating application logic.

- Topic: Restrict custom chrome rendering to frameless mode
  - Decision: Add `show_custom_window_frame` to `RenderStyle` and only draw the custom border, hamburger icon, and resize-grip triangle when the active host is frameless.
  - Rationale: The standard decorated window should render only the client area. Leaving the custom chrome in the background layer caused the framed window to keep the old overlay decorations and made the radial background appear visually offset.

- Topic: Split the decorated-window menu bar by responsibility
  - Decision: Replace the single `View` top-level menu in the decorated host with `File`, `Observer View`, and `Display Settings`, while keeping the frameless hamburger popup as a container for the same three grouped submenus.
  - Rationale: The decorated window should use a normal desktop-style menu bar. Grouping actions by role makes the standard host easier to navigate without duplicating action wiring.
