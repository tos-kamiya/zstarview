- Topic: Direct coordinate display precision
  - Decision: Increase the direct latitude/longitude display in the startup
    resolver from 2 decimal places to 5 decimal places.
  - Rationale: The parsed coordinates themselves were already preserved at
    full precision and persisted with 6 decimal places; only the human-facing
    `display_name` was being shortened. Updating the formatter improves the
    visible precision without changing the underlying calculations or saved
    location key.

- Topic: Shared lat/lon formatting helper
  - Decision: Add a shared `latlon_format` utility with a single precision
    constant and use it for both the startup resolver display string and the
    Overture building cache dataset name.
  - Rationale: The GUI display and cache key should round coordinates in the
    same way to avoid duplicated formatting rules. The new helper keeps the
    latitude/longitude precision in one place while preserving the existing
    cache naming convention for the non-coordinate parts of the key.

- Topic: Separate display and cache precision
  - Decision: Split latitude/longitude precision into a 5-digit display
    constant and a 4-digit building cache constant, while keeping building
    cache lookup on the exact 4-digit dataset key.
  - Rationale: The UI can stay at 1m-ish precision while the on-disk cache
    key remains coarser at roughly 10m. That keeps the cache naming rule
    centralized without introducing fallback reuse before the new cache scheme
    is deployed.

- Topic: README screenshot caption update
  - Decision: Update the three README variants so the Sagrada Familia example

  - Rationale: The screenshot asset was replaced, and the old "park beside"
    wording would no longer match the image shown in the docs.

- Topic: Transparent theme addition
  - Decision: Add a new `transparent` theme preset with a very dark, low-alpha
    window background and keep it functionally in the dark-theme path for text
    and overlay tuning.
  - Rationale: The app already renders its main window with translucent Qt
    surfaces, so a blackish semi-transparent preset can be useful on dark
    desktops without forcing a new rendering model. Reusing the existing dark
    theme behavior for asterisms, DSO hover styling, and label outlines keeps
    the change small and predictable.
  - Alternatives Considered: A separate `translucent` preset was considered as
    the user-facing name, but `transparent` is simpler and still accepts
    `translucent` as a CLI alias for convenience.
