# 2026-04-28 Session Notes

- Topic: Version bump after render typing cleanup
  - Decision: Bump the package version by +0.0.1 to `1.21.2`.
  - Rationale: The render typing cleanup and its follow-up test fix were
    already validated and committed; this bump marks the follow-up patch
    release boundary cleanly.

- Topic: Urban outline gallery refresh
  - Decision: Reformat the `Urban outline examples` gallery in `README.md`
    from a 4-column row into a 3x2 grid and add the Switzerland mountain
    viewpoint and Sagrada Familia park screenshots.
  - Rationale: The new screenshots belong in the existing urban outline
    showcase, and a 3x2 layout keeps the gallery balanced after expanding
    the set to six examples.

- Topic: Urban outline gallery ordering
  - Decision: Reorder the six screenshots in westward geographic order from
    Tokyo through Singapore, Dubai, Switzerland, Barcelona, and Sydney.
  - Rationale: The gallery now reads more naturally as a geographic tour
    rather than a purely visual grid, which matches the user's requested
    sequencing.

- Topic: README variants sync
  - Decision: Apply the same 3x2 gallery layout and westward ordering to
    `README_pypi.md` and `README_ja-JP.md`.
  - Rationale: The published PyPI README and the Japanese README should stay
    consistent with the main README so the gallery presents the same set of
    urban outline examples everywhere.

- Topic: Lauterbrunnen naming
  - Decision: Use `Lauterbrunnen, Switzerland` in the English READMEs and
    `ラウターブルンネン（Lauterbrunnen）` in the Japanese README.
  - Rationale: The Japanese transliteration makes the location easier to
    recognize for readers who do not know the Swiss place name already.

- Topic: Urban outline table split
  - Decision: Split the six urban outline examples into two separate
    3-column tables instead of one 3x2 table.
  - Rationale: The visual grouping is clearer when the top and bottom rows
    are rendered as independent blocks, while keeping the same ordering and
    content.

- Topic: Direct coordinate display precision
  - Decision: Increase the direct latitude/longitude display in the startup
    resolver from 2 decimal places to 5 decimal places.
  - Rationale: The parsed coordinates themselves were already preserved at
    full precision and persisted with 6 decimal places; only the human-facing
    `display_name` was being shortened. Updating the formatter improves the
    visible precision without changing the underlying calculations or saved
    location key.

- Topic: Shared lat/lon formatting helper
  - Decision: Add a shared `latlon_format` utility with a single precision
    constant and use it for both the startup resolver display string and the
    Overture building cache dataset name.
  - Rationale: The GUI display and cache key should round coordinates in the
    same way to avoid duplicated formatting rules. The new helper keeps the
    latitude/longitude precision in one place while preserving the existing
    cache naming convention for the non-coordinate parts of the key.

- Topic: Separate display and cache precision
  - Decision: Split latitude/longitude precision into a 5-digit display
    constant and a 4-digit building cache constant, while keeping building
    cache lookup on the exact 4-digit dataset key.
  - Rationale: The UI can stay at 1m-ish precision while the on-disk cache
    key remains coarser at roughly 10m. That keeps the cache naming rule
    centralized without introducing fallback reuse before the new cache scheme
    is deployed.
