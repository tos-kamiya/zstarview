# Session 2026-04-18

Scope: Investigate whether the app can display dwarf planets as satellite-sized cross markers, and determine the data source / accuracy tradeoff before implementation.

- Topic: Dwarf planet rendering
  - Decision: Current solar-system ephemeris data covers Pluto, but not other dwarf planets in a way that can be confirmed locally.
  - Rationale: The existing `de442s.bsp` path supports the major planets and Pluto barycenter. Adding Ceres / Eris / Haumea / Makemake would require either another data source or an approximate orbital model.
  - Status: Awaiting user confirmation on which bodies to show and whether approximate positions are acceptable.

- Topic: JPL Horizons sample sequence
  - Decision: Implement the prototype in the requested order, starting with an observer-ephemeris sample that reuses the existing `zstarview.satellites.fetch` Horizons helpers.
  - Rationale: The repository already has working lookup and observer CSV helpers for Horizons. Reusing them keeps the sample aligned with the eventual app code and avoids duplicate API plumbing.
  - Status: In progress.

- Topic: Horizons sample completion
  - Decision: Added `dev-samples/jpl_horizons_observer.py` for a single alt/az sample and `dev-samples/jpl_horizons_trajectory.py` for a 1-hour repeated-sample trajectory.
  - Rationale: The observer sample proved the lookup-to-ephemeris flow works once the small-body command is sent as `DES=<spkid>;`. The trajectory sample keeps the implementation simple by repeating the single-time query at fixed intervals.
  - Validation: Both scripts compiled cleanly and returned live `Ceres` results from Horizons for a Tokyo observer location.

- Topic: Main-window JPL integration
  - Decision: Wire JPL small-body search into the existing "Search Objects" dialog and render persistent marker/label overlays from the selected target state.
  - Rationale: The dialog can stay focused on selection while the window handles view jumps and overlay persistence. This keeps the feature close to the existing search flow without adding a separate menu path.
  - Validation: Static checks passed. Pytest collection in the current environment is blocked by missing runtime dependencies (`astropy`, `PySide6`) in the active interpreter.

- Topic: JPL refresh retry policy
  - Decision: Re-query persistent JPL small-body positions on a one-hour cadence and, on failure, schedule the next retry one hour later instead of immediately retrying.
  - Rationale: This keeps the refresh behavior predictable and avoids bursty retries against Horizons when the network or service is temporarily unavailable.
  - Status: Implemented with a dedicated controller and one-shot timer.

- Session wrap-up
  - Validation: `py_compile` and `ruff check` passed for the modified GUI, renderer, test, and support files.
  - Validation: `pytest` was not runnable in the active `.venv` because `pytest` is not installed there.
  - Follow-up: Commit the JPL integration changes once the working tree is in the desired final state.

- Search dialog fallback refinement
  - Decision: Collapse the JPL small-body branch back into the main `Search Objects` dialog and only query JPL when the local star/asterism filter finds no match.
  - Rationale: This keeps the menu simple for the common case and makes the fallback behave like one search flow instead of two separate modes.

- Search UX clarification
  - Decision: Add an explicit JPL database button under the search field and query both major bodies and small bodies from the JPL fallback path.
  - Rationale: The button makes the fallback action discoverable, and major-body coverage keeps common planets/moons available without a separate search mode.

- Keep-marker fix
  - Decision: Apply `Keep marker` to all JPL results, including major bodies, while only scheduling periodic refreshes for small bodies.
  - Rationale: The keep option should control persistence consistently; major-body targets do not need timer-driven refresh, but their marker and label should still remain visible.

- Sun and Moon exclusion
  - Decision: Exclude `Sun` and `Moon` from the JPL fallback path and leave them to the solar-system view.
  - Rationale: These bodies already have dedicated handling in the app, so sending them through JPL adds noise and an unnecessary network dependency.
