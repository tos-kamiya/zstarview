- Topic: CLI content FOV option
  - Decision: Specify a new `--content-fov-deg` option that widens the draw-eligible angular range for all layers while keeping the window edge fixed at 90 degrees from the view center.
  - Rationale: The requested behavior is overscan, not a projection-scale change. Keeping the 90-degree edge invariant preserves the current geometry while reducing empty corner regions consistently across stars, background, clouds, aircraft, guide lines, and other overlays.
- Topic: CLI content FOV implementation
  - Decision: Thread `--content-fov-deg` through CLI parsing, window/runtime options, sky-data generation, raster compositing, and vector overlay visibility checks.
  - Rationale: The option needs to affect both prefiltered celestial datasets and runtime-only layers. Treating it as a shared render setting keeps stars, sky disc, clouds, aircraft, guide lines, and labels visually aligned.
- Topic: Content FOV rendering rules
  - Decision: Treat `content_fov_deg` as the only draw-limit for stars, including faint stars, and use a short post-FOV background fade instead of suppressing dim stars outside the old 90-degree boundary.
  - Rationale: Once `content_fov_deg` is the shared draw envelope, special-casing dim stars against the legacy 90-degree background boundary makes the feature inconsistent. A small outer fade keeps the window edge visually soft without breaking layer alignment.
- Topic: Outer fade alpha tuning semantics
  - Decision: Express the per-theme outer fade opacity using absolute alpha values instead of multipliers against the boundary-color alpha.
  - Rationale: The multiplier-based formula made visual tuning unintuitive because a value like `0.75` still became much more transparent after being applied to an already translucent boundary color and then faded again across the radial gradient.
- Topic: Radial background fade rebuild
  - Decision: Rebuild the background gradient stops so the alpha profile is explicit and monotonic from the content-FOV boundary to the window edge.
  - Rationale: Incremental tweaks had produced a visible dip-and-rise around the FOV boundary. Using fixed `core`, `mid`, `boundary`, `outer`, and `edge` alpha stops is easier to reason about and avoids non-monotonic fades.
- Topic: Wide-layout sky/cloud geometry
  - Decision: Make sky-disc generation and sky/cloud compositing use the actual window geometry (`center`, `radius`, and full viewport size) instead of a fixed `radius*2` square.
  - Rationale: In low-altitude wide layouts, the old square assumptions made sky and cloud layers appear clipped at the legacy 90-degree disc width even when `content_fov_deg` allowed wider overscan.
- Topic: Terrain horizon behavior over ocean
  - Decision: Treat DEM `nodata` samples as sea level (`0.0m`) when building the terrain horizon scan grid.
  - Rationale: Copernicus DEM returns `nodata` for ocean cells, but ocean observers are a valid use case. Falling back to sea level preserves terrain-horizon rendering for offshore coordinates and avoids surfacing a spurious runtime error banner when the correct horizon is the geometric sea horizon.
- Topic: Terrain horizon behavior when no DEM tiles exist
  - Decision: Treat an empty Copernicus DEM tile download set as an ocean-only horizon and emit an empty terrain profile instead of a failure.
  - Rationale: Large ocean regions can legitimately have no downloadable Copernicus DEM tiles at all. In that case the correct user-visible result is simply "no terrain polyline", not a persistent error state that suppresses future updates.
- Topic: GOES-East satellite refresh
  - Decision: Update GOES-East handling from `G16` to `G19` and normalize legacy `G16` configuration values to `G19`.
  - Rationale: NOAA transitioned GOES-East operations to GOES-19 in April 2025. Selecting `G16` now points at a stale bucket and causes avoidable "data not found" failures for Atlantic observers, while aliasing preserves compatibility with older local configs.
- Topic: README partial-cloud coverage note
  - Decision: Add a README link to `docs/images/screenshot5.png` and note that parts of Europe can now show partial cloud coverage with faint yellow missing-data tint instead of a simple unsupported-region message.
  - Rationale: The new screenshot documents the current user-visible behavior for 77-87% cloud coverage, and the note clarifies a behavior change caused by the GOES-East update.
