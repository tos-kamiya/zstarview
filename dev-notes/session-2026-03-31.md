# Session 2026-03-31

- Scope: Adjust cloud stripe visibility after the new minimum-width threshold hid expected cloud regions.

- Topic: Revert the 2px minimum stripe visibility threshold
  - Decision: Removed the hard `2.0px` minimum-width gate so thin cloud stripes are allowed to render again.
  - Rationale: The threshold improved legibility but also suppressed cloud structure in regions where clouds should still be visible, which is a larger regression than the thin-band noise it avoided.

- Topic: Remove the extra cloud opacity scale and lower the CLI default
  - Decision: Removed the compositor-side `0.7` cloud opacity multiplier and changed the CLI `--cloud-opacity` default from `0.15` to `0.1`.
  - Rationale: Cloud opacity should now mean exactly what the CLI says, and the previous combination of `0.15 * 0.7` was both indirect and visually stronger than desired for the current stripe rendering.

- Topic: Lower the cloud amount normalization floor percentile
  - Decision: Changed the lower percentile used for `cloud_amount_field` normalization from `20` to `8`.
  - Rationale: Sparse cloud regions had become too hard to see after the width-based stripe rewrite. Lowering the normalization floor keeps more low-cloud signal visible without changing the rest of the stripe renderer.

- Topic: Remove the fixed 10px viewport margin
  - Decision: Changed `get_screen_geometry()` so the sky/cloud disc uses `0px` horizontal and vertical margins instead of a fixed `10px` inset.
  - Rationale: The requested behavior is to let the disc extend into the full window bounds, including the area beneath the frame/border, instead of reserving a permanent inner gutter.

- Topic: Sync specification and design docs with the cloud and viewport changes
  - Decision: Updated `docs/specification.md` with the direct `--cloud-opacity` behavior and border-underlay rendering notes, and updated `docs/design.md` to describe `cloud_amount_field`, width-based cloud stripes, percentile normalization, and the zero-margin viewport geometry.
  - Rationale: The user-visible behavior and the internal implementation had both shifted enough that the docs were no longer describing the current system accurately.

- Topic: Document a multi-height cloud projection option
  - Decision: Updated the specification and design docs to allow approximating clouds with multiple representative shell heights instead of a single fixed `5km` shell, and recorded a `3km + 8km` half-and-half blend as the initial design candidate.
  - Rationale: A single shell height is simple but tends to create unnatural gaps in some views. Documenting the multi-height option first makes the intended direction explicit before any implementation work.

- Topic: Implement two-shell cloud projection blending
  - Decision: Replaced the single `5km` cloud shell with a two-shell blend using `3km` and `8km`, mixed at `0.5 / 0.5`, and used the maximum shell radius when selecting Himawari observer tiles.
  - Rationale: The two-shell blend is a lightweight visual correction that reduces single-height projection gaps without needing per-pixel cloud-top estimation. Using the maximum shell for source selection keeps the fetched tile set large enough for both projections.

- Topic: Cache cloud stripe coordinate transforms
  - Decision: Added small LRU caches for the normalized bin-index grids used by `build_cloud_amount_field_from_rgba()` and the viewport-dependent sampling grids used by `_render_variable_width_cloud_stripes_rgba()`.
  - Rationale: The cloud stripe path was rebuilding the same full-frame coordinate transforms on every cloud update. Those transforms depend only on canvas size, viewport geometry, stripe period, and field resolution, so memoizing them removes repeated setup cost without changing output.
  - Alternatives Considered: Lowering stripe resolution or changing hatch density would reduce work too, but that would also change visual output.

- Topic: Sync cloud stripe and overscan documentation
  - Decision: Updated the specification to describe the unified `--cloud-stripe MODE[,COUNT[,WIDTH]]` CLI and updated the design doc to reflect dual stripe modes plus the current low-altitude/FOV overscan behavior.
  - Rationale: The cloud rendering path now supports both width-based and alpha-based stripe encodings, and cloud fetch/render intentionally uses a small overscan below the visible edge. The docs needed to match the implementation rather than the older width-only description.

- Topic: Increase default CloudAmountField resolution
  - Decision: Raised the default `CloudAmountField` bin count from `192` to `320`.
  - Rationale: The stripe-length direction was still too coarse with the previous `(u, v)` field resolution. Increasing the default bin count improves along-stripe detail without changing the rendering model or user-facing controls.
  - Alternatives Considered: Larger values such as `384` or `512` would preserve more detail, but `320` is a safer first step for keeping the cloud-field build cost moderate.

- Topic: Bump application version after cloud stripe tuning
  - Decision: Increased the package version from `1.8.3` to `1.8.4`.
  - Rationale: The cloud stripe rendering defaults changed in a user-visible way, so the release version should advance with the committed fix set.

- Topic: Avoid stale GOES hourly listings during timer-driven refreshes
  - Decision: Changed the GOES S3 hour-listing cache so the current UTC hour is never reused from the in-memory cache; only closed hours remain cacheable.
  - Rationale: NOAA can publish additional CMIPF files into the current hour while the app is running. Reusing the first listing for that hour can pin repeated timer refreshes to an older scene, even when a newer file has already appeared.
  - Alternatives Considered: Adding a short TTL would also work, but skipping cache only for the active UTC hour is simpler and preserves caching for immutable historical hours.
