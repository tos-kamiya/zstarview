# 恒星描画の段階的リファクタリング引き継ぎ

作成日: 2026-11-06。状態: 調査と計画のみ。実装・ベンチマークは未実施。

## 目的と範囲

恒星の見た目、等級による選別、投影、面積補正、合成方法を維持しつつ、キャッシュ命中時の不要な計算と再生成時のメモリ確保を削減する。
各段階を独立したコミットにし、効果のない変更は採用しない。アプリ全体の最大負荷が恒星描画であるとは未確認。
天体計算の精度・更新周期、雲・地形、GPU化、スレッド追加は今回の範囲外。共有 `ApplicationServices.native_work_lock` の規約を維持する。

## 現状の確認事項

- `src/zstarview/render/stars.py`: `StarRenderCache` は所有者ごとの画像1件キャッシュ。
- `_draw_stars_render` は等級選別、投影、BV色変換、サイズ・面積補正を実行した後に通常経路のキャッシュを確認する。
- `_star_cache_key` は高度・方位・サイズ係数・色係数の4配列を `tobytes()` とMD5で走査する。
- 通常経路は `screen_positions is None` の場合にだけ画像キャッシュを利用する。この条件を無条件に外さない。
- 明背景は `_draw_stars_light_background_rgba` に分岐し、独自のキー・画像生成を持つ。通常経路と同一と仮定しない。
- 再生成時には画面サイズの float32 RGBキャンバスや追加レイヤーを確保する。最終QImageは `.copy()` で配列から独立させている。
- `gui/window_render.py` の `_render_cached_star_surface_image` に上位の恒星面キャッシュがあり、さらにフレームキャッシュがある。下位関数だけの高速化が通常操作に効くとは限らない。
- 上位の恒星面キーには視野角・画像サイズ等がある。下位キーだけを独立利用する場合の依存関係の完全性は、今回まだ監査していない。

## Step 1: 再現可能な計測基盤と基準値

まず呼び出し元を調べ、通常・高速・明背景・補間座標指定経路と各キャッシュの責務を図または表にする。恒星面・フレーム・下位画像の命中数、再生成数、下位関数の呼び出し数を区別する。

計測用スクリプトを `dev-samples/` に用意し、入力生成や初期ロードを測定区間から除く。日時・地点・カタログ・等級上限・視線・視野角・描画サイズ・DPR・モード・乱数種を固定して保存する。星数は入力数と描画対象数の両方を記録する。

以下を別々に計測する。

1. 下位キャッシュ命中: 同一入力で繰り返し呼ぶ。
2. 下位キャッシュ不命中: 視線等を決めた系列で変更し、毎回再生成する。
3. キャッシュ無効・独自座標経路: `screen_positions` を指定する。
4. 実操作: 静止、ホバー、ドラッグ、ズーム、天体データ更新。上位キャッシュも有効な通常構成で測る。

代表条件は小画面と大画面、少数と多数の星、通常と高速、暗背景と明背景。全組み合わせを毎回測る必要はないが、最終評価では各分岐を含める。
`perf_counter_ns` 等で中央値・p95・サンプル数を記録し、CPU時間、RSSのピークと操作終了後の保持量も確認する。Pythonの割当計測だけではNumPy/Qtの全メモリを代表しない。
ウォームアップ後に同じ回数を複数回実行し、構成の順序を入れ替える。環境・コミット・コマンド・生データを残す。初回生成は温まった再生成と分ける。

完了条件: 基準値が再測定でき、時間の支配項と各キャッシュの実際の利用頻度を説明できる。

## Step 2: キャッシュ契約と描画結果を固定

キーの依存表を作る。配列内容・並び・選別、BV色、等級、恒星時刻、視線・視野角、画面サイズ、geometry、明るさ・サイズ、輪郭、高速モード、瞬き、独自座標を含め、どのキャッシュで何を保証するか明示する。
既存キーに不足が見つかった場合は最適化と分けて修正・検証する。キーが同じなら結果も同じ、という契約を先に成立させる。

既存の `tests/test_star_overscan_render.py`、`test_star_render_scale.py`、`test_star_flare_profile.py` を確認する。必要な追加テストは、同一入力での再利用、描画に影響する入力変更での無効化、キャッシュ所有者の独立性、等級境界、独自座標、リサイズ後の古い画像混入に絞る。
GUIイベントループを必要としない小さなオフスクリーン画像比較または純粋ロジックを中心にする。QImageを利用する既存テストの環境設定に合わせる。
固定入力に対して旧実装と画素を比較する。数式・dtype・演算順序を維持する変更では完全一致を目指し、差があれば原因を説明してから進む。

完了条件: キャッシュの有効条件と変更時の期待動作が明確になり、回帰を検出できる。

## Step 3: A — キャッシュ判定を前へ移す

キーの構成に必要な入力の正規化とサイズ検証だけを先に行い、投影・BV変換・サイズと面積補正の前に命中判定を置く。まず通常経路だけを扱い、明背景は同じコミットに無理に統合しない。
既存ハッシュ方式を残してA単独の効果を測る。空集合の早期return、painter状態・合成モード、独自座標時の再利用禁止を維持する。

完了条件: 画素比較と対象テストが通り、命中時に重い準備処理が実行されない。命中・不命中の両方の時間を記録する。

## Step 4: B — 配列ハッシュを更新識別子へ置換

恒星配列の生成・受け渡し・更新箇所を調べ、不変スナップショットと更新識別子の契約を定義する。同一オブジェクトのin-place変更やカタログ交換、配列の並び変更を取りこぼさないことが必須。
既存スナップショットの識別で十分ならそれを利用し、単なる `id(array)` のみに依存しない。共有構造への変更が広範囲になる場合は、レンダラー入力の小さなラッパー等で段階的に導入する。契約を保証できない経路はハッシュ方式を残す。
元データ識別子に加え、選別条件・描画パラメータはキーに保持する。更新識別子が保証する範囲を文書化する。

完了条件: データ変更を取りこぼさない検証が通り、B単独とA+Bを測定できる。

## Step 5: C — 描画バッファを所有者単位で再利用

まず大きなキャンバス1個を対象に、所有者ごとの作業領域を導入する。毎回必要領域をゼロクリアし、サイズ・dtype変更時だけ再確保する。効果確認後に追加レイヤーへ広げる。
グローバル共有を避け、同時使用・再入可能性を呼び出し元で確認する。最大サイズの無制限保持を避け、縮小・破棄の方針を決める。画像キャッシュの無効化と作業領域の破棄は役割を区別する。
QImageの `.copy()` は最初は維持する。ゼロコピー化は所有権・寿命・次フレームによる画像破壊の問題があるため別案件とする。面積補正や加算順序は変更しない。

完了条件: リサイズ、繰り返し描画、複数所有者で画像汚染がなく、再生成時の時間とピーク・保持メモリのトレードオフが明確。

## Step 6: 組み合わせ評価と採否

同一の計測基盤で次を比較する。BとCの単独測定は基準実装にそれぞれの変更だけを適用した構成で行い、比較用変更を本番APIの恒久フラグとして残す必要はない。

| 構成 | 目的 |
| --- | --- |
| 基準 | 比較元 |
| Aのみ / Bのみ / Cのみ | 各変更の寄与 |
| A+B | 判定順序とキー生成の相互作用 |
| A+B+C | 最終的な性能・メモリ |

A/C、B/Cの相互作用を個別に論じる必要が出た場合はA+C、B+Cも追加する。単独効果の和を最終効果とみなさない。
下位ベンチマークと実操作の結果を別に報告する。ドラッグでは不命中、静止では上位キャッシュ命中が多い可能性があるが、実測で確認する。
採用基準はStep 1のばらつきを見て設定する。計測誤差を超える改善、対象外経路での重大な悪化なし、見た目の維持、保持メモリが許容範囲、をすべて確認する。固定の改善率を未測定の段階で約束しない。

## Step 7: 完了・次の担当者への引き継ぎ

対象テストから全体テストへ進め、型・lintを実行する。

```bash
uv run -p .venv/bin/python pytest tests/test_star_overscan_render.py tests/test_star_render_scale.py tests/test_star_flare_profile.py
uv run -p .venv/bin/python pytest
uv run -p .venv/bin/python mypy src/zstarview tests
uv run -p .venv/bin/python ruff check src/zstarview tests
git diff --check
```

新規テストと計測スクリプトにも必要なチェックを適用する。既存失敗と今回の失敗を区別して記録する。
最終報告には構成別の数値、環境、画像比較結果、採否と理由、コミット、残課題を含める。
確定した責務・データ契約は `docs/design.md` に反映する。外部動作が変わらなければ `docs/specification.md` は変更不要。出荷時の性能改善は測定に沿って `release-notes.md` に記す。

次の候補はホバー判定と描画での投影座標共有。入力や寿命の共有設計が広がるため、今回のA/B/Cの結果を見て別計画にする。動的レイヤーの更新周期変更も今回には含めない。

## 着手時の作業ツリーへの注意

調査時点で既存の未コミット変更・未追跡成果物あり。`git status --short` で再確認し、今回の変更と混ぜない。本資料と当日のセッションログ以外は今回編集していない。
