Session scope: inspect typhoon data source and strength fields

- Topic: Tropical cyclone strength fields in the current data path
  - Decision: The `Active_Hurricanes_v1` fetch path does include strength-related fields on each point, specifically `MAXWIND`, `GUST`, and `MSLP`, and the model preserves them as `maxwind_kt`, `gust_kt`, and `mslp_hpa`.
  - Rationale: The client parser maps these fields directly into `TropicalCyclonePoint`, and the snapshot serialization keeps them available for downstream use. However, the current render path only uses position and storm name, so those strength values are not yet reflected visually.

- Topic: Strength-based cyclone marker and wider visibility cutoff
  - Decision: Switched the tropical cyclone overlay marker to a rounded rectangle whose width tracks `maxwind_kt` and whose height uses a nominal `10km` reference, both shrinking with distance. Increased the visibility cutoff from `128km` to `400km`.
  - Rationale: `maxwind_kt` is the cleanest strength signal in the current payload, and the wider cutoff better matches the user's desired presentation range while keeping the implementation simple and deterministic.
  - Validation: Ran `uv run -p .venv/bin/python ruff check src/zstarview/render/tropical_cyclones.py tests/test_tropical_cyclones.py` and `uv run -p .venv/bin/python pytest tests/test_tropical_cyclones.py`.

- Topic: Conical cyclone marker geometry
  - Decision: Changed the marker from a flat rectangle to a cone-like shape with a tip at ground / water height and a circular base projected from `10km` altitude.
  - Rationale: This matches the requested physical interpretation more closely while keeping the implementation in the existing 2D projection pipeline.
  - Validation: Re-ran `uv run -p .venv/bin/python ruff check src/zstarview/render/tropical_cyclones.py tests/test_tropical_cyclones.py` and `uv run -p .venv/bin/python pytest tests/test_tropical_cyclones.py` after the geometry change.

- Topic: Horizontal disk base sampling
  - Decision: Refined the cone base so it is generated as a sampled circle on a plane parallel to the local ground / water surface at `10km` altitude, rather than as a screen-space ellipse.
  - Rationale: Sampling the base in geographic space keeps the bottom face aligned with the intended horizontal plane and makes the visual model consistent with the requested geometry.
  - Validation: The same `ruff` and `pytest` checks remained green after the refinement.

- Topic: Cone silhouette and label anchor fix
  - Decision: Replaced the cone-body polygon fan with a simpler silhouette made from the tip and the leftmost/rightmost projected base-ring points, and moved the label anchor to the tip.
  - Rationale: The fan was self-intersecting in screen space and visually collapsed on the left edge. Anchoring the label to the tip matches the requested placement directly below the pointed vertex.
  - Validation: Re-ran `ruff check` and `pytest tests/test_tropical_cyclones.py`; both passed.

- Topic: Cone fill and rim separation
  - Decision: Changed the marker to fill only the cone volume with a single triangular body, then draw the base rim as an outline and the two side edges separately.
  - Rationale: This avoids the double-darkening that came from overlapping a filled ellipse with a filled triangle, while matching the requested 3D cone cues.
  - Validation: Re-ran `ruff check` and `pytest tests/test_tropical_cyclones.py`; both passed.

- Topic: Cone volume fill simplification
  - Decision: Replaced the separate body and base fills with a single filled polygon spanning the tip and sampled base ring, then overlaid only the rim and side edges.
  - Rationale: A single fill removes the transparent gap on the base face and avoids the darker overlap artifact from stacking multiple filled shapes.
  - Validation: Re-ran `ruff check` and `pytest tests/test_tropical_cyclones.py`; both passed.

- Topic: Cone outer contour projection
  - Decision: Switched the cone draw path to the convex hull of the projected tip plus base-ring sample points, so the visible outer polygon is drawn directly.
  - Rationale: The previous layered fills were still exposing a partial base face and a side fragment. The convex hull matches the observer-facing silhouette more closely and removes internal overlaps.
  - Validation: Re-ran `ruff check` and `pytest tests/test_tropical_cyclones.py`; both passed.

- Topic: Tropical cyclone default opacity
  - Decision: Lowered the default tropical cyclone overlay opacity from `0.4` to `0.25` in the shared constant used by CLI and GUI startup paths.
  - Rationale: This keeps the current rendering style but makes the overlay less visually dominant by default.
  - Validation: Updated the related CLI and window-sync expectations, then ran `ruff check` on the affected files and `pytest tests/test_cli_cloud_missing_tint_opacity.py tests/test_window_render_sync.py tests/test_cli_export_image_args.py`; all passed.

- Topic: Water surface representation in docs
  - Decision: Confirmed that the spec describes the water surface as "small blue dots" and the design describes the sea-mask path as point-cloud normalization; neither document constrains the dot to a specific glyph such as a filled circle.
  - Rationale: The current screen rendering as light-blue filled circles is consistent with the documented "dot" representation, while leaving the exact marker shape as an implementation detail.

- Topic: Resolution-dependent water surface density
  - Decision: Switched water surface sampling to three azimuth step tiers, `2.0° / 1.0° / 0.5°`, and select the tier from the render surface size so larger surfaces use denser point sets.
  - Rationale: The fixed `2.0°` sampling looked sparse on large client areas, especially when the point diameter stayed at `6px`. Tying the step to surface size keeps the default window lightweight while restoring perceived density on 4K-scale views. The cache key now includes the chosen step so different density tiers do not collide.
  - Validation: Ran `compileall` over `src/zstarview` and `tests`, then re-ran targeted pytest coverage for the water overlay, cache, controller, and export-image paths.

- Topic: 4K water density refinement
  - Decision: Raised the `0.5°` cutoff so 4K-class surfaces stay on `1.0°`, reserving `0.5°` for much larger surfaces.
  - Rationale: In fullscreen 4K, `0.5°` produced visibly merged dots and pushed the point count to `33840+0`, which was denser than the current marker diameter can support cleanly. Keeping 4K at `1.0°` preserves the denser look without turning the overlay into a continuous band.

- Topic: Water surface tier thresholds
  - Decision: Set the tier thresholds to `1200px` for `1.0°` and `2400px` for `0.5°`.
  - Rationale: This keeps the default window on `2.0°`, promotes medium-sized surfaces to `1.0°`, and only enables `0.5°` on much larger surfaces than 4K-class views. It aligns the runtime behavior with the desired visual density without needing an 8K display to confirm the finest tier.
