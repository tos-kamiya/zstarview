- Topic: Apply terrain occlusion to water rendering
  - Decision: In normal rendering, fade water dots and boundary polylines when
    a nearby terrain-horizon sample at the same azimuth is higher than the water
    and closer to the observer. Use the same 0.48 alpha scale as hidden
    secondary ridges; retain the existing appearance when profile distance data
    is unavailable. Skip this calculation in fast viewport-interaction
    rendering.
  - Rationale: Water behind a ridge should not appear equally prominent, while
    water in front of a ridge must remain visible. Comparing both altitude and
    distance avoids treating nearby water as hidden merely because the terrain
    horizon is higher.
  - Validation: Added focused unit tests for behind/in-front/above and azimuth
    mismatch cases; water and overlay pipeline tests pass.

  - Rationale: The terrain controller publishes the DEM horizon profile before

- Topic: Proposed place-search cache behavior
  - Decision: Cache normalized Nominatim candidate lists by normalized query,
    country filter, language, result limit, provider identity, and cache schema
    version. Use a fresh cache entry immediately; if it is stale, try the
    network and fall back to the stale entry only for network or server
    failures, with an explicit offline/cached status. Do not replace a usable
    positive entry with an error or an empty response.
  - Rationale: Candidate-list caching supports both startup `--place` lookup and
    the interactive search UI, prevents repeat requests for the same search,
    and provides useful offline behavior without silently presenting cached
    coordinates as current online results. The public Nominatim policy asks
    applications to cache requests and forbids autocomplete-style querying.
  - Alternatives Considered: Caching only the selected place is already
    approximated by `last_city`, but helps only with an implicit repeat of the
    last selection and cannot satisfy another explicit `--place` query. An
    indefinite cache with no freshness metadata was rejected because place
    names and OSM results can change and users need to know when stale data is
    being used.

- Topic: Revised online-first place-search cache
  - Decision: When a place search is explicitly requested, try Nominatim first
    and do not read the cache before the request. On a successful response with
    one or more normalized candidates, replace the matching cache entry and
    record its UTC retrieval time. On DNS, connection, or timeout failure, read
    the cache and use an exact matching entry if available. Do not cache empty
    results or failures.
  - Rationale: Online searches always receive current provider results, while a
    prior successful query remains usable offline. Positive-only caching avoids
    making a temporary empty response indistinguishable from a durable absence.
    The fallback must be driven by a failed request rather than a generic
    connectivity probe, because a system-level online indication does not prove
    that Nominatim itself is reachable.
  - Alternatives Considered: Reading a fresh cache before every online request
    was rejected for this workflow because the desired behavior is to refresh
    explicitly requested searches whenever the provider is reachable. The
    earlier TTL proposal is therefore not used to suppress online requests;
    retrieval time remains metadata shown for offline fallback and may support
    later cache cleanup.
  - Constraint: The public `nominatim.openstreetmap.org` policy currently sets
    an absolute maximum of one request per second, not one request per 0.5
    seconds. Searches must be user-triggered, serialized, and rate-limited to at
    least one second between requests; autocomplete requests remain disabled.

- Topic: Place-search cache specification confirmed
  - Decision: Adopt the online-first design above. A user-triggered search is
    sent to Nominatim subject to the one-request-per-second limit. If the
    provider cannot be reached, zstarview falls back to a matching positive
    cache entry. Whenever a cached result is shown, the UI also shows the
    entry's retrieval date and time.
  - Rationale: The retrieval timestamp makes the age and provenance of offline
    results visible instead of presenting them as current provider data. This
    preserves current online behavior while giving previously searched places
    a predictable offline path.

- Topic: Place-search cache design readiness review
  - Decision: Consider the functional specification sufficient for user-visible
    behavior, but require a small internal design section before implementation.
    The design must define one shared online-first search service for CLI and
    startup-dialog paths, cache schema/path and atomic writes, exact fallback
    error classes, query-key normalization, UTC timestamp handling, and a
    process-wide serialized one-second rate limiter.
  - Rationale: The current code has two Nominatim entry paths
    (`location_resolver.nominatim.search_nominatim` and
    `location_resolver.place_search.search_place_candidates`). Adding fallback
    independently would risk divergent cache formats, rate limiting, and error
    behavior. The existing `last_city` payload stores only a selected location
    and must remain separate from the reusable candidate cache.

- Topic: Place-search cache storage format
  - Decision: Prefer one versioned JSON file per normalized search key under a
    dedicated cache directory, with a SHA-256-derived filename and atomic
    temporary-file replacement. Do not introduce SQLite for this cache.
  - Rationale: Lookup is exact by query key, entries are small, and expected
    volume is low. Per-entry JSON is inspectable, easy to discard on corruption,
    consistent with existing project cache metadata, and avoids lost updates
    between unrelated searches in concurrent processes. SQLite would add schema
    migration, connection, locking, and recovery concerns without a need for
    relational queries or large-scale indexing.

- Topic: Filesystem-safe place-cache keys
  - Decision: Never embed the query in a cache filename. Serialize the
    normalized query, normalized country code, normalized language, provider,
    and key-schema version as canonical JSON encoded as UTF-8, and use its
    SHA-256 hex digest as the filename. Store the original and normalized key
    fields inside the JSON entry and verify them after loading.
  - Rationale: A fixed lowercase hexadecimal filename is portable across the
    supported filesystems and avoids separators, reserved names, control
    characters, Unicode normalization differences, path traversal, and path
    length growth. Verifying the embedded fields guards against a misplaced or
    incorrectly addressed cache entry in addition to the negligible hash
    collision risk.

- Topic: Equal place-cache keys and hash collisions
  - Decision: Distinguish intentional normalization equivalence from a digest
    collision. If two raw queries have the same complete canonical key, treat
    them as the same cache entry and replace it after a successful online
    search. If the SHA-256 filename exists but its embedded canonical key is
    different, do not read or overwrite that file; log the mismatch and store
    or address the second entry through a deterministic collision suffix.
  - Rationale: Refusing all updates for equivalent normalized queries would
    conflict with the online-first requirement and leave results permanently
    stale. Comparing the full embedded key, rather than trusting the digest
    alone, prevents a true collision or misplaced file from being mistaken for
    the requested search.

- Topic: Hash-bucket JSON representation
  - Decision: Use each SHA-256 filename as a bucket that can contain multiple
    cache entries. Select and update an entry only after comparing its complete
    canonical key. Append a new entry when the digest matches but no canonical
    key does; replace only the matching entry after a successful online search.
  - Rationale: A bucket representation handles a digest collision without
    filename suffix allocation or directory scans. Almost every bucket will
    contain one entry, while the schema remains correct for multiple entries.
    Atomic replacement preserves the complete bucket, and each entry can be
    validated by recomputing the filename digest from its embedded key.
