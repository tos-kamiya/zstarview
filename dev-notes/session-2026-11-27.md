# Session 2026-11-27

Scope: Benchmark building wall radius.

- Topic: Performance of a 1.0 km building wall radius
  - Decision: Compare the existing 0.2 km and 1.0 km options without editing production code.
  - Rationale: The urban-outline data radius controls building tile selection and the DEM request. The wall radius controls distance filtering, wall generation and occlusion. Keeping the data radius fixed isolates the cost of extending walls.
  - Method: Run `QT_QPA_PLATFORM=offscreen .venv/bin/python /tmp/zstarview-wall-bench.py LOCATION` at commit `c87b9970` on an Intel Xeon W-2235 with Python 3.13.18. Use cached building and DEM tiles, with the DEM fetch replaced in the benchmark process by local tile lookup. The existing layer code samples the DEM and generates geometry. Use the default 2.5 km data radius, 5,000 outline ring candidates, a 1.7 m observer height, and a fixed 800 x 800 Qt raster surface with view center (altitude 15°, azimuth 180°) and 90° edge and content FOV. Clear the observer-centric result cache for each layer build, leaving other in-process caches intact. Clear the wall path cache before the initial paint. Take the median of ten subsequent paints with unchanged geometry and view for each build. These paint times cover only the urban layer when it is rendered, independently of GUI frame image reuse.
  - Sites: Tokyo Tower (35.658611, 139.745556), PLATEAU. Taipei 101 (25.0330, 121.5624) and Matsue (35.4638, 133.0635), Overture buildings and parts.
  - Overture results (median of three for each radius, 0.2 km → 1.0 km):
    - Matsue: 99 → 824 wall segments before occlusion, 9,124 → 21,790 generated quads, 0.324 → 0.657 s layer build, 0.116 → 0.303 s wall generation, 81 → 171 ms first paint, 16 → 22 ms repaint with cached paths.
    - Taipei: 1,521 → 12,807 segments, 49,877 → 447,836 quads, 3.29 → 14.08 s layer build, 0.80 → 10.08 s wall generation, 337 → 1,978 ms first paint, 136 → 223 ms repaint with cached paths. Occlusion took 0.086 → 2.991 s.
  - Initial Tokyo result at 0.2 km (one sample): 5,053 segments, 34,143 quads, 19.17 s layer build, 1.50 s wall generation including 0.75 s occlusion, 763 ms first paint, 507 ms repaint with cached paths. Interrupted the next full run after over two minutes without a completed sample. The 1.0 km segment count is 170,142.
  - Bounded Tokyo result at 1.0 km: `/tmp/zstarview-wall-bounded.py` reproduced 170,142 input segments and stopped the exact occlusion function after 30.0 s without completing. The total build and paint were not measured to completion at 1.0 km for Tokyo.
  - Conclusion: The 1.0 km radius increases both initial worker latency and paint cost, with large variation by building density and geometry. Azimuth bins narrow occlusion comparisons, but each target can still compare against many segments in the same bin. Cached wall paths avoid repeating projection at a fixed view, and the GUI's base frame cache can avoid the layer repaint altogether. Keep 0.2 km as the global default given the observed dense-site costs.

- Topic: Reuse roof outline candidate selection for walls
  - Method: Temporarily capture the selected ring candidates from `compute_urban_outlines` in the benchmark process and pass their distinct buildings to the existing wall generator. Use the 5,000-candidate default and keep the same data and view as above. Production code is unchanged.
  - 1.0 km result: Matsue kept 824 input segments and 21,790 generated quads. Taipei kept 12,085 of 12,807 input segments and generated 443,257 quads, down from 447,836. Tokyo kept 132,782 of 170,142 input segments.
  - Rationale: The existing cap counts scored rings across the urban data radius. Buildings close to the observer tend to keep their slots, and one selected building can generate many wall segments, especially with LOD2 geometry.
  - Tokyo's filtered 1.0 km occlusion exceeded the 10 s timing limit. Taipei's filtered first paint took about 2.0 s in one run, close to the unfiltered median of 1.98 s.
  - Extending wall eligibility to the full 2.5 km urban radius with the same candidate filter increased the segment counts to 2,562 in Matsue, 50,285 in Taipei and 316,837 in Tokyo. Taipei and Tokyo occlusion were cut off after 1 s in this count-focused run.
  - Summary: Reusing the candidate cap alone does not bound wall complexity adequately. No production changes.

- Topic: Distance-dependent wall subdivision
  - Decision: Use the largest of 2 m, one tenth of the horizontal distance to the footprint, and the existing area-based step. Keep the distance eligibility and occlusion rules.
  - Rationale: At a fixed physical step, far walls generate small angular patches that add projection and paint work. Increasing the step with distance reduces that work while preserving detail close to the observer.
  - Validation: 11 nearby wall tests passed, including a regression test using identical geometry at two distances. Ruff and scoped diff checks passed. At 1.0 km, three runs with the same benchmark setup yielded 21,790 → 956 quads and 171 → 39 ms median first paint in Matsue, and 447,836 → 9,963 quads and 1,978 → 160 ms median first paint in Taipei. The occlusion input and survivors did not change. No commits, tags or pushes.
