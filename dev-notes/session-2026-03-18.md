# Session 2026-03-18

- Scope: Define the initial user-facing specification and INPROGRESS notes for an OpenSky-based aircraft overlay.

- Topic: Aircraft overlay documentation scope
  - Decision: Add the aircraft overlay only to `docs/specification.md` and `docs/implementation-history.md`, and keep it out of `docs/design.md` for now.
  - Rationale: The external behavior is clear enough to specify, but the internal threading, controller ownership, and cache layout are not settled yet.

- Topic: Default update cadence for aircraft data
  - Decision: Set the default OpenSky refresh interval to `4 minutes`.
  - Rationale: The feature is intended to work within the free usage tier. A coarse cadence is acceptable because the goal is ambient motion in the sky rather than exact traffic tracking.

- Topic: Position propagation model between API refreshes
  - Decision: Change the initial design to a snapshot-only model with no interpolation or extrapolation between OpenSky refreshes.
  - Rationale: A `4 minute` cadence is too coarse for convincing motion synthesis. Keeping aircraft fixed at the latest successful snapshot is simpler, keeps the displayed position tied to real API data, and reduces implementation risk for the first slice.

- Topic: Aircraft overlay internal design scope
  - Decision: Promote the aircraft feature into `docs/design.md` and define a dedicated controller/state/provider split.
  - Rationale: The user requested a concrete implementation design. Controller ownership, thread boundaries, and data models are now specific enough to document.

- Topic: Bounding-box open question
  - Decision: Fix the initial observer-derived `bbox` to `±1.0°` in both latitude and longitude, and define it as a shared code constant.
  - Rationale: A `2.0° x 2.0° = 4 square degree` query stays inside OpenSky `/states/all`'s `1 credit` band while still covering a wide area around the observer.

- Topic: Refresh cadence revision after credit check
  - Decision: Move the default aircraft refresh interval from `4 minutes` to `5 minutes`, and define it as a shared code constant.
  - Rationale: `4 minutes` is too close to the anonymous `400 credits/day` ceiling. `5 minutes` lowers the daily request count to `288`, leaving practical headroom for failures and retries.

- Topic: Aircraft controller scaffold
  - Decision: Add a dedicated `aircraft` package with an observer-centered bbox helper, OpenSky state-vector normalizer, and a Qt-side `AircraftController` / `AircraftState` scaffold.
  - Rationale: This creates a clean seam for later UI wiring and real API integration without entangling OpenSky fetch logic directly into `SkyWindow`.

- Topic: First visible aircraft overlay slice
  - Decision: Project fetched aircraft snapshots into observer-relative `alt/az`, keep only above-horizon markers, and draw them as small yellow points in the normal render path.
  - Rationale: This completes the first end-to-end user-visible slice without introducing interpolation. Yellow markers are intentionally high-contrast against the existing sky palette and are easier to pick out than white test points.

- Topic: Distance-aware aircraft marker sizing
  - Decision: Keep aircraft as point markers, but scale marker radius by observer distance instead of adding route lines.
  - Rationale: With `5 minute` snapshot updates and no interpolation, route lines would imply false continuity. Distance-aware point sizing gives useful depth cues without suggesting a precise flight path.
