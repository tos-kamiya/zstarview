# Session 2026-04-24

- Scope: investigate and fix moon phase orientation while rotating the zenith view.

- Topic: Moon phase rotation while changing view azimuth
  - Decision: Use the projected screen-up angle directly for the moon image rotation instead of negating it.
  - Rationale: In a zenith-centered view, changing `view_center` azimuth rotates the sky projection in the same direction. The existing negated angle made the moon phase bitmap rotate in the opposite direction while the moon position and other sky geometry followed the view.
  - Alternatives Considered: Adjusting the generated phase bitmap axes was not chosen because the reported symptom is tied to screen/view rotation, and the existing phase generation is shared by normal and hover drawing.

- Topic: Verification
  - Decision: Add a focused regression test for zenith-view azimuth changes and run the related moon/planet rendering tests.
  - Rationale: The bug is easiest to lock down by asserting that a `+45` degree view-azimuth change produces a `+45` degree screen-rotation change for the moon phase image.
  - Commands: `uv run -p .venv/bin/python pytest tests/test_moon_render_orientation.py tests/test_moon_phase_image.py tests/test_planet_marker_style.py`; `uv run -p .venv/bin/python ruff check src/zstarview/astro.py tests/test_moon_render_orientation.py`.

- End-of-session summary: fixed the moon phase screen rotation sign, added a regression test, updated implementation history, and verified the targeted tests plus lint.

- Topic: Direction grid cleanup
  - Decision: Keep the GUI hover entry point and CLI export entry point separate, but collapse the duplicate latitude-line loops inside `_draw_direction_grid()`.
  - Rationale: Both entry points already share the rendering body; the remaining duplication was only the identical handling of the horizon band and the 10-degree fine latitude bands.
  - Commands: `uv run -p .venv/bin/python pytest tests/test_direction_hover_guide.py tests/test_export_image_layer_gating.py tests/test_cli_export_image_args.py`; `uv run -p .venv/bin/python ruff check src/zstarview/render/guides.py tests/test_direction_hover_guide.py tests/test_export_image_layer_gating.py tests/test_cli_export_image_args.py`.

- Topic: Bottom-right resize grip visibility
  - Decision: Increase the bottom-right triangular grip marker from 14 px to 28 px and update the regression test to look for a point that moves from outside the old triangle to inside the larger one.

- Topic: Unified label layering before HUD
  - Decision: Collect label candidates across the base scene, fast overlays, hover overlays, and search overlays, then draw them once just before HUD text is rendered.
  - Rationale: The previous per-layer direct drawing made later labels collide with earlier ones. A shared candidate list lets later labels walk around earlier reservations while keeping marker rendering separate.

- End-of-session summary: unified label candidates across the scene, moved label drawing into a single pre-HUD pass, added regression tests for label ordering and search-target candidate collection, and verified the focused pytest and ruff checks.

- Topic: Missing label-candidate argument in HUD overlay
  - Decision: Pass the shared label candidate list through `_draw_overlay_layer()` so the unified HUD path satisfies its existing signature.
  - Rationale: The runtime error came from the refactor path that now threads label candidates through the HUD overlay. Wiring the same list through keeps the pre-HUD label aggregation intact and fixes the crash without changing label placement policy.

- Topic: Asterism hover labels bypassing shared placement
  - Decision: Pass the shared label candidate list into the asterism hover renderer so the highlighted asterism name participates in the same overlap avoidance as star labels.
  - Rationale: The asterism highlight label was still being drawn directly in the hover path, which skipped the shared candidate resolver and could land on top of star labels. Threading the list through keeps the existing priority order working.

- Topic: Shorter status line with icons
  - Decision: Replace the verbose status prefixes for clouds, satellites, aircraft, terrain horizon, and urban outlines with compact emoji-prefixed messages in the window status line.
  - Rationale: The status bar is UI-only text, so using icons makes the combined line easier to scan without changing the underlying state or error handling. The existing ASCII log messages remain unchanged.

- Topic: Urban outline icon adjustment
  - Decision: Use `🂓` for the urban outline status segment instead of `🏢`, `🗼`, or `🏘`.
  - Rationale: The requested glyph may render differently across platforms, but it matches the user's preference and keeps the status line compact.

- Topic: Terrain status icon adjustment
  - Decision: Use `▲` for the terrain status segment.
  - Rationale: The triangle reads as a compact, neutral terrain marker and stays visually distinct from the building and cloud icons already in use.

- Topic: Shorter failure banners and hidden-layer placeholders
  - Decision: Replace verbose download and fetch failure banners with short status text such as `unavailable`, `failed`, `timed out`, or `partial`, and show `icon ---` for layers disabled by CLI opacity settings.
  - Rationale: The status line should stay compact and should still make disabled layers visible as intentionally hidden. Emitting a placeholder keeps the line informative without exposing long exception strings.
  - Alternatives Considered: Leaving failure messages unchanged would keep the current verbosity. Omitting disabled layers entirely would hide useful state and make command-line suppression less obvious.

- Topic: Drag interaction design update
  - Decision: Document frameless window drag as a viewport interaction and treat it like resize-driven interaction for update suppression.
  - Rationale: The code path now begins viewport interaction on drag start and ends it on drag release, so the design record should explain why heavy sky/cloud refreshes are deferred while the window is moving.
  - Alternatives Considered: Keeping drag outside the interaction model would leave the design inconsistent with the current mitigation and make the crash workaround harder to justify later.
