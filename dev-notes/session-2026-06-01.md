- Topic: Tropical cyclone fast overlay integration
  - Decision: Moved tropical cyclone drawing out of the base scene and into `render_fast_overlay_layers_into_painter`, matching the aircraft and satellite overlay path. Removed the dedicated cyclone projection interval constant and reused the aircraft prediction interval for cyclone reprojection.
  - Rationale: The cyclone overlay was still coupled to base-scene caching, which let unrelated redraw paths control when it became visible. Treating it as a fast overlay makes redraw behavior consistent with aircraft and satellites, and removing the bespoke interval keeps the timing model simpler.
  - Validation: Updated render-cache-key tests to keep cyclone state out of the base cache while still tracking it in the present-frame cache.
- Topic: Tropical cyclone column presentation
  - Decision: Replaced the 500 m radius cylinder with a simple 3 px column line through the cyclone center at 0, 5, 10, and 15 km altitude.
  - Rationale: The cylinder was visually fragile and frequently collapsed in projection. A line matching the water overlay dot radius is more legible and directly represents the centerline through the sampled altitudes.
  - Validation: `uv run -p .venv/bin/python pytest tests/test_window_render_sync.py tests/test_scheduler_idle.py tests/test_tropical_cyclones.py -q`
- Topic: Fast-mode dynamic overlay suppression
  - Decision: Suppressed the dynamic overlay pass in the downsampled fast frame used during viewport interactions, while leaving normal present-frame fast overlays unchanged.
  - Rationale: Resize/drag fast frames reuse cached projection state, so aircraft, satellites, and cyclones can appear at their pre-resize positions. Hiding the full dynamic overlay pass avoids stale markers without changing the normal render path.
- Topic: Viewport interaction sky-data handoff
  - Decision: Keep viewport interaction mode active after idle if a sky-data update was started, then exit fast mode when the updated sky data arrives.
  - Rationale: Returning to normal rendering before the new celestial data is ready combines the new view center with the old visible-star subset, leaving stars absent in regions that were outside the previous view.

- Topic: Tropical cyclone cylinder rendering
  - Decision: Project a fixed 1km-radius cylinder with 8 radial samples and 1km vertical samples from 0km through 15km, and render the projected rings/sides when the apparent screen width is at least 4px.
  - Rationale: This makes nearby tropical cyclone markers use physical dimensions instead of a fixed screen-space width while retaining a legible minimum representation for distant or edge-on cases.
  - Alternatives Considered: Keeping the fixed water-dot line width. Rejected because it does not represent the requested physical radius.

- Topic: Narrow tropical cyclone fallback
  - Decision: When the projected physical cylinder is narrower than 4px on screen, draw the existing centerline as a 4px cosmetic line.
  - Rationale: A very narrow projected polygon can disappear or alias; the line fallback preserves visibility without exaggerating wide nearby cylinders.
  - Validation: `uv run -p .venv/bin/python pytest tests/test_tropical_cyclones.py -q` -> `18 passed in 1.28s`
  - Validation: `uv run -p .venv/bin/python ruff check src/zstarview/render/tropical_cyclones.py tests/test_tropical_cyclones.py`
