# Session 2026-04-21

- Scope: Investigate and fix cloud stripe baseline gaps seen in debug renders.

- Topic: Cloud stripe baseline gaps in width mode
  - Decision: Reworked width-mode stripe sampling so cloud amount is read from the stripe baseline projected point only, rather than from positions between baselines.
  - Rationale: The debug frame showed isolated gaps where baseline segments dropped out while later diagonal lines remained. Sampling only the baseline removes the interior-of-band dependence that was letting the renderer skip the baseline in some local regions.
  - Validation: `uv run -p .venv/bin/python pytest tests/clouddisc/test_cloud_hatch.py tests/clouddisc/test_cloud_missing_overlay.py`
  - Validation: `uv run -p .venv/bin/python ruff check src/zstarview/gui/composite.py tests/clouddisc/test_cloud_hatch.py`

- Topic: Remove cloud stripe debug snapshot saving
  - Decision: Deleted the cloud stripe pre-compose debug image save path and its dedicated test.
  - Rationale: The debug-only file dump was no longer needed after the baseline-only sampling change, and removing it keeps the compositor simpler and avoids retaining an extra filesystem side effect.

- Topic: Cloud FOV overscan before clipping
  - Decision: Render cloud stripes with a small fixed FOV margin above the visible content FOV, then let the existing disc clipping remove anything outside the final view.
  - Rationale: The visible sky already needs the edge, but the cloud hatch looked like it stopped too early. Overscanning only the cloud pass preserves the final crop while allowing cloud stripes to extend into the outer ring before clipping.

- Topic: Reduce cloud FOV overscan
  - Decision: Trimmed the cloud render margin from `+20deg` to `+12deg`.
  - Rationale: The larger margin was acceptable but broader than necessary. Reducing it keeps the same edge coverage while limiting how far the cloud pass expands beyond the visible FOV.

- Topic: Raise default content FOV
  - Decision: Updated the default `content_fov_deg` from `100deg` to `115deg` across CLI parsing, GUI runtime defaults, export-image fallbacks, and the viewer data default.
  - Rationale: The user asked for a wider default content field so edge objects and clouds are less likely to drop out near the visible boundary. Keeping the default aligned across entry points avoids behavior drift between GUI, export, and direct viewer construction.

- Topic: Split content FOV and projection FOV
  - Decision: Updated the specification and design docs to treat `--content-fov-deg` as the drawable-content extent and a new `--edge-fov-deg` as the screen-projection scale.

- Topic: Edge FOV is startup-only
  - Decision: Clarified that `--edge-fov-deg` is applied only at startup and is not part of the live UI state or frame-cache invalidation key.
  - Rationale: The value is not changed during runtime, so including it in redraw cache keys would add complexity without any behavioral benefit.
