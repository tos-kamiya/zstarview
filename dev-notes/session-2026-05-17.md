- Topic: Long-running sky-disc memory pressure
  - Decision: Reduced the full-window sky-disc `QImage` LRU cache from 32
    entries to 2 and added a regression test for the cache bound.
  - Rationale: Periodic sky updates include continuously changing sun
    coordinates, so a large cache has poor reuse and can retain many Qt-backed
    full-window images. Keeping only the most recent entries preserves
    duplicate-request protection while reducing long-running memory pressure
    that can surface as Qt/native crashes.
  - Alternatives Considered: Removing the cache entirely would also fix the
    retention risk, but a tiny cache keeps immediate duplicate stale-render
    follow-up requests cheap.

- Topic: Shared GUI worker pool
  - Decision: Routed all long-running GUI background work through a single
    shared `ThreadPoolExecutor(max_workers=1)` and replaced per-task
    `threading.Thread` launches with `submit_gui_work(...)`.
  - Rationale: The app was still creating independent background threads for
    sky, cloud, terrain, satellite, aircraft, water, urban-outline, JPL, and
    startup/search jobs. A size-1 pool guarantees those expensive jobs do
    not overlap, which is the most direct way to serialize the native-heavy
    work without changing each subsystem's internal logic.
  - Alternatives Considered: Keeping separate threads plus a global lock
    still leaves lifecycle complexity spread across modules. The shared pool
    centralizes queueing and makes shutdown ordering explicit.

- Topic: Pool lifecycle
  - Decision: Make the shared GUI worker pool lazily re-creatable after
    shutdown instead of treating shutdown as terminal for the whole process.
  - Rationale: The app shuts the pool down during window teardown, but the
    test suite and any future in-process restart paths may submit work again.
    Recreating the pool on demand keeps the size-1 serialization behavior
    while avoiding a permanent `RuntimeError: cannot schedule new futures`.
- Topic: Water overlay crash mitigation
  - Decision: Stop the GUI water-overlay update path from refetching Copernicus
    DEM tiles for `target_ground_sampler`, and add step-by-step progress logs
    plus `faulthandler` enablement at startup.
  - Rationale: The remaining crash window was in the water overlay update path
    after terrain had already populated ground elevation. That path was

    for the GUI to render the existing sea mask and Overpass water polygons.

  - Alternatives Considered: Leaving the DEM refinement enabled would keep a
    richer inland-water model, but it also preserves the native crash risk.
    A subprocess isolation redesign would be more robust, but it is a much
    larger change.

- Topic: Water overlay cache migration
  - Decision: Rename the per-scope water overlay cache files to
    `*_simplified.json`, keep the legacy `*.json` as a migration source, and
    compare mtimes so a newer legacy cache can regenerate the simplified
    cache on load.
  - Rationale: Dense inland-water caches can grow very large, so the new
    filename makes the simplified form explicit and avoids confusing it with
    the older raw cache. Keeping the legacy file as input-only preserves
    existing user caches while still converging on the smaller format after
    an update.
  - Alternatives Considered: Leaving the filename unchanged would keep the
    migration opaque and leave old raw caches mixed with the new simplified
    ones. Using a separate compatibility file would avoid overwrite concerns
    but would double the on-disk cache footprint.
