# Session 2026-05-12

- Scope: classify main-window rendering layers by target surface vs direct window drawing.

- Topic: Main-window render target split
  - Decision: The scene pipeline is rendered almost entirely into offscreen `QImage` surfaces; the main window itself only receives a final `drawImage` blit, plus a small resize-grip marker in the frameless chrome. The only intentionally smaller-than-window surface is the star layer's low-resolution `QImage` path in `_draw_star_layer`.
  - Rationale: This keeps the expensive scene composition off the window paint step and makes the threading/refactor boundary easier to reason about. The star downsample path is the only layer that materially depends on a reduced render surface size.

- Topic: Fast-mode vs deferred redraw
  - Decision: Arrow-key rotation and resize enter `viewport_interaction_mode` immediately, which switches rendering to a reduced fast path. That fast path keeps only the essential scene cues and suppresses expensive overlays until the interaction idle timer or key-release path restores the full render.
  - Rationale: Immediate feedback matters while the user is actively manipulating the view, but the detailed layers are expensive and are better recomputed once input settles.

- Topic: GUI entrypoint split
  - Decision: Add a new `zstarview-gui` entrypoint and keep the legacy viewer module as a compatibility/reference wrapper for now.
  - Rationale: This lets the command-line surface move forward without forcing a simultaneous refactor of the old module and the rendering state machine.

- Topic: Fast-mode auto-refresh gating
  - Decision: Disable timer-driven refreshes for satellite, aircraft, persistent-search, and overlay-projection updates while viewport interaction is active; resize now only requests an immediate redraw and lets idle transition trigger the heavier refreshes.
  - Rationale: This keeps fast-mode strictly about quick visual feedback and prevents background update churn during drag/resize interaction.

- Topic: Fast-mode status line
  - Decision: Keep drawing the status line during viewport interaction so background activity remains visible even when the rest of the frame is in fast-mode.
  - Rationale: The status line is low-cost and gives immediate feedback that long-running work is still active, which helps explain the delayed refresh behavior.

- Topic: Viewport exit sky refresh
  - Decision: Allow sky-data refresh to start on viewport-interaction exit paths even though generic background updates stay blocked during fast-mode.
  - Rationale: The release/idle transition depends on kicking off a fresh sky render; deferring that request entirely caused the app to remain in fast-mode and never return to normal rendering.

- Topic: Fast-mode draw cleanup
  - Decision: Strip hover/search/label overlay work from the fast-mode render branch and keep only the status line.
  - Rationale: Fast-mode should minimize work to the visible essentials; the removed overlay paths are only useful once the full normal render resumes.

- Topic: Terrain fast path split
  - Decision: Add a dedicated fast-mode terrain horizon entrypoint and keep the secondary ridges renderer normal-mode only.
  - Rationale: The fast interaction path only needs the main horizon line, so separating the code removes an unnecessary mode branch from the normal renderer.

- Topic: Star renderer entry split
  - Decision: Add dedicated `draw_stars_fast(...)` and `draw_stars_normal(...)` entrypoints, while keeping a compatibility `draw_stars(...)` wrapper for older callers and tests.
  - Rationale: The star layer now follows the same fast/normal boundary as terrain, which makes the pipeline call sites clearer without forcing every existing caller to change at once.

- Topic: Earth guide entry split
  - Decision: Add dedicated `draw_earth_guide_fast(...)` and `draw_earth_guide_normal(...)` entrypoints, and update the compositor to choose the entrypoint explicitly instead of passing a fast-mode flag through one shared call.
  - Rationale: The earth guide has a noticeably different fast-mode shape and is another clear boundary for the viewport-interaction path. Keeping the compatibility wrapper preserves existing tests and callers while the compositor adopts the clearer split.

- Topic: Night light glow entry split
  - Decision: Add a `draw_night_light_glow_normal(...)` entrypoint and keep the legacy `draw_night_light_glow(...)` as a compatibility wrapper that no-ops in fast-mode.
  - Rationale: Night-light glow is only meaningful in the normal render path, so making the compositor call the normal entrypoint directly keeps the fast-mode boundary explicit without breaking existing tests.

- Topic: GUI command rename
  - Decision: Point the canonical `zstarview` GUI script at `zstarview.gui.app:main`, keep `zstarview-gui` as an alias, and switch the desktop launcher generator to `zstarview`.
  - Rationale: The new GUI entrypoint is now the default command, while the old `viewer` entry remains available only as an internal implementation detail and debug path.

- Topic: GUI wrapper removal
  - Decision: Remove the thin `zstarview.gui.app` wrapper and point both `zstarview` and `zstarview-gui` at `zstarview.gui.viewer:main`.
  - Rationale: The wrapper added an extra hop without adding behavior. Keeping both script names mapped to the same real entrypoint preserves the user-facing command surface while eliminating the compatibility shim.

- Topic: Fast/normal impl split
  - Decision: Rename the shared star and earth-guide renderers to `_render` helpers and introduce separate `_draw_*_fast_impl(...)` / `_draw_*_normal_impl(...)` entrypoints that forward to them.
  - Rationale: The mode-specific entrypoints are now explicit, while the shared rendering code has a neutral name. That makes the fast/normal boundary easier to scan without duplicating the low-level rendering logic yet.

- Topic: Startup splash removal and startup log handoff
  - Decision: Replace the splash-screen startup log path with a buffered startup log handler that can feed an overlay inside the main window until the initial scene is ready.
  - Rationale: This keeps the user-facing startup feedback in the actual main window, removes the separate splash surface, and gives us a clean cutoff point when the window transitions into normal rendering.

- Topic: Startup load race suppression
  - Decision: Suppress viewport-interaction-driven background refreshes until the deferred initial load has actually started.
  - Rationale: Showing the window before location resolution can trigger resize-driven timers; blocking those timers until startup resolution completes avoids background fetches during failure paths and prevents shutdown races.

- Topic: Startup error persistence and auto-close switch
  - Decision: Keep startup error logs visible in the main window by default, colorize warning/error lines, and add `--close-on-startup-error` for users who want the previous auto-close behavior with a non-zero exit code.
  - Rationale: The default should make startup failures easy to inspect in-context, while the CLI switch preserves the older automation-friendly behavior for scripts and wrappers that expect a failing exit code.

- Topic: Startup error menu visibility
  - Decision: When startup fails, raise the frameless window's hamburger menu so the user can still open the app menu while reading the persistent error log.
  - Rationale: Keeping the log visible is not enough if the menu is visually buried during startup failure; raising the menu preserves access to exit/help actions without changing the default success path.

- Topic: Water surface note review
  - Decision: Reviewed `ChatGPT-zstarviewで水面描画.md` and confirmed it is a useful design note for adding nearby water rendering via OSM/Overpass data.
  - Rationale: The note correctly separates inland water, river polygons, river centerlines, and coastline handling, and it calls out the main implementation risks: incomplete OSM coverage, multipolygon inner rings, and Overpass query limits.

- Topic: Water overlay spec/design update
  - Decision: Documented water overlay as a ground-side auxiliary layer, with `water polygon` and `water only style` separated in the spec/design and cache freshness aligned to the DEM scale at `90日`.
  - Rationale: Keeping the water cache on the same long-lived time horizon as DEM avoids unnecessary refetch churn while still leaving room for a short negative cache on empty or failed bbox queries.

- Topic: Water overlay sample probe
  - Decision: Added `dev-samples/overpass_water_overlay_probe.py` as a dependency-free Overpass probe that reconstructs water polygons and waterways into normalized JSON and optional SVG preview output.
  - Rationale: The sample makes the outer/inner ring split, polygon-vs-line split, and bbox-based query shape explicit without tying the design to the production cache layer yet.

- Topic: Water overlay sample simplified to polygons
  - Decision: Simplified the probe to `water polygon` only and removed waterway line output from the sample.
  - Rationale: The SVG review suggested that centerline waterways add noise in this view, so keeping the sample focused on polygon fill and holes makes the intended data structure clearer.

- Topic: Water overlay cache-key clarification
  - Decision: Clarified the spec/design so water overlay cache keys are derived from center `lat/lon`, `radius_km`, `source`, and `feature_set`, with `bbox` treated as a derived query range.
  - Rationale: This matches the existing building-cache pattern and keeps the cache identity tied to the user-facing search radius instead of an incidental bbox serialization.

- Topic: Water overlay triangulated SVG probe
  - Decision: Added a triangulated SVG preview path to `dev-samples/overpass_water_overlay_probe.py` by ear-clipping each outer ring and subtracting holes with background-colored triangles.
  - Rationale: A triangle preview makes long, narrow, and irregular water polygons easier to inspect without introducing extra dependencies. Keeping the implementation in the sample script preserves the production design discussion while still giving a concrete shape check.
  - Validation: `python3 -m py_compile dev-samples/overpass_water_overlay_probe.py`; generated `/tmp/suwajinjaato-triangulated.svg` from `suwajinjaato-water-overlay.json` successfully.

- Topic: Shapely-based triangulation
  - Decision: Switched the triangulated SVG probe to `shapely.constrained_delaunay_triangles` after adding `shapely` to the development dependencies.
  - Rationale: Constrained Delaunay triangulation preserves polygon boundaries and holes better than the earlier hand-rolled ear-clipping prototype, which produced too many long skinny triangles on irregular water polygons.
  - Validation: `uv run python dev-samples/overpass_water_overlay_probe.py --lat 35.18522541965554 --lon 133.32492589284828 --output-json /tmp/suwajinjaato-water-overlay.json --output-triangulated-svg /tmp/suwajinjaato-water-overlay-triangulated.svg` completed successfully.

- Topic: Triangulation simplification pre-pass
  - Decision: Added a local-meter pre-pass using `set_precision(..., grid_m)` and `simplify(..., preserve_topology=True)` before constrained triangulation.
  - Rationale: The first Shapely triangulation was visually clean but produced a very large triangle count. Simplifying first reduces unnecessary vertices while keeping the polygon topology intact, which is a better fit for preview and eventual render-mesh exploration.
  - Validation: Rebuilt `/tmp/suwajinjaato-water-overlay-triangulated-simplified.svg` from `suwajinjaato-water-overlay.json` with `grid_m=1.0` and `simplify_m=20.0`; the output contained 682 triangle paths.

- Topic: Water surface 3-point patch rule
  - Decision: Model each water surface patch with three anchor points, keep all three, and switch between flat and sloped-plane handling based on DEM height spread rather than discarding one point.
  - Rationale: A three-point patch keeps the geometry simple while still allowing the surface to follow gentle terrain gradients. The flat/sloped split is a better fit than a raw length threshold because it reacts to actual sampled elevation differences.
  - Validation: Captured as the production-side design direction; no runtime code change was needed for this step.

- Topic: Water overlay core module split
  - Decision: Added `src/zstarview/water_overlay.py` as the first production slice for water overlay normalization. It now holds the water polygon footprint model, ring reconstruction helpers, Overpass bbox/query helpers, and the 3-point `flat` / `sloped` patch classifier.
  - Rationale: Splitting the work keeps acquisition/normalization separate from mesh generation and GUI wiring, which reduces risk and makes each follow-up slice easier to validate.
  - Validation: Added `tests/test_water_overlay.py`; `uv run pytest tests/test_water_overlay.py` passes.

- Topic: Water overlay mesh-generation slice
  - Decision: Added `src/zstarview/water_surface_mesh.py` as the next production slice. It projects footprints into a local AEQD plane, applies `set_precision` and topology-preserving `simplify`, then uses `shapely.constrained_delaunay_triangles` to produce triangle meshes.
  - Rationale: This keeps mesh generation isolated from GUI rendering while still using the same geometric preprocessing that the dev sample proved to be effective.
  - Validation: Added `tests/test_water_surface_mesh.py`; `uv run pytest tests/test_water_surface_mesh.py` passes.

- Topic: Water overlay render and controller wiring
  - Decision: Wired water surfaces into the render scene and added a dedicated water overlay controller/state pair in the GUI layer. The renderer now projects water triangles from the local tangent plane onto the sky-dome view, and the window starts a background water overlay update on startup.
  - Rationale: This keeps the production path aligned with the existing background layers: resolve data off the UI thread, store it in window state, and let the render pipeline consume it. Using a shared observer elevation for projection keeps the mesh visually attached to the ground without adding a separate terrain-occlusion pass yet.
  - Validation: `uv run python -m py_compile src/zstarview/render/pipeline.py src/zstarview/render/water.py src/zstarview/gui/window_render.py src/zstarview/gui/window.py src/zstarview/gui/window_updates.py src/zstarview/gui/water_overlay_state.py src/zstarview/gui/water_overlay_controller.py src/zstarview/water_overlay_layer.py src/zstarview/water_surface_mesh.py`; `uv run pytest tests/test_water_overlay.py tests/test_water_surface_mesh.py`

- Topic: Water overlay scan-anchored fallback
  - Decision: Added a scan-anchored `water run` fallback to the water overlay design. Narrow rivers and valley water can be shown by marking the terrain horizon distance samples that fall inside a water polygon, then drawing those consecutive samples as a blue segment or thin ribbon. Large lakes and ponds remain polygon-fill driven.
  - Rationale: This reuses the same distance-scan mental model as the terrain horizon renderer, which should keep near-river water from "fighting" with the polygon mesh projection. It also preserves the existing polygon path for large, stable water bodies.
  - Validation: Documentation-only update; no runtime code change required for this decision.

- Topic: Water overlay runtime rollback
  - Decision: Rolled back the runtime water overlay wiring and mesh/controller path, while keeping `src/zstarview/water_overlay.py` and the sample polygon probe intact. The production code now stops at polygon normalization and ring reconstruction; GUI/render integration, mesh generation, and the dedicated water controller/state were removed.
  - Rationale: The near-river projection was visibly unstable, so the safest boundary is to keep the polygon acquisition layer and remove the screen-space path until the scan-anchored fallback is ready. This preserves the core OSM parsing work without letting the partially tuned renderer affect the rest of the UI.
  - Validation: `uv run python -m py_compile src/zstarview/render/pipeline.py src/zstarview/gui/window.py src/zstarview/gui/window_render.py src/zstarview/gui/window_state.py src/zstarview/gui/window_updates.py src/zstarview/cli/export_image.py src/zstarview/water_overlay.py tests/test_water_overlay.py`; `uv run pytest tests/test_water_overlay.py`
