# Session 2026-05-30

- Scope: Add a dev-samples probe for publicly accessible tropical cyclone data via ArcGIS FeatureServer.

- Topic: Public ArcGIS hurricane feed probe
  - Decision: Added `dev-samples/arcgis_active_hurricanes_probe.py` to fetch the public `Active_Hurricanes_v1` FeatureServer without an API key or token and print a short summary for each layer.
  - Rationale: The probe demonstrates the no-auth path directly, keeps the example self-contained, and avoids coupling the exploratory sample to any authenticated ArcGIS setup.
  - Validation: ` .venv/bin/python -m py_compile dev-samples/arcgis_active_hurricanes_probe.py `
  - Validation: `uv run -p .venv/bin/python ruff check dev-samples/arcgis_active_hurricanes_probe.py`
  - Follow-up: Improved the probe output to fall back to the service URL basename when metadata omits a name and to format `ADVDATE` as UTC wall-clock time instead of raw epoch milliseconds.
  - Follow-up: Made `Observed Position` query the latest `DTG` first and show only the current position record so the sample distinguishes the current point from historical observations.
  - Follow-up: Refocused the probe on the active storm's current position, forecast position, and wind polygon layers; the script now derives the storm identity from the latest observed position and filters the other layers to the same storm.
  - Follow-up: Replaced server-side storm filters on the forecast and wind layers with client-side filtering after fetching the layer contents, because the earlier query parameters caused some layers to return `Invalid query parameters` and lose data in the sample output.
  - Topic: Document tropical cyclone overlay behavior
    - Decision: Added specification and design notes for a public ArcGIS-based tropical cyclone feed, including current position, forecast position, wind polygon layers, ADVDATE-based refresh, 90-minute lightweight update checks, and 3-hour cache expiry.
    - Rationale: The feed is useful enough to document now, but the exact rendering style is still open, so the docs capture data semantics and cache/update policy without overcommitting to visual design.
  - Topic: Inverted danger-surface visualization
    - Decision: Documented a stepped inverted-terrain presentation as an allowed rendering metaphor, with stronger wind bands placed closer to the ground and weaker bands lifted higher.
    - Rationale: The metaphor preserves the horizontal footprint of the storm while making the strongest wind field read as the lowest, most dangerous layer. The shape can stay circular or polygonal; it does not need a square base.
