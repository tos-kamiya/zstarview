- Topic: README water-overlay usage note

  - Rationale: The water overlay is the one runtime feature most likely to expose users to Overpass's fairness controls. The README should warn about the practical download cost without describing the public-instance guidance as a hard limit.

- Topic: Water mesh triangulation backend swap
  - Decision: Remove `shapely` from the core dependency set, add `mapbox-earcut` as the triangulation backend, and restore the water-surface mesh helper and dev-sample triangulation path on top of it.
  - Rationale: `mapbox-earcut` has prebuilt wheels on the target platforms, including Windows ARM64, so it avoids the source-build failure that blocked `pipx install`. The water mesh path only needs polygon triangulation, so the smaller dependency is sufficient for the same role.
  - Summary:

    - Updated `dev-samples/overpass_water_overlay_probe.py` to triangulate via the shared mesh helper instead of `shapely`.

- Topic: Dev-sample grid-split prototype for thin water polygons

  - Rationale: The sample needs a way to probe whether grid-based subdivision reduces thin triangles without changing production code yet. Keeping the prototype in `dev-samples/` makes the experiment easy to turn on and off, and the existing shared mesh helper still owns the final triangulation step.

- Topic: Dev-sample default grid size
  - Decision: Set the default `--triangulation-cell-m` value to `300.0` in the sample.
  - Rationale: Manual testing showed that 300m was sufficient to tame the thin polygon cases while keeping the output readable. Making it the default reduces friction when rerunning the experiment.

- Topic: Core water mesh grid refinement
  - Decision: Add a `split_cell_m` refinement step to `build_water_surface_mesh()` that clips earcut triangles to a meter grid and re-triangulates the clipped pieces.
  - Rationale: The core package stays free of `shapely`, but the mesh still benefits from cell-based subdivision when thin triangles show up. Doing the split after earcut keeps the implementation pure Python and local to the existing mesh helper, while preserving the original polygon area in tests.

- Topic: Fixed 300m split cell size
  - Decision: Hard-code the grid refinement cell size to `300.0` meters in the core mesh helper and remove the CLI knob from the sample.
  - Rationale: Manual testing showed that 300m was a good default, so exposing the value as a runtime option just adds surface area without practical benefit. Fixing it in the core keeps behavior consistent across callers and avoids carrying a sample-only control path.

- Topic: Restore pre-triangulation cell clipping
  - Decision: Move the 300m grid split back in front of earcut by clipping each shell and hole ring to grid cells before triangulation.
  - Rationale: Post-triangulation splitting changed the visual pattern. Clipping the rings first keeps the output closer to the original sample behavior while still avoiding a shapely dependency in the core package.

- Topic: Drop triangulated preview from sample

  - Rationale: The sample is used to inspect raw overlay shapes, and polygon fill rendering is sufficient for that job. Removing the triangulation preview simplifies the sample and avoids implying that the triangle soup is required for 2D drawing.

- Topic: Restore grid-split SVG preview
  - Decision: Add `--output-split-svg` to `dev-samples/overpass_water_overlay_probe.py` so the experiment can emit a 300m grid-clipped polygon SVG without triangulating first.
  - Rationale: The visual check needs the intermediate cell-clipped polygon shapes, not a triangle soup. Keeping this as a separate output preserves the plain SVG preview and makes the grid behavior easy to compare side by side.

- Topic: Share grid clipping with core

  - Rationale: This keeps the experiment aligned with the production clip path and avoids maintaining a second copy of the same cell-splitting algorithm in `dev-samples/`.

- Topic: Remove core triangulation
  - Decision: Delete the earcut-based mesh path from `src/zstarview/water_surface_mesh.py` and keep that module focused on local projection and 300m grid clipping helpers only.
  - Rationale: The application no longer needs polygon-to-triangle conversion in the core package. Removing the triangulation path eliminates the extra dependency and keeps the sample-side split preview aligned with the same core clipping code.

- Topic: Water overlay startup guard
  - Decision: Skip `start_background_water_overlay_update()` when `water_overlay_opacity <= 0.0`.
  - Rationale: The GUI was still spawning water-overlay work during initial load and terrain callbacks even when the layer was disabled, which caused unnecessary Overpass/DEM work and made the app feel slow. Guarding the shared entrypoint keeps the disabled state truly inert.

- Topic: Riverbank-only split preview
  - Decision: Limit the 300m grid-split SVG preview in `dev-samples/overpass_water_overlay_probe.py` to polygons whose kind is `riverbank`.
  - Rationale: Riverbank polygons are the cases where height variation matters, while lakes and sea polygons can stay coarse. Restricting the split keeps the experiment focused and reduces the number of generated pieces.

- Topic: Sample coastline parity
  - Decision: Reuse `zstarview.water_overlay.extract_water_polygons()` in `dev-samples/overpass_water_overlay_probe.py` so coastline-derived sea polygons are reconstructed the same way as in the core app.
  - Rationale: The sample's bespoke extraction path skipped open coastline ways, which made sea disappear around locations like Kobe Port Tower. Reusing the core extraction logic keeps the sample aligned with production behavior while preserving the grid-split experiment for riverbank polygons.

- Topic: Sample coastline restore
  - Decision: Keep the sample's original local extraction for closed water polygons and append only `kind == "coastline"` footprints from the core extractor when a bbox is available.
  - Rationale: Replacing the whole extraction path with the core helper still did not reliably restore the sea preview in the sample. Restoring the original path for normal water polygons keeps the sample stable, while selectively importing coastline output preserves the sea preview without changing the riverbank-only split rule.

- Topic: Sample coastline retry
  - Decision: If the first Overpass response yields no coastline footprints, retry the same request once and prefer the retry only when it includes coastline output.
  - Rationale: Coastline reconstruction around Kobe was inconsistent across identical requests. A single retry is a low-cost way to recover the sea preview when the first response lacks enough coastline geometry, without changing the main extraction logic.

- Topic: Sample coastline margin
  - Decision: Query Overpass with a small radius margin, then clip the resulting polygons back to the requested view bbox before writing SVG/JSON.
  - Rationale: The coastline extraction becomes more reliable when it has a little more context outside the visible area. Clipping the results back to the original bbox keeps the preview focused while preserving the sea reconstruction benefit.

- Topic: Preserve coastline footprint
  - Decision: Keep coastline footprints un-clipped in the sample output once they are found, while still clipping non-coastline water polygons to the view bbox.
  - Rationale: The coastline footprint is what makes the sea visible. Clipping it aggressively could erase the reconstructed sea face, so the sample favors visibility over a tight crop for that specific kind.

- Topic: Clip coastline geometry collections
  - Decision: Treat `GeometryCollection` results from coastline clipping as collections of drawable polygon pieces instead of discarding them.
  - Rationale: Clipping coastline polygons against the view bbox can produce mixed geometry outputs. Recursing through geometry collections preserves the polygon pieces that matter for the sea preview and avoids dropping coastline entirely.

- Topic: Sample coastline retry selection
  - Decision: Fetch the Overpass response up to three times in the sample and keep the polygon set with the highest coastline count, breaking early once a coastline is seen.
  - Rationale: Overpass responses around the Kobe test area were inconsistent across identical requests. Picking the coastline-rich response makes the sea preview much more reliable while keeping the retry count small.

- Topic: Sample coastline attempt cap
  - Decision: Raise the sample's Overpass retry budget to eight attempts.
  - Rationale: The Kobe coastline preview still fluctuated between coastline-rich and coastline-free responses. A slightly larger retry budget improves the odds of selecting a response that preserves the sea preview without changing the visible output logic.

- Topic: Sample cache input
  - Decision: Add `--input-cache` to `dev-samples/overpass_water_overlay_probe.py` so the sample can render directly from an existing water-overlay cache file.
  - Rationale: The user already has a cache snapshot with enough coastline context. Reading that file directly avoids Overpass variability and lets the preview use the exact data already generated by zstarview.

- Topic: Sample water color coding
  - Decision: Color SVG output by water category, using separate styles for sea/coastline, river-like water, and lake-like water.
  - Rationale: The cache data already retains tags such as `water=river`, `water=lake`, `water=reservoir`, and `natural=coastline`. Distinguishing them visually makes it easier to inspect which surfaces are being treated as rivers versus standing water.

- Topic: Sea highlight color
  - Decision: Change the sea/coastline color in the sample SVG output to an orange palette.
  - Rationale: Orange separates sea from the blue river/lake palette more clearly and makes coastline faces easier to spot at a glance in the preview.

- Topic: River-only split criterion
  - Decision: Use the sample's water-category classifier to split only river-like polygons, including `water=river`, `water=stream`, `water=canal`, `water=drain`, and `waterway=riverbank`.
  - Rationale: The classification has proven accurate for distinguishing sea, lake, and river surfaces. Limiting grid subdivision to the river-like class keeps the split focused on thin, shape-sensitive water surfaces and avoids unnecessary subdivision of lakes and seas.

- Topic: Remove shapely from water overlay
  - Decision: Drop `shapely` from the core water overlay path and from the dev-sample helpers, keeping the geometry processing in pure Python.
  - Rationale: The packaging problem on Windows ARM64 came from shapely wheels and build-time dependencies. The current water overlay flow only needs ring assembly, point-in-ring checks, and SVG path emission, so a geometry dependency is unnecessary.

- Topic: Formalize water categories
  - Decision: Update the specification and design docs to describe sea, river-like, and lake-like water categories, and to treat river-like footprints as the only diagnostic split target.
  - Rationale: The Westminster Bridge and Kobe Port Tower cache data separate those categories cleanly enough for practical use. Writing that down makes the sample behavior and core classification easier to keep aligned.

- Topic: Apply water categories in core sampling
  - Decision: Add a shared `classify_water_surface_category()` helper in `zstarview.water_overlay` and use it in the core water point sampler so river-like surfaces can keep DEM sampling while sea and lake-like surfaces stay flat.
  - Rationale: The dev-sample classifier already distinguished sea, river, and lake well enough. Moving the rule into core keeps the app and the experimental scripts on the same classification logic and avoids a second copy of the tag mapping.
