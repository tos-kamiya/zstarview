# Session 2026-05-15

- Scope: Investigate whether GUI shutdown can cancel in-flight Himawari downloads instead of waiting for every worker to finish.

- Topic: Cloud download cancellation on shutdown
  - Decision: Add a cooperative abort event to cloud fetches and set it during GUI shutdown so active GOES/Himawari downloads can stop early instead of waiting for every file transfer to complete.
  - Rationale: The current shutdown path waits on worker threads, and Himawari can download many tiles sequentially. Boto3 S3 transfers support a progress callback, so the worker can raise a cancellation signal from that callback and unwind cleanly.
  - Alternatives Considered: Leaving shutdown as a hard wait was rejected because it keeps the window open for the full download duration. Killing threads was not considered safe.

- Topic: Terrain and urban-outline cancellation on shutdown
  - Decision: Extend the same abort-event pattern to Copernicus DEM fetches and Overture building imports, and set the event from the terrain/urban controllers during shutdown.
  - Rationale: Both paths can make repeated remote requests or run long-lived subprocesses. DEM downloads can be interrupted via the S3 progress callback, while Overture is best canceled by terminating the subprocess from a polling loop.
  - Alternatives Considered: Waiting for all tiles/processes to finish was rejected for the same reason as cloud shutdown. Rewriting both paths around threads or async I/O would be larger than needed for the shutdown problem.

- Topic: Water overlay startup responsiveness
  - Decision: Add the same abort event to the water overlay controller, and make the water overlay geometry loops periodically yield the GIL while checking for cancellation.
  - Rationale: The startup freeze was happening during the water overlay path, not on close. That code performs a lot of pure Python work after the download completes, so a cooperative abort alone is not enough; the worker also needs to yield so the GUI thread can keep processing input.
  - Alternatives Considered: Deferring the layer entirely would reduce startup work but would not address later updates. Rewriting the geometry stage in a separate process would be more invasive than needed.

- Topic: Water overlay startup order
  - Decision: Defer the first water-overlay update until the terrain horizon has either resolved or been skipped, and only start it immediately when terrain is disabled.
  - Rationale: The initial water update was racing the terrain update and making the status line look like the layer was initialized twice. Waiting for terrain keeps the startup sequence deterministic and avoids showing `loading` after water is already visible.
  - Alternatives Considered: Removing the terrain-dependent second pass would make the water layer less accurate when DEM ground becomes available.

- Topic: Water surface rendering split
  - Decision: Treat lakes and seas as flat, constant-height polygons, and keep rivers as DEM-attached surface textures instead of splitting polygons for scanline membership tests.
  - Rationale: The point-in-polygon test already handles arbitrary non-convex rings with holes, so the split was not needed for correctness. Keeping river footprints intact preserves hole handling and lets the renderer choose the surface height model explicitly by category.
  - Alternatives Considered: Continuing the grid split for rivers would still work, but it adds geometry churn without improving the membership predicate itself.
