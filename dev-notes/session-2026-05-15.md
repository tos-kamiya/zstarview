# 2026-05-15 Session Notes

- Topic: Water footprint thinning threshold direction
  - Decision: Change the vertex-spacing threshold from inverse-distance to distance-proportional growth.
  - Rationale: The previous formula made distant geometry harder to thin, which was the opposite of the desired behavior. A proportional threshold better matches the visual goal of stronger far-field simplification.
  - Validation: Add a regression test that confirms the threshold increases as observer distance grows.

- Topic: Preview script thinning threshold alignment
  - Decision: Apply the same distance-proportional threshold curve to `dev-samples/overpass_water_overlay_probe.py`.
  - Rationale: The preview script should match the runtime simplification behavior so diagnostics reflect the same geometry thinning rules.

- Topic: Water thinning scale calibration
  - Decision: Set the proportional threshold base to 50m at 1km and make it linear in distance.
  - Rationale: The previous 180m scale was too aggressive for the target visuals. A 50m/km slope keeps far-field thinning but preserves more river and coastline structure.

- Topic: Pair-based threshold selection
  - Decision: Derive the simplification threshold from the nearer endpoint of each vertex pair instead of using one threshold per polygon.
  - Rationale: This keeps thresholding local to the edge being evaluated and avoids over-thinning rings that mix near and far sections.

- Topic: Coastline bbox stitching in preview script
  - Decision: Stitch coastline inner rings to the bbox boundary when consecutive boundary vertices jump across the rectangle interior.
  - Rationale: Directly closing the coastline ring cuts across the bbox and produces inward corners. Following the bbox boundary preserves the intended coastline outline in the SVG preview and normalized output.

- Topic: Coastline bbox corner insertion
  - Decision: When a coastline ring crosses from one bbox edge to another, insert every bbox corner on the perimeter arc between those edge attachments instead of only one corner or a straight shortcut.
  - Rationale: The large coastline case needed three intermediate bbox corners between the left-edge attachment and the bottom-edge attachment. Using the bbox perimeter order keeps the coastline shape consistent and avoids shaving off the wrong corner.

- Topic: Coastline preview simplification strategy
  - Decision: Stop trying to stitch coastline cuts through the bbox perimeter in the preview script. Instead, fetch a slightly larger query bbox at 1.2x the requested radius and let the extra context hide corner rounding.
  - Rationale: Explicit stitching kept getting the wrong corner order and over-complicated the preview path. Overfetching is simpler, less fragile, and makes the coastline edge treatment less visually obvious without bespoke geometry surgery.

- Topic: Water overlay query bbox scaling in main app
  - Decision: Apply the same 1.2x query bbox expansion in the main water overlay fetch path used by GUI and image export.
  - Rationale: Matching the preview script keeps coastline context consistent across tools, while preserving the requested view radius for sampling and rendering.

- Topic: Water preview bbox marker
  - Decision: Draw the requested 1x bbox as a dashed rectangle in the SVG preview output.
  - Rationale: The preview now fetches a 1.2x query bbox, so a visible 1x marker helps distinguish the actual view extent from the wider fetch region without reintroducing coastline stitching logic.

- Topic: Coastline polygon early rejection in preview
  - Decision: Drop coastline polygons whose polygon bbox does not overlap the requested view bbox.
  - Rationale: The coastline data can span a much larger area than the interior water polygons, so bbox overlap is a cheap and safe early rejection step before any rendering or simplification.

- Topic: Coastline bbox filter basis
  - Decision: Use the requested Overpass query bbox as the overlap basis, not the retrieved polygon bbox.
  - Rationale: The cache payload already records the requested query bbox, and that is the correct frame of reference for deciding whether a polygon should be kept or discarded before previewing.

- Topic: Cache coastline filtering basis
  - Decision: For `--input-cache`, filter coastline polygons against the current view bbox instead of the bbox stored in the cache payload.
  - Rationale: The cache may have been generated with a much larger fetch radius, which would keep far-away coastline geometry that is irrelevant to the current preview.

- Topic: Far small water filtering
  - Decision: Keep coastline handling unchanged, but drop lake/river footprints when they are both far from the observer and smaller than the area threshold during observer-side simplification.
  - Rationale: Bbox overlap is too weak for coastline rejection, and remote small ponds/streams create more visual clutter than value in the overlay. A distance-and-area filter removes those cases without affecting nearby water or coastline geometry.

- Topic: Small water threshold alignment
  - Decision: Align the small-footprint drop rule with the vertex-spacing simplification scale, and exempt river-like water from the drop rule.
  - Rationale: Reusing the same distance-based scale keeps the footprint pruning behavior consistent with the existing ring simplification logic. River-like features are more visually important than tiny ponds, so they remain visible even when small.

- Topic: Lake drop scaling
  - Decision: Apply a 2x multiplier to the lake drop threshold while leaving river-like water exempt.
  - Rationale: Lakes can be pruned more aggressively than rivers without harming the intended visual signal. Doubling the size threshold keeps the rule simple and makes the pruning effect easier to reason about alongside the existing vertex-spacing scale.

- Topic: Water color separation
  - Decision: Add water-surface categories to overlay points so sea/coastline, river, and lake can be rendered with different colors; update the SVG preview so sea/coastline uses a blue fill and lake uses a distinct greenish fill.
  - Rationale: A single water color made lakes blend into the same visual class as coastline and rivers. Separate colors make the overlay easier to read, and a sea-colored coastline fill matches the intended side of the coastline geometry better than the previous land-like tone.

- Topic: Lake pruning strength
  - Decision: Increase the lake drop multiplier to 4x the vertex-spacing threshold scale, leaving river-like water untouched.
  - Rationale: The previous 2x multiplier still left some distant lakes visible. Raising the multiplier keeps the rule aligned with the existing distance-based simplification scale while making lake pruning noticeably stronger.

- Topic: Lake pruning by area
  - Decision: Switch the lake-specific drop rule to an area check derived from the same distance-based vertex-spacing threshold, instead of only comparing ring width and height.
  - Rationale: Small lakes can still survive a width/height gate when they are thin or skewed. Area-based pruning is a better match for the visual complaint and removes tiny lakes more reliably while preserving rivers.

- Topic: SVG preview land background
  - Decision: Change the SVG preview background from a pale blue to a land-toned neutral color so coastline sea fill reads as water instead of making the whole scene look blue.
  - Rationale: The previous background color blurred the distinction between land and sea in the bbox preview. A land-toned background makes coastline fill and lake colors easier to interpret at a glance.

- Topic: Long-side water pruning
  - Decision: Replace the area-based lake/other pruning with a long-side check: compare the larger of the footprint's projected width or height against the distance-scaled vertex-spacing threshold, and keep river-like water exempt.
  - Rationale: The visible problem is better captured by the footprint's longest dimension than by area. This keeps the rule aligned with the existing simplification scale while making it easier to suppress tiny non-river water bodies that still survive area-based checks.

- Topic: Other-water pruning strength
  - Decision: Use the same 4x size threshold for `other` water as for `lake`.
  - Rationale: The remaining non-lake water bodies in the cache are visually similar to lakes for pruning purposes. Matching the multiplier keeps the rule simple and makes the filter behavior predictable across the two non-river categories.

- Topic: Water pruning threshold escalation
  - Decision: Increase the lake/other size threshold by another 4x, for a total of 16x relative to the base vertex-spacing threshold.
  - Rationale: The previous setting still let some small distant polygons survive. A stronger multiplier makes the filter aggressive enough to suppress the tiny water shapes visible in the screenshot while preserving rivers.

- Topic: Probe ring-level water pruning
  - Decision: Apply the size filter per outer/inner ring in the probe, not just per whole footprint, and report `removed_rings` separately from `removed_vertices`.
  - Rationale: The screenshot data includes multi-ring `relation` footprints. Filtering only the footprint as a whole lets small rings survive if another ring is large. Ring-level pruning matches the visual problem better, while `removed_vertices` remains a simplification-only metric.

- Topic: Probe pruning scale rollback
  - Decision: Reduce the probe-side size filter scale from 16x back to 4x.
  - Rationale: The 16x setting removed too much water and nearly erased the overlay. 4x keeps the ring-level pruning in place while preserving enough water geometry to read the scene.

- Topic: Probe pruning scale reset
  - Decision: Reduce the probe-side size filter scale from 4x to 1x.
  - Rationale: Even 4x was still too aggressive for the scene. Returning to 1x keeps the ring-level filter available but minimizes over-pruning of visible water features.

- Topic: Probe pruning coefficient removal
  - Decision: Remove the explicit probe-side size-filter coefficient and keep the size check at the base threshold.
  - Rationale: The user wants the current 1x behavior without an extra scaling knob. Keeping the threshold literal makes the probe easier to reason about and avoids accidental future drift.

- Topic: Outline-only water footprint SVG
  - Decision: Add a separate SVG sample script that renders only outer rings as stroked outlines and skips polygon fills and inner rings.
  - Rationale: The user wanted a diagnostic view where the footprint geometry is visible without fill-based sea/land interpretation. Keeping it in a new script avoids changing the existing filled-preview behavior.

- Topic: Outline renderer cache input
  - Decision: Add `--input-cache` support to the outline-only SVG sample so it can read the zstarview cache JSON directly.
  - Rationale: The outline renderer is most useful against the cached footprint snapshot, and supporting the cache path avoids an extra conversion step while keeping the script self-contained.

- Topic: Coast-only outline rendering
  - Decision: Restrict the outline renderer to `coastline` footprints only, using the footprint kind or source field as the filter.
  - Rationale: The user wanted coastline outer rings specifically. Filtering at load time keeps river and lake geometry out of the debug SVG without changing the input format or the existing filled preview script.

- Topic: Coastline inner-ring fill experiment
  - Decision: Add a separate coastline renderer that draws only the inner rings and fills them with a sea color.
  - Rationale: The coastline outer ring is just the bbox frame, so it cannot represent water surface by itself. Rendering only inner rings as filled shapes is the next direct experiment for visualizing the sea side of the coastline geometry.
