# Session 2026-04-11

- Scope: Bump the application version to `1.9.1`.

- Topic: Version bump
  - Decision: Update the package version from `1.9.0` to `1.9.1`.
  - Rationale: The user requested a patch-level release after the terrain guide defaults and related test adjustments.

- Topic: Cloud alpha suppression threshold
  - Decision: Lower the low-cloud suppression floor from `0.05` to `0.03` in grayscale cloud encoding.
  - Rationale: A `0.05` floor suppressed a moderate cloud weight that the tests expect to remain visible, while still keeping very low weights such as `~0.02` at zero.

- Topic: Cloud shell altitude spacing
  - Decision: Change the default cloud shells from two layers at `3 km` and `8 km` to three layers at `4 km`, `6 km`, and `8 km` above the Earth's surface.
  - Rationale: The new tuple keeps the same upper bound while spreading the sampled shells evenly, which matches the requested rendering balance and keeps the GUI/export paths aligned.

- Topic: Cloud shell blend weights
  - Decision: Blend the default three shells with fixed weights of `25%`, `50%`, and `25%` for the near, middle, and far shells respectively.
  - Rationale: This keeps the default rendering biased toward the middle shell while still preserving the near/far context, and it leaves explicit non-default shell sequences on equal weights for compatibility.

- Topic: Cloud shell blend weights adjustment
  - Decision: Change the default blend weights to `20%`, `60%`, and `20%` for the near, middle, and far shells.
  - Rationale: This increases the emphasis on the middle shell while keeping the same three-shell altitude layout and preserving the existing equal-weight fallback for custom shell sequences.

- Topic: Resize flash suppression
  - Decision: Keep the previous sky/cloud buffers visible during window resize and request an immediate repaint instead of clearing them first.
  - Rationale: Resize events were briefly exposing the translucent window background before the new frame arrived. Preserving the old buffers avoids the flash while still letting the next render replace them.

- Topic: Window repaint opacity
  - Decision: Mark the client painting widget as opaque to Qt and keep the last good cloud frame when cloud refresh fails.
  - Rationale: The repeated flash was still visible outside resize, which points to repaint clearing rather than data content alone. Preventing Qt from system-clearing the client area and retaining the prior cloud frame reduces the chance of desktop exposure between refreshes.

- Topic: Fast overlay cache split
  - Decision: Exclude satellite and aircraft overlays from the cached base frame, and draw them as a separate fast overlay pass on each repaint.
  - Rationale: The 2-second overlay timer was invalidating the full cached frame, which dragged the cloud-heavy base scene through repeated recomposition. Splitting the cache keeps the cloud scene stable while still letting satellite and aircraft overlays refresh independently.

- Topic: Frameless window flash suppression
  - Decision: Disable system background erasing on the frameless host window and its wrapper widget.
  - Rationale: The visible flash showed the desktop behind the window, which indicates the translucent top-level shell was briefly exposing cleared pixels between repaints. Keeping the host and wrapper from being system-cleared removes that gap while preserving the existing client-widget paint path.

- Topic: Final frame presentation cache
  - Decision: Compose fast overlays and HUD into an off-screen final frame cache, then present that completed image in `paintEvent`.
  - Rationale: The old path still drew overlays and HUD directly into the live window after the base frame transfer, which left more opportunity for the translucent frameless shell to expose the desktop during repaint. Retaining the existing base-frame split but adding a final presentation cache reduces live-window drawing to a single completed image transfer.

- Topic: XWayland frameless flicker note
  - Decision: Add a README troubleshooting note that `QT_QPA_PLATFORM=xcb` can cause frameless-window flicker on Wayland, especially when maximized.
  - Rationale: Reproduction showed the flicker depended on forcing the X11 backend from a Wayland session rather than on a recent application regression. Documenting the condition and workaround is the lowest-risk fix.

- Topic: Earth guide display fallback
  - Decision: Keep the below-horizon earth guide as a line-only overlay and avoid polygon fill.
  - Rationale: Polygon fill makes "which land am I on" handling expensive and brittle, while pre-baked bitmap masks are too slow in the current render path. The existing line-only path stays aligned with the compositor cache model and preserves interactivity.
  - Notes: The remaining work in this session is to make the line-only guide easier to read without reintroducing fill-heavy rendering.

- Topic: Grid-split land mask
  - Decision: Generate a 10 degree lon/lat land-mask grid at build time and render the grid cells as fillable rectangles instead of trying to fill raw coastline polygons at runtime.
  - Rationale: The coastline rings were still fragmenting at the observer-specific clipping stage, which made fill fragile. Pre-splitting the simplified land geometry into coarse land cells keeps the runtime path simple and makes the filled regions stable enough for an orientation aid.

- Topic: Earth guide rollback
  - Decision: Remove the fill pass from earth guide rendering and restore the original coastline-based runtime land data.
  - Rationale: The grid mask introduced too many false interior islands and made the guide heavy and unreadable. The contour-only presentation is the safer fallback for now.

- Topic: Octilinear SVG generator
  - Decision: Keep `build_coarse_earth_guide_svg.py` as-is and add a separate octilinear generator that simplifies the land outlines into horizontal, vertical, and 45 degree segments in SVG space.
  - Rationale: The goal is to reduce coastline detail without reintroducing filled land masks. A separate script keeps the earlier coarse prototype available while making the new line-style experiment easy to compare and discard if needed.
- Topic: Octilinear seam normalization
  - Decision: Normalize each ring around the seam before projection and render the octilinear preview as stroke-only.
  - Rationale: The first preview still wrapped some coastline segments across the full world width and the fill pass amplified the artifact into horizontal bands. Keeping the path in a single seam-centered window and removing fill makes the preview behave like a legible line-only guide.
- Topic: Polar ring split
  - Decision: Split world-spanning polar rings, such as Antarctica, into two longitude halves before projection.
  - Rationale: A single closed ring around the pole still tends to drag the outline across the viewport seam. Cutting the ring into two parts at the opposite meridian keeps each half locally closed enough for a legible octilinear stroke preview.
- Topic: South-pole closure for Antarctica
  - Decision: Wrap the split Antarctic halves with a south-pole anchor so the closing edge stays on the low-latitude side.
  - Rationale: The previous half-ring closure still drifted toward the high-latitude side of the map. Anchoring both ends at the south pole keeps the closure visually tied to Antarctica instead of the equatorial side.
- Topic: Antarctic southern-edge pinning
  - Decision: Stop longitude splitting for Antarctica and pin the ring break to the southernmost edge instead.
  - Rationale: The seam-centered split still made the outline close from the north side. Choosing the most southern edge as the path break keeps the closure where the viewer expects Antarctica to be closed.
- Topic: Antarctic re-unwrapping after reorder
  - Decision: After rotating Antarctica around the southern endpoints, run a second longitude unwrapping pass before SVG projection.
  - Rationale: Reordering a ring can reintroduce large longitude jumps even if the original seam unwrap was correct. The second unwrap keeps the reordered Antarctica contour continuous while still preserving the southern endpoints as the open ends.
