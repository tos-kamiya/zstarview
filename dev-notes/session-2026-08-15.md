- Topic: GUI responsiveness investigation
  - Finding: Full sky snapshot work (star/DSO/planet positions, sky-disc generation,
    and night-light profile computation) is submitted to the shared GUI worker pool.
    However, each interactive viewport step synchronously recalculates the bright-star
    subset in the GUI event handler, and cache misses synchronously rasterize the base
    frame, star surface, dynamic overlays, and labels from `paintEvent`.
  - Impact: Repeated arrow-key navigation can stall on the per-step star transform,
    while view, time, overlay, twinkle, resize, or theme changes can invalidate render
    keys and produce longer GUI-thread stalls during repaint. This is a plausible direct
    cause of degraded interaction even though the periodic astronomy update itself is
    backgrounded.

Summary: Confirmed that most data acquisition and astronomy snapshot work is
backgrounded, but identified synchronous interaction-star calculation and cache-miss
painting as GUI-thread hotspots. No implementation or test changes were made.

- Topic: Delayed popup-menu display
  - Finding: `show_menu()` itself only synchronizes two altitude action states, maps
    the popup position, and calls `QMenu.exec()`. There is no expensive menu rebuild or
    `aboutToShow` callback in this path.
  - Finding: The 700 ms GUI scheduler calls `_update_twinkle()`. On each new 2-second
    bucket it performs up to `twinkle_count` nearest-star searches synchronously, then
    requests a repaint. The twinkle target tuple is part of the star-surface cache key,
    so that repaint rasterizes the star surface again on the GUI thread. The current
    default of 30 increases this synchronous work relative to the original default of
    10.
  - Impact: A menu-button event arriving while target selection or star-surface
    rasterization is running cannot be handled until that GUI-thread work completes.
    This matches delayed menu appearance more directly than the background sky worker.
  - Follow-up: Confirm with timing around `_update_twinkle()`, star-surface cache misses,
    and `show_menu()`. Likely fixes are to avoid full star-surface cache invalidation for
    twinkle-only changes and/or move target selection out of the GUI scheduler.

- Topic: Twinkle algorithm cost review
  - Finding: Each of 30 sampled directions rebuilds the same eligibility/FOV mask,
    extracts candidate arrays, and evaluates vectorized spherical trigonometry over
    all eligible stars. After finding a catalog `star_index`, the caller scans the
    `star_index` array again to recover its row and altitude. The work is therefore
    repeated full-array processing rather than 30 constant-time point operations.
  - Measurement: With the bundled catalog at Vmag 7, a representative Tokyo view had
    9,670 visible rows from 14,117 loaded rows. Thirty nearest-star searches took about
    20.6 ms in one local run, excluding the subsequent repaint.
  - Conclusion: The lookup is worth simplifying but is not by itself a likely source
    of a multi-second menu delay. The larger architectural cost is that the target
    tuple participates in the star-surface cache key, causing the full faint-star
    surface to be rasterized again every 2-second twinkle update.
  - Preferred improvement: Keep the cached star surface independent of twinkle state
    and draw the small transient dark-dot overlay after transforming the cached star
    surface. As a secondary optimization, compute the eligible rows and unit vectors
    once per sky snapshot and batch the 30 nearest-direction queries, returning row
    indices directly.

- Topic: Twinkle rendering and lookup optimization
  - Decision: Remove twinkle state from base-frame and star-surface cache keys. Draw
    the selected dark dots as a volatile overlay with the same interpolation transform
    as the cached star surface. Build the eligibility mask and candidate unit vectors
    once per update, evaluate all sampled directions with one matrix multiplication,
    and retain source row indices for alpha lookup and rendering.
  - Rationale: A two-second display effect should neither rerasterize the complete
    faint-star surface nor repeat identical full-array filters for every sampled point.
    Source rows also remove the second `star_index` scan in the GUI scheduler.
  - Measurement: For the same 9,670-row representative Tokyo view used in the earlier
    check, the new 30-direction batch lookup had a median of about 0.76 ms across 20
    measured runs, compared with about 20.6 ms for the previous repeated lookup.
  - Validation: The full suite completed with 1,545 passed and 5 skipped. Ruff passed
    for all changed source files and for the touched split test files when ignoring
    their pre-existing `F403`/`F405` star-import diagnostics. `git diff --check` passed.

- Topic: Calendar-aligned dynamic display tick
  - Decision: Replace the 700ms polling scheduler with a calendar-second-aligned
    one-second tick. Publish stars, precomputed planets, aircraft, satellites,
    and twinkle together on even-second ticks with one repaint request. Keep
    fast-mode recovery on an independent 1000ms single-shot idle timer.
  - Rationale: Separate two-second deadlines currently produce visible repaint
    bursts roughly 700ms apart. A shared tick time removes inter-layer timing
    skew, while next-tick planet precomputation keeps the roughly 20ms Skyfield
    calculation off the UI thread and makes the star interpolation transform
    unnecessary for directly calculated planet positions.
  - Implementation: Use a single-shot timer re-armed at each next wall-clock
    second boundary, merge the asterism check into that tick, and publish dynamic
    layer state once per even calendar second. Planet worker results are buffered
    with their render generation and target bucket; completion does not repaint.
  - Validation: The full offscreen test suite passed, including new coverage for
    boundary timing, single-publish behavior, and buffered planet completion.
    Ruff and `git diff --check` passed for all touched files. The repository-wide
    mypy run remains blocked by the existing baseline errors across many files.
