# Session 2026-05-09

- Topic: Night light overlay design for zstarview
  - Decision: Treat NASA Black Marble 2016 Grayscale 500m tiled GeoTIFF as an external, versioned cache-only dataset. Do not bundle it with the application; download it on demand into the local cache root and reuse it on startup when present.
  - Rationale: The dataset is too large for packaging, but it is a stable public source and fits the app's cache-first startup model. The overlay should only be enabled when the sun is below the horizon, and its visual treatment should be a fixed glow band above the terrain horizon with distance-weighted strength.
  - Alternatives Considered: Bundling the tiles, periodic TTL-based refresh, and making glow height vary with distance. These were rejected because they add packaging and UX complexity without improving the intended visual behavior.

- Topic: Documentation update
  - Decision: Update `docs/specification.md` and `docs/design.md` to include the new night light overlay, cache behavior, and draw-time smoothing constraints.
  - Rationale: The feature crosses user-facing behavior and internal data flow, so the spec and design need to stay aligned.

- Topic: Night light rendering revision
  - Decision: Replace the night-light band renderer with DSO-style per-sample ellipses centered on the sampled glow positions, using a horizontal ellipse orientation and layered alpha passes.
  - Rationale: The prior polyline/band composition still clipped in a way that looked like a hard left/right cutoff. Per-sample ellipses match the existing DSO drawing model, preserve the cache-only data pipeline, and are easier to tune as localized glow spots.
  - Alternatives Considered: Keeping the band renderer and widening the FOV handling, or deleting rendering entirely. Those were rejected because they either preserved the cutoff artifact or removed too much behavior before the replacement was defined.

- Topic: Night light compositing placement
  - Decision: Move night light painting into `SkyCompositorCache.draw()` so it shares the same sky-disc content-FOV mask as the sky/cloud composite instead of using a separate fixed-radius clip in the render pipeline.
  - Rationale: The cutoff artifact was coming from the extra `geometry.radius` clip in the post-composite overlay path. Compositing the overlay alongside sky/cloud keeps the night lights aligned with the same 110-degree disc mask and avoids a second, narrower clip.
  - Alternatives Considered: Leaving the overlay in `render/pipeline.py` and widening its clip there. That kept the extra clip logic separate and was the source of the mismatch.

- Topic: Night light banding reduction
  - Decision: Slightly reduce the bright core alpha while keeping the widened urban-outline glow color and width scales in place.
  - Rationale: The visible stepping was coming from the inner bright layer reading as a distinct line. Lowering the strongest pass softens the transition without changing the overall shape or color balance.
  - Alternatives Considered: Broadening the blur further or changing the scan geometry. Those would risk losing the outline-like character that the current rendering is aiming for.

- Topic: Night light fast-mode behavior
  - Decision: Skip night-light overlay painting entirely when `fast_mode` is enabled.
  - Rationale: Fast-mode is for interactive responsiveness, so the night-light overlay should not add any extra compositing cost or visual churn while the user is panning or changing the view.
  - Alternatives Considered: Rendering a simplified overlay in fast-mode. That would still cost time and complicate the interaction path without much value.

- Topic: Night light fast-mode computation
  - Decision: Also skip `compute_night_light_glow_profile()` entirely when `fast_mode` is enabled in the sky snapshot worker.
  - Rationale: If the overlay will not be painted during interaction, computing and caching the profile adds pure overhead. The interaction path should only compute the minimum sky data needed for responsive updates.
  - Alternatives Considered: Computing the profile but discarding it at draw time. That still pays the full sampling cost and does not help the responsive path.

- Topic: Night light profile retention during fast-mode
  - Decision: Preserve the previous night-light profile while `viewport_interaction_mode` is active instead of overwriting it with `None` from the fast-mode worker payload.
  - Rationale: Fast-mode skips recomputation, so clearing the profile would make the overlay disappear until the next non-fast sky refresh. Retaining the last good profile keeps the normal-mode frame ready as soon as interaction ends.
  - Alternatives Considered: Clearing the profile immediately. That would force a gap where the overlay disappears entirely until the worker recomputes it.

- Topic: Night light fast-mode rollback
  - Decision: Revert the fast-mode night-light computation suppression and profile retention changes, keeping only the draw-time fast-mode skip.
  - Rationale: The earlier interaction update path was causing the night-light overlay to stay hidden until a later sky refresh. Rolling back the compute/state changes returns the behavior to the pre-compute-skip version while preserving the simpler draw-side fast-mode optimization.
  - Alternatives Considered: Keeping the compute suppression and continuing to debug the interaction path. That had already proven unhelpful and obscured the original behavior.

- Topic: Night light layer toggle and opacity control
  - Decision: Expose night lights as an independent display-layer toggle in the menu and drive its base strength from a CLI/UI `night_light_opacity` value.
  - Rationale: The user-facing control should match the other overlay layers, while the opacity value makes the layer tunable without hard-coding a different color model. Using the same value in GUI state, CLI options, render style, and compositor cache keys keeps the layer behavior consistent across interactive and export paths.
  - Alternatives Considered: Making night lights a binary toggle only, or baking the strength into the renderer. Those approaches would make the layer less adjustable and harder to keep consistent between GUI and export.

- Topic: Night light alpha scaling refinement
  - Decision: Use `night_light_opacity` as the main alpha for the glow, and express the softer layers as relative coefficients from that base instead of multiplying the base opacity by another `0.12`.
  - Rationale: The previous formula made the default `0.12` opacity behave like a second attenuation step, which pushed the overlay much too dim. Treating the CLI/UI value as the primary strength makes the layer easier to reason about and keeps the default visible.
  - Alternatives Considered: Keeping the extra `0.12` multiplier and only increasing the default. That would preserve the same confusing scaling model and still make other opacity values harder to predict.

- End of session
  - Updated spec and design to reflect NASA Earth at Night / Black Marble GeoTIFF usage.
