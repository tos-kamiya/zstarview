# Session 2026-04-22

- Topic: Visibility boost extends to sky and cloud discs
  - Decision: Apply the tiered CLI visibility boost to sky disc and cloud disc opacity as well, using the weaker small-layer tier.
  - Rationale: Projector-like displays can make the broad translucent background discs harder to read, so lightly boosting them keeps the composition visible without turning the scene opaque.
  - Alternatives Considered: Leave sky and cloud discs unchanged; rejected because the user explicitly wanted them included in the continuous boost path.

- Topic: Visibility boost implementation
  - Decision: Add `--visibility-boost` and expand it in `window_inputs.py` into tiered opacity multipliers before the render pipeline.
  - Rationale: This keeps the policy in the CLI-to-window translation layer, makes supplement layers easier to rescue on projector-like displays, and leaves star rendering untouched.
  - Alternatives Considered: Thread a boost flag deeper into the renderer; rejected because it would mix policy into drawing code and complicate layer-specific tuning.

- Topic: Visibility boost at CLI translation layer
  - Decision: Use a CLI-facing visibility boost that is expanded into tiered opacity multipliers before the render pipeline.
  - Rationale: This keeps the boost policy out of the deep renderer, lets supplemental layers get a stronger boost than small figures, and preserves the existing star-first layout.
  - Alternatives Considered: Encode the boost directly in the renderer; rejected because it spreads policy across drawing code and makes layer-specific tuning harder.

- Topic: Never-rises tint strength adjustment
  - Decision: Lower the shared `never-rises` tint strength from `0.12` to `0.08`.
  - Rationale: The tint was reading as slightly too strong in the sky disc and the ground-fill compositor, so a stronger reduction keeps the cue visible while softening the color shift.
  - Alternatives Considered: Stop at `0.10`; rejected because the user asked for a further reduction and `0.08` keeps the tint visible without looking heavy.

- Topic: Cloud stripe density scaling
  - Decision: Treat `--cloud-stripe COUNT` as the stripe density for the default 600x600 render buffer, and scale the effective stripe count with the actual buffer size during rendering.
  - Rationale: This keeps the default appearance unchanged at the normal window size while making larger render buffers denser instead of preserving a fixed absolute stripe count.
  - Alternatives Considered: Keep the count fixed and only document it as a default; rejected because it does not satisfy the requested size-dependent density.

- Topic: Cloud density anchored to star render surface
  - Decision: Re-anchor cloud stripe density to the star layer's downsampled render surface size instead of the raw viewport size.
  - Rationale: The star layer already shrinks on larger windows, so using the same reduced surface keeps the cloud hatch granularity aligned with the actual star rendering pipeline.
  - Alternatives Considered: Continue scaling against the viewport/client rect; rejected because it diverges from the star layer's effective pixel density.

- Topic: Symmetric cloud stripe expansion
  - Decision: For the width-based cloud stripe mode, expand each stripe symmetrically around the baseline and double the stripe spacing by using a doubled period.
  - Rationale: This makes the band grow to both the upper-right and lower-left instead of only one side, while preserving the previous overall density by spacing the stripe centers farther apart.
  - Alternatives Considered: Mirror only the drawn pixels without changing the period; rejected because it makes the stripes look too dense.

- Topic: Documentation sync for cloud stripes
  - Decision: Update the specification and design docs to describe the star-render-surface density reference and the symmetric width-mode stripe shape.
  - Rationale: The docs had drifted from the current implementation after the cloud-stripe rendering changes, especially around density scaling and the center-outward width-mode shape.
  - Alternatives Considered: Leave docs unchanged; rejected because the current behavior would remain unclear to future readers.

- Topic: Version bump
  - Decision: Bump the application version from `1.20.10` to `1.20.11`.
  - Rationale: The user requested a `+0.0.1` bump, so a patch-level increment keeps the versioning consistent with the existing scheme.

- Topic: View-change cloud clearing
  - Decision: Clear cached cloud image, missing mask, and cloud amount data when viewport interaction starts, instead of preserving them while a background cloud render is still running.
  - Rationale: Reusing the previous cloud buffers during a view change could briefly show a mismatched cloud disc or missing tint at the wrong apparent field of view. Clearing the buffers makes the transition blank until the new cloud render arrives.
  - Alternatives Considered: Keep preserving in-flight cloud buffers; rejected because it caused the stale visual frame the user observed.
