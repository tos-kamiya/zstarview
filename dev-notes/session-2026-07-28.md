- Topic: Molecular-cloud visualization specification discussion
  - Decision: Treat the proposed AKARI-style molecular-cloud view as a
    static, celestial-coordinate scientific overlay, separate from the
    time-varying weather-cloud overlay. The first design target is a modest
    resolution 3-band far-infrared presentation using AKARI FIS-like 90/140/
    160 micrometre channels, with a restrained palette and non-linear
    brightness stretch.
  - Rationale: The reference discussion values AKARI's quiet, continuous
    dust-cloud texture over WISE-like point-source contrast. Keeping this as
    an observation view avoids implying that infrared intensity is visible
    light or that the layer is a physically exact naked-eye rendering.
  - Scope: Define user-visible behavior, data contract, preprocessing,
    projection, caching, composition, controls, failure behavior, and open
    decisions only; do not implement or modify runtime rendering code.

- Topic: Bundle molecular-cloud display data
  - Decision: Prefer bundling a deliberately reduced, display-oriented
    molecular-cloud asset with the application when its size and redistribution
    terms permit it. Do not bundle the original high-resolution survey files.
  - Rationale: Far-infrared dust structure is effectively static over normal
    application use, so requiring a first-run download would add friction
    without providing meaningfully newer information. A bundled derived asset
    also gives deterministic offline behavior.
  - Design constraint: Keep the source survey, preprocessing parameters,
    data version, coordinate system, band mapping, and license attribution in
    a manifest. Treat a future asset refresh as an application/data revision,
    not as a live runtime update.

- Topic: Coordinate representation for molecular-cloud data
  - Decision: Keep the bundled molecular-cloud asset in a location- and
    time-independent celestial coordinate system. Generate an observer-specific
    Alt/Az grid or rendered image as a derived runtime cache when needed.
  - Rationale: An Alt/Az grid depends on observer latitude, longitude, time,
    and optionally the selected projection. Bundling it would either restrict
    the application to one observer condition or duplicate large data for
    many conditions. This also keeps molecular-cloud data distinct from the
    existing time-varying weather-cloud Alt/Az source.

- Topic: Redistribution license for processed molecular-cloud data
  - Finding: DARTS states that released data are in principle available free
    of charge, including commercial use, under the ISAS Data Policy, while
    warning that some datasets may have restrictions from third-party
    copyrights. The AKARI product pages identify the source and processing
    products but do not by themselves establish a universal redistribution
    license for every derived asset.
  - Decision: Treat bundled redistribution as conditionally acceptable only
    after checking the exact AKARI product's terms/readme. Preserve source,
    authors, publication references, version, processing description, and
    license/attribution text in a separate NOTICE or data manifest. Do not
    relicense the data under the application's code license.
  - Rationale: A small transformed texture is still derived from an external
    scientific dataset, and application packaging should not erase its
    attribution or impose a new license on it.

- Topic: User-side AKARI download and preprocessing
  - Decision: Prefer an explicit setup/download flow that fetches the chosen
    AKARI map from its official distribution endpoint, preprocesses it locally,
    and stores only a compact display cache. Do not download large source maps
    automatically during ordinary GUI startup.
  - Rationale: This avoids shipping external scientific data inside the
    application, keeps the application package small, and makes the user's
    local copy distinct from application redistribution. The official LAMBDA
    listing shows that the full-resolution band files are large, so a
    controlled preprocessing step is also necessary for storage and startup
    performance.
  - Design constraint: Record source URL, release/version, checksum, license
    text, citation, preprocessing parameters, and timestamp in the cache
    manifest. Use temporary files and verify the download before publishing a
    READY marker; retain a stale valid processed cache if a later refresh
    fails.
