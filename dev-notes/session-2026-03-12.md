# Session 2026-03-12

- Scope: Adjust urban skyline distance bands based on actual overlay behavior from tower viewpoints.

- Topic: Remove near-field skyline bands from the default overlay
  - Decision: Change cumulative urban skyline defaults to `2, 3, 4.5, 6.75, 10.125, 15.1875, 22.78125 km`.
  - Rationale: Very near bands collapse toward the lower edge from tall tower viewpoints and add clutter rather than useful skyline structure.

- Topic: Retune default skyline radii for faster short-range generation
  - Decision: Change the default skyline radii to `0.15, 0.225, 0.3375, 0.50625, 0.759375, 1.1390625, 1.70859375, 2.562890625, 3.8443359375, 5.76650390625 km`.
  - Rationale: The recent workflow shifted toward denser near-field sampling with a practical upper bound just under `6 km`. Starting at `0.15 km` avoids the noisiest `0.1 km` band while keeping the geometric progression and stopping at the last geometric step instead of appending an extra terminal radius.

- Topic: Estimate skyline building heights from storey counts when CityGML height is missing
  - Decision: In CityGML skyline generation, use `measuredHeight` when valid and fall back to `storeysAboveGround * 3.5m` when `measuredHeight` is missing or carries the `-9999` sentinel.
  - Rationale: Several cities carry incomplete `measuredHeight` coverage. A conservative storey-based fallback recovers some high-rise candidates without changing the GeoJSON skyline path or overriding explicit height values.

- Topic: Replace the app-facing urban skyline with an urban outline layer
  - Decision: Stop using the max-altitude urban skyline overlay in the window and instead load an urban outline layer that draws sampled building-top footprint polylines directly on the sky dome.
  - Rationale: For close urban viewpoints, the skyline reduction was hiding building shape. The outline layer preserves per-building roof-edge shape, ignores front/back-face visibility, and is easier to inspect around viewpoints like GINZA SIX.

- Topic: Define a bundled derived-tile format for urban debug layers
  - Decision: Use a tile-per-file JSON format that keeps only bbox, `height_m`, `height_source`, and exterior footprint rings for buildings at or above `40m`.
  - Rationale: The runtime bottleneck is repeated CityGML XML parsing. A lightweight derived tile format preserves the existing tile-selection logic while making on-demand debug-layer generation practical. Bundle targets are limited to Tokyo23, Kyoto, and Osaka to keep size under control.

- Topic: Prefer Tokyo Tower as a visual check target in docs and examples
  - Decision: Switch the main CLI examples in the skyline appendix and sample script to `Tokyo Tower`.
  - Rationale: Tokyo Tower is a more representative visual validation target for urban skyline layering than Tokyo Skytree, whose very high observer altitude pushes most surrounding structures far below the eye line.

- Topic: Parallelize CityGML skyline generation by tile
  - Decision: Add `--workers` to `urban_skyline_from_citygml.py` and process selected GML tiles with `ProcessPoolExecutor`.
  - Rationale: Tile-level parallelism matches the current merge model, avoids re-reading all buildings per azimuth slice, and keeps the final combine step a simple per-radius `max`.

- Topic: Reduce skyline jaggedness by filling azimuth spans
  - Decision: Change skyline rasterization from per-sample-point bin updates to polyline interpolation between consecutive sampled perimeter points.
  - Rationale: The previous method treated the building outline too much like sparse point samples, which produced strong bin-to-bin aliasing. Filling the intervening azimuth bins makes the skyline behave more like a continuous footprint silhouette.

- Topic: Draw urban skyline overlays with cylindrical screen mapping
  - Decision: Keep the sky and terrain on the existing dome projection, but project urban skyline lines with a cylindrical-style azimuth/altitude screen transform.
  - Rationale: Near urban skyline layers looked visually glued to the celestial dome. A linear azimuth-vs-altitude mapping reads more like a surrounding city silhouette while keeping the rest of the sky rendering unchanged.

- Topic: Switch skyline layers from cumulative radii to thin radial bands
  - Decision: Interpret each skyline layer as the maximum obstruction within a `90 m` radial band starting at the configured radius, instead of using cumulative max up to that radius.
  - Rationale: In dense areas such as around Tokyo Tower, cumulative layers collapse onto the same envelope. A wider thin band preserves differences between near and far structure while reducing empty azimuth bins and tower-like spikes.

- Topic: Parallelize derived PLATEAU tile conversion
  - Decision: Add `--workers` to `build_plateau_derived_tiles.py` and convert GML tiles with `ProcessPoolExecutor`, while keeping JSON file writes in the parent process.
  - Rationale: The number of `udx/bldg/*.gml` files is large enough that sequential XML parsing is slow. Tile conversion is embarrassingly parallel, and parent-only writes avoid output races and keep logs simple.

- Topic: Switch urban debug layer generation to derived tiles
  - Decision: Make `urban_debug_layer_from_citygml.py` read `plateau_derived/.../*.json` via `--derived-dir` instead of reading CityGML directly.
  - Rationale: The derived tile format already preserves the data needed for debug roof-edge overlays, and removing runtime XML parsing makes regeneration practical after bundling Tokyo23, Kyoto, and Osaka derived datasets.

- Topic: Enable urban outlines for arbitrary coordinates
  - Decision: Build the urban outline layer on demand from the derived tile directory, instead of depending on a precomputed aggregate JSON.
  - Rationale: The app already needs derived tiles for arbitrary coordinates, so the extra aggregate JSON only duplicates data and processing.

- Topic: Add tile_index.json for derived PLATEAU tiles
  - Decision: Add a `tile_index.json` per `bldg/` directory with a root city bbox and per-tile bbox entries, plus a generator script.
  - Rationale: The index lets the app reject unrelated cities before touching tile JSON files, keeps tile selection cheap, and also serves as a manifest for spotting missing or renamed tile files.

- Topic: Use tile_index.json at runtime when present
  - Decision: Make derived-tile selection read `tile_index.json` first and fall back to scanning `bldg/*.json` only when the index is missing.
  - Rationale: This keeps current data backward-compatible while avoiding directory-wide JSON reads for indexed datasets.

- Topic: Remove the old skyline memo and Tokyo23-only derived path
  - Decision: Delete `src/zstarview/hikitsugimemo.md`, remove the `TOKYO23_PLATEAU_DERIVED_DIR` constant, and resolve urban outlines by scanning `src/zstarview/data/plateau_derived/*/bldg`.
  - Rationale: The old memo and skyline-specific path no longer match the current architecture. Runtime urban outline generation now depends on per-city derived datasets plus `tile_index.json`, so the code should not imply a Tokyo-only implementation.
