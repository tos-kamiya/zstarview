# Session 2026-03-12

- Scope: Adjust urban skyline distance bands based on actual overlay behavior from tower viewpoints.

- Topic: Remove near-field skyline bands from the default overlay
  - Decision: Change cumulative urban skyline defaults to `2, 3, 4.5, 6.75, 10.125, 15.1875, 22.78125 km`.
  - Rationale: Very near bands collapse toward the lower edge from tall tower viewpoints and add clutter rather than useful skyline structure.

- Topic: Prefer Tokyo Tower as a visual check target in docs and examples
  - Decision: Switch the main CLI examples in the skyline appendix and sample script to `Tokyo Tower`.
  - Rationale: Tokyo Tower is a more representative visual validation target for urban skyline layering than Tokyo Skytree, whose very high observer altitude pushes most surrounding structures far below the eye line.

- Topic: Parallelize CityGML skyline generation by tile
  - Decision: Add `--workers` to `urban_skyline_from_citygml.py` and process selected GML tiles with `ProcessPoolExecutor`.
  - Rationale: Tile-level parallelism matches the current merge model, avoids re-reading all buildings per azimuth slice, and keeps the final combine step a simple per-radius `max`.

- Topic: Reduce skyline jaggedness by filling azimuth spans
  - Decision: Change skyline rasterization from per-sample-point bin updates to polyline interpolation between consecutive sampled perimeter points.
  - Rationale: The previous method treated the building outline too much like sparse point samples, which produced strong bin-to-bin aliasing. Filling the intervening azimuth bins makes the skyline behave more like a continuous footprint silhouette.

- Topic: Draw urban skyline overlays with cylindrical screen mapping
  - Decision: Keep the sky and terrain on the existing dome projection, but project urban skyline lines with a cylindrical-style azimuth/altitude screen transform.
  - Rationale: Near urban skyline layers looked visually glued to the celestial dome. A linear azimuth-vs-altitude mapping reads more like a surrounding city silhouette while keeping the rest of the sky rendering unchanged.

- Topic: Switch skyline layers from cumulative radii to thin radial bands
  - Decision: Interpret each skyline layer as the maximum obstruction within a `90 m` radial band starting at the configured radius, instead of using cumulative max up to that radius.
  - Rationale: In dense areas such as around Tokyo Tower, cumulative layers collapse onto the same envelope. A wider thin band preserves differences between near and far structure while reducing empty azimuth bins and tower-like spikes.

- Topic: Keep high-observation buildings in the same bundled viewpoint dataset
  - Decision: Do not introduce a separate user-facing dataset for towers vs. observation-deck buildings. Keep using `tower_viewpoints.json` as the bundled entry point and broaden its schema instead.
  - Rationale: Splitting the dataset would leak internal data-source differences into the user experience. A single bundled viewpoint list is simpler, while an added `observer_height_m` field is enough to represent decks whose observation height differs from full structure height.

- Topic: Add a merge path for WDQS high-observation candidates
  - Decision: Add `src/zstarview/data/build_wikidata_viewpoints.py` to merge extra WDQS JSON arrays such as `query-2.json` into the existing bundled viewpoints dataset by `qid`.
  - Rationale: `query-2.json` is useful for missing high-observation buildings such as Abeno Harukas, but it is noisy and duplicated. A merge script keeps the existing curated tower data intact while allowing incremental expansion from additional WDQS result files.
