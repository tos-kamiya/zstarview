## Addendum
- Topic: GUI screen update and cache documentation
  - Decision: Added a dedicated design note at `docs/design/gui-screen-update-and-cache.md` and linked it from the design index.
  - Rationale: The runtime doc already covers the update loop at a high level, but the GUI cache layers and invalidation points are easier to explain in a focused document that maps directly to `window_updates.py`, `window_render.py`, and `composite.py`.
- Topic: Simplified redraw policy and optional atomic publish
  - Decision: Documented a simplified redraw policy that limits frame-cache-triggering updates to user actions, view/resize changes, and 1-minute refreshes, while keeping aircraft/satellite updates separate. Also added an optional atomic-publish note for cases where the current generation can be published as a single input set without conflicting with the simplification.
  - Rationale: Reducing the number of redraw triggers should shrink the space for ordering bugs during view changes. Atomic publication is useful only if it does not add back the same complexity, so it is explicitly subordinate to the simplification.
- Topic: Search and hover overlay classification
  - Decision: Classified search targets, mouse hover, labels, and HUD as a separate immediate UI overlay layer rather than a 2-second refresh layer.
  - Rationale: These elements must track mouse and selection state immediately, so they should stay tied to interaction-driven repaints instead of the short-lived aircraft/satellite refresh cadence.
- Topic: Fast-mode settle and cloud source-ready simplification
  - Decision: Made viewport-interaction settle restartable when a new fast-mode transition occurs, and removed the immediate repaint from cloud source-ready so the projected result can drive the next repaint instead.
  - Rationale: Restarting the settle timer reduces the chance that an in-flight interaction expires too early, while keeping cloud source-ready silent narrows the set of repaint triggers and reduces ordering sensitivity during view changes.
- Topic: Geo-satellite source-ready simplification
  - Decision: Applied the same silent source-ready policy to geo-satellite updates, keeping only the later ready event as the repaint trigger.
  - Rationale: Geo-satellite follows the same two-stage fetch/project flow as clouds, so matching the repaint policy keeps the view-change pipeline consistent and reduces another source of out-of-band repaints.
- Topic: Documentation alignment for cloud and Geo-satellite cache behavior
  - Decision: Updated `docs/specification.md`, `docs/design/runtime.md`, `docs/design/rendering-pipeline.md`, and `docs/design/gui-screen-update-and-cache.md` to state that cloud source-ready does not trigger repaint directly, Geo-satellite may reuse a cached raw image from a previous launch, and visible repaint still comes from the later projection-ready step.
  - Rationale: The implemented code already separates raw source readiness from the visible overlay result. Aligning the docs with that split keeps the user-facing behavior and the internal pipeline description consistent.

## Addendum
- Topic: Scheduler log improvements for repeat counters and `%t` filenames
  - Decision: Added a `repeat_label` property to `ScheduledOccurrence` and updated the `_sleep_until` wait log to include the job line number (`task N`) and a `(1/4)`-style repeat counter. Removed the repeat counter from the initial "scheduled next" log so the counter appears while waiting rather than at schedule-load time. Changed `_sleep_until` so that when a command argument contains `%t`, the wait log shows the expanded filename(s) instead of the raw UTC timestamp, and dropped the seconds portion of the wait time when it exceeds five minutes.
  - Rationale: Showing the line number and repeat index in the wait message makes it easy to correlate each pending run with the schedule file. Dropping seconds for long waits reduces noisy log output without losing meaningful precision.

## Addendum
- Topic: Square Window correction timing
  - Decision: Documented the `Square Window` behavior as an event-driven correction that occurs when leaving fast-mode for normal rendering, rather than as a size-based "keep checking until square" loop.
  - Rationale: A size-based exit condition can be unstable because Qt layout and frame decorations may not report an exact square at the moment the correction is pending. Using explicit pending and in-progress flags keeps the behavior deterministic and avoids resize/repaint loops.
  - Rationale: The user resize should be accepted first to preserve interaction feel, and the square correction should run once at the transition back to normal drawing.
