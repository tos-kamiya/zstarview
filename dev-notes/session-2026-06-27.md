## Addendum
- Topic: Square Window correction timing
  - Decision: Documented the `Square Window` behavior as an event-driven correction that occurs when leaving fast-mode for normal rendering, rather than as a size-based "keep checking until square" loop.
  - Rationale: A size-based exit condition can be unstable because Qt layout and frame decorations may not report an exact square at the moment the correction is pending. Using explicit pending and in-progress flags keeps the behavior deterministic and avoids resize/repaint loops.
  - Rationale: The user resize should be accepted first to preserve interaction feel, and the square correction should run once at the transition back to normal drawing.

## Addendum
- Topic: Square Window implementation and validation
  - Decision: Implemented `Square Window` as a checkable menu item whose enabled state sets a pending correction, and whose correction is applied once when paint transitions back from fast-mode to normal drawing. The correction path now uses the shorter client-side dimension and is guarded by an in-progress flag so resize notifications do not re-enter the same correction path.
  - Rationale: This keeps the resize interaction responsive, avoids a loop that depends on the window already being square, and makes the repaint transition deterministic. The explicit pending flag also lets fullscreen or maximized windows defer correction safely until they return to a normal resizable state.
- Topic: Resize hold suppression
  - Decision: Added a mouse-button gate to the square-window correction path so the resize correction is skipped while any mouse button remains held during a drag resize.
  - Rationale: Qt/Unity-style resize handling can briefly hide the window while the drag is active. Deferring the square correction until the button is released avoids forcing the window into a disappearing state during the drag itself.
- Topic: Square Window post-correction paint
  - Decision: Reverted the paint path so that once the square correction has been applied, that paint cycle returns without drawing and explicitly requests another repaint. The next paint, still in fast-mode, draws the corrected square frame.
  - Rationale: Drawing in the same cycle can mix the pre-correction and post-correction geometry, which distorts the fast-mode aspect ratio. Deferring the draw to the next paint keeps the corrected geometry and the fast-mode render inputs aligned.

## Addendum
- Topic: Night-light and ridge-glow cutoff investigation
  - Decision: Traced the visible cutoff to the terrain-visibility masking and altitude-row cropping path in `src/zstarview/night_lights.py` and `src/zstarview/gui/composite.py`, not to a direct distance-based early-stop in the render loop.
  - Rationale: The glow profile is built from 3 km distance samples up to 128 km, then each distance band is masked by `_terrain_visibility_threshold_grid()` and `_terrain_band_target_mask()` / `_terrain_band_target_altaz_mask()` using a 0.5 degree fade. After that, `_crop_night_light_alpha_grid_altitude_bins()` drops altitude rows whose max alpha is at or below `1e-3`, with one pad row kept on each side. That means very faint upper rows can disappear entirely and interpolate to zero, which can read as a sharper upper edge.
  - Rationale: The same crop path is reused for both `alpha_grid` and `edge_alpha_grid`, so the night-light layer and ridge-glow layer can both show the same cutoff shape.

## Addendum
- Topic: Soften faint upper-row cropping
  - Decision: Lowered `GLOW_MASK_NIGHT_LIGHT_ALTITUDE_CROP_ALPHA_THRESHOLD` from `1.0e-3` to `1.0e-4` and added a regression test that keeps a faint upper row alive through the crop path.
  - Rationale: The glow pipeline already computes its intermediate alpha fields in `float64`, so the hard edge was more likely coming from the crop threshold than from accumulated precision loss. Reducing the cutoff gives the upper tail more headroom before rows are discarded, which should make the top edge read less like a hard line.

## Addendum
- Topic: Ridge-glow altitude taper
  - Decision: Restored vertical decay for the `edge_alpha_grid` path in `src/zstarview/gui/composite.py` so ridge glow no longer stays bright all the way up the projected altitude range.
  - Rationale: The shared ray-field helper had been treating any precomputed `alpha_grid` as a reason to disable the altitude falloff entirely. That was acceptable for the night-light base layer, but it made ridge glow behave like a tall curtain when `ridge_glow_opacity` was pushed high. Keeping the decay on for the edge layer limits the visible emission to a more horizon-hugging shape.
  - Verification: `uv run -p .venv/bin/python pytest tests/test_glow_mask.py -q` and `uv run -p .venv/bin/python ruff check src/zstarview/gui/composite.py tests/test_glow_mask.py`

## Addendum
- Topic: Suppress flat-terrain ridge glow pillars
  - Decision: Added a minimum relative-elevation floor of `20 m` to `_terrain_sample_edge_strength_rows()` so near-flat DEM rows no longer become ridge-glow source rows.   - Rationale: The remaining pillar artifact was coming from tiny DEM undulations being expanded into full ridge-glow columns. A small prominence floor preserves real ridges while preventing flat salt-flat noise from becoming a bright vertical plume when `ridge_glow_opacity` is high.

## Addendum
- Topic: Make ridge-glow source strength binary
  - Decision: Changed `_terrain_sample_edge_strength_rows()` so the DEM-derived value is a binary ridge candidate mask rather than a magnitude proportional to relative elevation. Points above the minimum prominence threshold now contribute `1.0`, and all other points contribute `0.0`.
  - Rationale: The ridge glow should not encode terrain height as brightness. Using a binary candidate mask keeps the glow tied to the presence of a ridge-like feature while removing the visual coupling between elevation magnitude and emitted light.
