# Session 2026-07-07

Scope: OpenSky aircraft cache behavior for multiple zstarview processes.

- Topic: Shared OpenSky rate-limit design for aircraft overlay
  - Decision: Document a process-shared `rate_limit.json` and OS-backed
    `fetch.lock` around OpenSky aircraft fetches. The rate-limit sidecar is
    global to the OpenSky aircraft cache directory, not keyed by bbox.
  - Rationale: Per-bbox cache files suppress duplicate requests only for the
    same observation area. Multiple zstarview processes at different
    viewpoints can otherwise multiply OpenSky request frequency. A shared
    timestamp plus file lock lets all processes coordinate before fetching.
  - Alternatives Considered: Reusing any recent aircraft cache from another
    bbox was rejected because aircraft positions and the visible aircraft set
    can change substantially within minutes. Existence-only lock files were
    rejected because a crashed process can leave stale files behind.

- Topic: Rate-limit skip display behavior
  - Decision: When global rate-limit suppression blocks an OpenSky request and
    the target bbox has no fresh cache, skip the aircraft layer for that cycle
    and wait for the next scheduled refresh.
  - Rationale: Showing stale or different-bbox aircraft data would be more
    misleading than temporarily showing no aircraft.

- Topic: `zstarview-export-image` OpenSky exception
  - Decision: Keep `zstarview-export-image` outside the GUI global
    rate-limit skip rule. It should acquire `fetch.lock` and then fetch
    OpenSky data for the requested single image when the target bbox has no
    fresh cache. If the lock cannot be acquired, the command should fail
    instead of silently omitting aircraft.
  - Rationale: Export-image is an explicit single-shot command, so suppressing
    aircraft because another GUI instance fetched a different bbox recently
    would make the generated image less useful. The lock still prevents
    simultaneous OpenSky calls, and a successful export fetch updates the
    shared rate-limit sidecar for GUI processes.

- Topic: GUI status for shared rate-limit skips
  - Decision: Treat `rate-limited-skip` as a deferred update in GUI state, not
    as a successful aircraft refresh. The status line should show `deferred`
    instead of the timestamp from another process's different-bbox
    OpenSky fetch.
  - Rationale: The shared timestamp only explains why this process skipped the
    fetch. It is not a successful aircraft snapshot time for the current
    observation bbox.
