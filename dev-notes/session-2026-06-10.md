# Session 2026-06-10

- Scope: Refine the night-light band placement by fully anchoring each band to the previous ring.

- Topic: Night light inverse-sqrt distance scaling
  - Decision: Drive both band width and alpha with an inverse-square-root distance scale, using the existing near-distance clamp and retaining the width floor.
  - Rationale: Sharing the same distance falloff for geometry and opacity keeps the far bands visually lighter without introducing a separate tuning curve for brightness.

- Topic: Night light lower-edge 9:1 split
  - Decision: Position each band's lower edge at a 9:1 split between the previous ring and the current ring.
  - Rationale: Keeping the edge strongly tied to the previous ring preserves the attached-to-ridge look while still leaving a small current-ring influence.

- Topic: Night light lower-edge full anchoring
  - Decision: Set each band's lower edge to a 5:5 split between the previous ring and the current ring.
  - Rationale: The band should sit halfway between the adjacent rings again, which keeps the placement symmetric and makes the visual anchor easier to reason about.

- Topic: Night light lower-edge anchoring
  - Decision: Remove the band center offset logic and anchor each ribbon's lower edge directly to the sampled horizon altitude.
  - Rationale: The center-based placement could still make the glow appear below the horizon after projection. Anchoring the lower edge removes that bleed while keeping the band thickness above the ridge line.
- Topic: Water overlay empty-cache reuse
  - Decision: Treat a cached empty footprint set as a valid cache hit in `WaterOverlayController` and skip the Overpass refresh path for it.
  - Rationale: The previous `if not footprints:` branch forced a fresh network lookup even when the on-disk cache already proved there were no water polygons for that scope. That made the cache look ineffective and could surface transient HTTP 504 warnings on repeated launches with the same options.
  - Validation: Added a regression test that injects an empty cached scope and asserts that the controller does not call `fetch_water_overlay_footprints()`.
- Topic: Water overlay terrain-completion ownership
  - Decision: Route water-overlay updates through the terrain-completion path only, and remove the initial-load, resize, and toggle-on call sites that could start the water worker independently.
  - Rationale: Water is not visible when terrain is disabled, so the terrain controller already provides the gating event that matters. Keeping the water worker behind the terrain-ready transition avoids redundant fetch attempts and makes the startup flow easier to reason about.
  - Validation: Added a regression test that the initial-load chain now advances from terrain directly to urban, plus a terrain-ready test that still starts the water worker.
