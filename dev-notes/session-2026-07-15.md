# Session 2026-07-15

Scope: Confirm the source and runtime acquisition path for building data.

- Topic: Building data source verification
  - Decision: Confirmed that runtime building data for urban outlines and building-top lookup is downloaded from Overture Maps Buildings through the external `overturemaps` CLI, then converted into local derived tiles.
  - Rationale: `import_overture_buildings.py` constructs `overturemaps download --bbox ... --type ...` commands, and the GUI controller plus location resolver call that importer.
  - Follow-up: No code changes were requested; existing unrelated worktree changes were preserved.

- Topic: Historical PLATEAU usage
  - Decision: Confirmed from repository history that PLATEAU CityGML was previously imported offline into lightweight derived building tiles and bundled for runtime use.
  - Rationale: Historical commits include PLATEAU zip/CityGML import utilities and bundled derived tiles; the March 2026 refactor removed that pipeline and switched the default runtime source to Overture.

- Topic: PLATEAU initial-download UX
  - Decision: Treat PLATEAU acquisition/preprocessing as an explicit preparation tool rather than an automatic runtime download when the location is covered by PLATEAU.
  - Rationale: CityGML distributions can be very large; the main application should remain responsive and predictable. Runtime should consume only an already prepared derived cache and should not silently fall back to Overture inside a PLATEAU-covered area.

- Topic: Optional PLATEAU preference
  - Decision: Revise source selection so a valid prepared PLATEAU cache is preferred when present; otherwise the application uses the normal lightweight Overture path, including inside PLATEAU coverage.
  - Rationale: Users may prefer PLATEAU quality in some installations but fast startup and small local state in others. PLATEAU preparation remains explicit through `zstarview-download-plateau-buildings` and is never triggered implicitly at application startup.

- Topic: PLATEAU cache update detection
  - Decision: Check the PLATEAU catalog whenever `zstarview-download-plateau-buildings` is run. Reuse a completed cache only when its preparation year, registration year, specification, building file count, and summed building file size match the catalog; otherwise download and replace it after confirmation.
  - Rationale: This detects normal PLATEAU revisions without requiring a large archive download first, while keeping application startup offline and fast. Existing caches without the new metadata are treated as stale and are rebuilt by the preparation CLI.

- Topic: Replace stale PLATEAU cache
  - Decision: When catalog metadata differs, move the existing completed dataset to an `outdated-<timestamp>` directory before installing the newly converted dataset at the original cache path.
  - Rationale: Update detection must not be blocked by the existing completed-cache protection. Retaining the old directory provides a recovery path if conversion fails.

- Topic: PLATEAU detailed geometry design
  - Decision: Start with LOD1 geometry and fall back to LOD0. Use LOD1 to derive an observer-facing silhouette without directly drawing dense wall lines; consider LOD2 only after confirming that LOD1 improves outlines without making the display crowded. Keep LOD3 and LOD4 out of scope.
  - Experiment target: Use municipality code `13103` (Minato, Tokyo), which contains Tokyo Tower, to compare Overture Maps, PLATEAU LOD0, and PLATEAU LOD1 geometry first.
  - Rationale: LOD1 is a lower-risk experiment for the existing roofline-oriented renderer. It can test volume-aware silhouettes while controlling visual density, cache size, and processing cost.

- Topic: LOD1 roof polygon projection
  - Decision: Treat the top face of each LOD1 box as the roof polygon. Project its vertices to observer-relative Alt/Az coordinates and pass only the polygon boundary through the existing urban-outline clipping, sampling, and simplification path; do not draw wall interiors or bottom faces.
  - Rationale: This reuses the Overture Maps outline behavior and keeps the LOD1 experiment from increasing screen clutter.

- Topic: LOD1 implementation phase
  - Result: PLATEAU conversion now prefers `lod1Solid`, records `geometry_lod`, writes derived schema version 2 metadata, and routes LOD1 footprints through an explicit roof-polygon outline emitter. LOD0 remains the fallback and wall interiors are not emitted.
  - Verification: PLATEAU/cache/urban-outline focused tests passed (40 tests); Ruff passed.
  - Follow-up: Validate the visual result with the prepared Minato (`13103`) cache and compare it with Overture Maps.

- Topic: Verify Minato LOD2 source data
  - Result: The 13103 catalog reports 1,214 LOD2 building features and 6 LOD3 features. The tile `53393599` containing Tokyo Tower reports 1,258 LOD2 features and `maxLod: 3`.
  - Finding: Tokyo Tower (`bldg_7aff4a51-be8b-405b-abe4-ac489697cbc8`) has 79 `RoofSurface` elements in the inspected CityGML building, with roof elevations ranging from approximately 24m to 350.5m. The LOD2 geometry is therefore suitable for a multi-level roof-silhouette experiment.
  - Follow-up: Extract `RoofSurface` polygons only, preserve their per-vertex elevations, and compare the resulting sparse roof outline with the current LOD1 plate.

- Topic: Implement LOD2 RoofSurface silhouettes
  - Decision: Store LOD2 `RoofSurface` rings with per-vertex elevations in derived tile JSON, and project each roof boundary directly to observer-relative Alt/Az coordinates. Do not store or draw LOD2 wall interiors. Restrict the detailed path to buildings at least 40m high; use the existing LOD1/LOD0 roof outline path otherwise.
  - Result: The derived tile schema is now version 3. Cache metadata records `lod2-roof-surfaces` and the number of detailed roof rings. The 13103 Tokyo Tower sample parses as geometry LOD2 with 79 roof surfaces and an elevation range of 24.563m to 350.514m.
  - Validation: Focused pytest suite passes 42 tests; Ruff passes for the changed modules and tests.
