# Session 2026-07-15

Scope: Confirm the source and runtime acquisition path for building data.

- Topic: Building data source verification
  - Decision: Confirmed that runtime building data for urban outlines and building-top lookup is downloaded from Overture Maps Buildings through the external `overturemaps` CLI, then converted into local derived tiles.
  - Rationale: `import_overture_buildings.py` constructs `overturemaps download --bbox ... --type ...` commands, and the GUI controller plus location resolver call that importer.
  - Follow-up: No code changes were requested; existing unrelated worktree changes were preserved.

- Topic: Historical PLATEAU usage
  - Decision: Confirmed from repository history that PLATEAU CityGML was previously imported offline into lightweight derived building tiles and bundled for runtime use.
  - Rationale: Historical commits include PLATEAU zip/CityGML import utilities and bundled derived tiles; the March 2026 refactor removed that pipeline and switched the default runtime source to Overture.

- Topic: PLATEAU initial-download UX
  - Decision: Treat PLATEAU acquisition/preprocessing as an explicit preparation tool rather than an automatic runtime download when the location is covered by PLATEAU.
  - Rationale: CityGML distributions can be very large; the main application should remain responsive and predictable. Runtime should consume only an already prepared derived cache and should not silently fall back to Overture inside a PLATEAU-covered area.

- Topic: Optional PLATEAU preference
  - Decision: Revise source selection so a valid prepared PLATEAU cache is preferred when present; otherwise the application uses the normal lightweight Overture path, including inside PLATEAU coverage.
  - Rationale: Users may prefer PLATEAU quality in some installations but fast startup and small local state in others. PLATEAU preparation remains explicit through `zstarview-download-plateau-buildings` and is never triggered implicitly at application startup.

- Topic: PLATEAU cache update detection
  - Decision: Check the PLATEAU catalog whenever `zstarview-download-plateau-buildings` is run. Reuse a completed cache only when its preparation year, registration year, specification, building file count, and summed building file size match the catalog; otherwise download and replace it after confirmation.
  - Rationale: This detects normal PLATEAU revisions without requiring a large archive download first, while keeping application startup offline and fast. Existing caches without the new metadata are treated as stale and are rebuilt by the preparation CLI.

- Topic: Replace stale PLATEAU cache
  - Decision: When catalog metadata differs, move the existing completed dataset to an `outdated-<timestamp>` directory before installing the newly converted dataset at the original cache path.
  - Rationale: Update detection must not be blocked by the existing completed-cache protection. Retaining the old directory provides a recovery path if conversion fails.
