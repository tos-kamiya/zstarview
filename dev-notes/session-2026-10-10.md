- Topic: GUI-thread cyclic garbage collection
  - Finding: A standalone QCoreApplication/QObject-cycle experiment showed a Qt wrapper's Python finalizer running on the worker that called gc.collect, rather than the object's creator/main thread. This demonstrates the unsafe lifetime mechanism, not reproduction of the reported SIGSEGV.
  - Decision: During viewer.main, disable automatic cyclic GC, retain reference counting, and schedule owner-thread collections via a one-second QTimer. Collect young objects when allocation pressure reaches the usual threshold, and full generations every 30 seconds. Skip busy native_work_lock ticks without blocking the GUI. Drain services on normal/failed/cancelled launch exit before restoring the previous GC-enabled state.
  - Rationale: Python permits GC outside the Qt owner thread, while Qt requires thread-safe object destruction. Pinning cyclic collection to the GUI thread mitigates this class of fault without disabling cycle reclamation permanently or pinning dependency versions. The exact crash cause is still unconfirmed; explicit third-party collects and earlier heap corruption are not covered by this mechanism.
  - References: https://docs.python.org/3/library/gc.html and https://doc.qt.io/qt-6/threads-qobject.html.
