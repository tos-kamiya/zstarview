# Session 2026-04-27

Scope: Compare earth guide latitude rendering with celestial equator/ecliptic rendering and investigate fullscreen jagged lines.

- Topic: Celestial reference line sampling
  - Decision: Increase celestial equator and ecliptic sampling from 5 degree steps to 1 degree steps.
  - Rationale: The reference-line renderer feeds precomputed alt/az points directly into `drawPolyline()`, so coarse sampling shows up as visible kinks when the window is large. Earth guide outlines already use much denser, projection-aware subdivision, so the two systems differed materially in smoothness.
- Topic: Celestial reference line adaptive subdivision
  - Decision: Move equator/ecliptic smoothing into the renderer and subdivide by screen-space error instead of fixed angular spacing.
  - Rationale: Screen-space error is the right trigger because the same angular segment occupies more pixels as the window grows. The first implementation kept the error check in normalized coordinates, which did not actually scale with window size; switching the error metric to screen coordinates fixed that.

- Topic: Arrow-key viewport interaction mode confirmation
  - Decision: Confirmed that arrow-key altitude/azimuth changes enter simplified viewport-interaction mode immediately and keep it active for 700 ms after the last input.
  - Rationale: The key handler passes `interactive_viewport=True` into `_rotate_view()`, which starts the viewport-interaction timer, updates the reduced star set, and requests an immediate repaint. The renderer then uses `hud.viewport_interaction_mode` to skip heavy layers and draw only the reduced interaction set.
- Topic: Earth guide fast-mode fill suppression
  - Decision: Skip Earth guide fill-line rendering during viewport-interaction fast mode.
  - Rationale: The latitude-band fill pass is the expensive part the user noticed, while the outline fragments are still cheap enough to keep for orientation. Disabling only the fill pass preserves the simplified interaction cues without spending time on the dense cross-latitude line work.
- Topic: Sky reference line single-point projection
  - Decision: Preserve projection calls for single-point reference-line inputs before the segment loop.
  - Rationale: The renderer only draws segments between adjacent points, but the existing test intentionally feeds one-point equator/ecliptic/horizon inputs to assert the view-center argument path. Projecting the lone point keeps that contract intact without changing rendered output.
- Topic: Fast-mode large-star outline suppression
  - Decision: In viewport-interaction fast mode, draw 7px-and-larger stars as filled squares instead of outline rectangles.
  - Rationale: The fast-mode star set is already reduced to `Vmag <= 4.0`, so the extra outline path is mostly visual cost without much interaction value. Routing those stars through the same filled-rectangle path as smaller stars removes the outline batch work while keeping the same positional cues.
- Topic: Arrow-key rotation coalescing
  - Decision: Coalesce queued arrow-key rotations into a pending delta and apply them in one flush on the GUI thread.
  - Rationale: The existing viewport-interaction idle timer only controls when normal rendering resumes; it does not batch input. Accumulating the queued deltas before updating the view center reduces redraw churn and avoids paying the star/cloud work for every repeat event.
- Topic: Idle-timeout reason logging
  - Decision: Thread explicit reason strings through sky and cloud updates so viewport-interaction idle expiry can be distinguished from timer-based refreshes in logs.
  - Rationale: The 700 ms timeout itself is not visible in the existing `Updating sky data...` log line. Recording `viewport-interaction-idle` and `view-change-idle` at the update entry points makes the timeout-originated cloud rebuilds observable without changing the rendering behavior.
- Topic: Arrow rotation debounce
  - Decision: Replace the zero-delay rotation flush with a short 50 ms debounce timer and restart it on every arrow press.
  - Rationale: The earlier timer-based batching still flushed between repeat events, so it did not actually coalesce the queued inputs. A short restartable debounce keeps the pending delta accumulating while the key stream is active and only flushes when there is a pause or release.
- Topic: Arrow-key batching rollback
  - Decision: Remove the arrow-key pending-delta batching and return to immediate per-key rotation updates.
  - Rationale: The coalescing path made the interaction feel indirect and hard to reason about, and it was not a good fit for the UI. Restoring immediate response keeps the control behavior explicit while still allowing the viewport-interaction mode to remain simplified.
- Topic: Fast-mode ground tint suppression
  - Decision: Skip ground tinting entirely during viewport-interaction fast mode, including terrain-below-horizon fill and never-rises tint.
  - Rationale: The simplified interaction path is meant to stay cheap and visually stable. The terrain-fill pass and the extra never-rises tint both come from the same inverse-projection/masking work, so disabling them together avoids redundant processing and keeps the fast path closer to a plain sky/cloud composite.
- Topic: Arrow-key release-driven full refresh
  - Decision: Keep viewport-interaction mode active until the arrow key is actually released, then trigger the normal sky/cloud/terrain refresh from the release event.
  - Rationale: The 700 ms idle timeout still makes the simplified path drop back too early while a key repeat stream is active. Moving the handoff to the release edge keeps fast mode active for the whole physical key hold and makes the cloud rebuild line up with the end of the gesture instead of the timer.
- Topic: Release-time black-frame suppression
  - Decision: Do not repaint the full scene immediately on arrow-key release; wait for the refreshed sky disc to arrive, then start the follow-up cloud and terrain updates.
  - Rationale: The black partial sphere came from repainting with the stale sky disc from the previous view center, not from a clip bug. Deferring the first full-mode repaint until the new sky disc is ready removes the intermediate black frame while still restoring the normal layers as soon as the background sky update completes.
- Topic: Celestial reference line fixed sampling
  - Decision: Draw the celestial equator and ecliptic as fixed-sample polylines instead of recursively subdividing them by screen-space error.
  - Rationale: These lines are great-circle references whose main job is orientation, so the asterism-style sampled polyline path is simpler and cheaper while keeping the visual result stable at the current sampling density.
- Topic: Right-bottom resize grip focus restore
  - Decision: Restore keyboard focus to the sky view after the frameless window size grip releases the mouse button.
  - Rationale: The resize grip can retain focus after a drag-resize, which leaves arrow-key rotation handled by the wrong widget until the user clicks back into the view. Scheduling a focus restore on mouse release keeps the resize interaction unchanged while returning keyboard control to the sky canvas immediately afterward.
- Topic: Arrow-key routing after resize grip interaction
  - Decision: Route arrow-key presses and releases through an application-level event filter when the main window is active, instead of relying only on the child widget focus chain.
  - Rationale: The resize grip can leave the focus chain in an unexpected state even after focus restoration attempts. Intercepting the arrow keys at the application level keeps the viewport rotation path available whenever the sky window is active, while still allowing popups and dialogs to keep their own keyboard handling.
- Topic: Resize grip subclass removal
  - Decision: Remove the temporary size-grip subclass and focus-restore callback once application-level arrow-key routing made them unnecessary.
  - Rationale: The app-level event filter and focus proxy now handle the keyboard path directly, so the subclass added no useful behavior and only increased maintenance cost. Keeping the grip as a plain `QSizeGrip` leaves the chrome simpler while preserving the working key routing fix.
