# 近景建物の壁表示の引き継ぎ

作成日: 2026-11-24。更新日: 2026-11-25。
状態: PLATEAU・Overture Mapsとも既存の平面輪郭と高さから近景壁を描画する処理は実装済み。
次の課題は **PLATEAUのLOD2壁面を使った形状改善**。Overture Maps側は現状維持とする。
以下の旧記録には実装前の記述を含むため、現在の方針は直下の節を優先する。
現行方式はAlt/Az形式、2 mを基本とした分割、画面用画像による半透明合成を採用。
壁は描画先の幅・高さの半分の画像へ描画して拡大する。視線移動時の見た目の評価は未実施。

## 次の対応: PLATEAU LOD2の壁面を利用する

### 背景と方針

- 現行の近景壁はLOD1由来の平面輪郭を建物の全高まで押し出す。東京タワーのように
  高さごとに幅が変わる建物では、土台と同じ幅の直方体状に描かれる。
- 港区2025年の元CityGMLタイル `53393599` の東京タワー
  `bldg_7aff4a51-be8b-405b-abe4-ac489697cbc8` にはLOD2の `WallSurface` 264面、
  `GroundSurface` 33面、`RoofSurface` 79面がある。壁面には斜めの脚や展望台下の
  形が含まれ、地面部分はLOD0/LOD1の四角い輪郭より四方に広がる。
  現在の派生データは屋根面とLOD1由来の輪郭を保存するが、壁面は保存しない。
  比較図: `dev-notes/nearby-walls-trial/tokyo-tower-original-geometry.png`。
- **PLATEAUの利用可能なLOD2壁面を頂点ごとの座標・標高とともに保存・描画する。**
  詳細壁面がない、または利用できない建物は、従来の輪郭と高さによる近似壁を使う。
  フォールバックは建物単位を基本とし、詳細壁と全高の近似壁を無条件に重ねない。
  実際の鉄骨や窓の透過形状までモデル化されているとは限らない。
- 屋根面を次の高さまで垂直に下ろす試作は、壁面のない高さの傾斜・くびれを再現できず、
  部分的な屋根や傾斜屋根では誤った壁を作りうるため採用しない。比較画像と試作コードは
  `dev-notes/nearby-walls-trial/` を参照する。
- Overture Mapsの描画とキャッシュ形式は今回変更しない。London Eyeのデータは多数の
  `building_part` からなり、現行方式でも輪が確認できる。壁あり・なしの比較画像は
  同ディレクトリの `london-eye-walls-500m.png` と `london-eye-walls-off.png`。

### 設計・実装時の確認

1. `src/zstarview/data/plateau_buildings.py` のCityGML読み込み・派生タイル作成と、
   `src/zstarview/data/urban_outline_common.py` の `BuildingFootprint`、タイル読込を拡張し、
   有効なLOD2壁面を保持する。面の外周・穴、複数ポリゴン、無効・欠損形状、頂点順序、
   LOD間の重複を調べ、実際に対応できる形式を明示する。屋根面のみの建物は従来へ戻す。
2. 派生スキーマのバージョン、旧キャッシュの読み込み・更新判定、offline時の挙動を設計する。
   自動での大量再取得・再変換を前提にせず、既存の利用可能なキャッシュとフォールバックを
   保つ方法を検討する。変換に必要な元CityGMLが残っていない場合も想定する。
3. `src/zstarview/urban_outline_layer.py` の `_nearby_wall_faces` と描画経路を確認し、
   傾斜・凹形・水平に近い面を含む任意の3D壁面の分割、投影、視野端・方位角の継ぎ目を
   正しく扱う。現行の垂直な矩形を前提とする完全遮蔽判定をそのまま流用しない。
   不明な遮蔽は除外せず、透明度を重ねて増やさない既存の合成方針を維持する。
4. CityGML頂点の標高と既存の観測地点・建物DEM標高の基準を確認し、屋根・地面・壁の
   高さを整合させる。近景半径の距離判定、フェード、観測地点を含む建物の扱い、
   壁半径0や都市アウトライン無効時の挙動を維持し、詳細形状による例外も検証する。
5. GUIと静止画像で、東京タワーの土台・脚・展望台付近を現行と比較する。通常建物、
   壁面なし、複数面、傾斜・凹形、古いキャッシュとofflineのテストを加える。
   面数・キャッシュ容量・変換時間・初回描画と視線移動時の応答を測る。必要な仕様・
   設計文書とリリースノートは実装内容に合わせて更新する。replayは別スコープ。

## 旧記録: Overture Mapsへの対応（実装済み）

この節は実装前の引き継ぎ記録であり、「未実装」「渡していない」等の記述は現在の状態ではない。
通常経路はコミット `a04a286a` で対応済み。以下のデータ制約や未検証の項目は引き続き参考となる。

### 目的と現状

- PLATEAU未準備の地点ではOverture Mapsが通常の都市アウトラインのソースとなる。
  この場合にも、既存の派生キャッシュを使って近景の建物に壁を表示する。
- 壁生成処理自体は `BuildingFootprint` を受け取るソース非依存の処理だが、
  GUIの `src/zstarview/gui/urban_outline_controller.py` と静止画像出力の
  `src/zstarview/cli/export_image_layers.py` はPLATEAU経路にだけ
  `include_nearby_walls=True` と `wall_radius_km` を渡している。Overture通常経路では
  渡していないため、現在は屋根輪郭だけが表示される。
- `--urban-outline-wall-radius-km` と起動ダイアログの `Ground` / `Urban Outline` /
  `Building wall radius km` は実装済み。既定0.2 km、0は壁のみ無効、有効距離は
  `--urban-outline-radius-km` を上限とする。Overtureでも同じ設定・フェード・遮蔽・
  不透明度の合成を使う。遠距離skyscraper補助の経路には壁を追加しない。
- 通常Overture経路で `radius_km` の引数が既定値のまま渡されていない箇所も確認する。
  設定した建物検索半径と壁半径の制限がGUIと静止画の両方で一致するようにする。

### データの注意点

- `src/zstarview/data/import_overture_buildings.py` は `Polygon` / `MultiPolygon` の
  リング、高さ、`min_height_m`、`parent_building_id` を派生タイルへ保存する。
  高さは `height`、`roof_height`、階数×既定階高の順で解決され、値がない建物は
  変換時に除外される。高さや建物の網羅率には地点差があり、PLATEAU並みの表示を保証できない。
- `building` と `building_part` を両方利用する場合、`_merge_building_footprints` は
  部分がある親建物を除外する。部分形状が親全体を覆わない場合の欠落や、部分同士の重なり、
  `min_height_m` のある浮いた部分を確認する。親と部分を無条件に重ねない。
- `geometry_to_rings` は `MultiPolygon` の複数ポリゴンのリングを平坦化するため、
  外周と穴の所属が派生形式に明示されない。現行の観測地点を含むリングの除外処理と
  合わせ、中庭・複数の外周で壁が欠落したり誤って描かれたりしないか検証する。
  派生形式の変更が必要かは実データを見て別途判断する。
- 既存の重複排除、各建物代表点のDEM標高と観測地点の共通標高を使う。ソースの高さや
  平面形状は近似であり、詳細な実壁面・窓等は存在しない。既存のOvertureキャッシュの
  情報で試し、必要性が明らかになるまでキャッシュ形式の変更や再取得は前提にしない。

### 実装・検証の手順

1. PLATEAUとOvertureの通常近距離経路で壁半径と取得半径を共通に渡し、GUIと
   `zstarview-export-image` を対応させる。`--urban-outline-skyscraper-only`、
   `-u 0`、壁半径0、PLATEAU優先、offline時の既存フォールバックを維持する。
2. `building` / `building_part`、`min_height_m`、欠損高さ、同一・異なるIDの重複、
   観測地点を含む建物、中庭とMultiPolygon、半径境界、0と既定・変更値をテストする。
   重なりの透明度と、遮蔽除外後の見た目も確認する。
3. PLATEAUキャッシュが選択されない地点の準備済みOvertureキャッシュで試し、壁が描かれること、
   半径変更と無効化、視野移動時の応答を確認する。高さ欠損で壁がない地点は別地点でも確認する。
4. 変更後はCLIヘルプ、`docs/cli-ground.md` と日本語版、両README、
   `docs/specification.md`、`docs/design.md` の「PLATEAUのみ」という説明を更新する。
   `zstarview-export-replay` は現在壁を描かず、このオプションも受け付けないため、
   対応を広げる場合は別途スコープとDEMの扱いを検討する。

## 目的と方針

観測地点からごく近い建物について、現在の屋根・輪郭に加えて壁を半透明に描く。
壁の最小距離は5 m、外側半径は `--urban-outline-wall-radius-km` で変更でき、既定は200 m。
壁の不透明度は5〜10 mで増やし、10 mから有効な外側半径まで減らす。
距離は建物中心ではなく平面輪郭の最も近い辺までの水平距離で判定する。

既存の建物平面輪郭と高さから壁面を近似し、視線方向に依存しない投影用データを
事前計算する。保持形式は下記の2案から実装時に比較する。画面表示時には現在の
視線方向・視野・画面サイズに投影し、壁を一枚のマスクにまとめて半透明で合成する。
観測地点と観測高度、建物データ等が変わらなければ事前計算結果を再利用する。
時刻の変化だけでは再計算しない。

## データと現状

- `src/zstarview/data/urban_outline_common.py` の `BuildingFootprint` は平面輪郭、
  建物高さ、下端高さ、地面標高、任意のPLATEAU屋根面などを保持する。
- 建物の読み込み時の重複排除は `85d7c0bd` で実装済み。合成ID以外の完全一致レコードを
  除外し、同一IDでも内容が異なるものは保持する。詳細は
  `dev-notes/handoff-2026-11-24-building-id-deduplication.md` を参照。
- Overtureは輪郭と高さを派生タイルに保存し、利用可能なら `min_height_m` も保存する。
  高さは階数からの推定の場合があり、高さを解決できない建物は変換時に除外される。
- PLATEAUの変換は輪郭、高さ、利用可能な `RoofSurface` を保存するが、詳細な壁面は
  保存しない。実装済みのPLATEAU壁は輪郭の辺を高さ方向に立ち上げた近似壁である。
  詳細な実壁面は元データからの抽出・派生形式の変更が必要で、今回の前提ではない。
- `src/zstarview/urban_outline_layer.py` は建物ごとに代表点のDEM標高を割り当てる。
  至近距離では平面位置、地面標高、推定高さの誤差が目立つ可能性がある。
- 現在の `src/zstarview/data/urban_outline_from_buildings.py` は観測地点を含む
  建物を除外する。まずはこの扱いを維持する案だが、中庭・屋上なども含めて実装時に確認する。
  既存の候補数上限や高さ条件が200 m以内の建物にも影響するか確認する。
- 近景の壁には都市アウトラインの表示向け簡略化を適用せず、派生キャッシュで利用可能な
  輪郭の頂点を使う方針。細い輪郭の直線化や候補の間引きなどを壁に流用しない。
  投影精度のための壁面の分割は別途必要。PLATEAU変換時にはLOD1のリング群から最大の
  リングだけを選択しており、派生キャッシュに元の全形状が残るとは限らない。
  欠落形状を再取得・再変換するかは実データで影響を確認してから判断する。
- 傾斜屋根などでは単純な一定高さの壁と詳細屋根の端が一致しないことがある。

## 投影・合成の検討

- 壁を一枚の大きなポリゴンとして投影せず、元の壁面を高さ方向・水平方向に分割する。
  特に近い壁は見かけの角度が大きいため、観測地点からの角度の広がりや投影誤差に
  応じた分割を検討する。`src/zstarview/render/tropical_cyclones.py` の台風マーカーは、
  高さ方向を1,000 m間隔でサンプリングし、投影した点を線で結ぶ先例である。
- 投影用データの保持形式は未決定。いずれも視線方向に依存しないデータとして再利用する。
  - 案A: 分割した壁の各頂点を **Alt/Azと観測地点からの距離**で保持する。
  - 案B: 分割した壁の各頂点を **観測地点基準の東・北・上の3D座標**で保持する。
    面の分割やクリッピングを扱いやすい可能性があるため、案Aと比較する。
  どちらも画面投影は描画時の視線方向に応じて行う。分割は元の3D壁面上で行い、
  視野端のクリッピング、方位角0/360度の継ぎ目、天頂付近などを正しく扱う。
- 観測地点から頂点までの距離は視線方向に依存しないが、画面上の投影や視線方向の
  奥行きは依存する。距離をそのまま面の固定的な描画順と同一視しない。
- 壁面の分割前に、単一の別壁面が対象の四隅への視線をすべて遮り、かつその不透明度が
  対象以上なら対象を除外する。方位角で候補を絞り、光線と壁面の交点の位置・高さ・
  前後関係で完全遮蔽を判定する。部分遮蔽や複数の壁の組み合わせによる遮蔽は残す。
  透明度の低い手前壁によって、不透明度の高い奥壁を除外しない。
- 同一色・同一透明度の壁をまとめる初期案では、各面を半透明で直接重ねない。
  面を一枚のカバレッジマスクにまとめ、指定の不透明度を一度だけ適用して合成する。
  壁が重なっても暗くなり続けず、背後の星も透ける。共有辺やアンチエイリアス部分で
  重複や隙間が出ないマスクの生成方法は検証する。
- 均一色のマスクの和だけなら、奥の壁が同じ色の手前の壁と重なる部分の描画順や
  距離判定は必須ではない。建物別の色・陰影や最前面の壁の属性を使う場合には、
  距離を使って可視面を決める。壁単位の遠い順は交差・斜めの重なりで不正確になり得る。
- 法線による裏面除外だけでは、凹形状の自己遮蔽や別建物による遮蔽を解決できない。
  裏面除外は必須条件とせず、必要なら輪郭の向きや穴を考慮して検討する。
- 壁マスクと既存の屋根面・輪郭、星や地形との合成順、壁の色と不透明度、
  Inverted Cityや画像出力での扱いは未決定。既存表示との整合を確認する。

## 解像度とキャッシュ

全周の高解像度Alt/Az画像を常駐させるより、壁の投影用データを再利用し、現在の
画面に対応するマスクを作る案とする。視線方向、視野角、画面サイズ、投影条件が
変われば画面用マスクは作り直す。観測位置・高度、建物データ、DEMなどの変更時は
事前計算の無効化も必要。

初期比較には恒星レイヤーと同じ縮小率を使い、壁の縁や細い隙間の品質と描画時間を
画面解像度の場合と比較する。恒星の描画面は
`src/zstarview/render/pipeline.py` の `compute_star_render_surface_size` で決まり、
天球円直径が既定の600 pxを超えると平方根に応じて縮小する。恒星の解像度が壁にも
最適とは限らない。参考として、1,200 × 800 pxの1バイト/画素マスク本体は約0.9 MiBで、
画像形式の余分な領域や一時バッファは別に必要。

## 実装時の確認項目

1. 実データで200 m判定、欠損高さ、建物部分の下端、凹形状、穴、観測地点を含む建物を確認する。
2. 分割・投影・クリッピングを検証する。大きく視野を占める近い壁、方位角の継ぎ目、
   視野端、天頂付近を含める。
3. 重なり部分と分割境界で不透明度が増えないこと、描画順の影響、背後の星との合成を確認する。
4. 恒星相当と画面解像度を比較し、縁の品質、メモリ、描画時間とキャッシュの無効化を測る。
5. 必要なテストと実地点の見た目を確認し、実装が決まったらユーザー向け仕様と内部設計を
   それぞれ `docs/specification.md`、`docs/design.md` に反映する。
