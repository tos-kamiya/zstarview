## 2. 製品概要

`zstarview` は、指定した地点と時刻における空の見え方をデスクトップ上で表示するアプリケーションである。

主な目的は次の通り。

- 地点ごとの星空を視覚的に把握できること
- 昼間、薄明、曇天でも空の状態を把握しやすいこと
- 現在時刻だけでなく任意時刻の空を確認できること
- 位置指定、表示方向変更、重ね合わせ表示を軽快に行えること

## 3. 想定利用者と主な用途

### 3.1 想定利用者

- 任意の都市や座標から見た星空を確認したいユーザー
- タワーや展望地点からの見え方を確認したいユーザー
- 観望前に雲や地形も含めて空の状況を把握したいユーザー
- 特定の星、惑星、アステリズム、DSO の位置関係を見たいユーザー

### 3.2 代表的な用途

1. 都市名を指定して現在の星空を表示する。
2. 緯度経度を直接指定して、その地点の空を表示する。
3. タワー名または山名を指定して、そのビューポイントからの見え方を表示する。
4. 視線方向を変えて、天頂から地平線付近まで任意方向を観察する。
5. 指定日時の空を表示して、過去または未来の見え方を確認する。
6. 雲表示や地形地平線を補助情報として重ねて観察する。
7. 星名検索や代表天体ジャンプで目的の天体へ素早く移動する。
8. 準惑星や小天体を検索して、その方向へ視界中心を合わせる。

雲表示は観望補助用の近似表示であり、利用可能な衛星時刻、観測地点、部分欠損に応じて見え方が変わってよい。
雲の状態表示は、衛星ソースの取得中は `Downloading`、取得済みソースからの画像生成中は `Projecting` としてよい。
視線変更中は、旧視線条件で生成された雲画像を暫定表示せず、一時的に非表示としてよい。

## 5. 起動と入力

### 5.1 起動形式

`zstarview [options] [location]` 形式で起動する。
通常の GUI 起動では `location` を前回値から引き継いでよい。
初回起動時の既定地点は `Tokyo` である。

### 5.2 地点入力

`location` には次の形式を許容する。

- 都市名
  - 例: `Tokyo`
- 国コード付き都市名
  - 例: `JP/Tokyo`
- GeoNames ID
  - 数値のみ
- タワー名
  - 例: `Tokyo Skytree`
- 明示タワー名
  - 例: `t/Tokyo Skytree`
- 山名
  - 例: `Mount Fuji`
- 明示山名
  - 例: `m/Mount Fuji`
- Wikidata ID
  - 例: `wikidata:Q57965`
- 緯度経度
  - 例: `35.68;139.76`
  - 例: `N35.68;E139.76`
  - 例: `@35.68,139.76`
  - 例: `https://www.google.com/maps/@35.68,139.76,17z`
  - 例: `maps.google.com/maps/@35.68,139.76`
  - 例: `https://www.google.com/maps/place/...!3d35.68!4d139.76...`

Google Maps URL は、`!3dLAT!4dLON` があればその座標を優先し、なければ `@LAT,LON` を用いてよい。
`lat;lon`、`@lat,lon`、Google Maps URL は、緯度 `[-90, 90]`、経度 `[-180, 180]` の範囲チェックを行う。

### 5.3 地点解決の優先順位

- `--place` が指定されている場合は、Nominatim を使った明示的なオンライン検索を優先する。
- `t/NAME` は tower viewpoint としてのみ解決する。
- `m/NAME` は mountain viewpoint としてのみ解決する。
- そのほかの名前入力は、GeoNames、内蔵 viewpoint dataset、緯度経度解析の順序で解決してよい。
- `auto` 指定時は IP アドレスから現在地を推定する。

### 5.4 `--place` 検索

- `--place QUERY`
  - OpenStreetMap Nominatim を使って自由入力文字列を検索する。
  - 位置引数 `location` とは相互排他とする。
  - 対話選択は行わず、正規化後の先頭候補を採用して通常起動する。
- `--place-countrycode CODE`
  - `countrycodes` パラメータとして検索対象国を ISO 3166-1 alpha-2 で制限する。
- `--place-lang LANG`
  - Nominatim への `Accept-Language` として送る。
  - 既定値は `en` とする。

`--place` は 1 回だけ検索を行い、候補一覧を反復照会する経路は持たない。
候補が複数ある場合は、起動時の対話選択を行わず、先頭候補を採用する。
Nominatim への検索は利用者が明示的に実行した場合に限り、複数の検索要求は直列化する。
公開 Nominatim サービスへの要求間隔は 1 秒以上とし、入力途中の文字列を使った自動補完検索は行わない。

`--place` と起動前設定ダイアログの place search は、次の共通仕様で地名検索結果をローカルキャッシュへ保存する。

- ネットワーク利用時はキャッシュを先に参照せず、Nominatim から最新の候補を取得する。
- 1 件以上の有効な候補を取得できた場合だけ、候補一覧と取得日時をキャッシュへ保存する。
- 0 件結果、HTTP エラー、通信失敗、応答解析失敗によって、保存済みの正常なキャッシュを上書きしてはならない。
- キャッシュの照合には、正規化した検索文字列、国コード、応答言語を使用する。
- 検索文字列にファイル名として使用できない文字が含まれていても、キャッシュを安全に保存および検索できるものとする。
- DNS 解決失敗、接続失敗、タイムアウトなどにより Nominatim と通信できない場合は、一致するキャッシュを検索する。
- 一致するキャッシュが見つかった場合は、その候補を使って地点を解決し、キャッシュデータの取得日時を利用者に表示する。
- 通信できず、一致するキャッシュもない場合は、地名検索にネットワーク接続が必要であり、利用可能なキャッシュもないことを表示して起動を中断してよい。
- HTTP エラー、レート制限、応答解析失敗、オンラインでの 0 件結果は、通信不能時のキャッシュフォールバックとは区別し、起動を中断してよい。

このキャッシュはオフライン時のフォールバックを目的とし、ネットワーク利用時の検索結果更新を抑制するためには使用しない。

### 5.5 `auto` による現在地取得

`location=auto` の場合は `ip-api.com/json` を使って現在地を推定する。

- 解決結果として緯度、経度、タイムゾーン、都市名、国名を取得してよい。
- 失敗時は起動を中断し、原因を利用者へ表示する。
- この経路は `ip-api.com` の利用条件に従う。

### 5.6 追加の地点補正

- `-B`, `--use-building-top`
  - 都市名、`--place`、緯度経度、Google Maps URL で解決した地点について、近傍の建物頂部を観測基準にしてよい。
  - tower / mountain viewpoint には適用しない。
  - 候補が複数ある場合は、その建物グループの最大 `height_m` を使ってよい。
  - 候補建物が見つからない場合は地表基準を使う。
  - 建物検索では、準備済みPLATEAU、観測地点周辺を包含する有効な通常2.5km Overtureキャッシュ、有効な0.15km Overtureキャッシュの順に再利用する。
  - Overtureキャッシュは`building`と`building_part`がともに存在し、30日TTL内かつ既知の最新Overtureリリースと一致する場合に有効とする。
  - 再利用できるキャッシュがない場合だけ0.15km範囲を取得し、片方のfeature typeだけ有効な場合は不足分だけ取得する。
- `--height-add-m`
  - 観測基準の上に足す追加高さを指定する。
  - 既定値は `1.7m` とする。
- `--observer-height-m`
  - `--height-add-m` の互換オプションとして扱う。

都市名または緯度経度入力時は、観測基準を地表とし、実効観測点は「地表 + 追加高さ」とする。
山名入力時は山頂ビューポイント、タワー名入力時はタワービューポイントを基準にする。
Google Maps URL に高度らしき数値が含まれていても、追加高さとしては使わない。

### 5.7 時刻仕様

- 現在時刻
  - 実時間表示を使う。
- 相対時間シフト
  - `--hours` または `--days` によるオフセットを適用する。
- 絶対日時表示
  - `--datetime` により日時を明示指定する。

タイムゾーンは、地点から解決した値を使い、`--timezone` が指定された場合は最優先で上書きする。
解決できない場合のみ UTC を使う。

### 5.8 重要な描画入力オプション

以下のオプションは、表示スケール、見える範囲、外観、補助レイヤーの有無を制御する。

- `--edge-fov-deg`
  - ウィンドウ端に対応する角距離を指定する。
  - 投影スケールを変える。
  - 既定値は `95`。
- `--content-fov-deg`
  - 描画対象として保持する角距離上限を指定する。
  - 投影スケールは変えない。
  - 既定値は `110`。
- `-Z`, `--view-center-az`
  - 視線中心の方位を指定する。
- `-A`, `--view-center-alt`
  - 視線中心の仰角を指定する。
- `--sky-opacity`
  - sky disc の色強度を直接制御する。
- `--cloud-opacity`
  - 雲レイヤーの最終合成強度を制御する。
  - 既定値は `0.05` とする。
  - 通常ビューアでは、太陽高度が `-9` 度以下で最大、`-4` 度以上で無効となる滑らかな係数により、夜間の実効値を最大 `1.3` 倍まで持ち上げる。
- `--inverted-city`
  - GUI起動直後の表示モードを`Inverted City`にする。
  - 指定しない場合の起動直後の表示モードは通常表示とする。
  - 設定ファイルへ保存せず、`zstarview-export-image`では受け付けない。
- `--terrain-horizon-opacity`
  - 地形地平線の表示強度を制御する。
  - 既定値は `0.003` としてよい。
- `--earth-guide-opacity`
  - 地平線下の地球裏面ガイドの表示強度を制御する。
  - 既定値は `0.028` としてよい。
- `--night-light-opacity`
  - 夜間光オーバーレイの表示強度を制御する。
  - 既定値は `0.16` としてよい。
- `--akari-ir-bands-opacity`
  - AKARI遠赤外線バンドレイヤーの表示強度を制御する。
  - 既定値は `0.10` とする。
  - `0` を指定した場合はレイヤーを無効化する。
- `--ridge-glow-opacity`
  - 夜間光プロファイル由来の ridge glow レイヤーの表示強度を制御する。
  - 既定値は `0.04` としてよい。
- `--water-surface-opacity`
  - 水面レイヤーの表示強度を制御する。
  - 既定値は `0.4` としてよい。
- `--urban-outline-opacity`
  - 都市アウトラインの表示強度を制御する。
- `--road-light-max-candidates`
  - 道路夜間光で高コストな処理を行う道路候補の最大数を制御する。
  - 既定値は `5000` とする。`0` を指定した場合は道路夜間光を無効化する。
- `--overlay-font-size`
  - キャンバス上のラベルや HUD のベース文字サイズを制御する。
- `--visibility-boost`
  - 補助レイヤーや小さい図形の見え方を持ち上げる倍率として扱う。
- `--display-tone-curve off|BLACK,WHITE`
  - 完成した表示フレームの暗部と明部を、表示装置で識別できる出力範囲へ
    再配置する。
  - `off` は補正を無効にし、既定値とする。
  - `BLACK,WHITE` は整数の組として受け付ける。`BLACK` は黒背景から
    確実に見分けられる最も暗い無彩色値、`WHITE` は白背景から確実に
    見分けられる最も明るい無彩色値を表す。例えば `12,247` とする。
  - 入力は `0 <= BLACK < WHITE <= 255` を満たさなければならない。
  - `--visibility-boost` を置き換えず、レイヤー固有の強調と表示装置向けの
    トーン補償を独立して扱う。
  - 通常ビューア専用とし、`zstarview-export-image`では受け付けない。
- `--calibrate-display-tone-curve`
  - 未補正の near-black / near-white 階調パッチを通常ウィンドウで表示し、利用者が
    `BLACK` と `WHITE` を選択するキャリブレーション専用モードとする。
  - 測定後は `--display-tone-curve BLACK,WHITE` というオプション断片を
    terminalへASCIIで表示し、同じ文字列をクリップボードへコピーできる。
  - 通常の星空表示を起動せず、別プロセスによる再起動も行わない。
  - 同時に指定された地点、時刻、レイヤーなどの通常表示オプションを
    引き継いでビューアを起動してはならない。
  - CLI用設定を暗黙に保存してはならない。
  - 通常ビューア専用とし、`zstarview-export-image`では受け付けない。
- `--bright-bodies {outline,fill}`
  - 明るい天体の描画モードを指定する。
  - `outline` では明るい星、太陽、月、惑星の輪郭を強調してよい。
- `--theme`
  - `night`、`day`、`white`、`black`、`transparent`、`transparent-10` から `transparent-90` までの 10 刻みを受け付ける。
  - `transparent` は `transparent-40` の別名として扱ってよい。
- `--window-frame`
  - `frameless` または `window` を受け付ける。

### 5.9 補助レイヤーの有効無効

- `--show-guidelines-initial`
  - 地平線、天の赤道、黄道、方位ラベル、天頂マーカー、never-rises 領域の初期表示を指定する。
- `--cloud-opacity 0`
  - 雲表示を無効化する。
- `--terrain-horizon-opacity 0`
  - 地形地平線を無効化する。
- `--earth-guide-opacity 0`
  - Earth guide を無効化する。
- `--night-light-opacity 0`
  - 夜間光を無効化する。
- `--akari-ir-bands-opacity 0`
  - AKARI IR bandsレイヤーを無効化する。
- `--ridge-glow-opacity 0`
  - ridge glow を無効化する。
- `--water-surface-opacity 0`
  - 水面表示を無効化する。

GMN メテオ軌跡の既定opacityは`0.4`とし、通常起動後に遅延して取得する。
`--meteor-trails-opacity 0`を指定したセッションでは取得・描画を行わず、Layersメニュー
から再有効化できない。正値で起動したセッションではGUIの`Meteor trails`トグルで
表示を切り替えられる。初期版では専用の表示期間、色、線幅、流星群フィルタを設けない。

夜間光は地形地平線の生成結果に依存してよい。地形地平線が用意できた時点で alpha grid を 1 回だけ作成し、その後は同じ地形条件の間は再利用してよい。地形地平線が更新された場合のみ、night light の再計算を行ってよい。
night light と ridge glow は、太陽高度が `-9` 度付近から弱まり始め、`-4` 度で完全に消えてよい。

夜間光のデータ源は、EOG の 2025 年次 VIIRS Nighttime Lights VNL v2.2
`average_masked` GeoTIFF とする。大容量のラスタデータは PyPI パッケージへ
同梱せず、変換済みGeoTIFFをGitHub Release `night-lights-2025`のリリース
アセットとして配布する。実行時は固定URLの`manifest.json`を先に取得し、
manifestに記載された必要なタイルだけを取得してローカルキャッシュへ保存する。
各タイルはmanifestのSHA-256とGeoTIFFメタデータを検証し、検証完了後にだけ
キャッシュへ確定する。取得済みキャッシュが利用できる場合は、ネットワーク接続
なしでも夜間光を表示できる。再配布する変換済みデータにはEOGの帰属表示、
GeoTIFFへ変換した旨、CC BY 4.0のライセンス情報を含める。
- `--urban-outline-opacity 0`
  - 都市アウトラインを無効化する。

0 を指定して無効化したレイヤーは、そのセッションでは GUI から再有効化できないものがある。

### 5.10 起動時スプラッシュでの静的レイヤー準備

起動時は、観測地点と観測高度が確定した後、通常の GUI 画面を表示する前のスプラッシュ表示中に、静的な補助レイヤーの準備を先行してよい。

この先行準備には、次を含めてよい。

- DEM の取得または再利用
- 地形地平線の生成
- 夜間光の alpha grid と ridge glow の生成
- 水面レイヤーの生成
- 都市アウトラインの取得、変換、描画キャッシュ作成
- 必要であれば、これらに依存する初回の静的合成結果のキャッシュ作成

この段階では、時間経過やユーザー操作で変化しやすい次のレイヤーは待たせてよい。

- 雲オーバーレイ
- Geo-satellite 雲経路

### 5.11 クライアント領域のアスペクト比と表示範囲

`zstarview` の sky disc は、クライアント領域の幅と高さの比率に応じて円盤の配置と半径を決めてよい。

- 表示方向そのものは `-A` / `--view-center-alt` と `-Z` / `--view-center-az` で決まる。
- 画面端に対応する角度スケールは `edge_fov_deg` であり、これが投影の基準である。
- `content_fov_deg` は overscan 用の内容保持範囲であり、window edge の角度スケールを置き換えない。
- 実行時には `content_fov_deg` が `edge_fov_deg` 未満にならないよう正規化される。
- `width >= height` のときは、sky disc を上端がクライアント領域上端に接するように配置してよい。
- `width < height` のときは、sky disc をクライアント領域中央に配置し、横方向へはみ出してよい。
- `width < height` かつ `width / height` が 1 に近いときは、クライアント領域の高さの半分を `edge_fov_deg` の半径として扱ってよい。
- `width / height` が `1 / 2` 以下の縦長領域では、クライアント領域の高さの半分を `content_fov_deg` の半径として扱ってよい。
- `1 / 2 < width / height < 1` では、上記 2 状態の間を線形補間してよい。
- `Square Window` を実行した場合は、クライアント領域の短辺に合わせて 1 回だけ正方形へ補正してよい。

このため、同じ view center でもクライアント領域のアスペクト比が変わると、ウィンドウ内に見える天球の切り取り方は変わってよい。ただし、投影の基準角は `edge_fov_deg` であり、`content_fov_deg` は保持対象の外縁として扱う。
縦長ウィンドウでは、四隅に `content_fov_deg` の外側の領域を見せることで、円形視野を矩形ウィンドウで切り取っていることを示してよい。

#### 6.2.2 大気散乱モデル

昼間の sky disc は、大気中の単一散乱を積算するモデルで生成する。実験用スクリプトでの比較を経て、Rayleigh散乱とMie散乱を組み合わせたモデルを採用する。

- 地球は完全な球体とし、観測地点は地表上に置く。
- 太陽光は太陽方向から平行光線として大気へ入射する。
- 観測者から各視線方向へ進み、高度100 kmを実質的な大気上端として、各地点の散乱光を積算する。大気密度が十分小さいため、500 kmまでの積算と見た目の差がないことを確認している。
- Rayleigh散乱と、低高度に集中したエアロゾルのMie散乱を別成分として扱う。
- 高度15〜35 kmの薄い球殻をオゾン層の近似として扱い、散乱地点へ届く太陽光と、散乱地点から観測者へ届く光が球殻を通過した距離に応じたRGB別のオゾン吸収を適用する。現在の既定係数は調整後の弱い値とし、代表RGB波長で赤・緑の減衰を青より大きくする効果を控えめに扱う。
- オゾン球殻は可視光を発光するレイヤーではなく、シャピュイ吸収による波長依存の透過率として扱う。これにより、太陽が地平線下にある薄明時ほど長い光路の影響が現れ、ブルーアワーの青みを近似する。
- 太陽高度が `+3`〜`-12` 度の薄明時には、単一散乱で失われる高空の青い明るさを補うため、薄明多重散乱のRGB近似を加える。補正は地平線付近より高高度方向で強く、太陽高度とともに滑らかに消える。これは人工的な青色発光ではなく、未計算の高次散乱を近似する空色放射成分である。
- エアロゾルの散乱量は、CAMS（Copernicus Atmosphere Monitoring Service）から抽出した、全球約80 km（ADSの0.75度格子）・月別AOD550の静的データを利用する。アプリには空色計算に必要な項目だけを抽出した軽量な派生データを同梱し、CAMSの元データを同梱しない。
- 同梱データは過去の解析値・観測値を平均した気候値であり、現在の天気や将来の予測値を表さない。観測地点の緯度経度と暦月から対応格子セルを選び、既定のエアロゾル鉛直プロファイルと組み合わせて空色計算へ適用する。
- 通常のアプリ実行では、CAMS APIへの接続、アカウント作成、API認証情報の設定を要求しない。
- 同梱データは配布物に必須のアプリケーション資産として扱い、通常動作では外部データ取得やデータ欠損フォールバックを行わない。
- インストール不備・資産破損などで同梱データを検証できない場合だけは、空色計算を停止させず、やや清浄寄りの標準固定大気プロファイルへ退避する。これは通常の気候値選択ではなく、異常時の防御的な動作である。
- RGB各成分は、太陽から散乱地点までの光路と、散乱地点から観測者までの光路で、それぞれの消散係数に応じて減衰する。
- 現行の3成分近似では、夕焼けの橙色が緑へ寄りすぎないよう、積算した散乱光へ小さなRGBバランス係数を適用する。既定値は `[0.98, 1.00, 1.00]` とし、光学的厚さや大気経路長そのものは変更しない。
- 太陽光が視線方向へ散乱した成分だけを表示し、太陽から観測者へ直接届く光、太陽円盤そのものの光は sky disc の積算に含めない。
- 太陽が地平線下にあっても、高空の大気が太陽に照らされていれば散乱光を表示する。
- Mie散乱はRayleigh散乱より太陽方向へ強く集中し、夕焼けを低空の広い範囲へ拡散させる。
- 現行実装はRGB 3成分の近似モデルである。将来のスペクトル版では、可視光を12〜16個程度の波長帯に分け、各波長のRayleigh散乱、Mie散乱、光学的厚さ、太陽光スペクトルを個別に計算する。
- スペクトル版の色変換は、各波長の光量をCIE XYZカラーマッチング関数で積算し、D65白色点を基準としたXYZからsRGBへ変換する。D65を3つのRGB波長として扱わず、sRGBの広帯域チャンネルをXYZ経由で再現する。
- スペクトル版では、AOD550をÅngström指数などの波長依存モデルで各波長のエアロゾル光学的厚さへ変換する。Ångström指数やエアロゾル吸収特性が未指定の場合は、既定値をメタデータに記録する。
- スペクトル版は現行のRGB版と同じ地球形状、光路積分、太陽高度下の散乱、同梱CAMS気候値を使用し、色計算部分だけを置き換える。通常のアプリ実行では追加のネットワーク取得を行わない。

このモデルでは、昼の青空、地平線付近の明るさ、夕焼けの広がり、薄明の暗化を個別の夕焼け色補正としてではなく、地球の曲率・大気密度・RGB散乱係数・散乱位相関数の結果として扱う。直接光を除外するため、太陽そのものの表示は太陽レイヤーが担当する。

### 6.4 星と天体

- 恒星は等級に応じて明るさとサイズを変えて表示する。
- 色のある恒星は色指数を反映した見た目を持ってよい。
- `--sky-opacity` の既定値は `0.16` とする。これにより空色を読み取りやすくする。
- 空色ディスクが有効な場合、`vmag <= 4.0` の恒星は通常の一括描画から分離し、恒星ごとに描画する。
- `vmag <= 4.0` の恒星は、恒星本体の前に局所的な黒または濃いグレーの下敷きを描いて、空色上でのコントラストを確保する。
- `vmag <= 2.0` の恒星は、個別描画の下敷きの上に、従来の明るい恒星用ひし形を重ねてよい。
- `2.0 < vmag <= 4.0` の恒星は、個別描画の下敷きの上に通常の恒星本体を描く。
- `vmag > 4.0` の恒星は、従来どおり一括描画してよい。
- 個別描画する恒星は、下敷きを先に全件描画し、その後に恒星本体とひし形を描く。これにより近接した恒星の下敷きが、先に描いた恒星本体を覆うことを避ける。
- 太陽、月、惑星は恒星とは別スタイルで識別しやすく描画する。
- `vmag <= 4.0` の通常の惑星マーカーも、恒星と同じ考え方で個別の暗色下敷きまたは輪郭を付けてよい。
- 太陽のクロスゲージと月の位相描画は、明るい恒星向けの個別下敷きの対象外として扱う。
- 月は位相を反映して表示する。`--bright-bodies outline` の通常表示では、明るい側の外周弧と明暗境界の内側の弧を描き、暗い側の外周は描かない。
- `--bright-bodies outline` の正確な満月では外周円全体を表示し、正確な新月では明るい側の外周弧を表示しない。
- `Enlarge Moon` が有効なとき、または月にマウスホバーしたときは、月を通常時の5倍で拡大し、塗りつぶし式の月相画像を表示する。
- 月の通常描画がベースレイヤー、ホバー時の拡大月がHUDレイヤーに分かれる場合でも、クロスゲージは重複表示しない。拡大月の画像はベースレイヤーのクロスゲージの上に重ねる。
- 旧来の「暗い星だけを特別扱いで背景境界外へ出さない」動作は行わない。

#### 6.4.1 恒星・惑星の時間更新と滑らかな表示

- 恒星と空色ディスク、雲の色、夜間光の重い計算は、既定では 60 秒間隔のスナップショット更新を維持する。
- 60 秒のスナップショット間では、恒星の再計算を毎回行わず、2 秒周期の軽量な表示補間を行う。
- `--sky-update-interval` が 90 秒以下の場合に限り、この表示補間を行う。90 秒を超える場合は、恒星の位置更新間隔に対して補間量が大きくなりすぎるため、スナップショット位置をそのまま表示する。
- 空色ディスクは `--sky-update-interval` から独立して更新する。太陽高度が `+15`〜`-15` 度の範囲では15秒ごと、それ以外では60秒ごとに低解像度ディスクを再生成する。恒星・DSOの更新間隔と恒星位置の補間は `--sky-update-interval` に従う。
- 恒星サーフェイスの基準時刻は更新間隔の中間時刻とし、区間の前半を `-更新間隔/2`〜`0` 秒、後半を `0`〜`+更新間隔/2` 秒として補間する。これにより、スナップショット切り替え時の位置差を抑える。
- 行列による補間量は中間時刻からの経過時間の75%を上限とする。更新間隔の境界では小さな正方向の位置更新を残し、近似誤差による「行き過ぎて戻る」動きを抑える。
- 補間では、恒星の暗い成分を透明な恒星サーフェイスとして保持し、現在の視点に対応する 3x3 射影変換を適用して表示してよい。
- 射影変換は画面中心だけでなく、四隅付近、各辺の中央付近、画面中央など複数の対応点を使って近似し、四隅付近の誤差を確認できるものとする。
- 現行の通常ビューアでは、画面端の投影基準は `edge_fov_deg`、オーバースキャンを含む保持範囲は `content_fov_deg` で決まる。補間は後者の範囲も含めて破綻しないことを目標とする。
- 明るい恒星（`vmag <= 4.0`）とその暗色下敷き、`vmag <= 2.0` のひし形は、恒星サーフェイスに焼き込まず、合成時に補間後の位置へ直接描画してよい。
- 空色ディスクは恒星サーフェイスと分離し、明るい恒星の暗色下敷きは半透明の黒または濃色として空色ディスク上へ合成する。
- 惑星、太陽、月は恒星補間とは別に、現在時刻の位置を2秒周期で直接計算して表示する。これらの計算結果は表示位置に使用するが、空色ディスク、雲の色、夜間光の重いスナップショット計算は更新しない。
- この補間表示は通常ビューアを対象とし、Atlasと `zstarview-export-image` の描画経路は従来どおりとする。

#### 6.4.2 シンチレーション表示

- シンチレーションは、恒星の大気揺らぎを物理的にシミュレーションするものではなく、恒星の存在感を高めるための表示上の演出とする。
- 通常の `zstarview` GUIでは既定で有効とする。Atlasと `zstarview-export-image` では無効とする。
- GUIの2秒周期の軽量表示更新に同期して、現在の表示フィールド内からランダムなalt/azを1点選ぶ。
- 選んだ位置から角距離1度以内にある、最も近い対象恒星をシンチレーション対象とする。対象がない更新では何も描画しない。
- 地平線下の恒星、表示対象外の恒星、個別描画される明るい恒星は対象外とする。太陽、月、惑星などの太陽系天体も対象外とする。
- 対象恒星の表示位置へ、恒星の表示サイズの1.0倍の暗色半透明ドットを重ねる。ドットは恒星を完全には隠さなくてよい。
- ドットは恒星サーフェイスへ重ねてから、恒星サーフェイスと同じ2D射影変換を適用する。ドットの位置や不透明度は2秒周期の更新間で補間しない。
- altを `h` とすると、`h > 0` の強度係数は次で求める。

  ```text
  h_eff = max(h, 10 degrees)
  strength = (sin(10 degrees) / sin(h_eff)) ** 1.5
  alpha = 0.2 * strength
  ```

- altが10度以上の場合は式に従って低高度ほど強くし、altが0〜10度の場合は10度の値を使う。altが0度以下の場合は適用しない。
- 同じ恒星が連続して選ばれることは妨げない。効果は選択された恒星に対して、その2秒周期の表示区間だけ見えるものとする。

### 6.5 地平線と地面

- 地平線上と地平線下が視覚的に区別されること。
- 地平線下の領域には地面色のティントを適用する。
- 地形地平線が有効な場合は地形地平線を境界として使う。
- 地形地平線が無効な場合は幾何学的地平線を使う。
- 地面ティント、Earth guide、never-rises 領域は、用途に応じて別の補助色として扱ってよい。

### 6.6 DSO とアステリズム

- DSO は名称付きの主要天体に限定してよい。
- アステリズムは IAU 星座境界ではなく一般的な線パターンとして表示する。
- どちらも通常は淡い補助表示とし、ホバー時は強調してよい。
- 表示有無は GUI から切り替えられる。

### 6.7 簡易表示トグル

- `Space` で、簡易表示をトグルしてよい。
- 簡易表示は、天体以外の要素をなるべく消して見やすくするための全体表示モードとして扱ってよい。
- 簡易表示は 2 段階として扱ってよい。
  - ラベルなし簡易表示
  - ラベル付き簡易表示
- Urban Outlineが有効な場合、表示モードの循環順は常に `通常 -> Inverted City -> ラベルなし簡易表示 -> ラベル付き簡易表示 -> 通常` とする。起動時のdefaultが通常かInverted Cityかによって、循環の開始位置だけが異なる。
- Urban Outlineが無効またはCLIでロックアウトされている場合、`Inverted City`を状態遷移から除外し、`通常 -> ラベルなし簡易表示 -> ラベル付き簡易表示 -> 通常` の順で循環する。
- Urban Outlineを無効にした時点で`Inverted City`が有効な場合は、通常表示へ戻す。Urban Outlineを再び有効にしても、`Inverted City`へ自動復帰しない。
- 現在の表示状態はHUDに、通常時は`Normal [Space]`、反転時は`Inverted City [Space]`、簡易表示時は`Simplified: with labels [Space]`または`Simplified: no labels [Space]`と短く表示してよい。
- 起動直後の表示モードを`default_display_mode`、現在の表示モードを`current_display_mode`として扱う。`--inverted-city`がない場合のdefaultは通常表示、指定された場合のdefaultは`Inverted City`とする。Urban Outlineが利用できない場合はdefaultを通常表示へフォールバックする。
- `current_display_mode`が`default_display_mode`と同じ場合は、通常の固定・動的ステータス行だけを表示する。`Space`で一周して起動時のdefaultへ戻った場合も同様とする。
- `current_display_mode`が`default_display_mode`と異なる場合は、通常の2行ステータスに加えて3行目へモード表示を追加する。モード表示は通常の文字色を背景にし、黒い文字で現在のモード名と`[Space]`を表示する。
- ラベルなし簡易表示は、次を非表示にしてよい。
  - 地点名、地点要約、時刻、ステータス情報
  - DSO
  - アステリズム
  - 雲オーバーレイ
  - 夜間光オーバーレイ
  - 航空機オーバーレイ
  - GMN メテオ軌跡
  - 台風・サイクロン
  - 都市アウトライン
  - 水面レイヤー
  - sky disc
  - Earth guide
  - 副稜線
- 簡易表示中も、`current_display_mode != default_display_mode`の場合は通常の2行ステータスを維持し、モード名と`[Space]`だけを示す追加モード行を表示してよい。これによりステータス表示は3行構成となる。
- ラベル付き簡易表示でも、星、太陽、月、惑星、人工衛星、地平線、天の赤道、黄道、方位ラベル、天頂マーカー、天の極マーカー、および hover によるラベル表示は残してよい。
- ラベル付き簡易表示では、名前付き恒星ラベルと衛星ラベルを固定位置で表示してよい。
- ラベルなし簡易表示では、名前付き恒星ラベルと衛星ラベルを出さなくてよい。

### 6.8 GMN メテオ軌跡

GMN メテオ軌跡は、Global Meteor Network（GMN）が実際に観測した流星の
発光区間を、過去の観測痕跡として天球上へ重ねる補助レイヤーである。現在飛行中の
物体、流星の発生予報、または観測されなかった流星の再現として扱ってはならない。

#### 6.8.1 表示対象と時刻

- 表示対象は、表示時刻以前にGMNから取得できる最新の観測時刻を終端とする直前24時間
  とする。境界を含み、`window_end - 24 h <= meteor_time <= window_end` を満たす観測だけを
  使う。これにより、GMNの登録遅延によってリアルタイム画面の表示窓が空になることを
  避ける。
- 選択窓に含まれる観測は、地理的選別後、開始UTC時刻が新しい順に最大
  `--meteor-trails-max-candidates` 件だけを描画する。既定値は `200` とし、`0` では無制限と
  する。超過分は古い観測から表示対象外とする。ステータスの件数は実際に描画する件数を示す。
- 基準は実時間の現在ではなく zstarview の表示時刻とする。過去日時へ移動した場合も、
  表示時刻より後の観測を使わず、その時点までに取得可能な最新観測から24時間窓を決める。
- 各流星には、GMNデータの開始UTC時刻と、実際に発光した区間の始点・終点の緯度、
  経度、高度を使う。軌道全体や放射点から推定した線へ置き換えない。
- GMNの開始時刻または始点・終点のいずれかに有効な座標・高度がないレコードは
  描画しない。Duration、最大光度、速度、流星群コードは利用可能なら保持してよいが、
  初期版の選別や外観を左右する必須項目とはしない。

#### 6.8.2 地理的選別と観測時方向表示

- 候補抽出では、観測地点と発光区間の始点、終点、または中点との地表距離を使い、
  いずれかが `500 km` 以内にある観測を候補としてよい。この距離は処理量を抑える
  上限であり、可視性を保証する距離ではない。
- 最終的な可視性は、楕円体高を含む始点・終点と観測地点を3次元で扱い、地球曲率を
  考慮した Alt/Az へ変換する。地平線による除外や線分クリップは行わない。
- 可視部分は流星の発生時刻における観測地点からの Alt/Az として保存し、その観測時の
  方位・高度を画面へ投影する。表示時刻が進んでも恒星背景と同じように回転させず、
  地球の自転によって現在は地平線下となる過去の軌跡も、発生当時の見かけの方向に残す。
- この表示は「GMNから取得できる直近24時間分の発光区間を、発生当時に観測地点から見えた
  方向へ写した履歴」であり、現在その方向に物理的な痕跡が残っていることを意味しない。
- 現在の視野外となる部分は画面へ描画しない。観測時刻・表示時刻いずれの Alt/Az を使った
  地平線判定も行わない。

#### 6.8.3 外観と操作

- 各観測は、始点から終点までの静的な発光軌跡として描画する。始点と終点は細く、
  始点から終点の80%にあたる位置で太くなる細長いひし形とする。外側は淡い黄色、
  内側は白で描画し、観測時刻ラベルはその中間色とする。Durationに合わせて線上を
  移動するアニメーション、光芒、頭部マーカーは表示しない。
- 各軌跡の開始位置には、表示時刻から見た観測時刻の経過時間を小型の符号付き時間ラベル
  （例: `-32h`）で表示する。通常のラベル配置や重なり回避は適用しない。
- 全観測を低彩度の同系色で描画し、流星群別の色分けは行わない。恒星、惑星、月、
  地平線、ラベルよりも目立たない低い不透明度とする。
- 不透明度は、表示時刻から見た観測開始時刻の経過時間に対して減衰させる。
  経過24時間までは基準値のままとし、そこからさらに72時間かけて30%まで線形に下げ、
  それ以降は30%のままとする。基準は窓の終端ではなく表示時刻なので、公開遅延のある
  古い窓ほど軌跡全体が薄くなるが、表示対象の軌跡が消えることはない。
- 最大光度による線幅・不透明度の変更は初期版では行わない。後から導入する場合も、
  対数変換と上限を使い、極端に明るい観測が画面を支配しないものとする。
- GUIのメニュー名は `Meteor trails` とし、トグルをOffにした場合は取得済みデータを
  破棄せず、そのセッション内で再表示に利用してよい。
- ビューポート操作中の `fast-mode` では軌跡を描画せず、通常描画へ戻った時点で再表示する。
  設定した不透明度と取得済みデータは `fast-mode` 中も保持する。

#### 6.8.4 データ取得、キャッシュ、欠損

- データ源はGMN公式データページで公開される高レベルの日次機械可読ファイルを基本とする。
  REST APIまたは第三者Python APIを必須経路にしてはならない。
- GMNの日次ファイルはUTC 00:00区切りではなく、太陽黄経1度ごとの約24時間を収録する。
  公式ディレクトリ索引から表示窓の前後に対応するファイルを解決し、各レコードの開始UTC
  時刻を使って24時間窓へ厳密に絞り込む。取得した元データまたは必要項目へ正規化した
  データをローカルキャッシュへ保存してよい。
- 公式ディレクトリ索引と各日次データファイルは、zstarviewがGMNから正常取得した時刻
  `fetched_at_utc`から6時間をfreshとし、その間は再取得しなくてよい。ファイル名の日付や
  観測レコードの時刻をキャッシュ鮮度の判定には使わない。内容が前回と同じ場合も、正常に
  取得できれば`fetched_at_utc`を更新する。キャッシュにはGMN配布ファイル名、収録日の目安、
  `fetched_at_utc`、データ形式を識別できる情報を保持する。
- GUIの更新確認は有効化中に1時間ごとに行ってよいが、実際のGMNへの再取得は各キャッシュの
  `fetched_at_utc`が6時間を超えた場合に限る。これはアプリ起動からの経過時間ではない。
- 更新対象の取得に失敗した場合、表示窓を覆う既存キャッシュがあれば、その取得日時に
  かかわらず観測履歴として使用してよい。キャッシュがない日付の部分は欠測として扱い、
  レイヤーを利用できる範囲だけ表示する。
- 取得、解析、または投影に失敗しても星空本体の起動と操作を継続し、GMNレイヤーだけを
  非表示または部分表示にする。秒・分単位のポーリングは行わず、有効化中の更新確認は
  おおむね1時間間隔とし、実際の再取得は各キャッシュの6時間TTLに従う。
- 観測が0件であることは、その地域・時間帯に流星が存在しなかったことを意味しない。
  観測局分布、天候、昼夜、カメラ視野、機器停止による観測バイアスと欠測を含む。

#### 6.8.5 帰属と状態表示

- レイヤーが有効な間は、`Meteor observations: Global Meteor Network` と同等の
  データ源表示を画面内または状態表示に含める。
- 有効なデータを読めた場合のステータスは、表示中の軌跡の件数と、表示時刻から見た実際の
  表示軌跡の相対範囲を`M {count}, {oldest}-{newest}h ago`のASCII形式で表示する。例えば
  表示中の軌跡が54時間前から30時間前なら`M 100, 54-30h ago`とする。表示軌跡が0件の場合
  だけは、選択した24時間窓の範囲を使う。古い側は時間数を切り上げ、新しい側は切り捨てる。
  0件でも`No meteors`のように流星が存在しなかったと断定してはならない。
- 取得にもキャッシュ利用にも失敗した場合は `Meteor trails: unavailable` と同等の
  短い状態を表示してよい。URL、例外、スタックトレースは画面へ表示せずログへ記録する。
- ライセンス・データ提供元一覧には、軌跡データがGlobal Meteor Network提供であり、
  CC BY 4.0で利用していることとGMN公式データページへのリンクを掲載する。

初期版では、流星群名・放射点の表示、期間選択、fireball強調、発生時刻に合わせた
アニメーション、CNEOS等の別データ源との統合、およびランダムな流星生成を対象外とする。

### 6.9 雲オーバーレイ

雲オーバーレイは、利用可能な衛星データに基づく近似表示として扱う。

- `--cloud-opacity 0` はそのセッション中の雲表示を無効化する。
- 取得済みソースがあれば、視点変更では再取得せず、観測者中心の (altitude, azimuth) グリッドを再利用して軽量に投影し直してよい。
- 取得中は `Downloading`、投影中は `Projecting` と表示してよい。
- 雲データが壊れている、欠損している、または再取得中である場合は、既存画像を維持してよい。
- 雲の warm-threshold 正規化は、赤道中心 `0°` の単線ではなく、おおむね `±5°` の赤道帯サンプルを使ってよい。
- その赤道帯サンプルは、雲を白っぽく見せるための基準値を安定化する目的で使う。
- 雲の基本色は白とする。ただし夜間は過度に目立たないよう、太陽高度に応じて白から青灰色へ滑らかに寄せてよい。
- 雲の合成では、雲のある部分の空をグレースケールへ寄せる下地処理と、雲色の加算を併用する。下地処理の係数は `cloud_opacity * 4.0` を最大 `1.0` でクリップし、雲色の加算は `cloud_opacity` を係数とする。

#### 6.9.1 雲高度シェルと夕焼け色

雲オーバーレイは、雲量を単一の平面へまとめるのではなく、複数の高度シェルに分けた近似表示へ拡張してよい。既定のシェルは地表からおおむね `3 km`、`5 km`、`7 km` とする。

- 雲ソースの全体的な雲量に応じて、各高度シェルの寄与を滑らかに変化させる。
- 各シェルの雲量は、描画直前まで独立したフィールドとして保持してよい。
- 表示時は高いシェルから低いシェルの順に合成し、近い低層雲が遠い高層雲を覆う関係を保つ。
- シェルごとの色は、太陽高度、太陽方向、シェル高度、および雲量を使った表示上の近似として決めてよい。
- 昼間の基本色は白とする。薄明時は太陽方向の低空色を下からの散乱光の近似として使い、低層雲ほど強く、高層雲ほど弱く暖色へ寄せるなど、シェルごとに異なる夕焼け補正を適用してよい。
- 太陽高度が `-8°` 未満の場合は夕焼け補正を無効化する。`-8°` 以上では固定の上限時間帯を設けず、低空色の `R-B` と `R-G` がともに暖色側へ外れた場合だけ補正を有効にする。昼間の青〜白の低空色では従来の白〜青灰色の雲色を維持する。
- 雲の高度情報は衛星データから厳密に観測されたものではなく、シェル分配による近似である。特定の雲の上面・下面や局所的な雲頂高度を保証しない。
- 雲シェルの色付けは完成済みの空色ディスク画素をそのまま転用せず、太陽方向の仰角 `0`〜`10°` の空色モデルを低空からの散乱光の近似として、シェルごとの上限付き混合に使う。これにより、夕焼け時に雲全体が過度に赤くなることを避ける。
- シェル分割を利用できない古いキャッシュや取得結果は、単一フィールドの雲として安全に表示してよい。

### AKARI IR bands

AKARIの90 / 140 / 160 µm遠赤外線マップを疑似カラーで表示する独立レイヤーを提供する。

- GUIメニュー名は `AKARI IR bands` とする。
- GUIは他のレイヤーと同じチェック式の表示／非表示制御だけを提供する。
- GUIに専用の強度スライダーや表示モード選択は設けない。
- 起動前ダイアログの `Stars` に `AKARI IR bands opacity` を表示する。
- CLIでは `--akari-ir-bands-opacity` だけで表示強度を制御する。
- 既定値は `0.10` とし、`0` はOFFとして扱う。
- データキャッシュがない場合、GUIメニュー項目は無効化する。
- アプリ起動時に自動ダウンロードは行わない。
- 表示は夜間のみとし、太陽高度に応じて滑らかにフェードする。
- 最終的なAKARI opacityは太陽高度 `-9` 度で0、`-18` 度で指定値となるよう滑らかに変化させる。
- `--akari-ir-bands-opacity` で指定する値は、太陽高度 `-18` 度以下の最大実効opacityとして扱う。`0` は従来どおりOFFとする。
- 簡易表示では太陽高度によるフェードを適用せず、指定された最大実効opacityで表示する。
- このフェードは空の暗さに対応する視覚的な補正であり、AKARIデータ自体の時間変化を表すものではない。

#### 6.9.2 雲ストライプ

雲量を画面に落とし込む際は、以下の 4 つのストライプモードを切り替えられるものとする。

- `--cloud-stripe MODE[,COUNT[,WIDTH]]`
  - `MODE`: `width`（既定）、`width-quantized`、`halftone`、`alpha` のいずれか。
  - `COUNT`: ディスクを横切る絶対的なストライプ本数。ウィンドウサイズや星レイヤーのレンダリング面サイズに応じてスケールしない。大きなウィンドウではストライプ間隔が広がり、一本一本が太くなる。
  - `WIDTH`: モード依存の幅係数。
    - `halftone`: 円/線の太さを調整する係数。既定値は `1.7`。
    - `width`: 最大帯幅に対する比率。既定値は `0.85`。
    - `alpha`: 帯幅に対する比率。既定値は `0.25`。
  - 既定値は `halftone,30,1.7` とする。
  - `COUNT` または `WIDTH` を `0` にすると、そのセッション中の雲描画を無効化する。

- `halftone` モード
  - 画面固定の 45° 傾いた正方形グリッド（`u = x - y`、`v = x + y`）に基づく。
  - 各セルで雲量を 8 段階（0〜7）に量子化し、レベルに応じた直径の円を描く。
  - 同じレベルが右下方向に連続するセルは、`RoundCap` ペンで太い線分（halftone）として接続する。
  - グリッド間隔は、画面が小さい場合でも 20px 未満にならない。
  - 縁取りは付けない。

- `width` モード
  - 中心対称のストライプを描き、雲量に応じて帯の見かけ幅を変える。

  - `width-quantized` モード
  - `width` の変形として、雲量を `0%`、`25%`、`50%`、`75%`、`100%` の5段階に量子化する。
  - 太さが変わる箇所には隙間を設け、各ストライプ区間は丸い端点で描く。

- `alpha` モード
  - 帯幅は固定し、雲量に応じて帯のアルファ値を変える。

#### 6.9.3 実験的 Geo-satellite 経路

- `Geo-satellite` は、既存の GOES/Himawari 雲オーバーレイとは別の実験的な Europe 補助経路である。
- 対象範囲は、おおむね緯度 `32N` 〜 `73N`、経度 `15W` 〜 `35E` としてよい。
- 観測者がこの責務領域内にいる場合は、雲表示のデータ源として Geo-satellite のみを使ってよい。
- 責務領域の外では、Geo-satellite を無理に使わず、既存の雲表示を使ってよい。
- データ源は MET Norway Geo-Satellite API を使ってよい。
- 画像種別は既定で `infrared` としてよい。
- 以前の起動で保存された Geo-satellite の原画像 cache があれば、それを再利用してよい。再利用時も、最終的な雲表示はその原画像から再構成してよい。

#### 6.9.4 取得失敗時

- 取得失敗時は、既存の雲画像を維持してよい。
- 壊れた画像や未定義の代替画像を表示してはならない。
- 雲取得失敗の原因調査には、通常起動とは別の雲ソース診断 CLI を利用できるものとする。

#### 6.9.5 モデル予報降水オーバーレイ

モデル予報降水オーバーレイは、Open-Meteo Weather Forecast API が返す現在時刻の
予報降水量を、観測地点周辺の方向と距離を読むための斜めの雨線として表示する。雨量計、
地上降雨レーダー、または準リアルタイム衛星降水による実況表示とは扱わない。

- レイヤーは既定で `Off` とし、利用者が明示的に有効化した場合だけ Open-Meteo へ
  問い合わせる。
- 雲および熱帯低気圧レイヤーと同様に、現在時刻から前後5分以内のリアルタイム表示で
  だけ利用可能とする。過去または未来の時刻を表示するときは取得、描画、およびメニュー
  操作を無効化する。
- 利用できる provider は Open-Meteo Free API（非商用利用限定）だけとし、provider の
  選択肢や Commercial API の API key 入力経路は設けない。
- `zstarview-gui` の設定ダイアログでは降水不透明度を保存できるが、保存時には利用条件の
  確認や Open-Meteo への通信を行わない。正の不透明度を指定して実際に `zstarview` を
  起動するときにだけ、未確認なら確認ダイアログを表示する。
- 確認ダイアログには Free API が非商用利用限定であること、呼び出し上限、CC BY 4.0 の
  帰属条件、および Open-Meteo 利用条件へのリンクを表示する。同意した場合は確認条件の
  version を共通設定へ保存し、起動を継続する。
- 確認ダイアログをキャンセルした場合は、降水レイヤーだけを無効化して続行せず、APIへ
  通信する前かつメイン画面を生成する前に起動を中止する。`zstarview-gui` からの起動では
  `Open-Meteo Free API terms were not accepted. zstarview was not started.` と同等の
  最終メッセージをエラー時と同じ経路で表示し、`zstarview-gui` も終了する。保存済みの
  不透明度は変更しない。
- Helpメニューには、設定値や同意状態にかかわらず Open-Meteo 利用条件を確認できる項目を
  常設する。
- Helpメニューの `Licenses and Data Sources...` は、そのzstarviewバージョンに同梱された
  ライセンス・データ提供元一覧をアプリ内ダイアログで表示する。一覧はオフラインで閲覧でき、
  マウスとキーボードによる選択、`Ctrl+A`、`Ctrl+C`、右クリックコピー、および `Copy All`
  に対応する。提供元リンクは既定の外部ブラウザで開いてよい。
- 降水レイヤーのメニュートグルは常に表示する。保存された降水不透明度が `0` の場合は
  無効化し、正の場合だけ操作可能にする。トグルをOffにしても保存された不透明度は失わず、
  Onに戻したときは同じ値を使う。未同意の実行は起動を完了できないため、実行中のトグル
  から同意確認を開始する経路は設けない。
- `zstarview-export-image` は降水不透明度オプションを受け付ける。値が `0` の場合は同意を
  確認せず、正の場合は `zstarview` または `zstarview-gui` からの対話的な起動経路で保存
  された有効な同意versionがある場合だけ降水を取得・描画する。
- `zstarview-export-image` 自身は非対話コマンドとして利用条件を表示・確認・記録しない。
  正の不透明度で有効な同意がなければ、Open-Meteoへの通信と出力生成を始める前に非0で
  終了し、同意には `zstarview` または `zstarview-gui` を起動する必要がある旨をASCIIの
  stderrメッセージで案内する。失敗した出力ファイルを残さない。
- Open-Meteo の返す対象時刻、およびモデル由来の値であることを利用者が
  確認できるようにする。集計間隔は応答検証と内部データには保持するが、コンパクトな
  status line には表示しない。表示とライセンス一覧には Open-Meteo の帰属を含める。
- 降水レイヤーが有効な間は、対象時刻とともに `Forecast: Open-Meteo` に相当する
  コンパクトなstatusを表示する。レイヤーが無効な間は画面上の帰属表示を行わない。
  `zstarview-export-image` で降水を描画する場合も、同じ帰属を出力画像内に表示する。
- 周辺降水の既定の表示範囲は観測地点から `8 km` 以上 `32 km` 以下とする。遠方の降雨を
  広域警戒情報として表示することより、現在の観測環境に近い周辺降雨を読み取る
  ことを優先する。
- 観測地点そのものの予報降水量も取得し、降水強度が `0.1 mm/h` 以上なら現在地の雨線を
  画面中央に表示する。現在地には地理的な方位がないため、この雨線は地表上の地点として
  Alt/Az 投影せず、視線方向を変えても画面中央に留まるスクリーン空間の表示とする。
- 現在地の雨線は周辺の近距離雨線と同じ二色線、斜線、本数による強度表現を使い、高さ、線幅、
  線間隔をそれぞれ `1.4` 倍とする。本数は通常の雨線と同じ最大6本に制限し、強い降水でも
  画面を過度に覆わないようにする。
- 周辺の雨線は緯度経度格子や同心円に沿って並べず、観測地点中心のひまわりの種状
  （黄金角）配置とする。既定では `8`～`32 km` の環状範囲に `48` 点を置く。
- 観測地点と周辺48地点の計49地点は1回の複数座標リクエストとして問い合わせる。各雨線群は
  Open-Meteo が各地点に対して返したモデル予報値を使い、元の気象モデル格子点を表すものとは
  扱わない。
- 降水のない点は雨線を表示しない。欠測は降水量 `0` と区別し、欠測値から雨線を生成
  しない。
- 雨線は濃い青の実線を下地に、薄い青の細い点線を重ね、各表示点に `///` のような
  右上がりの平行線を置く。両方の線端は角型とする。降水強度は線の本数で表し、
  `ceil(log2(1 + r_mm_h / 2))` を1～6本へ制限する。
- 雨線の基準線幅は `2.2 px` とし、viewer の line-width scale を乗算する。薄い青の
  点線は基準線幅の `0.4` 倍、ダッシュパターンは `[0.4, 5.6]` とする。濃い青・薄い青
  の各線は距離補正後のレイヤー不透明度の `0.7` 倍で描画する。
- 雨線の表示角上の高さと不透明度は距離だけで減衰させる。`8 km` では高さ `16/3°`・
  不透明度係数 `1.0`、`32 km` では高さ `2°`・不透明度係数 `0.35` とし、その間を線形
  補間する。不透明度係数は利用者が指定したレイヤー全体の不透明度へ乗算する。
- 雨線の高さは実際の降水の鉛直範囲を意味しない。距離を読みやすくするための
  表示上の誇張であり、雲底、雲頂、雨滴の落下高度を表さない。
- 起動後に Open-Meteo を取得できない、または有効な予報値がない場合は、降水
  オーバーレイだけを表示せず、他の星空表示を継続する。未同意は取得失敗として扱わず、
  前述のとおり起動前に中止する。
- 同一地点・同一 provider の予報は10分以上の間隔を空けて更新し、取得結果はプロセス
  内だけで再利用する。更新に失敗した場合は以前の雨線を維持せず、降水オーバーレイを
  非表示にする。

### 6.10 地形地平線

- DEM から推定した地形地平線を補助線として表示できる。
- 距離帯ごとの副稜線を表示してよい。
- 副稜線は、同じ方位付近で手前のより高い稜線に隠れるほど、より薄く・より目立たない見た目にしてよい。
- 副稜線の色は地形地平線と同系のベージュ系で描いてよい。
- 地形地平線は地点依存であり、時刻依存ではない。
- `opacity == 0` の場合、取得、計算、描画を行わない。
- キャッシュ済み DEM が古い場合でも、再取得失敗時は既存キャッシュを警告付きで使ってよい。
- DEM のキャッシュは、要求範囲を満たす Copernicus DEM タイルの集合として扱う。
- 通信に失敗した場合、要求範囲に対応する有効または期限切れのキャッシュタイルがあれば、それを使って地形地平線を生成してよい。
- 利用可能な DEM キャッシュタイルがない場合は、地形地平線だけを表示せず、星空本体の表示は継続する。
- キャッシュ利用時のウィンドウ下部の状態表示は `Terrain: cache`、利用可能なデータがない場合は `Terrain: unavailable` とする。

### 6.11 都市アウトライン

- 観測地点周辺の建物輪郭を、LED照明による冷たい都市光を抽象化した淡い青白色`(207, 229, 255)`で表示し、閉じた輪郭には同色の薄い面塗りを重ねてよい。
- 屋根ポリゴンの面塗りは人工照明の一部として扱い、基準アルファを1.2倍したうえで、night light と同じ太陽高度係数を最終的な塗り強度へ乗算する。太陽高度 `-4` 度で最低強度となり、`-9` 度で最大となるよう、その間を滑らかに補間する。太陽が最低高度を通過した後の上昇側では、最低高度から `-9` 度へ向かう間に活動係数を100%から45%まで滑らかに減衰させる。
- 屋根ポリゴンの面塗りには夜間最大光量の5%を最低係数として適用し、昼間も薄い色を残す。
- 建物の輪郭線は屋根面の照明とは別の地物基準として扱い、面塗りとは独立した、より弱い減衰または通常の表示強度を適用してよい。
- 通常近距離レイヤーと遠距離スカイスクレーパー補助レイヤーを分けて扱ってよい。
- 取得や再取得はバックグラウンドで行ってよい。
- 建物データのソースは、対象地点に対応する有効なPLATEAU派生キャッシュがある場合はPLATEAUを優先し、ない場合はOverture Mapsを利用してよい。
- PLATEAUの対象地域であっても、PLATEAU派生キャッシュが未準備なら、起動時にPLATEAUの大容量データを自動取得せず、通常のOverture Maps取得経路を利用してよい。
- PLATEAU派生キャッシュは、利用者が明示的に `zstarview-download-plateau-buildings` を実行して準備するものとする。
- PLATEAUの元CityGMLデータの取得・展開・変換は準備CLIの責務とし、通常の `zstarview` 起動処理に含めない。
- PLATEAUとOverture Mapsのデータは、同一地点で無条件に重ね合わせず、PLATEAUキャッシュが有効な範囲ではPLATEAUを単独で利用してよい。
- 完了済みPLATEAUキャッシュが観測地点と検索半径をカバーする場合、通常の都市アウトラインと遠距離補助レイヤーはPLATEAUを使用し、Overture Mapsの建物取得を開始してはならない。
- PLATEAUキャッシュがない場合、または観測地点をカバーしない場合は、従来のOverture Maps経路へフォールバックしてよい。
- `opacity == 0` のセッションでは取得しなくてよい。
- 高密度な輪郭は視認性を優先して間引いてよい。
- 画面上で `x` または `y` の広がりが十分小さい閉輪郭は、面塗りを省略してよい。

#### Inverted City

- `Inverted City`は`Space`による表示状態の一つとして提供し、Layersメニューには個別のトグルを設けない。
- `Inverted City`を有効にすると、建物の輪郭、屋根ポリゴンの面塗り、遠距離スカイスクレーパー補助レイヤーを、幾何学的な水平面 `alt=0` を基準に上下反転して表示する。
- 高度の表示変換は、概念的に `alt_inverted = -abs(alt)` とする。通常の建物が水平面より上にある場合は下へ反転し、タワーなどから見て元々水平面より下にある建物も上空へ反転せず、水平面より下に留める。DEM由来の地表高度によって建物が低く見える場合も、その高度を反映した結果として建物は地下側に表示されてよい。
- 天体計算、観測地点、観測高度、地形地平線、地面ティント、Earth guide、水面、道路夜間光は変更しない。
- 道路夜間光は`Inverted City`の反転対象に含めない。
- このモードは星の可視性や物理的な遮蔽を再計算するものではなく、都市レイヤーが空の上に重なって見えることを避けるための表示補助および演出である。
- `Urban Outline`が無効な場合、`Inverted City`を有効にしていても都市レイヤーは表示しない。
- `Inverted City`の状態は同じGUIウィンドウ内の地点変更、時刻変更、視線変更では維持してよい。`Space`による表示状態の変更では、上記の循環規則に従う。defaultとcurrentのモード値は一時状態であり、アプリケーション終了時に保存しない。
- アプリケーション終了時に状態を保存してはならず、次回起動時は無効とする。
- `--inverted-city`はGUI起動時の初期モード指定としてのみ扱い、設定ファイルや起動プロファイルへ保存しない。
- `zstarview-export-image`には導入せず、画像出力は通常の都市アウトライン表示とする。

### 6.12 水面レイヤー

- 海と inland water を別ソースとして扱ってよい。
- 水面レイヤーは `Water Surface` と表示してよい。
- inland water は、`ele` / `water_level` がなければ DEM から推定した高さを使ってよい。
- 水面は、取得した水域ポリゴンを水面ドットへ変換して表示してよい。
- 川・湖などの内陸水域の水面ドットは、観測地点から5m未満のサンプルを除外する。
- 水面ドットに加えて、同じ水域ポリゴンの簡略化済み外周を観測地点から見た境界折れ線として表示してよい。これにより、遠距離の川や湖でも水域の輪郭と広がりを識別できるようにする。
- 境界折れ線は元データの高密度な頂点列を直接描画せず、観測地点基準で簡略化したポリゴンから生成する。水面内部のドット表示は維持する。
- 境界折れ線には、観測地点から最大10kmの距離、前方半球、視野範囲、地平線下の表示範囲によるクリッピングを適用する。水面ドットの検索・描画範囲は従来の高度依存設定を維持する。距離円を横切るポリゴン辺は、辺と距離円の交点を補間して分割してよい。
- 方位角の 0 度/360 度境界、視野境界、距離境界をまたぐ折れ線は、それぞれ別のフラグメントとして描画してよい。
- 境界線の表示は水面ドットと同じ水面レイヤーに属し、河川・湖沼の種別ごとの色分けと表示強度を継承してよい。
- 通常描画時の水面ドットと境界折れ線は、同じ方位の地形地平線より低く、かつ地形地平線より遠方にある部分を、地形に遮られた部分として稜線と同様に薄く表示してよい。ビューポート移動中などの簡易描画では、この遮蔽判定を省略してよい。
- 外部 API へ送る水面取得リクエストは、`zstarview/1.32.11 (+water-overlay)` を付けてよい。
- サービスごとに識別が必要な場合は、`zstarview/1.32.11 (+service)` 形式の接尾辞を足してよい。
- `Terrain Horizon` が無効な間は水面レイヤーも表示しなくてよい。
- 水面キャッシュは、観測地点と要求範囲に対応する水域ポリゴンおよび水面点列の結果として扱う。
- 通信に失敗した場合、同じ地点のキャッシュがあれば、その取得日時や TTL にかかわらず水面レイヤーへ再利用してよい。同じ地点で要求範囲が異なる場合は、要求範囲を包含する既存キャッシュを優先してよい。
- 同じ地点の利用可能な水面キャッシュがない場合は、水面レイヤーだけを表示せず、星空本体の表示は継続する。
- キャッシュ利用時のウィンドウ下部の状態表示は `Water: cache`、利用可能なデータがない場合は `Water: unavailable` とする。
- `W` で on/off してよい。

#### 道路夜間光 (`Road Night Lights`)

- OSM の道路 `way` を補助的な夜間光レイヤーとして表示してよい。
- 対象とする `highway` 値は `motorway`、`trunk`、`primary`、`secondary`、`tertiary` とする。`*_link` 系は初期対象に含めない。
- 道路データは観測地点から最大10kmの範囲を、対象5分類をまとめた1回の要求で取得してよい。
- 10km範囲の取得がHTTP 504または通信タイムアウトで失敗した場合は、同じ地点について5km範囲で1回だけ再取得してよい。5kmで取得できた場合は、その範囲の道路データを使用し、5km用キャッシュへ保存する。
- 道路データのキャッシュ有効期間は、取得日時から30日とする。30日以内のキャッシュはAPIへ再要求せずに利用してよい。
- 30日を超えたキャッシュは stale として保持し、まず10km範囲の更新を試みる。更新がHTTP 504または通信タイムアウトで失敗した場合は、5km範囲へ1回だけフォールバックする。
- 10kmまたは5kmの更新に成功した場合は、成功した範囲のキャッシュを保存する。更新に失敗し、staleキャッシュが存在する場合は、そのキャッシュを道路レイヤーの表示に使用してよい。
- 期限切れキャッシュもなく、10kmおよび5kmの取得に失敗した場合は、道路夜間光だけを表示せず、他のレイヤーの処理を継続する。
- 描画対象は観測地点から0.5km以上10km以下の道路部分とする。0.5km未満の道路は、近距離の光が画面を過度に占有することを避けるため表示しない。
- 道路の中心線ストロークに沿って、日没後から深夜にかけて弱い連続光を描画してよい。
- 連続ストロークは車のヘッドライトを抽象化した約6000Kの白色とし、`--road-light-opacity` の値をそのまま基準光量として描画する。
- 連続ストロークの高さは、各道路座標でDEMから求めた地表高に0.5mを加えた位置とする。この0.5mは車のライトの位置を抽象化するとともに、光が地表に埋もれることを防ぐための高さとする。
- 連続光は太陽高度 `-4` 度から `-9` 度まで増加させる。太陽が最低高度を通過した後の上昇側では、最低高度から `-9` 度へ向かう間に活動係数を100%から45%まで滑らかに減衰させ、明け方には街路灯を想定した約240m間隔の小さな光点を主体としてよい。
- 道路ランプを表す光点の高さは、各光点でDEMから求めた地表高に8mを加えた位置とする。
- ヘッドライト風ストロークの開始・終了時の太陽高度フェードは、既存の `night lights` と同じ扱いとする。
- 道路ランプを表す光点は太陽高度`0`度で消灯し、`0`度から`-4`度にかけて滑らかにフェードし、`-4`度以下でヘッドライト基準光量の約0.8倍とする。深夜の時刻変化による減衰は適用しない。
- 道路の連続光とランプの光点には距離による滑らかな減衰を適用し、約0.5kmで最大、10kmでは基準値の約20%まで弱めてよい。
- `--road-light-max-candidates N` で、道路 `way` 単位の描画候補数に上限を設ける。既定値は `5000` とし、`0` では道路夜間光レイヤーを無効化する。
- この上限は、環状範囲に交差する道路を観測地点からの最短距離で並べ、近い順に候補を選別した後、道路形状の簡略化、DEMサンプリング、Alt/Az投影を行う前に適用する。角長、道路の頂点数、道路種別、取得順は選別基準にしない。採用した1本の `way` から生成する連続ストロークとランプ光点は、まとめて1候補として扱う。
- 同距離の場合は `way_id` などの安定した識別子で決定的に並べる。道路データの分割単位に依存する角長を評価しないため、データの保存分割による優先順位の揺れを避ける。
- 上限は取得データや道路キャッシュの保存件数を制限しない。キャッシュ済みの全道路データから、観測地点に応じて候補を再選別できるようにする。
- CLIでは `--road-light-opacity` で道路光の基準opacityを指定できる。`0` を指定した場合は道路データの取得・描画を無効にし、起動中のLayersメニューから再有効化できない。
- `zstarview-export-image` でも同じRoad Lightsデータと描画強度を使用し、正の `--road-light-opacity` で画像へ道路光を描画する。取得失敗やタイムアウト時は、部分データを許可する実行では道路光だけを省略して画像出力を継続する。
- 起動時ダイアログの `Overlays` タブには `Road light opacity` を用意する。
- Layersメニューには `Road Lights` を用意し、ショートカット `R` で道路ランプとヘッドライトの両方を切り替える。
- 道路種別ごとに光量、光点間隔、最大表示距離を変えてよい。ただし、これは実際の交通量や街路灯位置の再現ではなく、OSMの道路形状から生成する抽象表現とする。
- 道路データを取得できない場合やキャッシュがない場合は、道路夜間光だけを表示せず、星空本体と他のレイヤーの表示は継続する。
- 初期実装の表示強度は既定値を使い、レイヤーを取得できない場合は自動的に省略する。

#### 海岸線ベクタタイル配布・キャッシュ

OSM Water Polygonsから生成した海岸線ベクタタイルを、アプリ本体に同梱せず、GitHub Releasesから任意に取得して利用できる。未取得・取得失敗・破損時にも、現在の水面ドット表示を失敗させてはならない。

- キャッシュの既定ルートは `CACHE_PATH/coastline/osm-water-polygons/{source-date}/schema-1/` とする。
- トップレベルは既存の32×16全球グリッドとし、データ量が大きいタイルだけを4×4の子タイルへ分割する。
- 通常タイルは単一の圧縮ベクタファイル、分割タイルは子タイルのmanifestと子ファイルを保存する。
- manifestにはデータソース、データ日付、EPSG:4326、グリッド、分割方式、アセット名、ファイルサイズ、SHA-256を記録する。
- 描画時は観測地点から最大10km以内の海岸線だけを読み込み、簡略化した境界折れ線として描画する。
- 川・湖などの内陸水域の境界も最大10kmまで描画する。水面ドットの検索・描画範囲は従来の高度依存設定を維持する。
- 配布アセットはx列単位とし、`coastline-grid-x00-{source-date}.zip` から `x31` までの形式で管理する。
- 専用CLIは `--lon-min` と `--lon-max` で経度範囲を受け取り、重なるx列をグリッド境界まで拡張して取得する。全世界取得…2510 tokens truncated…Square Window`: クライアント領域を現在の短辺に合わせて 1 回だけ正方形へ補正するメニュー項目。実行時にただちにリサイズし、その後の通常のウィンドウリサイズ動作は固定しない。
- `Default Window Size`: デフォルトのウィンドウサイズに戻す。
- `Fit to Screen`: アスペクト比を保ったまま、画面の利用可能領域の 90% に収まる最大サイズにリサイズする。
- `Fullscreen` (`F11`): フルスクリーン表示をトグルする。
- `Exit` (`Q`): アプリケーションを終了する。

### 6.13 Display tone curve

Display tone curveは、色再現性や端部階調の識別能力が十分でないTV・モニターで、
黒つぶれと白飛びを避けるための任意の表示補償である。測色器によるICC
キャリブレーションではなく、利用者が無彩色の隣接帯を目視して求めた識別限界を
入力とする。

- 補正対象は通常ビューアの完成済みpresent frameとする。
- 補正はpresent frameをウィンドウへ描画する直前に適用する。
- hover、検索マーカー、最終ラベル、HUD、status lineは補正後に描画し、
  display tone curveの対象に含めない。
- RGB各チャンネルへ同じ単調増加LUTを適用し、alphaは変更しない。
- 完全な黒 `(0, 0, 0)` と完全な白 `(255, 255, 255)` は維持する。
- `BLACK`付近までの暗部は識別可能な側へ滑らかに持ち上げ、`WHITE`付近より
  明るい階調は識別可能な側へ滑らかに圧縮する。中間調は可能な限り恒等変換を
  維持する。
- 補正はディスプレイで失われた情報を復元するものではなく、アプリの出力値を
  クリップされにくい範囲へ事前に再配置するものとする。
- `off`の場合は補正用画像を生成せず、従来のpresent frameを直接表示する。
- 補正が有効な場合だけ表示用の追加サーフェイスを生成してよい。
- スクリーンショット、周期デバッグ画像、`zstarview-export-image`の出力には、
  既定ではディスプレイ固有の補正を適用しない。

キャリブレーションパターンは、RGB `(0, 0, 0)` の背景上へnear-blackの番号付き
無彩色パッチを暗い順に、RGB `(255, 255, 255)` の背景上へnear-whiteの番号付き
無彩色パッチを暗い順に2階調刻みで並べる。各パッチは輪郭線を持たない塗りだけの
短い矩形とし、上下に基準背景が見える余白を設ける。矩形間は8px空け、各背景領域の
中央寄りに配置する。黒側では背景との境界を確実に識別できる最も暗い
（左側の）パッチ、白側では背景との境界を確実に識別できる最も明るい（右側の）
パッチを選択するよう、各パターンの近くで案内する。選択時はパッチ外のマーカーと現在値を
即座に更新する。
利用者には「ぎりぎり見える値」ではなく、通常の視聴条件で確実に区別できる値を
選ぶよう案内してよい。

### 6.14 表示調整ガイドライン

表示内容を調整するときは、情報量を一度に増やさず、次の順序でレイヤーを確認する。

1. **主役レイヤーだけを確認する。**
   - 恒星
   - 惑星
   - 月
   - これらだけで天体表示として成立していることを確認する。
2. **地物レイヤーを追加する。**
   - 地形地平線・稜線
   - 建物
   - 水面
   - 天体と地上の位置関係が把握できることを確認する。
3. **UIレイヤーを追加する。**
   - 星座線
   - ラベル
   - アステリズム
   - 情報が読める一方で、天体を覆うほど過密にならないことを確認する。
4. **背景レイヤーを最後に追加する。**
   - 空の色
   - AKARI IR bands
   - 雲
   - 大陸などの背景情報
   - 背景が主役にならず、空の空気感を補助することを確認する。

調整後に表示が成立しなくなった場合は、最後に追加または変更したレイヤーから強度、彩度、密度、表示範囲を疑い、直前の構成へ戻して原因を切り分ける。特に、恒星・惑星・月が見えにくくなった場合は、背景レイヤーを先に弱める。

表示全体の判断基準は、次の合言葉にまとめる。

> **主役は天体、背景は空気感、UIは案内、地形は基準。**

実装や調整の際は、少なくとも次を確認する。

- 星は見やすいか。
- 惑星や月は埋もれていないか。
- 地平線は分かるか。
- ラベルは読めるか。
- 背景は主役になっていないか。
- 色が多すぎないか。
- 高彩度は本当に必要なものだけになっているか。

### 7.3 起動前設定ダイアログ

`zstarview-gui` は、起動前設定ダイアログを先に開いてから GUI 本体を起動する専用エントリポイントとして扱ってよい。

- タブは `Observing Conditions`、`Celestial`、`Atmosphere`、`Ground`、`General` の順とする。
- `Observing Conditions` は折りたたみ可能な `Location`、`View`、`Time` の3セクションに分け、観測地点、視線・画角、観測時刻をまとめて扱う。
- `Celestial` は星、月、DSO、アステリズム、天球ガイド、AKARI IR bandsを扱う。
- `Atmosphere` は空の色、雲、Geo-satellite、降水予報、熱帯低気圧、航空機、
  GMN メテオ軌跡、人工衛星を扱う。
- `Ground` は地形、地表ガイド、水面、夜間・道路照明、都市外形を扱う。
- `Atmosphere` と `Ground` の各タブ内は、対象レイヤーごとのセクションに分けてよい。
- `City` 欄には約3行分の高さを持つ複数行入力欄を用いてよい。
- `Auto Search` ボタンは現在地自動取得の結果を反映してよい。
- `Search ...` ボタンは専用の place search dialog を開いてよい。
- `View` セクションには視線中心と FOV 系の値を置いてよい。
- `Time` セクションでは `Current time`、`Relative time`、`Absolute time` を切り替えてよい。
- `Reset` は前回起動値を既定値へ戻すために使ってよい。
- `Cancel` は GUI 起動を中止してよい。
- `General`タブに`Display tone curve`の現在値と`Calibrate...`ボタンを置く。
- `Calibrate...`は未補正の約800x600の通常ウィンドウを開き、黒側と
  白側の番号付き階調パッチをクリックして`BLACK,WHITE`を選択できるものとする。
- 確定した値は`zstarview-gui`の起動プロファイルへ保存し、同じ起動処理へ
  そのまま適用してよい。キャリブレーションのためにプロセスを再起動しない。
- キャリブレーションを取り消した場合は、保存済みの値を変更しない。

### 7.4 GUI 検索

GUI では `--search QUERY` に相当する検索を 1 件だけ実行してよい。
検索結果が 1 件の場合は、その対象を中心にして画像を生成してよい。
0 件または複数件の場合は、`--list` がない限り候補一覧を出して終了してよい。

### 7.5 ホバーとハイライト

- ホバー時に天体名やラベルを表示してよい。
- `jump highlight` は短時間の強調表示として扱ってよい。
- label は候補を集約してから、HUD 直前にまとめて描画してよい。
- 簡易表示では、名前付きの恒星ラベルをすべて表示してよい。
- 簡易表示の恒星ラベルは、`B-V` 由来の恒星色を使ってよい。
- 簡易表示の恒星ラベルは、ラベル文字の不透明度をおおむね `0.7` にしてよい。
- 簡易表示の恒星ラベルは、ラベルの左下隅が恒星位置に一致するように配置してよい。
- 簡易表示の恒星ラベルでは、重なり回避や位置探索を行わなくてよい。
- 太陽には、Moon と同じ程度の控えめな色味のラベルを付けてよい。
- 太陽ラベルには、丸囲みや別のマーカー装飾を付けなくてよい。
- `Space` による全体表示トグルは、Urban Outlineが有効な場合は `通常` -> `Inverted City` -> `簡易表示（ラベルなし）` -> `簡易表示（ラベル付き）` -> `通常`、無効な場合はInverted Cityを除いた順で切り替えてよい。

### 7.6 ビューポート操作中の簡易描画

視線変更またはウィンドウリサイズ直後は、短時間の簡易描画モードに入ってよい。
簡易描画では、明るい星のみを即時再投影して表示し、重い補助レイヤーは後段更新でもよい。

## 8. CLI 派生コマンド

### 8.1 `zstarview-export-image`

`zstarview-export-image` は、1 枚の画像を生成して終了する headless CLI である。

- GUI ウィンドウは常駐しない。
- 地点、時刻、視線、テーマ、各レイヤー opacity、`--enlarge-moon`、`--bright-bodies` などを受け付けてよい。
- `--output` は必須としてよい。
- `--image-size` で出力サイズを指定してよい。
- `--layer-timeout-seconds` で各レイヤーの待ち時間上限を指定してよい。
- `--allow-partial-data` により部分データ保存を許可してよい。
- 正の `-P` / `--precipitation-opacity` は、共通設定に現在versionのOpen-Meteo Free API利用条件への
  同意が保存されている場合だけ受け付ける。未同意なら通信・描画・出力作成前に非0で終了し、
  対話的な `zstarview` または `zstarview-gui` 起動による確認をASCIIのstderrで案内する。
- `zstarview-export-image` 自身は利用条件への同意を取得または保存しない。降水を描画した
  画像には通常viewerと同じ `Forecast: Open-Meteo` 帰属を含める。
- `--include-direction-grid` で静的な方向グリッドを重ねてよい。
- `--sixel` で端末へ SIXEL 出力してよい。
- PNG に保存する場合、出力画像には `zstarview` のアプリケーション情報と、描画時点の HUD 相当情報を PNG メタデータとして埋め込んでよい。
- 埋め込む HUD 情報には、利用者が画面上で確認できる固定情報を含めてよいが、マウスホバー依存の一時情報は含めなくてよい。
- `--place` が使われた場合は、入力クエリと解決結果の少なくとも一方をメタデータに含めてよい。
- メタデータは JSON のような構造化テキストとして保持してよい。
- `--output -` による stdout 出力や `--sixel` 出力でも、メタデータ用の内部表現は同じにしてよい。
- PNG メタデータの具体的なキー名や表現形式は内部実装に委ねてよいが、少なくともアプリのバージョン番号は識別できる必要がある。

PNG に埋め込むメタデータの正規フォーマットは `zstarview.export-image-metadata.v1` とする。
このフォーマットは少なくとも次のトップレベル項目を持つ。

- `schema`
  - 固定値 `zstarview.export-image-metadata.v1`
- `version`
  - `zstarview` 本体のバージョン番号
- `hud`
  - 固定 HUD 情報
- `place`
  - `--place` の生入力と解決結果
- `extra`
  - `--search` や cloud coverage ratio などの任意拡張

`hud` には少なくとも `lines` を含めてよい。
`place` には、`--place` 未使用時は空または省略可能な表現を用いてよい。
`extra` は将来拡張用であり、既存の読み手は未知フィールドを無視してよい。

既定では、必要なレイヤーが揃うまで保存してはならない。
`--output -` は PNG bytes を stdout へ流す用途とし、`--sixel` と併用してはならない。
`--sixel` 指定時は、事前に `img2sixel` の存在確認と SIXEL 対応端末の確認を行ってよい。

### 8.2 dataset 参照専用 CLI

次の即時終了オプションは、GUI を起動せずローカルデータだけを参照してよい。

- `--list-viewpoints KIND`
- `--list-viewpoint-names KIND`
- `--show-viewpoint-json NAME`

これらは tower / mountain の内蔵 dataset のみを対象とし、GeoNames 読込や設定保存を行わない。

### 8.3 OvertureMaps executable staging CLI

`zstarview-install-overturemaps-exe-cli` は、`overturemaps` 1.0.1 以上の Windows 向け実行ファイルを `zstarview` のキャッシュディレクトリへ配置する補助 CLI として提供してよい。

- 必須の位置引数 1 個で、コピー元の exe ファイルパスを受け付けてよい。
- コピー先は常に `CACHE_PATH/overturemaps.exe` としてよい。
- コピー元ファイル名に含まれるバージョン番号やプラットフォーム接尾辞は解釈せず、固定名 `overturemaps.exe` に正規化してよい。
- 既存の `CACHE_PATH/overturemaps.exe` がある場合は、上書きしてよい。
- キャッシュディレクトリが存在しない場合は作成してよい。
- コピー元は変更せず、そのまま残してよい。
- ネットワークアクセスは行わなくてよい。
- 成否は terminal の ASCII-only メッセージと終了コードで示してよい。
- 失敗時は、少なくとも「コピー元が存在しない」「コピー失敗」「書き込み権限不足」を区別してよい。

この CLI は、Arm64 版 Windows で `overturemaps-py` の wheel が使えない場合に、GitHub Releases から取得した `v1.0.1` 以上の `*-windows-x86_64.exe` を手元で staging する用途を想定してよい。

`overturemaps` の実行ファイル探索は次の優先順位としてよい。

1. `--overturemaps-bin` で明示された値
2. `zstarview-install-overturemaps-exe-cli` で `CACHE_PATH/overturemaps.exe` に staging されたファイル
3. `PATH` 上で `which` / `where` 相当の探索で見つかるもの

### 8.4 PLATEAU building preparation CLI

`zstarview-download-plateau-buildings` は、PLATEAUのCityGML建物データを利用者の明示操作で取得し、`zstarview` の派生建物キャッシュへ変換する準備CLIとして提供してよい。

- 通常の `zstarview` 起動時に、PLATEAU CityGMLの大容量ダウンロードを自動開始してはならない。
- CLIは対象自治体または対象データセットを指定できてよい。観測地点・半径を指定した場合は、その地点を含むPLATEAUデータセットを選択してよい。
- `--city-code` は単一の5桁コード、`13100-13122` の連続範囲、または `13100,13103,13122` のカンマ区切りで複数自治体を指定できてよい。
- PLATEAU配信サービスのCityGML APIまたは同等の公式配布URLからデータを取得してよい。
- ダウンロード開始前に取得対象・データ年度・概算サイズ・必要な空き容量を表示してよい。
- 利用者の明示確認なしに、大容量のCityGMLダウンロードを開始してはならない。
- `--temp-dir` を指定した場合、ダウンロードしたZIPと展開中のCityGMLを指定ディレクトリ配下に置いてよい。省略時はシステムの一時ディレクトリを使用する。
- CityGMLの取得、展開、建物形状・高さの抽出、派生タイル生成、`tile_index.json` 生成を一連の処理として行ってよい。
- 一時的なZIP・展開済みCityGMLは、派生タイル生成後に削除してよい。利用者が明示した場合は検査用に保持してよい。
- 保存先は既定で `CACHE_PATH/plateau_buildings` 配下としてよい。
- 完了したキャッシュには、データソース、自治体コード、データ年度、取得日時、対象範囲、変換状態をメタデータとして保存してよい。
- 部分ダウンロード、変換途中のファイル、失敗したキャッシュを有効なPLATEAUキャッシュとして扱ってはならない。
- CLIを再実行したときは、既存キャッシュに保存したPLATEAUカタログの整備年度、登録年度、仕様、建物ファイル数、建物ファイルサイズ合計を最新カタログと照合してよい。一致する場合は再取得せず再利用し、齟齬がある場合は更新データを再取得してよい。
- 通常の`zstarview`起動時にPLATEAUカタログへ接続して更新確認してはならない。起動時は保存済みの完成キャッシュだけを利用する。
- キャッシュメタデータには、整備年度、登録年度、仕様、建物ファイル数、建物ファイルサイズ合計、取得時刻を保存してよい。
- 成否、取得サイズ、変換した建物数、保存先、エラー内容はASCII-onlyの端末メッセージまたは結果JSONで通知してよい。
- 一時ファイルシステムの容量不足を検出した場合は、`--temp-dir` を使用した再実行例を端末メッセージで案内してよい。
- `--list` を指定した場合は、ネットワーク接続やファイル変更を行わず、有効なPLATEAU派生キャッシュを全年度・全自治体について列挙してよい。
- `--list` の通常出力は、自治体コード、データ年度、保存パスだけを1件1行で表示してよい。`--city-code` を指定した場合はその自治体コードで絞り込んでよい。
- `--list --jsonl` は、保存パスを含むキャッシュメタデータを1件1行のJSONオブジェクトとして出力してよい。
- `--list` は、完了状態・スキーマ・派生タイルインデックス・参照タイルを検証して有効なキャッシュだけを表示し、不完全または破損したキャッシュを表示してはならない。

通常の `zstarview` は、次の順序で建物データソースを選択してよい。

1. 観測地点に対応する有効なPLATEAU派生キャッシュ
2. 通常のOverture Maps派生キャッシュ
3. 必要に応じたOverture Mapsの取得

PLATEAUの対象地域であっても、PLATEAU準備CLIが実行されていなければOverture Mapsを利用してよい。

### 8.5 AKARI IR bands data preparation CLI

`zstarview-download-akari-ir-bands` は、AKARIの65 / 90 / 140 / 160 µm遠赤外線マップを公式配布元から取得し、
`zstarview` 用の銀河座標表示キャッシュへ加工する準備CLIである。

- 通常のGUI起動時に自動ダウンロードしてはならない。
- `--akari-ir-bands-opacity 0` は表示を無効化するが、データ準備CLIの実行とは独立する。
- 元FITSは既定で保持する。
- `--delete-source` を指定した場合だけ、処理成功後に対象バンドの元FITSを削除する。

## 9. 設定保持

- `zstarview` と `zstarview-export-image` は `~/.config/zstarview/config.json` を使い、前回地点と window geometry を引き継いでよい。
- `zstarview-gui` は `~/.config/zstarview/gui-launch-profile.json` を別に使ってよい。
- `zstarview-gui`のdisplay tone curveはGUI起動プロファイルへ保存してよい。
- CLIの`--calibrate-display-tone-curve`は`config.json`またはGUI起動プロファイルへ
  値を書き込まない。
- `zstarview` と `zstarview-export-image` は、`zstarview-gui` 専用の保存ファイルを読んで既定値を上書きしてはならない。
- 前回地点は文字列形式だけでなく、Nominatim 由来の構造化オブジェクトを保存してよい。
- Nominatim の地名検索キャッシュは前回地点の設定とは分離し、長期キャッシュとして扱う。
- `Inverted City`の状態は一時的なGUI表示状態であり、設定ファイル、起動プロファイル、export-imageの入力へ保存または引き継いではならない。

## 10. エラーと状態表示

### 10.1 起動失敗

- 地点解決失敗
- `--place` 検索失敗
- 入力不正
- 初期化失敗
- 画像保存失敗

これらは非 0 終了としてよい。
原因は terminal や splash に表示してよい。

### 10.2 診断用 GUI ランチャー

`zstarview-debug` は、`zstarview` と同じ GUI 起動処理を console script として提供する診断用入口として扱ってよい。

- Windows では terminal から起動しやすく、起動時ログや例外をその場で確認しやすくしてよい。
- GUI の内容や設定の扱いは `zstarview` と同じでよい。
- 通常利用向けの `zstarview` / `zstarview-gui` を置き換える必要はない。

### 10.3 雲ソース診断 CLI

`zstarview-diagnose-cloud-source` は、雲オーバーレイの衛星ソース取得が失敗する場合に、利用者が terminal から実行する診断用 CLI として提供してよい。
通常の星空表示や画像出力を行うためのコマンドではなく、失敗原因を段階的に切り分けるための補助入口である。

- `--output-dir DIR` は必須とする。
- 診断ログ、診断 JSON、worker 用作業ディレクトリ、ダウンロード済み衛星ファイル、必要な中間成果物は、既定ではすべて `DIR` 配下へ保存する。
- 既定では通常の zstarview 雲 cache を使わず、`--cache-dir` 未指定時は `DIR/cache` を診断用 cache として使う。
- `DIR` が既に存在し、診断成果物の混在が起きる可能性がある場合は、既定では失敗してよい。明示的な上書きまたは再利用オプションがある場合だけ続行してよい。
- 成功時も失敗時も、最終的な診断結果、保存先、失敗段階、関連ログファイル名を terminal に表示する。
- 失敗時の表示は、少なくとも「S3 一覧取得」「プロダクト選択」「ダウンロード」「NetCDF/Himawari 読み込み」「投影情報構築」「雲ソース grid 構築」のどの段階で失敗したかを区別できるものとする。

診断 CLI の主な引数は、GUI が起動する `zstarview.clouddisc.workers.cloud_source_worker` の引数と可能な限り同じ名前・同じ意味にする。
利用者は、ログ中の `Launching cloud source worker:` に続く引数を流用し、`--work-dir` を `--output-dir` に置き換えて診断できるものとする。

共通化する引数は次を基本とする。

- `--request-id`
- `--lat`
- `--lon`
- `--when-utc`
- `--cache-dir`
- `--sat-priority`
- `--bt-warm-k`
- `--bt-cold-k`
- `--alt-min-deg`
- `--search-back-minutes`
- `--connect-timeout`
- `--read-timeout`
- `--cloud-shells-km`

診断 CLI 固有の引数は次を基本とする。

- `--output-dir DIR`
  - 必須。診断成果物の保存先。
- `--source-file PATH`
  - 既に保存されている衛星ソースファイルを読み込み診断するための入力。
  - 指定時は、ネットワーク取得を行わず、ファイル読み込み以降の診断に進んでよい。
- `--force` または同等の明示オプション
  - 既存の `--output-dir` を再利用する。
- `--no-grid` または同等の明示オプション
  - 衛星ソースの取得・読み込みまでを診断し、観測者向け雲 source grid 構築を省略する。

`--output-dir` 以外の既定値は、通常 GUI の雲 worker 起動時に使う値とそろえてよい。
例として、`--sat-priority AUTO`、`--bt-warm-k 310.0`、`--bt-cold-k 190.0`、`--alt-min-deg 1.0`、`--search-back-minutes 120`、`--connect-timeout 5.0`、`--read-timeout 30.0`、`--cloud-shells-km 6374.0 6376.0 6378.0` を使ってよい。

実行例:

```bash
zstarview-diagnose-cloud-source \
  --output-dir cloud-diagnosis-hapeville \
  --lat 33.660109 \
  --lon -84.4102046
```

既存ファイルだけを診断する例:

```bash
zstarview-diagnose-cloud-source \
  --output-dir cloud-diagnosis-hapeville \
  --source-file OR_ABI-L2-CMIPF-M6C13_G19_sample.nc.tmp \
  --lat 33.660109 \
  --lon -84.4102046 \
  --no-grid
```

### 10.4 継続可能な失敗

- 雲取得失敗時でも星空表示は継続する。
- 地形地平線取得失敗時でも本体表示は継続する。
- 航空機データ取得失敗時でも本体表示は継続する。
- GMNデータの取得、解析、投影に失敗した場合でも本体表示は継続する。
- 一時的なネットワーク不調で全体が異常終了しないこと。

### 10.5 ステータス表示

- 下部ステータスは2段で表示する。上段に地形地平線、水面、道路夜景、都市アウトラインなどの固定情報、下段に雲、降水予報、Tropical cyclone、GMN メテオ軌跡、人工衛星、航空機などの動的情報を表示する。
- Observation info を画面下側に表示する場合は、下部ステータスの行数に応じた余白を確保し、文字列同士が重ならないようにする。
- 雲、地形地平線、航空機、都市アウトラインの取得状態や失敗状態を表示してよい。
- 都市アウトラインは、必要に応じて base レイヤーと skyscraper レイヤーの件数を `base+skyscraper` で表示してよい。
- Road Lightsのステータス行は、建物の都市アウトラインと同様に、候補数や上限適用後の採用数を表示しない。データソースや利用状態だけを短く表示し、候補数などの内部処理情報が必要な場合はログへ記録する。
- 地形と水面の状態表示は、下部ステータス行に収まる短い固定文言を使う。キャッシュを使用した場合は `Terrain: cache` または `Water: cache`、利用可能なデータがない場合は `Terrain: unavailable` または `Water: unavailable` とする。
- 下部ステータス行には通信理由、例外内容、取得日時、URL を表示しない。それらの詳細はログへ記録する。
- 期限切れキャッシュを使用した場合も、最新データとは表示せず `cache` として扱う。
- 人工衛星の軌道要素は24時間を fresh とし、通信失敗時も取得時刻から24時間以内のキャッシュに限って `cache` として表示する。24時間を超えたキャッシュやキャッシュなしの場合は `Satellites: unavailable` とする。
- 航空機のOpenSkyオーバーレイは既定では無効であり、ユーザーが航空機オーバーレイを明示的に有効化した場合だけ取得する。有効化後は成功時・失敗時とも既定で5分間隔で再試行する。取得失敗時は取得時刻から10分以内の航空機キャッシュに限って `Aircraft: cache` として表示し、それを超えた場合は `Aircraft: unavailable` とする。
- 衛星、航空機、Horizons、OpenSky の通信失敗では、下部ステータス行や失敗バナーにURL・例外内容・スタックトレースを表示しない。
- Tropical cyclone の取得失敗時は、古いキャッシュを表示継続せず、`Typhoon: unavailable` として当該レイヤーだけを非表示にする。星空本体の表示は継続する。
- Tropical cyclone の取得失敗後は、90分後に自動再試行する。成功時の存在確認は90分間隔、完全なデータ更新は3時間間隔とする。
- ステータス表示は画面操作を妨げない補助情報として提供する。

## 11. 非機能仕様

### 11.1 応答性

- UI は操作に対して即応すること。
- 重い処理は利用者操作を長時間ブロックしないこと。

### 11.2 耐障害性

- 外部データ取得失敗が発生しても、本体表示機能はできるだけ維持すること。

### 11.3 保守性

- 利用者向け仕様、内部設計、実装履歴を別文書として維持すること。

### 11.4 出力の文字種

- terminal、console、log、CLI help、exception message、subprocess の stdout/stderr に出る文字列は、ASCII-only を原則とする。
- UI 専用文字列は、画面表示のために必要な場合だけ非 ASCII を許容してよい。
- 外部データ由来の非 ASCII を出力に含める必要がある場合は、要約または escape して出してよい。

## 12. 既知の制約

- 雲表示は外部の衛星データ供給状況に依存する。
- 航空機表示は OpenSky Network の提供状況、認証条件、利用枠に依存する。
- 複数の GUI が同時に起動している場合、OpenSky への問い合わせ頻度を抑えるため、直近に別の GUI が航空機データを取得していれば、航空機表示は次回更新まで省略されることがある。
- `zstarview-export-image` は単発出力として扱い、GUI 共有の航空機取得抑制では省略しない。ただし同時 OpenSky 取得を防ぐ lock を取得できない場合は失敗してよい。
- 航空機表示は観測値と短時間予想に基づく近似表示であり、実際の飛行位置と一致しない場合がある。
- GMN メテオ軌跡はGMNの観測網、天候、昼夜、カメラ視野、機器稼働状況、および
  日次データの公開状況に依存し、流星活動を完全または均一に表すものではない。
- オフライン環境では雲表示は利用できない。
- 高密度な表示設定では計算量と描画負荷が増える。
- 表示精度は利用ライブラリ、元データ品質、地点解決結果に依存する。
