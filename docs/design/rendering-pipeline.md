# レンダリング・パイプライン

この文書は、`zstarview`、`zstarview-gui`、`zstarview-export-image` で共通する描画パイプラインをまとめる。
主要なデータモデルは [data-model.md](data-model.md) を参照する。

## 1. 役割

- GUI と export-image が同じ入力から同じ scene を作れるよう、共通パイプラインを使う。
- ベースシーン描画と HUD / 一時オーバーレイ描画を分ける。
- ラベル、ガイド、オーバーレイは、ウィジェットへ直結させず、合成可能な部品として扱う。
- renderer 固有の ad hoc な判断より、前処理済みの scene data と state を優先する。
- sky/glow と cloud は、見た目の base frame が近くても再描画トリガーと cache key を分けて考えてよい。

## 2. 合成の順序

描画は、概ね次の層を順に重ねる。

1. 背景
2. sky disc
3. 雲と欠損ティント
4. sky guides
5. 地形地平線と地面ティント
6. Earth guide
7. 星と天体
8. 都市アウトライン
9. 水面、航空機、人工衛星、夜間光、台風・サイクロン
10. ラベルと HUD

この順序は厳密な固定ではなく、レイヤーの種類ごとの責務を表す。
たとえば、雲は sky disc の上に乗るが、地平線下のティントや HUD はさらに上に置く。

通常ビューアの星・惑星の局所コントラストは、星と天体の層の内部で次の順に扱う。

1. `vmag <= 4.0` の恒星・通常惑星の暗色下敷きまたは輪郭
2. 恒星本体・惑星本体
3. `vmag <= 2.0` の恒星用ひし形マーカー、その他の天体マーカー

空色ディスクが無効な場合は、この局所コントラスト層を追加しない。これにより、
`--sky-opacity 0` は空色とそれに伴う補助的なコントラスト強調を同時に無効化する。

### 2.0.1 恒星サーフェイスと時間補間

恒星の 60 秒スナップショット更新によるフレーム切り替えを目立たなくするため、恒星の
描画資産を空色ディスクおよび重い base scene から分離する構成を採用してよい。

- 天文計算済みの恒星データと、そこから生成した暗い恒星（`vmag > 4.0`）の透明サーフェイスを、60 秒スナップショット単位で保持する。
- 恒星サーフェイスは更新間隔の中間時刻に生成し、その基準時刻からの経過時間（`-更新間隔/2`〜`+更新間隔/2`）に応じて 3x3 射影変換を適用してから合成する。
- `sky_update_interval` が 90 秒を超える場合は、この射影変換による補間を無効にする。更新間隔が長い場合に60秒用の補間量を拡張して適用しないためである。
- 実際に行列へ与える経過時間は基準時刻からの値の75%を上限とする。これは、平面近似の残差による逆戻りを避け、スナップショット境界に小さな正方向ジャンプを残すためである。
- 3x3 行列は 4 点だけで決め打ちせず、四隅付近、辺中央、中央を含む複数の対応点から最小二乗近似してよい。四隅付近は、`content_fov_deg` のオーバースキャン領域を含む実際の表示範囲の誤差評価点とする。
- 四隅そのものはクリッピングやサーフェイス境界の影響を受けるため、対応点は必要に応じて数％内側へ置く。
- 明るい恒星（`vmag <= 4.0`）は恒星サーフェイスへ焼き込まず、合成時に変換後の位置へ個別描画してよい。`vmag <= 2.0` のひし形も同じ経路で扱う。
- 明るい恒星の暗色下敷きは、恒星本体・ひし形と位置を共有する独立の透明レイヤーとして扱う。下敷きは `SourceOver`、恒星本体と加算的な光は `Plus` など、合成モードを分ける。
- 下敷きレイヤーを恒星の加算画像へ単純に混ぜて `Plus` 合成してはならない。黒成分が暗くならず、コントラスト下敷きとして機能しないためである。
- 新しいスナップショットが到着したら、恒星サーフェイスを交換し、中間時刻を補間の基準時刻として行列を更新する。
- 変換行列の更新は、重い天文計算とは独立した2秒周期の軽量な表示更新として扱う。行列の更新と実際の Qt repaint 要求は別の責務とする。
- 星座線、名前付き恒星ラベルなど恒星位置に追随する要素は、同じ変換を適用するか、同じ補間時刻で再投影する。
- 惑星、太陽、月は恒星サーフェイスへ含めず、通常ビューアでは2秒周期の専用更新で現在時刻の位置を直接計算し、表示レイヤーで描画する。
- 空色ディスク、雲の色、夜間光は60秒スナップショット側のキャッシュを維持し、惑星・太陽・月の表示位置更新では再生成しない。

この構成は、空色ディスク、地形、雲など地球側に固定されたレイヤーを動かさず、
恒星に関係する画像だけを変換するための現行設計である。実装検証では、画面中央、辺中央、
四隅付近の残差と、明るい星の輪郭・下敷きの見え方を検証する。

### 2.1 sky disc の色モデル

GUI の空色ディスクは、ウィンドウの最終描画面とは別の内部サーフェスへ描画する。内部サーフェスの幅と高さは最終クライアント領域の `0.25` 倍とし、寸法とディスク半径は切り上げて端部の被覆不足を避ける。中心座標も同じ縮尺へ変換する。合成時には `Qt.SmoothTransformation` でウィンドウ解像度へ拡大するため、恒星サーフェイスや明るい恒星の画面解像度描画とは独立して、空色計算のピクセル数だけを削減できる。

`compute_sky_snapshot()` は GUI と export-image で共有されるため、export-image の高解像度出力ではこの縮小を既定で適用せず、要求された出力サイズで空色ディスクを生成する。GUI worker だけが `SKY_DISC_RENDER_SCALE` を指定する。

`render/sky_disc.py` の `sky_color_samples` は、各画素を逆投影して得た視線の高度・方位と、太陽の高度・方位から RGB を決める。計算は次の順序で行う。

1. **夜間の固定色**

   太陽高度が `-12°` 以下なら、視線方向に関係なく `NIGHT_SKY_RGB` を返す。この場合は昼間の基礎色や太陽由来の補正を計算しない。

2. **視線高度による基礎色**

   昼間は、視線高度から `t_alt = clip(alt / 90 * 1.15, 0, 1)` を求め、`HORIZON_DAY_RGB` から `ZENITH_DAY_RGB` へ線形補間する。したがって、低高度ほど淡い青の地平線色、高高度ほど彩度を抑えた青の天頂色に近い。地平線を白〜灰色、天頂を強い青に固定しないことで、sky disc の不透明度を上げた場合も昼の空の連続した明るさを保つ。

3. **低高度の白化**

   霞色への補間は行わず、基礎色を低高度用の白に近い色へ補間する。白化の強さは視線高度の `low_altitude` を二乗した値に比例し、地平線付近でだけ立ち上がる。地平線側ほど強く、天頂ではゼロになるため、天頂の青から低空の白っぽい色への勾配を保ちながら、中高度への白化の広がりを抑えられる。これは太陽高度に依存せず、夕焼け色そのものとは別の処理である。

   低空の `0°`〜`4°` には、太陽高度が低い場合だけごく弱い暖色霞を追加する。基準強度 `LOW_HORIZON_WARM_STRENGTH = 0.10` は維持し、太陽高度の `sunset` 係数に応じて補正先の RGB を `LOW_HORIZON_WARM_RGB` から `SUNSET_RGB` へ移動させる。太陽高度が `4°` から `0°` へ下がるにつれて、対象高度を最大約 `6°` まで広げ、強さを最大 `50%` 増やす。これは太陽方向に限定した夕焼け補正ではなく、海面付近の空全体に広がる薄い地平線色として扱う。太陽高度が `0°` を下回ると、全体の薄明係数によって天頂色と同じように減衰する。

   これとは別に、視線高度 `0°`〜`8°` へ太陽に依存しないごく弱い暖色補正を重ねる。最大強度は `0.03` で、昼間に太陽と反対の方位を見た場合にも残る、大気の長い光路によるわずかな赤みを表す。夕焼け補正と競合しないよう、独立した小さな補正として扱う。

4. **太陽高度による広域の青補正**

   太陽高度 `0°`〜`45°` を `smoothstep` で補間し、太陽が高くなるほど `BLUE_DOME_RGB` へ近づける。補正量は視線高度が高いほど大きく、太陽高度による空全体の青さを基礎色へ加える。

5. **太陽との角距離による局所補正**

   視線と太陽の角距離を、両者の高度・方位から `cos_g` として求め、次の2つの係数に分ける。

   - `forward = max(0, cos_g)`: 太陽方向。太陽に近いほど大きい。
   - `back = max(0, -cos_g)`: 反太陽方向。太陽の反対側に近いほど大きい。

   角距離に依存する色変化は、独立した青色補正ではなく、次のグレアと反太陽補正で表現する。

6. **反太陽点側の補正**

   太陽と反対方向では `back = max(0, -cos_g)` を使い、`back^2.6`、太陽高度、視線高度から `ANTI_SOLAR_RGB` への補間量を決める。太陽高度が高いほど有効になり、反太陽方向の暗い青みを表す。

7. **太陽方向のグレア**

   太陽方向では `forward = max(0, cos_g)` を使い、`forward^p`（`p = 1.75 - 0.25 * tau`、現行の `TURBIDITY = 6` では `p = 1.625`）で中心からの減衰を決める。グローは既存色への加算を70%、目標色への置き換え方向の補間を30%として混合する。これにより加算光らしさを残しながら、既存の強い青色が夕焼けの赤橙色を打ち消すことを抑える。これは空全体の青補正とは別の、太陽近傍の明るさ・色補正である。

   グローの目標色は `SUN_GLOW_RGB`（ほぼ白）を基本とし、夕焼け係数に応じて `SUNSET_RGB` へ最大 `15%` 寄せる。グロー強度は `SUN_GLOW_STRENGTH = 0.30` と太陽高度による `sun_up`（`-12°`〜`6°`）で調整する。

8. **夕焼け補正**

   `sunset = 1 - smoothstep(-1°, 4°, sun_alt)` とし、太陽高度が低いほど有効にする。太陽高度 `-1°` 以下で最大、`-1°`〜`4°` で滑らかに変化する。低高度の視線、太陽方向、太陽高度による `sun_up` を掛け合わせ、`SUNSET_RGB` へ補間する。したがって夕焼けは空全体へ一様に加える色ではなく、低い視線の太陽側に強く現れる補正である。

   `SUNSET_SOLAR_GLARE_FACTOR = 1.0` のため、現行実装では太陽方向の夕焼け補正を抑制しない。太陽方向では夕焼け色が最も強くなり、角距離が増えるほど `forward` のべき乗によって弱くなる。

   太陽高度 `4°`〜`12°` では、グローの目標色を `SUN_GLOW_RGB` から
   `SUN_HIGH_ALT_GLOW_RGB` へ最大 `10%` 補間する。これは太陽高度に対する
   `smoothstep` と同じ太陽方向のグローマスクへ適用するため、太陽から離れた
   空や反太陽方向の色は黄色化しない。高高度用の目標色は
   `RGB(255, 240, 199)` 相当の淡い黄色とする。

9. **昼夜遷移（twilight）と夜空の床色**

   太陽高度 `-11°`〜`0°` から `twilight` を `smoothstep` で求め、昼間側の計算結果に掛ける。その後、すべての太陽高度で `NIGHT_SKY_RGB` を加える。これにより、薄明では昼間の色が連続的に消え、`-12°` 以下では固定の夜空色になる。

10. **彩度・露出・透明度などの後処理**

   入力 `saturation` は各色補正の強さをまとめて調整する `colorfulness`（既定値 `1.35`、有効範囲 `0.75`〜`1.25`）に変換され、主に青・反太陽・グレア・夕焼けの補正量へ影響する。最終 RGB には `exposure`、`alpha`、`eclipse_factor` を乗算してから `0`〜`1` にクリップする。さらにディスク画像化時には、テーマの `disc_opacity` を画像 alpha に設定する。これらは色相分布を決める要因ではなく、明るさ・合成強度を調整する要因である。

### 2.1.1 球形大気・Rayleigh/Mie散乱モデル

`sky_disc.py` のMieモデルは、球形地球上の単一散乱を数値積分して昼間側の色を求める。移行前の挙動確認用スクリプトは `dev-samples/atmospheric_sky_experiment.py` と `dev-samples/atmospheric_sky_mie_experiment.py` に置く。

観測地点を `o`、視線方向を単位ベクトル `v`、地球半径を `R`、大気上端を `R + H` とすると、視線上のサンプル点は次で求める。

```text
x(s) = o + s v
```

`s` は視線と半径 `R + H` の球面との前方交点までを範囲とする。地球内部へ向かう視線は大気の積算対象外とし、各サンプル点の高度は `|x(s)| - R` から求める。太陽方向 `u_s` についても、各サンプル点から大気上端までの光路を同じ球形交差計算で求める。太陽光路が地球内部を通るサンプル点は照明されないものとして除外する。

各RGB成分 `lambda` の散乱放射は、概念的には次の積分で定義する。

```text
L_lambda(v) = integral[
    I_sun_lambda
    * beta_lambda(x)
    * P_lambda(theta)
    * exp(-tau_sun_lambda(x) - tau_view_lambda(x))
    ds
]
```

- `I_sun_lambda` は入射太陽光のRGB強度。
- `beta_lambda` はその地点の散乱係数で、Rayleigh成分とMie成分を持つ。
- `tau_sun_lambda` は太陽から散乱地点まで、`tau_view_lambda` は散乱地点から観測者までの光学的厚さ。
- `P_lambda(theta)` は散乱位相関数。Rayleigh成分には `1 + cos(theta)^2` 型、Mie成分には前方散乱の強いHenyey–Greenstein型を使用する。
- 太陽から観測者への直接光を表す項はこの積分に含めない。

大気密度は地表から指数関数的に減少させ、Rayleigh成分は大きいスケールハイト、エアロゾル成分は約 `1.4 km` の小さいスケールハイトを使用する。これにより、Mie成分は地平線付近の夕焼けの広がりへ寄与し、上空の青色は主にRayleigh成分が担う。実験では大気上端を100 kmと500 kmで比較し、画像差がほぼないことを確認したため、組み込み時の実質的な上端は100 kmを基本とする。

#### 数値計算と表示解像度

GUIでは空色ディスクを最終画面の `0.25` 倍の内部サーフェスへ生成する。試作の基準値は視線方向64分割、太陽方向24分割だったが、視線方向を32分割へ下げても、240×100の比較画像で平均RGB差は `0.14/255`、最大差は `2/255` だった。処理時間は同条件で約2.61秒から約1.42秒へ短縮したため、組み込みでは視線方向32分割を使用する。

積分はGUIスレッドで行わず、既存のsky workerで実行する。太陽位置、観測地点、表示解像度、視線投影条件が同じ間は計算結果をキャッシュし、恒星・惑星の軽量な位置更新では空色を再計算しない。NumPy配列からQImageへの変換は主なボトルネックではなく、太陽光路と視線光路の光学的厚さを求める積分が計算量の中心である。

### 2.2 AKARI IR bands の色変換

AKARI IR bands は、準備済みの90 / 140 / 160 µm表示用データを銀河座標から画面の視線方向へサンプリングし、RGB画像として独立レイヤーにする。
色変換と合成は次の順序で行う。

1. 90 µmをB、140 µmをG、160 µmをRへ割り当てる。
2. 内部テーマに応じてRGBチャンネルを変換する。現在のテーマは
   `creative-hubble` で、`R'=R`、`G'=0.5R+0.5B`、`B'=B` とする。
   比較用に `akari` の直接割り当てと `jwst` の固定色加算を実装している。
3. RGB各成分へガンマ補正（現行値 `0.5`）を適用する。
4. RGBの最大成分をHSVのV値として扱い、V値のknee
   `v' = v / (1 + v)` で明るい領域を圧縮する。色相と相対的な成分比は維持する。
5. 太陽高度による夜間フェードとレイヤーopacityをRGBへ反映する。
6. 画面サイズの0.25倍で生成したRGBAレイヤーを平滑拡大し、最終合成時に加算合成する。

この色変換は可視光の色や物理温度を再現するものではなく、遠赤外線バンドの分布を見やすくするための疑似カラー処理である。

## 3. ベース描画と HUD

- ベース描画は、scene の視覚的な土台を作る。
- HUD は、hover、jump highlight、static observation overlay、status line のような一時的または情報密度の高い表示を担当する。
- ベース描画と HUD を分けることで、視点変更時に base frame を再利用しやすくなる。
- `zstarview-export-image` は、既定では HUD を入れずにベース描画中心で出力してよい。

### 3.1 sky/glow と cloud の再描画分離

- `night light` と `ridge glow` のデータ生成は cloud の有無とは独立して扱う。ただし通常ビューアでは、night light と共有する太陽高度係数を使って、夜間の cloud 合成強度を補助的に持ち上げてよい。
- cloud の source ready / render ready は cloud overlay の更新だけを起こし、sky/glow の再計算や再描画を待たせない設計としてよい。source ready 自体は repaint の直接トリガーにせず、投影完了や別の更新契機に任せてよい。
- 逆に、sky snapshot 完了や terrain 完了は sky/glow base の再描画だけを起こし、cloud のダウンロード完了を待たずに可視化してよい。
- 実装上は、base sky/glow cache と cloud overlay cache を分け、invalidate の粒度も別にしてよい。
- cloud データが未到着でも、sky/glow base は単独で描画してよい。

### 3.2 簡易表示

- GUI は `simplified_view_enabled` のような全体簡易表示フラグを持ってよい。
- `Space` はこの全体簡易表示をトグルする入力として扱ってよい。
- 実効表示は `simplified_view_enabled` とラベル設定から決めてよい。
- 実効表示の解決は、`normal` / `no-labels` / `labels` の 3 状態として扱ってよい。
- `Space` は `normal -> no-labels -> labels -> normal` の順で循環してよい。
- 実効表示が簡易側のときは cloud / night-light / Earth guide / secondary ridges / water / urban outline を抑止してよい。
- 主稜線は簡易表示のときだけ細く描いてよく、通常表示では省略してよい。
- 実効表示が簡易側のときも、hover 解決は止めず、hover ラベルは維持してよい。
- 簡易表示が有効なときは、HUD に `Simplified: with labels [Space]` または `Simplified: no labels [Space]` を短く出してよい。

## 4. オーバーレイの責務

### 4.1 天体とガイド

- 星、太陽、月、惑星は主要天体として描画する。
- Sky guides は、地平線、天の赤道、黄道、方位ラベル、天頂マーカー、天の極マーカーを含む。
- never-rises 領域は、Sky guides の一部として扱ってよい。

### 4.2 通常ビューアの明るい天体描画

通常ビューアでは、空色ディスクの既定不透明度を `0.2` とする。空色の明度によって
明るい天体が埋もれることを防ぐため、`vmag <= 4.0` の恒星は通常の一括ラスタ描画から
除外し、恒星単位の個別描画パスへ渡す。4.0 は対象に含める。

個別描画は次の2段階の恒星帯を持つ。

- `vmag <= 2.0`：暗色下敷き、恒星本体、既存の明るい恒星用ひし形
- `2.0 < vmag <= 4.0`：暗色下敷き、恒星本体

`vmag > 4.0` の恒星は従来の一括描画パスに残す。個別描画パスでは、まず対象恒星の
暗色下敷きを全件描画し、その後に対象恒星の本体とひし形を描画する。近接した恒星の
下敷きが、既に描いた恒星本体を覆わないようにするためである。

個別描画の下敷きは、空全体を塗り替える背景ではなく、恒星の見かけサイズに応じた
小さな局所形状とする。`vmag <= 2.0` のひし形には四角形の暗色角を残さず、ひし形に
整合する形状を使う。惑星は `vmag <= 4.0` の通常の惑星円盤に暗色の輪郭または下敷き
を付ける。太陽のクロスゲージと月の位相描画は、初期設計ではこの個別恒星下敷きの
対象外とする。

この個別描画は通常ビューアの表示方針であり、Atlas の明背景ラスターパスとは別に
管理する。実装時は、候補抽出、下敷き、恒星本体、ひし形の合成モードを分離し、
`vmag` 境界、形状、サイズ、アルファ、表示モードを星レイヤーのキャッシュキーへ
含める。export-image でも同じ条件と描画順を使用する。

### 4.3 雲と地平線

- 雲は sky disc の上に合成し、欠損領域は別ティントで表現してよい。
- 雲画像の生成は 2 段階に分ける。
  1. **取り込み段階（ingestion）**：衛星データを取得した直後に、観測者から見た (altitude, azimuth) グリッド `CloudAltAzGrid` に変換する。このグリッドはカメラ視点に依存せず、観測地点・衛星・時刻・雲シェルの組み合わせで一意に決まる。
  2. **描画段階（render）**：カメラが変わるたびに、`CloudAltAzGrid` から現在の視線中心・FOV・画面サイズに合わせて RGBA 雲画像を生成する。
- Geo-satellite もこの 2 段階に含めてよく、原画像の再利用と投影を別工程として扱ってよい。
- 取り込み段階では、衛星画素の (lat, lon, 雲シェル高度) を ECEF 上の点とみなし、観測者からの方向ベクトルをローカル ENU 座標に変換して altitude/azimuth を求める。
- 輝度温度（BT）から雲量への変換は、既存の `bt_warm` / `bt_cold` 正規化を流用してよい。
- 雲量の正規化では、赤道中心の単線ではなく、おおむね `±5°` の赤道帯サンプルを warm-threshold の基準に使ってよい。
- warm-threshold は、赤道帯サンプルを主軸に、視野内の局所サンプルを少量混ぜた補正としてよい。局所視野が安定しているときでも、赤道帯参照を主軸に残す。
- この補正は共通 render 経路で使われ、現時点では GOES / Himawari のどちらにも適用される。
- 複数の雲シェル（既定では 3 km / 5 km / 7 km）から来たサンプルは、シーン全体の雲量に応じた重みでブレンドして 1 つの雲量値 per (alt, az) セルにまとめる。
- 同一セルに複数サンプルが入った場合は `max` または平滑化された平均を使ってよい。MVP では `max` 寄りの統合で、薄い高層雲も視覚的に残すことを優先する。
- 描画段階では、`CloudAltAzGrid` から 4 つのストライプモードを生成できる。
  - `halftone`: 45° 傾いた画面固定の正方形グリッドを用い、各セルの雲量を 8 段階に量子化して円を描く。同じレベルが連続するセルは `RoundCap` ペンで太い線分（halftone）として接続する。各形状の背後にほんの少し太く低アルファの輪郭を描き、雲の縁を薄く強調する。
  - `width`: 中心対称のストライプを描き、雲量に応じて帯の見かけ幅を変える。
  - `width-quantized`: `width` の変形。雲量を5段階に量子化し、幅の変化点に隙間を設けた丸端ストロークとして描く。
  - `alpha`: 帯幅を固定し、雲量に応じて帯のアルファ値を変える。
- `--cloud-stripe MODE[,COUNT[,WIDTH]]` の `COUNT` はディスクを横切る絶対的な本数である。ウィンドウサイズや星レイヤーのレンダリング面サイズに応じてスケールせず、大きなウィンドウでは間隔が広がる。
- 既定の雲描画スタイルは `halftone,30,1.7` とし、既定の雲不透明度は `0.05` とする。`COUNT` または `WIDTH` を `0` にすると雲描画を無効化する。
- `CloudAltAzGrid` は観測地点・衛星・時刻・シェルに対してキャッシュしてよい。カメラの回転やズームでは取り込みをやり直さず、軽量な描画段階だけ再実行する。
- 欠損領域ティントも、alt/az グリッドに付随する `missing_mask` を同じ alt/az → 画面投影で描画してよい。
- 地形地平線は空と地面の境界を決める。
- Earth guide は地平線下の方向案内として、地形地平線とは独立した補助レイヤーとする。
- 簡易表示では Earth guide を抑止し、主稜線だけを細く再描画してよい。
- sky/glow は cloud source の到着を待たずに更新してよい。cloud overlay の再投影は、sky/glow base とは独立に遅延または再実行してよい。

### 4.3 地表系レイヤー

- 都市アウトラインは、観測地点周辺の建物輪郭を示し、閉じた輪郭には薄い面塗りを重ねてよい。
- 画面上で小さく潰れた閉輪郭は、面塗りだけ省略してよい。
- 水面レイヤーは、地形地平線や地面ティントと合わせて地表の読み取りを助ける。

### 4.4 移動体と補助情報

- 航空機は予測軌跡として描画する。
- 描画表現は折れ線に限定せず、帯状ポリゴンにしてよい。帯状ポリゴンを使う場合は、進行方向に沿った軌跡を細かくサンプリングし、投影後の点列からリボン状の面を構成してよい。
- その帯の視覚的な半幅は、概ね「2 秒程度で機体が移動する量」を目安に決めてよい。近距離の機体ほど太く、遠距離ほど細く見える段階的な幅制御を続けてよい。
- 帯幅の基準はスクリーン座標ではなく、機体の局所水平面で進行方向に直交する向きとしてよい。その後で投影してもよい。
- 地平線付近や旋回中は、局所水平面で左右境界を作ってから投影する方が、画面上の見かけよりも意味を保ちやすい。
- 人工衛星は小さなマーカーとして描画する。
- 夜間光と台風・サイクロンは、補助的な地理・気象情報として重ねる。
- 夜間光の glow は、街灯系の補助レイヤーとして扱い、色推定と合成を分けてよい。
- 簡易表示では、night-light 系の glow を抑止してよい。

## 5. ラベルの扱い

- ラベルは、星、惑星、DSO、アステリズム、衛星、航空機、検索結果など複数の候補源から集約する。
- まず候補を正規化し、その後に配置順を決める。
- 重なりやすいラベルは、局所グループを作ってから配置してよい。
- グループ内では、対象に近い候補、または上側の候補から先に配置してよい。
- 既に置かれたラベルの予約矩形を共有し、後続のラベルほど回避するようにしてよい。
- hover ラベルと persistent marker ラベルは、短い jump highlight とは別に扱ってよい。
- export-image では、必要なら marker/label を 1 件だけ持ち込むが、永続状態は残さなくてよい。
- 簡易表示で出す名前付き恒星ラベルは、`B-V` 由来の色をそのまま使い、文字不透明度を `0.7` 程度に抑えてよい。
- その簡易表示ラベルは、星座標に対して文字矩形の左下隅を合わせる固定配置としてよく、重なり回避は行わなくてよい。
- 人工衛星の簡易表示ラベルも `draw_satellite_overlay()` 側で同様に固定配置してよく、hover 用のラベル経路とは分けてよい。
- その衛星ラベルは、クロスマーカーの近傍に固定で置き、重なり回避を行わなくてよい。
- 簡易表示ラベルが有効なときは、hover 側の衛星名ラベルは抑止して重複を避けてよい。
- 太陽ラベルは、body marker とは別に Moon と同程度の muted なテキストとして描いてよい。
- 太陽ラベルには、装飾マーカーや囲みを追加しなくてよい。
- 航空機の帯状ポリゴンを使う場合、label collision の対象は帯の外形ではなく機体本体の基準点としてよい。
- 簡易表示モードは 3 状態で管理してよく、`Space` で `normal -> no-labels -> labels -> normal` と循環させてよい。

## 6. オーバーレイと HUD の境界

- static observation overlay は HUD 側で描画する。
- status line も HUD 側で描画する。
- hover の一時表示は、ベース描画ではなく HUD 側で足す。
- ベースフレームのキャッシュから mouse position、hover 対象、jump highlight、status 文言は除外してよい。
- 簡易表示では、HUD の固定情報ブロックを抑止し、代わりに `Simplified: with labels [Space]` のような最小状態ラベルだけ残してよい。

## 8. 設計意図

renderer は、正規化済みの scene data を受け取り、入口ごとの分岐を最小限にして最終画像を生成する。
それにより、3 つのアプリの見え方を揃えつつ、起動方法や永続化だけを入口ごとに変えられる。

### 4.2a 雲ストライプ描画モード

`CloudAltAzGrid` から画面への雲描画には、以下 3 つのストライプモードがある。
いずれも右下 45°（`u = x - y` 方向）の線を基本とし、`SkyCompositorCache` の
`cloud_stripe_mode` で切り替える。

- `halftone`
  - 画面に固定の正方形 2D グリッド（`Δu = Δv`、45° 回転）を置く。グリッド原点はビューポート左上。セル間隔は `target_stripes` で調整可能。
  - `target_stripes` はディスクを横切る絶対的な本数であり、ウィンドウサイズや星レイヤーのレンダリング面サイズに応じてスケールしない。大きなウィンドウではセル間隔が広がり、円/線も太くなる。
  - 各セルの中心点で `CloudAltAzGrid.amount` をサンプルし、width スタイルと同じパーセンタイル正規化（非ゼロ値の 12%ile / 92%ile）を適用後、8 段階の非線形量子化を行う。閾値は `1.4⁻ⁱ`（i=7..1）。
  - 量子化テーブル（[0, 1] を 8 分割）:

    | 雲量範囲    | レベル | 円直径（delta=30px 時） |
    |-------------|--------|------------------------|
    | 0.000 – 0.095 | 0    | 描画なし |
    | 0.095 – 0.133 | 1    | 2.8 px |
    | 0.133 – 0.186 | 2    | 5.7 px |
    | 0.186 – 0.260 | 3    | 8.5 px |
    | 0.260 – 0.364 | 4    | 11.3 px |
    | 0.364 – 0.510 | 5    | 14.1 px |
    | 0.510 – 0.714 | 6    | 17.0 px |
    | 0.714 – 1.000 | 7    | 19.8 px |

  - 円直径は `width_factor` でスケール可能。直径は `delta / 30 * wf / √2 * 0.95` で計算され、並行チェーン間の垂直距離（`delta / √2`）に対して隙間が確保される。
  - レベル > 0 の各セルは、斜め右下（v 方向、grid index で `(i, j+1)`）の隣接セルと同じレベルであれば連結する。連結チェーンは `QPainter` + `RoundCap` ペンで太い線分（halftone）として描画する。線幅 = 円直径。
  - 孤立セル（連結先がない、またはレベルが異なる）は、セル中心に円を描画する。`drawPoint` + `RoundCap` ペン（幅 = 円直径）で実現。
  - 各円/線を描く前に、線幅を 3 px 太くした低アルファ（既定 20%）の同じ RoundCap ストロークを 1 度描くことで、雲の縁に薄い縁取りを与える。
  - 色は白、不透明度は `hatch_cfg.strength`。円形クリップパスで円盤外を切り落とす。
  - `CloudAltAzGrid` 自体は変更せず、描画時にスクリーン空間で量子化する。

- `width`
  - `CloudAmountField`（正規化 (u, v) 空間にビン化した雲量場）からサンプル。
  - 中心対称のストライプを描き、雲量に応じて帯の見かけ幅を変える。

- `alpha`
  - 同じく `CloudAmountField` からサンプル。
  - 帯幅は固定し、雲量に応じて帯のアルファ値を変える。

- `--cloud-stripe MODE[,COUNT[,WIDTH]]` の既定値は `halftone,30,1.7` とする。`COUNT` または `WIDTH` を `0` にすると雲描画を無効化する。
- 既定の雲不透明度は `0.05` とする。通常ビューアでは、night light と同じ太陽高度遷移（`-9°` 以下で最大、`-4°` 以上で無効）を使い、cloud 用の boost `0.3` により実効値を最大 `1.3` 倍まで持ち上げる。
- 雲のグレースケール下地への寄せ量は、`cloud_opacity * 4.0` を `1.0` でクリップした係数を使う。白色 RGB の加算は `cloud_opacity` をそのまま係数に使う。
